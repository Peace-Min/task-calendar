# 근태 보고 처리 정책

확정: 2026-10-26, 사용자 결정. 상태: 정책 확정. 구현 및 검증 범위는 인계 보고를 참조한다. 운영 배포 전이며 회사 주간 실전송은 미검증이다.

근태, 일간보고, 주간보고, 보고 편집, 회사 연동, 전송 기록 DB와 관련된 작업 전에 이 문서를 반드시 읽는다. 이슈 #17의 초기 명세 및 작성본 분리 설계와 충돌하면 이 문서의 정책을 적용한다. 구현 완료와 운영 배포 완료를 이 정책 확정과 혼동하지 않는다.

## 목적과 원자성의 범위

회사 근태관리 시스템은 계속 사용하고 앱 DB에도 보고 기록을 보관한다. 회사 변경을 되돌리는 분산 트랜잭션은 구현하지 않는다. 원자성은 **회사 보고 성공을 조건으로 실행하는 앱 DB 변경 전체**에 적용한다.

여기서 회사 반영은 성공했지만 DB 저장은 실패한 상태를 허용한다. 이를 유실 복구 대기 건으로 영구 관리하거나 두 시스템의 자동 일치까지 보장하지 않는다. 회사 반영 여부의 성공 판정은 여전히 필요하다. 웹폼을 채우거나 요청을 발송한 것만으로 성공으로 판정하지 않는다.

## 필수 처리 순서

1. 입력 검증과 사용자 제출 확인. 이 시점에는 회사 보고 및 앱의 보고 기록 DB를 변경하지 않는다.
2. 요청의 로그인 계정, 보고 대상 날짜 또는 기간과 입력 내용을 한 번 확정한다. 처리 중 입력과 연속 클릭을 막는다. UI 스레드를 멈추는 동기 호출을 요구하는 것은 아니다.
3. 회사에 보고하고 성공을 확인한다. 실패하거나 성공 여부를 확인하지 못하면 DB 저장을 실행하지 않는다.
4. 성공한 요청과 동일한 내용으로 관련 DB 변경을 하나의 트랜잭션에서 수행한다. 본문, 시간 행 등 일부만 남지 않도록 한다.
5. DB 커밋 성공까지 확인한 뒤 전체 완료를 알리고 편집창을 닫는다. 캘린더는 DB 저장에 성공한 기록을 기준으로 갱신한다.

회사 요청 전 DB 접근 및 버전 확인은 가능하다. 다만 사전 확인이 통과해도 회사 처리 후 DB 오류는 발생할 수 있다. 사전 확인을 두 시스템의 원자성 보장으로 설명하지 않는다.

## 실패와 재시도

| 결과 | 앱 보고 기록 DB | 편집 화면과 재시도 |
|---|---|---|
| 회사 실패 또는 회사 성공 판정 불가 | 변경하지 않는다 | 편집창과 입력을 유지하고 실패 안내. 처리 잠금을 해제하여 재시도 허용 |
| 회사 성공, DB 처리 실패 | 트랜잭션을 롤백한다 | 동일한 실패 안내와 편집창 유지. 재시도는 회사 보고부터 다시 수행 |
| 회사 성공, DB 커밋 결과 판정 불가 | 성공이나 롤백을 단정하지 않는다 | 동일한 실패 안내와 재시도 허용. 실제 저장됐을 수 있으므로 DB 저장은 중복 없이 덮어써야 함 |
| 회사 성공, DB 커밋 성공 | 관련 기록 전체 반영 | 완료 안내, 편집창 닫기, DB 기준 캘린더 갱신 |

공통 실패 안내: **처리를 완료하지 못했습니다. 다시 시도해 주세요.**

버전 불일치 또는 서버 갱신 중처럼 재시도 전에 해결할 조건이 있으면 기존 안내로 그 이유를 추가 표시할 수 있다. 운영 진단에서는 회사 단계와 DB 단계를 구분하되, 화면에 별도의 DB 전용 재시도 절차를 만들지 않는다. 로그에 비밀번호나 보고 원문을 넣지 않는다.

사용자는 같은 날짜의 회사 보고를 다시 요청하면 기존 값이 덮어써지는 운용을 전제로 이 정책을 확정했다. 일간과 주간의 실제 대상 식별과 덮어쓰기 동작은 각각 검증해야 한다. 주간의 같은 기간 글 선택이 검증되지 않은 상태에서 일간의 전제를 그대로 확대하지 않는다.

실패 후 사용자가 내용을 고치고 재시도하면 새 입력 전체로 회사와 DB를 다시 처리한다. 한 번의 처리 도중에는 내용이 바뀌면 안 된다. 실패한 요청의 대상 날짜 또는 기간은 유지하고, 다른 대상 작성은 별도 작업으로 취급한다.

## 저장하지 않는 것과 허용하는 결과

- 회사 요청 전에 보고 작성본, 전송 대기 상태, 시도 스냅샷을 앱 DB에 쓰지 않는다.
- 이번 정책을 위해 로컬 파일, localStorage 등에 복구 큐나 보고 작성본 영구 저장을 추가하지 않는다.
- DB 전용 재시도, 부팅 시 자동 재전송, 주기적 재전송, 회사와 DB의 자동 대조 복구는 추가하지 않는다.
- 실패한 새 입력을 저장된 캘린더 기록처럼 표시하지 않는다. 원래 DB 기록이 있으면 그 기존 기록을 유지한다.
- 실패 후 앱 종료, 강제 종료 또는 장애가 발생하면 화면 메모리의 미저장 입력은 사라질 수 있다. 회사에만 반영된 결과는 그대로 두며 자동 복구하지 않는다.
- 재실행 시 DB에 이전 저장 성공 기록이 남는 것은 허용한다. 사용자가 그 내용을 확인하고 명시적으로 다시 보고하면 회사 값을 덮어쓸 수 있다. 자동으로 보고하지 않는다.
- 다른 PC나 회사 홈페이지에서 동일 계정으로 동시에 수정한 내용과의 전역 충돌 해결은 보장하지 않는다. 현재 앱 안의 연속 요청과 처리 중 입력은 반드시 제어한다.

기존 앱의 보고서 임시저장 기능을 이번 문서만으로 일괄 삭제하지 않는다. 위 규칙은 새 근태 보고 흐름의 실패 복구를 위한 저장을 추가하지 않는다는 결정이다. 기존 기능 제거는 영향 범위를 확인해 별도로 수행한다.

## 필수 검증

| ID | 주입 또는 조작 | 통과 기준 |
|---|---|---|
| P01 | 회사 실패 | DB 쓰기 0회, 입력 유지, 편집 가능, 재시도 가능 |
| P02 | 회사 성공 후 DB 실패 | 성공 안내 및 창 닫기 없음, DB 일부 반영 없음, 재시도 시 회사부터 호출 |
| P03 | 회사와 DB 모두 성공 | DB 커밋 뒤에만 완료 안내와 창 닫기, DB 기준 캘린더 갱신 |
| P04 | 처리 중 클릭 반복과 입력 시도 | 회사 요청 1회, DB 요청 내용이 해당 회사 요청 내용과 같음 |
| P05 | 실패 후 입력 수정 및 재시도 | 수정한 내용으로 회사부터 다시 실행, DB 전용 재시도 없음 |
| P06 | 회사 처리 응답 또는 DB 커밋 응답 유실 | 실패 안내 및 재시도 가능, 재시도 후 동일 대상 기록 중복 없음 |
| P07 | DB 트랜잭션 중간에 오류 | 새 기록은 부분 생성되지 않고, 기존 본문 및 시간 행 전체가 이전 값 유지 |
| P08 | 같은 대상 성공 요청 반복 | 일간 날짜와 주간 대상 기간 각각 기존 기록 덮어쓰기 확인 |
| P09 | DB 버전 갱신 중 또는 앱 버전 불일치 | 잘못된 구조에 쓰지 않고 실패 안내 및 입력 유지. 회사에만 반영됐을 가능성 허용 |
| P10 | 처리 중 계정 전환 | 이전 계정 결과를 새 계정 화면과 기록에 반영하지 않음 |
| P11 | DB 실패 후 앱 종료 및 재실행 | 새 입력이 캘린더에 저장된 것으로 표시되지 않고 자동 전송 및 복구 큐 생성 없음 |

먼저 모의 회사 응답과 실제 UI로 순서, 입력 잠금과 재시도를 검증한다. DB 롤백과 덮어쓰기는 `zz_` 임시 DB에서 실제 드라이버로 검증한다. 회사의 실제 저장 성공 판정과 주간 덮어쓰기는 사내 환경의 검증 항목으로 구분한다. 회사에 실제 보고서를 보내는 시험을 자동으로 실행하지 않는다.

현재 코드 감사: `node tests/audit-attendance-policy.mjs`. 이 명령은 모의 응답으로 현재 UI와 소스의 정책 위반을 찾는 감사다. 전체 구현 완료나 실제 회사 연동 검증의 대체가 아니다. 실패 항목을 정책에 맞춰 수정하기 전에는 준수 완료로 표시하지 않는다.
