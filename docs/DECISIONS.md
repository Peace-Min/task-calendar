## 배경: 제품의 무게중심 이동

- 시작: **개인 로컬 캘린더**(코어) + 일간/주간 보고(곁다리).
- 현재 인식: 사내에서 **기존 일간/주간 보고 방식을 이 캘린더로 대체**하려는 요구가 커짐. 그래서 실질 코어가 **"일정을 적으면 보고가 나오는 도구"** 로 이동. 캘린더=입력 수단, 보고=산출물.
- 그래서 확장을 논의했고, 아래 경계·범위를 확정했다.

## 결정 1. 제품 범위: "보고 루프 + 읽기 전용 팀 열람"에서 멈춘다

**IN(이 제품의 최대치):** 개인 일정·할일 → 일간/주간 보고 초안 → 제출/열람. 팀장·사업부의 **읽기 전용 열람 + 과제별 집계·조회**까지.

**STOP(다른 제품):** 과제 **할당, 상태 전이, 의존성, 간트, 승인 워크플로, 역할 권한 체계** = 프로젝트 관리. Jira/그룹웨어 영역.

- **구분 테스트**: "내 일정 → 내 보고" 루프를 돕는가(IN) vs "남의 일을 관리·조율"하는가(OUT).
  - 과제별 **집계·조회**(공수 합계) = 보고의 연장 → IN
  - 과제별 **관리**(배정·상태) = 프로젝트 관리 → OUT
- **근거**: 1~2인 유지보수로 PM 도구는 감당 불가 + 사내 실제 니즈는 "보고 대체"지 PM이 아님 + 넓히면 이 앱의 강점(가벼운 로컬 우선 + 자동 보고)이 무너짐.
- **재검토 트리거**: 조직이 PM 기능을 공식 요구하면 이 앱에 넣지 말고 **별도 제품/기존 그룹웨어 연동**으로 검토.

## 결정 2. 구조 리팩토링은 ①어댑터 + ②테스트망 "딱 그만큼", 기능에 얹어 점진 도입

확장(브라우저·미래 서버)이 요구하는 두 리스크만 막는다: **구조 오염**과 **회귀**.

### ① 능력 포트/어댑터 (`if(HOST)` 산탄 흡수)
- 환경별 "어떻게"를 **어댑터 객체**(위젯/브라우저/미래 서버)로 분리. 기능 코드는 환경을 모르고 **능력(`caps`)만 질문**하고 실행은 위임.
- .NET 용어로 **인터페이스+다형성(전략 패턴)** 이다. 새 환경 = **어댑터 추가**(기존 코드 무수정, OCP). switch/if-else와 다른 점이 이것.
- 환경 판별은 **`const Platform = HOST ? Widget : Browser` 딱 한 줄**에만 존재.
- 상세·예시코드: [ARCHITECTURE.md §5](ARCHITECTURE.md).

### ② 테스트 안전망 (Node 내장, npm 불요, 폐쇄망 호환)
- 별도 `tests/` 폴더(배포 산출물에 미포함, git으로 재사용). 앱 코드와 분리.
- 범위: **핵심 순수 로직**(페이로드 빌더·XML 직렬화 왕복) + **모의(mock) netcus fixture**(실 필드명만 같은 껍데기 HTML로 북마클릿 채움 검증, 실서버 무관).
- JS엔 인터페이스 강제가 없으므로, **"모든 어댑터가 같은 모양인지"를 테스트가 대신 보증**(C#의 컴파일러 체크 역할).

### 적정 범위(이걸 넘으면 과잉)
- 어댑터: **보고·저장 정도만** 우선. 기존 `if(HOST)` 15곳 **전면 이전 금지**. 신규(브라우저 보고)부터 하고, 나머지는 카테고리별(vcs, netcus, shell 순)로 필요 시.
- 테스트: 커버리지 100% X, UI 픽셀 테스트 X. 손으로 하던 검증을 스크립트로 굳히는 수준.
- **도입 방식**: 별도 대공사로 떼지 말고 **브라우저 보고 기능의 부산물로** 자연히 세운다(= YAGNI 위반 아님, 지금 필요한 기능을 올바르게 만든 결과).

## 결정 3. 지금 하지 않는 것 (YAGNI) + 다시 할 조건

아래는 **의도적으로 유예**한다. 확장을 "고려"는 하되 **미리 만들지 않는다.** 아직 안 올 수도 있는 것에 투자하지 않기 위해서다.

| 유예 항목 | 왜 지금 안 하나 | **다시 할 트리거** |
|---|---|---|
| 프레임워크(React/Vue), TypeScript, 번들러 | 의존성0, 오프라인, 1~2인 제약과 충돌 | (해당 없음. 이 제약이 유지되는 한 도입 안 함) |
| 빅뱅 재작성 | 동작하는 제품에 회귀 리스크 | (안 함. 항상 점진) |
| `if(HOST)` 15곳 전면 이전 | 대공사·회귀 위험 | 각 카테고리를 실제로 손댈 때 그 김에 |
| 서버 어댑터 **미리** 만들기 | 서버는 조직 승인 전 | DB/서버가 **공식 채택 결정**될 때 |
| 단일 HTML 5,000줄 분할 | 아직 참을 만함 | 항해가 실제로 불가능해질 때(의존성0 concat으로만) |
| DB 사용자 테이블 **활용 로직** | 집계/열람이 아직 범위 밖 | 사업부 집계·팀 열람이 확정될 때 |
| 조직 테이블 정규화 | 지금은 과제의 컬럼으로 충분 | 조직 계층 집계가 필요할 때 |

## 결정 4. DB/데이터: 하이브리드, "테이블은 미리, 활용은 나중", SoR는 조직 결정 대기

- **하이브리드**: 개인 데이터(일정, 할일, 메모)는 **로컬 XML 원본 유지**(오프라인·가용성), 조직·과제는 **DB 마스터**(주로 읽기). 팀 공유는 **공유 프로젝션 push**(원본은 로컬, 공유분만 단방향 사영, 팀장은 읽기 전용).
- **DB 스키마**: `과제`(코드, 이름, 소속) 중심. 사용자 테이블은 **골격(스키마, FK, role 컬럼)만 미리** 둘 수 있으나 **앱이 읽어 동작하는 로직은 집계 때** 붙임.
- **편집 권한**: 사용자 테이블/역할 시스템이 아니라 **DB 계정 권한(GRANT)** 으로 강제(앱은 read-only 접속). 클라이언트 권한 체크는 우회 가능하므로 신뢰 경계는 DB.
- **무결성 목표**: 이 앱이 책임지는 건 **"기술적 무결성"**(형식 검증 + **과제명을 자유입력 대신 목록 선택 강제**해 집계 축 표준화)까지. **"의미적 정확성"**(정직한 입력)은 도구가 보장할 수 없으니 조직의 검토와 문화, 이상치 플래그로 보완.
- **중대 전제**: 회사에 기존 과제관리 DB가 없어(파일 관리) 이 앱이 **최초 시스템(SoR)** 이 될 수 있음. 이는 코드가 아니라 **조직의 공식 채택 결정**이 선행돼야 하는 문제. 로컬 MySQL 프로토타입으로 **시연 → 조직 설득 → 공식화** 순서.
- **로컬→서버 승격**: 로컬 MySQL로 스키마와 연동을 검증하고, 안정화 후 **동일 스키마를 서버에 생성, 연결 대상만 전환.** 연결정보만 설정으로 갈아끼우는 구조.

> **갱신(2026-09-02, 실제로 간 길)**: 아래 07-08 갱신은 **API 서버가 서고 나서** 개인 데이터를 서버로 올리고, 그때 `data.xml`을 오프라인 캐시로 강등한다고 적었다. 실제는 다르게 갔다:
>
> - **중간 단계를 운영 배포로 썼다.** 07-08 갱신이 *"클라이언트가 DB에 직접 붙는 중간 단계(로컬 MySQL 검증기)에만 적용"* 이라고 한정한 GRANT-직결 모델을, **T2를 기다리지 않고 그대로 운영에 올렸다**(v0.18.0, 2026-09-02). API 서버는 없다. 그래서 **신뢰 경계는 여전히 DB GRANT**다.
> - **오프라인 캐시는 만들지 않았다.** `data.xml`은 캐시로 강등된 것이 아니라 **폐기**됐다(`DeployConfig.XmlRetired = true`). 온라인 전용이다. **ADR-18**(과제 카탈로그에 캐시를 두지 않기로 한 결정)을 캘린더 본체에도 그대로 적용했다.
> - **왜 그랬나**: 조직 채택(T2)은 개인이 만들 수 없는데, 그 전에 풀어야 할 문제("다른 자리 PC에서 내 일정 보기", "위젯↔브라우저 따로 놀기", "남의 일정 열람")가 전부 **DB를 전제**한다. API 없이 폐쇄망 MySQL 하나로 그 셋이 풀린다. 근거는 [ROADMAP.md](ROADMAP.md) **§1**.
> - **대가**: 앱 계정 비번이 exe 상수로 80대에 배포됨, 신뢰 경계가 API가 아닌 GRANT, 서버 못 붙는 날 미리알림 0건, 부팅 실패 시 재시도 없음. 각각 어디에 기록돼 있고 지금 상태가 무엇인지는 [ROADMAP.md](ROADMAP.md) **§1의 '그 대가' 표**가 정본이다.
> - **T2가 열리면** 직결을 API 경유로 옮기고, 그때 오프라인 캐시를 **다시 논의**한다(ROADMAP §4). 지금 캐시를 만들 근거가 아니다.

> **갱신(2026-07-08, [ROADMAP.md](ROADMAP.md) 합의)**: 위 **하이브리드(개인=로컬 XML 원본 + 공유 프로젝션 push)는 "외부 작성 요구 확정 전까지"의 중간 모델**이다. 외부(재택) 작성 + 조직 채택(ROADMAP **T2**)이 성립하면 **개인 데이터도 서버 DB가 단일 소스**로 승격된다(위젯 `data.xml`은 오프라인 캐시로 강등, ROADMAP 3단계). 이유: 어느 자리·어느 PC에서든 로그인만으로 접근 + 위젯↔브라우저 동기화 해소. **신뢰 경계도 이때 서버 API 계층으로 이동**한다. 최종 상태에선 클라이언트가 DB에 직접 붙지 않고 API만 호출하므로, 위의 "GRANT-직결(앱 read-only 접속)" 모델은 **클라이언트가 DB에 직접 붙는 중간 단계(로컬 MySQL 검증기)에만 적용**되고, 운영에선 GRANT를 API 서비스 계정에 적용한다. 로컬 MySQL 프로토타입과 시연은 **T2를 얻기 위한 설득 수단이므로 T2 이전에도 허용**(운영 서버 구축만 금지).

## 결정 5. 브라우저 보고: 지금은 "안내만", 자동 작성은 netcus same-origin 배포 시점으로 연기

**지금(확정):** 브라우저 모드에서 일간/주간 "전송"을 누르면 **netcus 창을 새 탭으로 열고**, 하단에 **"브라우저는 자동 작성 불가 → 📋 복사로 직접 붙여넣거나, ⋯ → XML 내보내기로 위젯에 옮겨 작성"** 안내만 표시한다. 자동 채움·자동 로그인은 **하지 않는다.**

**왜 자동이 안 되나(재론의 종결):**
- 브라우저 탭은 netcus와 **다른 origin**이라 **SOP**에 막혀 netcus 로그인 폼 조작, `goLogin()` 호출, id 자동 획득 **불가**. netcus엔 REST 로그인 API도 CORS 허용도 없어 fetch 로그인도 불가.
- 한글은 **euc-kr**인데 JS `fetch`/`TextEncoder`는 UTF-8 전용이라 직접 POST하면 깨짐.
- 대안들 평가: **북마클릿=폐기**(사용자 실사용 실패), **브라우저 확장(MV3)=IT 정책 종속**, **서버 릴레이=자격증명 보관 보안 리스크**. 지금 시점엔 어느 것도 부적절.

**올바른 해법(미래) = netcus와 same-origin 경로에 정적 배포:**
- 캘린더를 **`https://www.netcus.com/calendar/`**(같은 host **경로**, `calendar.netcus.com` 서브도메인은 다른 origin이라 ❌)에 정적 파일로 올리면 netcus와 **완전 동일 origin**이 된다. 그러면 SOP·CORS 소멸, **사용자 netcus 로그인 세션 그대로 공유**(자격증명 우리가 안 만짐), **무설치**, netcus.com이 공개라 **외부(재택)도 접근**.
- euc-kr은 netcus의 euc-kr 문서를 **same-origin iframe/팝업으로 조작**해 폼 채움(위젯이 WebView2에서 하던 방식과 동일. same-origin이면 브라우저에서도 허용).
- **리눅스 서버는 무관, 오히려 이상적**: same-origin은 OS가 아니라 host 기준. 정적 서빙은 리눅스가 표준이고 **서버측 netcus 로직도 불필요**(채움은 브라우저에서). netcus가 리눅스+JSP면 **회사 자체 Tomcat**일 공산이 커 배포도 현실적.

**착수 트리거는 게이트가 두 개다(혼동 금지):**

**(A) 자동 작성 게이트 = 아래 1~3(기술 전제) 전부 충족**. 이때 자동 작성을 구현한다(= [ROADMAP](ROADMAP.md) 1단계). **서버 코드·DB·로그인 없이 정적 배포만으로 가능**:
1. 회사가 **netcus.com 서버에 정적 앱 배포 가능**한가(자체 시스템·배포 권한). 이것이 make-or-break
2. netcus와 **같은 origin 조건**(같은 host의 **경로**로 서빙, 서브도메인 X, https·포트 동일)
3. netcus `X-Frame-Options`가 `DENY`가 아님(SAMEORIGIN 프레이밍 허용)

**(B) 데이터 서버화 게이트 = "회사 외부에서 보고 작성"이 공식 요구가 될 때**. 앱뿐 아니라 **개인 데이터(일정)도 서버 호스팅**이 필요하므로 결정 4의 DB, 로그인, 서버 프로젝트와 **한 단계로 합류**(ROADMAP 2~3단계, 위젯↔브라우저 동기화도 이때 단일 소스로 해결).

즉 "브라우저 보고 자동화"(A)와 "데이터 서버화"(B)는 **게이트가 다르다**. A는 same-origin 배포의 산물로 먼저 올 수 있고, B는 조직 채택이 스위치. 그전까지 브라우저는 위젯 전용 안내 + 일반 복사만. A의 구현은 `BrowserPlatform.report` 어댑터 교체 한 곳으로 끝난다(결정 2 ①의 효과).

## 결정 6. 편집 지점: 일간(원본)에서만, 주간·커스텀은 읽기 전용 투영

**원칙**: 데이터 편집(공수·커밋 문구 등)은 **원본 = 일간 스코프**에서만. 집계 뷰(주간·커스텀 보고서)는 **읽기 전용 투영**이며 편집 대상이 아니다.

| 표면 | 편집 |
|---|---|
| 일간 보고서(그날=1:1) | ✅ 원본 (커밋 내역 탭은 2026-10-26 삭제) |
| 주간 보고서, 커스텀 기간 보고서 | ❌ 읽기 전용(일간/커밋내역에서 고치면 자동 반영) |

- **이유**: ① 집계 줄은 여러 원본의 병합(중복제거)이라 "어느 원본?" 매핑이 모호하므로 특수분기 대신 **원칙으로 제거** ② 편집은 원본에서, 모든 집계는 자동 반영되는 **순수 투영**(데이터-투영 일관) ③ 제품 컨셉 = **"일일 기록을 잘하면 주간은 저절로 정확"**(기존 보고 대체 목표와 직결) ④ 분기 없이 단순. (주간은 이미 공수도 읽기 전용이고, 커스텀도 동일하게 맞춰 일관.)
- **쓰기 단일 경로**: 원본 변이는 **단일 API**(`setCommitSubject`/`deleteCommit` 등) 한 곳으로 모으고, 화면은 `(entryId, hash)` 식별 해석 + 텍스트만 넘긴다. `notifyDataChanged`가 전 뷰 갱신. 그 결과 DRY, 불변식 단일화, 테스트 용이를 얻고, [ROADMAP](ROADMAP.md) 서버 전환 시 **이 함수 내부만 API 호출로** 바뀌는 seam(화면 무수정)이 된다.
- **적용 규칙(미래 개발)**: 새 편집 UI를 만들 때 "이 표면이 **원본(일간)** 인가 **투영(집계)** 인가?"로 편집 허용 여부를 판단한다. 편집 = 반드시 단일 변이 API 경유(직접 데이터 변형 금지).

## 결정 7. Git, SVN 기능 전량 삭제, 커밋 기록은 바꾸지 않고 지운다 (2026-10-26)

**결정**: 하루 패널의 '커밋 내역' 탭과 커밋 불러오기, 달력의 커밋 칩, 과제 창의 저장소와 작성자 카드, 보고서와 월간 보고의 커밋 항목, 다른 사람 일정 보기의 커밋 탭, 커밋 기록 전용 일정 창, 사용설명서 Git 장을 모두 지운다. 서버에 이미 있는 커밋 기록(`source='git'`)은 일반 일정으로 바꾸지 않고 **전량 삭제**한다. 기획 [GIT-SVN-REMOVAL.md](GIT-SVN-REMOVAL.md).

- **왜 지우나**: 거의 쓰지 않는 기능인데 호스트(`Svn.cs`, `RepoPaths.cs`, git 실행), 웹, DB 표, 시험에 걸쳐 짐이 컸다. 저장소 경로는 DB 모드에서 이미 저장되지 않아 반쯤 깨진 상태였다.
- **왜 바꾸지 않고 지우나**: 커밋 기록을 일반 기록으로 바꾸면 제목과 날짜를 어떻게 옮길지, 커밋 목록은 어디에 둘지 규칙을 새로 정하고 시험해야 한다. 지우는 쪽이 가장 깔끔하고 공수가 적다(사용자 결정). 그 기록에 적은 메모, 장소, 공수도 함께 사라진다.
- **왜 구조 번호를 올려 한 번에 지우나**: 앱에서만 숨기면 사람마다 다음 저장 때 조금씩 지워져 끝을 알 수 없다. 구조 18 이관 조각(`db/deploy/migrations/v18-remove-git.sql`)이 커밋 기록, `cal_entry_commit` 표, `cal_entry.source`, `cal_category.uses_repo`, `cal_user_pref` 의 작성자와 커밋 본문 칸을 한 번에 지운다. 버전 관문이 17 앱을 막으므로 지운 뒤 옛 앱이 커밋을 다시 쓰는 일은 없다.
- **대가**: 되돌릴 수 없다. 배포 SQL 을 돌리기 전 Workbench 백업은 필수다([DB-RELEASE-OPS.md](DB-RELEASE-OPS.md)). 옛 XML, localStorage, DB 스냅숏의 커밋 흔적은 읽지 않고 버린다.
- **남긴 것**: 과제 데이터 내보내기는 남기되 캘린더.md 만 쓴다(Git, SVN patch 없음). 사용자 PC 의 `repo-paths.json` 은 지우지 않고 둔다(읽는 곳이 없다).

## 결정 8. 과제 데이터는 서로 독립이다: 칸끼리 묶는 규칙을 두지 않는다 (2026-10-26)

**결정**: 구분, 상태, 날짜를 서로 묶던 규칙을 지운다. 선진행(구분 2)이면 계약 날짜와 상태를 비우고 잠그던 규칙, 선진행으로 바꾸면 자동 개발 날짜를 비우던 규칙, 호스트가 저장할 때 그 칸들을 말없이 NULL 로 덮던 처리, 그리고 그 규칙 때문에 있던 선진행과 종료 코드 행의 숨김, 삭제 보호를 함께 지운다. '진행중만'(종료 하나만 빼던 필터)은 상태마다 체크박스로 바꾼다. 기획 [PROJECT-ADMIN-UX.md](PROJECT-ADMIN-UX.md) §1.2, §1.4.

- **왜**: 한 칸을 바꾸면 다른 칸이 저절로 바뀌거나 잠기는 규칙은 트리거와 같다. 화면에서 보이지 않게 데이터가 바뀌고(호스트는 아무 말 없이 덮었다), 사업부 장표와 실제 업무가 규칙과 어긋나면 사용자가 값을 넣을 길이 없다. 규칙이 이름이 아닌 번호에 묶여 있어도 '그 번호 행은 지울 수 없다'는 보호와 설치 스크립트의 강제가 따라붙어 코드표 관리가 무거워졌다.
- **원칙**: 저장하는 값은 사용자가 넣은 값 그대로다. 앱이 지키는 것은 무결성뿐이다(날짜 순서, 필수 칸, 코드표 이름 중복 금지, 외래키). 편의 기능은 처음 값을 채워 주기까지만 하고(새 과제의 개발 날짜 기본값: 계약 시작 + 1달, 계약 종료 - 1달), 사용자가 고친 값은 건드리지 않는다. 확인이 필요하면 묻는다(비슷한 과제 등록 확인창).
- **번호의 남은 뜻**: 상태 번호는 목록 점과 Excel 색만 정한다(1 진행중 초록, 2 종료 회색, 3 1차 납품완료 파랑). 구분 번호는 공식 과제를 내 과제에 처음 넣을 때의 기본 색만 정한다. 어느 행이든 숨기고 지울 수 있고 지워도 깨지는 것이 없다([CODE-TABLE-IDS.md](CODE-TABLE-IDS.md) §3).
- **다시 볼 조건**: 어떤 값이 다른 값에 따라 반드시 정해져야 한다는 업무 규칙이 생기면, 먼저 DB 의 CHECK 같은 무결성 규칙으로 표현할 수 있는지 본다. 화면이 값을 몰래 바꾸는 방식으로는 되돌리지 않는다.
