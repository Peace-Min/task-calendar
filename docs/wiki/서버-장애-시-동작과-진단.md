# 서버 장애 시 동작과 진단 (운영·관리자)

> 기준: v0.19.x · 정본 기획서 `docs/OFFLINE-RESILIENCE.md` · 검증 루프 `tests/loop-offline.mjs`

## 1. 원칙

| 원칙 | 뜻 |
|---|---|
| 온라인 전용 | 서버가 없으면 읽기·쓰기 모두 하지 않는다. 로컬 대기열·캐시 없음(ADR-18) |
| 정상일 때 폴링 없음 | 연결이 정상이면 위젯은 DB 를 주기적으로 찌르지 않는다. **끊긴 걸 안 뒤에만** 재연결 확인을 돈다 |
| 끊기면 편집 잠금 | 연결이 없거나 미저장 변경이 있으면 편집 진입점이 잠긴다. 읽기는 된다 |
| 원인을 보여 준다 | 오류를 종류로 나눠 화면에 다른 문구를 낸다. 원문은 [자세히]와 로그에 |

## 2. 오류 종류와 동작

| 종류 | 판정(MySQL 오류 등) | 화면 문구 | 자동 재시도 |
|---|---|---|---|
| network | 1042 · 2002 · 2003 · 2005 · 2006 · 2013 · 소켓 오류 · 시간 초과 | 서버에 연결할 수 없습니다 — 서버가 꺼져 있거나 네트워크 문제입니다 | 예 |
| auth | 1044 · 1045 · 1142 · 1143 · 3118(계정 잠김) | DB 접근이 거부되었습니다 — DB 이름·계정 설정과 서버 권한을 확인하세요(관리자) | **아니오** |
| schema | 1146(표 없음) · 1054(컬럼 없음) · schema_version 불일치 | DB 구조가 이 버전과 맞지 않습니다 | **아니오** |
| unregistered | app_user 에 계정 없음 | 이 계정이 서버에 등록돼 있지 않습니다 | 아니오 |
| unknown | 그 밖 | 서버 오류 — 잠시 뒤 다시 시도하세요 | 예 |

## 3. 재연결 주기

- 시작할 때 실패: **15초 → 30초 → 60초 → 이후 5분마다** 계속(network·unknown 만).
- 사용 중 끊김을 감지(저장 실패 · 다른 화면의 DB 실패): 같은 주기로 가벼운 연결 확인(`SELECT 1`, 연결 3초 한도).
- 창이 다시 보이면(최소화에서 복원 등) 한 번 즉시 확인(10초에 한 번 이하).
- 연결되면 순서대로: 미저장 변경 저장 → (시작 실패였다면) 캘린더 다시 읽기 → 과제 목록·코드 다시 읽기 → 미리알림 다시 걸기 → 「서버에 다시 연결되었습니다」.

## 4. 저장 응답만 끊긴 경우

저장 트랜잭션이 서버에서 COMMIT 된 뒤 응답만 끊기면, 예전에는 다음 저장이 **가짜 충돌**이 되어 [새로고침]이 최신 편집을 버렸습니다. 지금은 직전 저장이 네트워크 실패였고 이번 저장이 충돌(또는 중복 키)이면, 위젯이 서버 스냅샷을 다시 읽어 **내용이 같으면 성공으로 처리**합니다. 다르면 진짜 충돌로 안내합니다.

## 5. 보고 기록

회사 사이트 전송이 끝난 뒤 위젯의 보고 기록(cal_report_*) 저장이 실패하면 10초·30초·60초 뒤 다시 저장합니다. 그래도 실패하면 화면에 「보고는 전송됐지만 기록 저장에 실패했습니다」를 띄웁니다. 전송 자체는 성공이므로 다시 보낼 필요가 없습니다.

## 6. 로그로 진단하기

- 위치: `%APPDATA%\TaskCalendar\widget.log` (1MB 넘으면 `widget.log.1` 로 넘기고 30일 뒤 삭제)
- 장애 한 건마다 한 줄: `DB 오류 분류: kind=<종류> · detail=<원문 첫 줄>` (비밀번호는 기록하지 않음)
- 부팅: `=== 시작 v<버전> ===` 뒤에 `DB 부팅 조회: user_id=… rev=… schema=v…` 가 있으면 정상, `캘린더 부팅 조회 실패` 가 있으면 그 줄의 원인을 본다.

> ⚠️ Claude 데스크톱 앱처럼 **패키지 앱 안에서 띄운** 위젯은 `%APPDATA%` 가 그 앱의 사본 폴더(`%LOCALAPPDATA%\Packages\…\LocalCache\Roaming`)로 바뀝니다. Windows 시작 때 자동 실행된 위젯의 로그는 원래 `%APPDATA%` 에 있습니다. 두 곳의 로그가 다르면 이것 때문입니다.

## 7. 자주 나는 원인

| 증상 | 원인 | 조치 |
|---|---|---|
| 접근 거부 · 로그에 `Access denied for user 'taskmgr_app'@'%' to database 'taskcalendar'` | 그 서버에 `taskcalendar` DB 가 아직 없다(위젯이 새 DB 를 가리키는데 구축 전) | 서버 PC 에서 `db\deploy\setup-taskcalendar.cmd` 실행(2026-10-01 실제 사례) |
| PC 를 켜면 연결 오류, 몇 분 뒤 저절로 정상 | MySQL 서비스가 위젯보다 늦게 뜬다 | 조치 불필요(5분 꼬리 재시도가 푼다) |
| 접근 거부 · 1045 | 위젯에 빌드된 앱 계정 비밀번호와 서버 계정이 다르다 | `widget/DeployConfig.cs` 와 서버의 `taskmgr_app` 비밀번호를 맞춰 다시 빌드 |
| 「서버 DB 업데이트 필요」 | 서버 스키마가 위젯보다 낮다 | 해당 마이그레이션 적용(DEPLOY.md) |
| 「위젯 업데이트 필요」 | 위젯이 서버보다 낮다 | 위젯 업데이트 배포 |

## 8. QA — 장애를 만들어 확인하기(개발 PC)

- 디버그 실행(`TC_DEBUG_PORT=9222`)에서만 호스트 명령 `__dbFault {mode}` 가 동작합니다: `network` · `auth` · `commit-lost` · `off`. 배포 실행에서는 거부됩니다.
- `node tests/loop-offline.mjs` — 시작 장애·자동 복구·5분 꼬리·미저장 저장·접근 거부·가짜 충돌 해소·정상 시 무폴링을 실제 위젯에서 확인합니다(DB 비밀번호 불필요, 앱을 거쳐 서버에서 다시 읽어 확인).
- 확인하지 못하는 것: 닫기 확인 창(Windows 기본 창)은 사람이 한 번 눌러 봅니다.
