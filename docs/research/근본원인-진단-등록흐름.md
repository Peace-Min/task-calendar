# 근본 원인 진단 — "왜 UI/UX 불만이 반복되는가"

> 작성 2026-06-16 · 방법: UI/UX 전문 다중 에이전트 진단(워크플로 wmcnsry8q, 3렌즈 → 종합 → 적대적 검증) + 실제 preview 라이브 터치테스트(380px). 결론 = 또 다른 패치 목록이 아니라 **근본 원인 + 방향**.

## 한 문장 진단
**여섯 번의 패치가 전부 "기록을 담는 그릇(표시·레이아웃)"만 옮겼고, "기록을 만드는 행위(등록·입력)"는 첫 빌드 이후 단 한 번도 안 건드렸다.** 불만의 진원지(무거운 등록)와 패치의 작용점(배치)이 구조적으로 어긋나, 고칠 때마다 통증의 *위치*만 바뀌고 통증 자체는 보존된다. (상위 원인 = 멘탈모델 불일치: 사용자는 *캡처*(빨리 적기)를 원하는데 제품은 매번 *클래리파이*(정밀 분류)를 강제 — GTD가 경고한 안티패턴.)

## 증거 (코드·실측으로 검증, 검증 에이전트 통과)
- 일정 등록 모달 `entryModal`(task-calendar-prototype.html 554~611행)은 셀→드로어→'작업'버튼→우측탭→고도화 5번을 거치는 동안 **첫 빌드 그대로**. 입력 컨트롤 DOM 16개(첫 오픈 실노출 8~10개), 높이 **419px=화면 89%**, 본문 스크롤 필수.
- `＋새기록`(btnNew)·날짜 더블클릭·패널 `＋추가`(btnAddHere)·git 커밋 적용(applyCommits)이 **전부 이 한 모달로** 수렴.
- 정작 가벼운 한 줄 입력 `quickAddHtml`(제목+기한, due→캘린더·category→보고서 자동연결)은 **'할 일 탭' 본문에만 갇혀** 있음 → **비대칭**("할 일은 한 줄, 일정은 16칸")이 불만 재생산의 엔진.

## 반복 메커니즘
패치 → 배치가 깔끔해짐(일시 만족) → 눈이 다시 '적기'로 돌아감 → 안 고친 무거운 모달 그대로 → **같은 자리에서 같은 불만 재발견**. 통합(탭)을 해도 분리(드로어)를 해도 불만이 *사라지지 않고 자리만 옮긴* 사실이 "배치 문제가 아니라 입력 문제"임을 반증한다.

## 방향 — 단 하나의 조준점
**등록의 기본값을 모달 → 한 줄 빠른 캡처로 뒤집는다.** 표시 축은 건드리지 않는다.
1. **입구 하나** — 모든 생성 진입을 같은 한 줄 캡처바로 수렴(전역 `selectedDate` 상속).
2. **타입은 입력 안에서 토글** — `[일정|할일]` 토글/`할일 ` 접두사(결정론적, 오프라인). 입력 전 분기 금지.
3. **점진적 공개** — 첫 화면 제목+날짜+토글(스크롤 0). 반복·기간·시간·메모는 `상세 ▾`. 16칸 모달 = 그 펼친 상태 + 편집 전용으로 강등(이미 부분 존재하는 조건부 hidden을 더 밀어붙임).
4. **git 자동 캡처는 폼 거치지 않기**.

## 합격선 (주관 아닌 객관 기준 — 불만 반복의 메타 원인 = 합의 기준 부재였음)
제목만 있는 일정/할일 등록 시: **(a) 진입점 1개 · (b) 스크롤 0 + 노출 컨트롤 3개 이하 · (c) 반복·기간이 기본 화면에서 사라짐.** 셋 다 충족 = "등록 편함" 달성, 하나라도 미달 = 위치만 바꾼 7번째 패치.

## 정직한 구현 비용 (검증 보정)
- 일정(startTime/endTime/allDay/recur/endDate/commits)과 할 일(done/prio/completedAt)은 **데이터 구조가 다름** → 캡처바가 타입에 따라 `addTodo()` 또는 **경량 `createEvent()` 어댑터**로 분기(누락 필드 안전 기본값). 16칸 모달 재설계보다 훨씬 가볍지만 무비용은 아님.
- 도입 후 안정 베이스 무변경을 `__test` 라운드트립으로 회귀 검증.
