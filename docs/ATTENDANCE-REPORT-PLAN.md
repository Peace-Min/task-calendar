# 근태 및 보고 UX (#17)

2026-10-26. 기준: 이슈 #17과 사용자가 확정한 [근태 보고 처리 정책](ATTENDANCE-REPORT-POLICY.md).
상태: 정책 반영 및 지정 범위 검증 완료(2026-10-27). 회사 주간 실전송 검증과 운영 배포는 남아 있다. 개발 기준은 `feat/db-app`의 `2bcb5d2`, 작업 브랜치는 `feat/17-attendance-reports`다. 기존 작업 공간과 main은 수정하지 않는다.

## 확정 설계

- 개인, 과제와 별도의 근태 탭. 일간은 월 달력, 주간은 기간 겹침 검색과 페이지 목록. 상세와 편집은 팝업이다.
- 등록된 보고 과제 선택, 소수 시간과 업무 내용, 주간 차주 계획을 편집한다. 원문 제목과 공수는 구조화 입력으로 생성한다.
- 제출 확인은 입력 검증과 서버 과제명 조회만 수행한다. 작성본을 DB에 저장하지 않는다.
- 회사 성공 확인 후 기존 일간 보고 본문과 시간 행을 한 트랜잭션으로 저장한다. 주간도 회사 성공 후 저장한다.
- 기존 보고 표를 확장한다. 일간과 주간에 report_json, 주간에 submitted_at을 추가한다. 새 작성본 표는 만들지 않는다.
- 어느 단계든 실패하면 편집창과 입력을 유지하고 공통 실패 안내를 표시한다. 재시도는 수정한 현재 내용으로 회사부터 다시 실행한다.
- 처리 중에만 입력과 연속 클릭을 막는다. 모두 성공한 뒤에만 편집창을 닫고 DB 기준으로 달력을 갱신한다.
- 로컬 복구 큐, DB 전용 재시도, 부팅 시 자동 복구, 회사와 DB의 자동 대조는 추가하지 않는다.
- 미기록 근태는 회사 기존 값을 유지한다. 회사 주간 양식의 추가 항목을 보존하고 성공 후 되읽기로 확인한다.
- 기존의 주간 폼 채우기는 제출이 아니므로 성공한 보고로 DB에 기록하지 않는다. 근태 탭의 주간 보고는 직접 제출 경로다.
- 사용자 식별은 호스트 세션에서 읽는다. 계정 전환 시 화면과 검색을 초기화하고 늦은 회신을 새 계정에 반영하지 않는다.
- 보고 조회는 사용자, 기간, 검색과 페이지 단위다. 기존 주간 composed_at을 회사 제출 성공으로 소급 해석하지 않는다.

## 작성 UI 재검토 (2026-10-27)

보고 처리 정책과 백엔드 구현은 유지한다. 사용자가 캘린더 데이터 재사용 부족, 날짜 클릭 시 편집 직행, 여러 과제의 긴 폼을 지적했다. 이후 요청은 구현보다 프로토타입 우선이다. 캘린더 항목을 블록으로 선별 추가하는 A, 과제별 집중 편집 B, 초안 검토 C를 준비했다. B와 C 결합은 제안일 뿐 확정하지 않았다. 현재 제품 코드에 이 시안의 데이터 연결을 구현했다고 보고하면 안 된다. [최신 인계](handoff/2026-10-27-attendance-composer.md)와 [시안 안내](prototypes/attendance-composer/README.md)를 읽고 이어서 검토한다.

## 폐기한 초기 설계

DB 작성본 선저장, 마지막 제출본과 별도 작성본 관리, 전송 시도 DB 잠금 및 스냅샷, DB 저장만 재시도, 미반영 복구 큐는 사용자 최종 결정으로 채택하지 않는다. 초기 이슈 또는 시안에 이 내용이 남아 있어도 정책 정본을 우선한다.
