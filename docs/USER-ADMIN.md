## 1. 확정 요구 (사용자 원문 기준 — 이것이 판정 기준)

- "지금 과제도 관리자만 편집할 수 있잖아. 계정도 그런 식으로 접근하면 될 것 같은데."
- "관리자가 신규 직원이나 퇴사 직원 있으면 **App 단에서만** 관리하는 걸 원함."
- "**편집 권한 포함**해서."
- "직접 DB 에서 제어하면 실수할 가능성도 있잖아."
- 순번: "같은 직급이라도 입사일이나 타직장 연차를 고려해서 더 상단에" · "굳이 팀별로 안 하고 **전체 직원**끼리."
- 순번 갱신: "12 라고 하면 기존 12 부터 일일이 +1 씩 해줘야 함?" → 아니어야 한다.

요구를 한 줄로: **과제 관리와 같은 모양으로, 관리자가 앱 안에서 직원을 등록·수정·퇴사 처리·서열 조정한다. 관리자는 숫자를 보지 않는다.**

## 3. 데이터

### 3.1 컬럼

```sql
-- app_user (title 바로 뒤)
sort_order  SMALLINT UNSIGNED NULL DEFAULT NULL,   -- 전체 직원 서열. 작을수록 위. NULL=미지정(맨 뒤). 앱이 10 간격으로 재작성
```

- **UNIQUE 를 걸지 않는다.** 재작성 중간에 같은 값이 잠깐 공존해도 이름순으로 갈라져 실해가 없고, UNIQUE 가 있으면 밀기 UPDATE 가 중복 오류로 죽는다.
- **인덱스를 두지 않는다.** 89행이고 정렬 키는 `(소속명, sort_order, name)` 셋인데 첫 키가 조인 값이라 인덱스가 서지 않는다. 필요해지면 그때 실측으로 결정한다.
- **컬럼 COMMENT 를 두지 않는다.** 이 DB 는 컬럼 주석이 0/174 이고, 두면 이관 경로와 신규 구축 경로의 덤프가 갈린다(09-09 가 복구한 드리프트와 같은 종류). 문구는 `tools/schema-report/col-notes.json` 이 진다.
- **이름이 `cal_*` 의 `sort_order` 와 같지만 뜻이 다르다.** 캘린더 쪽은 사용자당 0 부터 빈틈없는 배열 인덱스이고, 이쪽은 관리자가 정하는 전사 서열이다. 마스터 표 넷(`org_unit`·`title_code`·`section_code`·`status_code`)이 이미 이 뜻으로 같은 이름을 쓰므로 맞추되, `CALENDAR-TABLE-DESIGN.md` §5.3 에 한 줄 적는다.

### 3.2 마이그레이션 — `migrate-2026-09-10-user-sort-order.sql` (10 → 11)

`migrate-2026-09-10-dev-end-date.sql` 과 같은 형식. 가드가 `'10'` 아니면 중단(재실행도 막는다).

```sql
ALTER TABLE app_user ADD COLUMN sort_order SMALLINT UNSIGNED NULL DEFAULT NULL AFTER title;

-- 초기값: 직급 서열(title_code.sort_order) → 이름 순으로 10 간격. 관리자가 손대기 전에도 명부가 말이 되게.
UPDATE app_user u
  JOIN (
    SELECT u2.user_id,
           ROW_NUMBER() OVER (ORDER BY (t.sort_order IS NULL), t.sort_order, u2.name, u2.user_id) * 10 AS n
      FROM app_user u2
      LEFT JOIN title_code t ON t.name = u2.title
  ) r ON r.user_id = u.user_id
   SET u.sort_order = r.n,
       u.updated_at = u.updated_at;   -- updated_at 명시 = ON UPDATE 발화 차단
```

- **창 함수를 쓰는 이유**는 §11-1 이다 — 처음 적은 `SET @r := 0` + `ORDER BY` 형태는 다중 표 UPDATE 에서 MySQL 이 받지 않는다. 결과(직급 서열 → 이름 순, 10 간격)는 같다.
- `updated_at = u.updated_at` 을 SET 에 명시하는 이유는 09-09 마이그레이션 (5) 와 같다 — 안 적으면 서버 `ON UPDATE` 가 89행의 갱신 시각을 전부 덮는다.
- 초기값은 **참고용**이다. 관리자가 한 번이라도 순서를 저장하면 앱이 전량 재작성한다.
- 사후검증: 컬럼 위치(`title` 다음), NULL 인 활성 사용자 0명, 판번호 11.

**신규 구축 경로**(비공개 저장소 `taskmgr-company-data/01-schema-users.sql`)에도 같은 컬럼을 같은 자리에 넣는다. 시드(`03-seed-users.sql`)는 값을 넣지 않는다 — 신규 구축 뒤 첫 명부는 전원 NULL(=이름순)이고, 관리자가 첫 저장을 하면 매겨진다. 이관 경로와 신규 구축 경로는 **구조**가 같아야 하지 **값**이 같을 필요는 없다(기존 원칙).

### 3.3 왜 삭제가 없는가 — 표가 스스로 막는다

`app_user` 를 부모로 삼는 외래키 11개가 전부 `ON DELETE RESTRICT` 다(09-09 통일). 일정·근태·공수·보고가 한 건이라도 있는 사람은 DELETE 자체가 `ERROR 1451` 이다. 퇴사는 `is_active=0` 이고 행은 남는다. 이건 새 결정이 아니라 `01-schema-users.sql` 이 이미 적어 둔 것("퇴사·휴직은 0. 행은 남겨 과거 데이터 참조를 지킨다")을 화면이 따르는 것이다.

### 3.4 권한 파일

`taskmgr-company-data/05-grants.sql` 의 `app_user` 줄을 `GRANT SELECT, INSERT, UPDATE` 로. `org_unit`·`title_code` 는 그대로 SELECT. DELETE 는 주지 않는다 — 과제와 같다. `db/deploy/grants-calendar.sql` 머리말의 권한 분포 서술도 함께 고친다.

## 4. 호스트 (`widget/ProjectDb.cs`)

사용자 쓰기를 `ProjectDb` 에 둔다. 이 파일이 이미 `app_user` 읽기(`LoadMembersJsonAsync`·`LoadAppUserJsonAsync`)와 **쓰기 관문**(`OpenWriteAsync`)을 갖고 있고, `tests/admin-auth.test.mjs` 의 "쓰기 SQL 은 관문을 지난다" 계약이 이 파일을 본다. 파일을 나누면 그 계약을 넓혀야 한다.

### 4.1 관리자 관문 — `OpenAdminAsync`

`OpenWriteAsync` 와 같은 순서(세션 → 연결 → 프리앰블 → **같은 연결로** 권한 조회)이되 `edit_role='admin'` 만 통과시킨다. 거부 문구: "직원 정보는 관리자만 고칠 수 있습니다." 판정은 로그인 시점이 아니라 **요청 시점**이다([USER-LOGIN §3.3](USER-LOGIN.md)) — 관리자에서 내려간 사람은 다음 저장부터 막힌다.

### 4.2 메시지 계약 (호스트 ↔ 웹) — 과제 관리와 같은 모양

| 메시지 | 방향 | 내용 |
|---|---|---|
| `loadMembers` (기존) | 웹 → 호스트 | 회신에 **관리자일 때만** 덧붙인다: `admin:true` · `members[].userId·orgId·viewScope·editRole·isActive·sortOrder` · `titles[]`(활성 직급) · `units[]`(활성 조직, 트리) · `includeInactive` 요청 시 퇴사자 포함. 관리자가 아니면 회신은 **지금과 글자까지 같다**(기존 시험이 그대로 통과해야 한다) |
| `saveUser` | 웹 → 호스트 | `{ userId?, loginId, name, title, orgId, viewScope, editRole }`. `userId` 없으면 INSERT, 있으면 UPDATE. 회신 `__userSaved(ok, msg)` |
| `setUserActive` | 웹 → 호스트 | `{ userId, active }`. 퇴사 처리와 복구. 회신 `__userSaved` |
| `saveUserOrder` | 웹 → 호스트 | `{ userIds: [...] }` 화면에 보이는 순서 그대로. 호스트가 10·20·30… 으로 **전량 재작성**. 회신 `__userSaved` |

성공하면 호스트가 곧바로 `loadMembers` 를 다시 돌려 명부를 갱신한다(과제의 `SaveProjectAsync → LoadProjectsToWebAsync` 와 같다). 웹은 응답을 기다리지 않고 재조회 결과로 화면을 그린다.

### 4.3 검증 — 호스트가 걸러 사용자 문장으로, 최종 보증은 DB 제약

| 필드 | 규칙 | 거부 문구 |
|---|---|---|
| `loginId` | TRIM · `^[A-Za-z0-9._-]{1,50}$` · 넷커스 계정과 같아야 한다(이메일 아님) | "로그인 ID 는 영문·숫자·`._-` 만 쓸 수 있습니다." / "이미 등록된 ID 입니다."(1062) |
| `name` | TRIM · 비어 있으면 거부 | "이름을 입력하세요." |
| `title` | 활성 `title_code` 에 있어야 | "등록되지 않은 직급입니다." (최종은 `fk_user_title`) |
| `orgId` | 활성 `org_unit` 에 있어야. 비워도 됨 | "등록되지 않은 소속입니다." (최종은 `fk_user_org_id`) |
| `viewScope` | `self / unit_tree / all` | "열람 범위 값이 올바르지 않습니다." (최종은 `chk_view_scope`) |
| `editRole` | `viewer / editor / admin` | "편집 권한 값이 올바르지 않습니다." (최종은 `chk_edit_role`) |

대소문자: `login_id` 는 콜레이션이 대소문자를 무시하므로 `PHMIN` 과 `phmin` 은 DB 에서 같은 ID 다. 호스트는 **입력을 그대로 저장**하되 중복 검사는 DB 에 맡긴다(1062). 정규화(소문자 강제)는 하지 않는다 — 넷커스가 어떤 표기를 쓰는지 이 앱이 정하지 않는다.

### 4.4 잠금 방지 — 관리자가 자기 문을 닫는 것을 막는다 (호스트 전담)

세 규칙. 화면은 힌트로 미리 잠그지만 **판정은 호스트**가 같은 트랜잭션 안에서 한다(`SELECT … FOR UPDATE`).

1. **자기 자신을 퇴사 처리할 수 없다.** "자기 계정은 퇴사 처리할 수 없습니다."
2. **자기 편집 권한을 바꿀 수 없다.** 올리는 것도 내리는 것도. "자기 권한은 바꿀 수 없습니다. 다른 관리자가 바꿔야 합니다."
3. **마지막 활성 관리자를 강등·퇴사 처리할 수 없다.** 대상이 admin 이고 `SELECT COUNT(*) FROM app_user WHERE edit_role='admin' AND is_active=1 FOR UPDATE` 가 1 이면 거부. "관리자가 한 명뿐이라 처리할 수 없습니다. 먼저 다른 관리자를 지정하세요."

이걸 안 막으면 관리자가 스스로를 잠그고 DB 로 가야 풀린다 — "앱에서만 관리한다"는 요구가 그 순간 깨진다.

### 4.5 동시성

낙관적 잠금은 두지 않는다. 관리자가 한두 명이고 편집이 드물다. 마지막 저장이 이긴다. 잠금 방지 셋만 `FOR UPDATE` 로 직렬화한다. `updated_at` 은 서버 `ON UPDATE` 에 맡긴다(이 표는 낙관적 잠금 토큰이 아니다 — `schema-calendar.sql` 머리말의 예외와 같은 성격).

### 4.6 세션과 반영 시점

- **권한·활성**: 즉시. 쓰기 관문이 요청마다 DB 에서 읽는다. 퇴사 처리된 사람은 다음 저장부터 막히고, 다음 부팅에서 로그인 게이트에 걸린다.
- **이름·직급·소속**: 그 사람의 세션 파일(`user.session`, 4필드)은 로그인 때 채워진다. 관리자가 고친 값은 그 사람이 **다시 로그인하거나 「사용자 정보」를 열 때** 반영된다. 즉시 반영이 필요하면 그때 세션 재조회를 넣는다 — 이번 범위 밖.
- **넷커스 계정**: 이 앱은 만들지 않는다. "신규 직원 등록"은 **이 앱에 등록**하는 것이다. 넷커스 로그인이 되는 ID 인지는 그 사람이 처음 로그인할 때 판명된다.

## 5. 화면 (`task-calendar-prototype.html`)

### 5.1 구성원 명부 — 관리자 편집 모드

- 관리자가 아니면 **지금과 똑같다**(DOM 에 편집 컨트롤이 없어야 한다 — 숨김이 아니라 부재. 시험 계약 §8-7).
- 관리자면 상단에 「직원 등록」 버튼과 「순서 편집」 토글, 「퇴사자 보기」 토글.
- 각 행 우측에 「편집」. 활성 행에는 「퇴사」, 퇴사자 행(퇴사자 보기 켰을 때)에는 「복구」.
- 「순서 편집」을 켜면 행마다 ▲▼ 가 나타난다. 끌어놓기는 v2 — 키보드로 닿지 않는 조작을 첫판에 넣지 않는다(명부 행이 `<button>` 인 이유와 같다).
- 순서를 바꾸면 화면에 즉시 반영하고 「순서 저장」을 눌러야 `saveUserOrder` 로 나간다. 저장 전 닫으면 되돌린다.
- **순번 숫자는 어디에도 표시하지 않는다.**

### 5.2 편집 폼 `#userEditModal`

로그인 ID(신규만 편집 가능 — 기존 사용자의 ID 는 넷커스 소유라 여기서 바꾸지 않는다) · 이름 · 직급(드롭다운, `titles`) · 소속(드롭다운 트리, `units`) · 열람 범위(라디오 3) · 편집 권한(라디오 3).

- 자기 행을 열면 편집 권한 라디오가 잠기고 힌트가 뜬다(§4.4-2). 최종 판정은 호스트.
- 저장 → `saveUser` → `__userSaved(ok,msg)` → 성공이면 폼 닫고 재조회, 실패면 폼 안 메시지(과제 폼의 `offEdMsgSet` 과 같다).
- 「퇴사」는 확인창 한 번("○○○ 님을 퇴사 처리합니다. 기록은 남고 명부에서만 사라집니다.") 뒤 `setUserActive`.

### 5.3 정렬은 호스트가, 화면은 그대로

명부 순서는 **호스트 응답 순서 그대로** 그린다. 화면에서 다시 정렬하지 않는다 — 두 곳이면 갈린다.

```sql
ORDER BY o.name, u.sort_order IS NULL, u.sort_order, u.name
```

소속 → 순번(NULL 은 맨 뒤) → 이름. 직급 서열을 여기 끼우지 않는다 — 전사 서열이 직급을 이미 담고 있고, 끼우면 관리자가 정한 순서를 직급이 뒤엎는다.

## 7. 정직한 한계 — 공유 계정

이 결정으로 `taskmgr_app` 계정이 `app_user` 에 쓸 수 있게 된다. 그 비밀번호는 배포본에 담겨 89대에 퍼진다. MySQL 에 직접 붙는 사람은 앱의 관리자 관문을 통째로 우회해 **누구든 admin 으로 만들 수 있다.** 과제 마스터는 이미 같은 상태이고 사용자가 이를 알고 받아들였다(2026-09-10). 다만 이 표는 "누가 관리자인가"를 담는 표라 결과가 더 무겁다.

## 7-1. 알려진 구멍 — 구현하고 나서 남은 둘 (2026-09-10)

§7 이 "알고 받아들인 한계"라면 이쪽은 **아직 판단이 안 끝난 곳**이다. 둘 다 실동작으로 확인한 것이 아니라 코드를 읽고 따진 것이라, 겪은 사람이 생기면 여기를 먼저 볼 것.

**(a) 「퇴사자 보기」를 끈 채 순서를 저장하면 퇴사자의 서열이 옛 값으로 남는다.**
`saveUserOrder` 는 웹이 보낸 `userIds` — 즉 **그때 화면에 보이던 사람들만** 10·20·30… 으로 다시 쓴다. 퇴사자는 그 목록에 없으므로 마이그레이션이 준 초기값(또는 퇴사 전 서열)을 그대로 들고 남는다. 그 사람을 나중에 복구하면 그 옛 숫자가 새 서열 사이에 **끼어든다**. 화면상으로는 "복구했더니 엉뚱한 자리에 있다"로 보인다. 조치는 그 자리에서 순서를 한 번 더 저장하는 것이고, 그때는 퇴사자도 목록에 있으니 함께 재작성된다. 구조적으로 막으려면 호스트가 목록 밖 사람을 뒤로 몰아 함께 재작성해야 하는데, 그러면 "보이는 순서 = 저장되는 순서"라는 단순한 계약이 깨진다 — 그래서 이번에는 고르지 않았다.

**(b) 이 마이그레이션 전의 DB 에 이 판의 위젯이 붙으면 명부가 통째로 빈다 — 그래서 배포 순서는 DB 가 먼저다.**
판번호 게이트(`CalendarDb.ExpectedSchemaVersion`)는 **전량 교체만** 거부한다(설계상 의도 — 전 쓰기 봉인은 과하다). 명부 조회는 그 게이트를 지나지 않으므로, 컬럼이 없는 DB 에 새 위젯이 붙으면 게이트가 아무 말도 하지 않는 채 `SELECT … u.sort_order` 가 `ERROR 1054` 로 죽고 **구성원 명부가 빈 채로 열린다.** 반대 짝(마이그레이션을 마친 DB + 구버전 위젯)은 무해하다 — 컬럼을 모를 뿐이다. **결론: 마이그레이션을 먼저 적용하고 그 다음에 위젯을 내보낸다.** 같은 문장이 마이그레이션 머리말과 `db/deploy/README.md` 순서표에도 있다.

## 8. 시험 계약 (구현과 함께 — 각 계약에 변이 시험을 짝으로)

1. **정본·마이그레이션 동치** — 이관 경로(v10 원본 + 새 마이그레이션)와 신규 구축 경로의 덤프가 같다. 컬럼이 `title` 바로 뒤. (기존 `schema-integrity` 계약⑥이 판번호 11 정합을 자동으로 잡는다.)

4. **입력 검증** — 정규식·빈 이름·미등록 직급/소속·도메인 밖 값이 사용자 문장으로 거부된다.

6. **정렬** — 명부 SQL 의 ORDER BY 가 §5.3 과 글자까지 같고, 화면이 재정렬하지 않는다(`renderMembers` 에 `sort(` 없음).
7. **관리자 아닐 때 부재** — 비관리자 세션으로 명부를 열면 편집 컨트롤이 DOM 에 없다. 관리자 회신에서 `admin` 을 빼면 같은 결과.

9. **판번호 게이트** — `loop-schema-gate.mjs` 가 판본 무관이라 손댈 것 없음. 위젯 상수 11 과 정본 시딩 11 의 정합은 `schema-guards` 가드 ⑨.

## 11. 정정 이력

> **2026-09-10 — 구현이 끝났다.** 본 저장소 커밋과 비공개 저장소 커밋 한 쌍으로 나갔고, 실 `taskmgr` 은 마이그레이션까지 적용해 판번호가 한 칸 올라간 상태다(값의 정본은 `db/deploy/schema-calendar.sql` 끝의 `cal_schema_meta` 시딩 줄, 실 DB 값은 `SELECT v FROM cal_schema_meta WHERE k='schema_version'`).
>
> 아래 열둘은 **설계와 다르게 처리한 곳**이다. 본문은 §3.2 만 실물에 맞춰 고쳤고, 나머지는 여기에만 적는다 — 본문을 지우면 "왜 그렇게 했나"가 함께 사라지기 때문이다. **본문과 여기가 다르면 여기가 맞다.**

**1. §3.2 의 초기값 SQL 이 MySQL 에서 안 돈다 — 창 함수로 바꿨다.**
`SET @r := 0` + `UPDATE … LEFT JOIN … ORDER BY` 형태였는데, MySQL 은 **다중 표 UPDATE 에 `ORDER BY` 를 허용하지 않는다**("For multiple-table syntax, ORDER BY and LIMIT cannot be used"). 사용자 변수 누적은 8.4 에서 평가 순서를 보장하지도 않는다. `ROW_NUMBER() OVER (…) * 10` 을 파생 표로 만들어 조인하는 형태로 대체했고 **결과 순서와 간격은 설계 그대로**다. 본문 §3.2 의 SQL 도 실제 마이그레이션(`db/deploy/migrate-2026-09-10-user-sort-order.sql`)과 같은 문장으로 고쳤다 — 문서와 SQL 을 두 벌 두면 어긋나고, 어긋난 쪽이 문서라 아무도 실행해 보지 않는다.

**2. 쓰기 세 명령의 payload 에 `includeInactive` 가 하나씩 붙었다(§4.2).**
설계는 `saveUser`·`setUserActive`·`saveUserOrder` 에 그 필드를 두지 않았다. 그런데 §4.2 마지막 줄의 약속대로 **호스트가 성공 직후 스스로 명부를 다시 읽어 밀어 주는데**, 그때 「퇴사자 보기」가 켜져 있었는지를 호스트가 알 방법이 없다. 호스트는 그 상태를 캐시하지 않는다(캐시하면 웹과 호스트에 같은 상태가 두 벌 생긴다). 그래서 웹이 매 요청에 현재 토글 값을 함께 실어 보내고 호스트는 그것을 재조회에 그대로 물려준다 — 저장했더니 켜 둔 「퇴사자 보기」가 꺼지는 일이 없다.

**3. §8-1 「정본·마이그레이션 동치」는 상시 시험에서 덤프를 뜨지 않는다.**
Node 시험은 MySQL 을 띄울 수 없다. 그래서 상시 게이트가 보는 것은 **두 소스(정본 DDL 과 마이그레이션)가 같은 것을 말하는가** — 타입·NULL 허용·`title` 바로 뒤라는 자리·UNIQUE/인덱스/COMMENT 부재다. 실제 `mysqldump --no-data` 대조는 **격리 DB 로 따로 실증**했고 두 경로의 차이는 0 이었다. 계약의 뜻은 같지만 **증명 수단이 둘로 갈렸다**는 사실을 여기 남긴다 — "시험이 초록이니 덤프가 같다"로 읽으면 틀린다.

**4. §8-3 「잠금 방지」도 절반은 정적 계약이다.**
같은 이유(단위시험이 DB 를 못 든다)로, 상시 시험은 **문구 세 개가 상수 한 곳에 있고 · 세 판정이 `FOR UPDATE` 로 읽으며 · 그 판정과 갱신이 같은 트랜잭션 안이라는 것**을 소스 모양으로 잠근다. `FOR UPDATE` 가 빠지면 두 관리자가 동시에 서로를 강등해 **아무도 남지 않을 수 있다** — 그 변이가 실제로 잡히는지까지 시험에 넣었다. 실 DB 에서의 거부는 루프 시험(`loop-ui-integrity.mjs`)의 불변식 U1(활성 관리자 ≥ 1)이 본다.

**5. 같은 날 앞선 판(`project-dev-end`)의 계약⑤ 를 완화했다.**
그 시험은 *"이 마이그레이션이 언제나 마지막 판"* 을 전제로 판번호를 검사하고 있었다. 이 판이 그 뒤에 붙자 그 전제가 깨졌다. 가정을 빼고 **① 한 번에 한 칸만 움직인다 · ② 가드가 그 출발값을 요구한다 · ③ 정본을 앞서가지 않는다** 셋으로 다시 적었다 — 이 셋은 판이 몇 개 더 붙어도 참이다. 옆 판을 손대야 했다는 사실 자체가 기록할 값이 있다: **판번호를 검사하는 시험은 "내가 마지막"을 전제하면 안 된다.**

**6. 브리지 `case` 세 개를 `membersGet` 바로 옆에 뒀다.**
설계는 자리를 말하지 않았다. 명부 조회와 명부 쓰기는 같은 도메인이고, 셋 다 성공 뒤 `membersGet` 과 같은 경로로 명부를 다시 읽는다. 흩어 두면 다음 사람이 "직원 관련 명령이 여기 전부인가"를 확신할 수 없다.

**7. `#userEditModal` 은 마크업에 **정적 껍데기**로 있다(§5.1 의 '부재' 계약 범위 조정).**
설계 §5.1 은 *"편집 컨트롤이 숨김이 아니라 부재"* 라고 적었고 §8-7 이 그것을 계약으로 잠근다. 실제로는 모달의 빈 폼(입력칸·라디오 컨테이너)이 HTML 에 정적으로 있고, **채워지는 것은 관리자 회신이 왔을 때뿐**이다. 그래서 '부재' 계약은 **명부 안의 편집 컨트롤**(「직원 등록」·「순서 편집」·「퇴사자 보기」·행의 ▲▼·[편집]·[퇴사])에 적용된다 — 그것들은 관리자 회신 없이는 DOM 에 생기지 않는다. 비관리자에게 열리는 문은 없지만, **계약 문장이 가리키는 대상이 설계보다 좁다**는 것을 알고 있어야 한다.

**8. 순서 편집 중에는 검색칸과 조직 선택을 잠근다(설계에 없던 규칙).**
▲▼ 는 "보이는 목록 안에서 한 칸"인데, 검색이나 조직 필터로 목록이 걸러져 있으면 **한 칸이 실제로 어디로 가는지 예측할 수 없다**(보이지 않는 사람을 뛰어넘는다). 그래서 순서 편집을 켜는 순간 검색어를 비우고 두 입구를 막는다 — 편집 중의 목록은 곧 전 명부다. 같은 이유로 순서 편집 중에는 「직원 등록」·「퇴사자 보기」도 감춘다(둘 다 명부를 다시 읽어 **편집 중인 순서를 날린다**).

**9. 직급이 사실상 필수가 됐다 — '직급 미정' 신규 등록이 안 된다.**
§4.3 표에 `title` 은 *"활성 `title_code` 에 있어야"* 라고만 적혀 있고 `orgId` 처럼 *"비워도 됨"* 이 없다. 구현이 그 표를 글자 그대로 따랐으므로 빈 값은 활성 코드 집합에 없어 *"등록되지 않은 직급입니다."* 로 거부된다. 설계대로이지만 **의도한 결과인지는 확인하지 않았다** — 직급이 아직 안 정해진 신입을 먼저 등록해 두는 운용이 필요하면 `title` 을 NULL 허용으로 여는 별건이다. 후속 후보로 남긴다.

**10. 비관리자 회신은 키도 순서도 같지만, 명부의 **행 순서**는 전원 바뀐다.**
§4.2 는 *"관리자가 아니면 회신이 지금과 글자까지 같다"* 고 적었다. 키 구성은 실제로 같다. 다만 명부 SQL 의 `ORDER BY` 가 §5.3 대로 `sort_order` 를 끼워 넣도록 바뀌었고 **그 정렬은 권한과 무관**하므로, 비관리자가 보는 명부도 (소속명, 이름) 순에서 (소속명, 서열, 이름) 순으로 **전원 바뀐다.** 그게 이 기능의 목적이므로 회귀가 아니라 의도된 변화지만, "비관리자에게는 아무것도 안 바뀐다"로 읽히면 틀린다.

**11. `grants-calendar.sql` 은 서술만 고쳤다 — 실제 GRANT 는 비공개 저장소에 있다.**
§3.4 는 두 파일을 함께 고치라고 적었고 그렇게 했지만, 두 파일의 **역할이 다르다**는 점이 설계에 드러나 있지 않았다. `db/deploy/grants-calendar.sql` 은 `app_user` 에 대해 `GRANT SELECT` 만 발행하고(캘린더가 그 표를 읽어야 하므로) 머리말에서 INSERT·UPDATE 의 존재를 **서술**한다. 실제로 쓰기를 여는 문장은 `taskmgr-company-data/05-grants.sql` 에 있다. **따라서 `db/deploy` 만으로 세운 서버에서는 직원 관리가 `ERROR 1142` 로 전부 죽는다** — 컬럼은 서 있으므로 명부는 보이고 저장만 실패한다. 비공개 저장소의 `05` 를 함께(또는 다시) 적용해야 한다.

**12. 확신이 안 서는 곳 둘을 [§7-1 알려진 구멍](#7-1-알려진-구멍--구현하고-나서-남은-둘-2026-09-10)에 따로 적었다.**
(a) 「퇴사자 보기」를 끈 채 저장한 순서가 퇴사자를 남겨 두는 것 · (b) 마이그레이션 전 DB 에 이 판의 위젯이 붙으면 명부가 `ERROR 1054` 로 비는 것(**배포 순서는 DB 가 먼저**). 둘 다 설계가 다루지 않았고 실동작으로 확인하지도 않았다 — 그래서 "정정"이 아니라 "구멍"으로 분리했다.
