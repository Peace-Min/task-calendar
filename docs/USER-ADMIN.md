## 1. 확정 요구 (사용자 원문 기준 — 이것이 판정 기준)

- "지금 과제도 관리자만 편집할 수 있잖아. 계정도 그런 식으로 접근하면 될 것 같은데."
- "관리자가 신규 직원이나 퇴사 직원 있으면 **App 단에서만** 관리하는 걸 원함."
- "**편집 권한 포함**해서."
- "직접 DB 에서 제어하면 실수할 가능성도 있잖아."
- 순번: "같은 직급이라도 입사일이나 타직장 연차를 고려해서 더 상단에" · "굳이 팀별로 안 하고 **전체 직원**끼리."
- 순번 갱신: "12 라고 하면 기존 12 부터 일일이 +1 씩 해줘야 함?" → 아니어야 한다.

요구를 한 줄로: **과제 관리와 같은 모양으로, 관리자가 앱 안에서 직원을 등록·수정·퇴사 처리·서열 조정한다. 관리자는 숫자를 보지 않는다.**

## 3. 데이터

### 3.1 컬럼

```sql
-- app_user (title 바로 뒤)
sort_order  INT UNSIGNED NULL DEFAULT NULL,        -- 전체 직원 서열. 작을수록 위. NULL=미지정(맨 뒤). 앱이 10 간격으로 재작성
```

- **UNIQUE 를 걸지 않는다.** 재작성 중간에 같은 값이 잠깐 공존해도 이름순으로 갈라져 실해가 없고, UNIQUE 가 있으면 밀기 UPDATE 가 중복 오류로 죽는다.
- **인덱스를 두지 않는다.** 89행이고 정렬 키는 `(소속명, sort_order, name)` 셋인데 첫 키가 조인 값이라 인덱스가 서지 않는다. 필요해지면 그때 실측으로 결정한다.
- **컬럼 COMMENT 를 두지 않는다.** 이 DB 는 컬럼 주석이 0/174 이고, 두면 이관 경로와 신규 구축 경로의 덤프가 갈린다(09-09 가 복구한 드리프트와 같은 종류). 문구는 `tools/schema-report/col-notes.json` 이 진다.
- **이름이 `cal_*` 의 `sort_order` 와 같지만 뜻이 다르다.** 캘린더 쪽은 사용자당 0 부터 빈틈없는 배열 인덱스이고, 이쪽은 관리자가 정하는 전사 서열이다. 마스터 표 넷(`org_unit`·`title_code`·`section_code`·`status_code`)이 이미 이 뜻으로 같은 이름을 쓰므로 맞추되, `CALENDAR-TABLE-DESIGN.md` §5.3 에 한 줄 적는다.

### 3.2 마이그레이션 — `migrate-2026-09-10-user-sort-order.sql` (10 → 11)

`migrate-2026-09-10-dev-end-date.sql` 과 같은 형식. 가드가 `'10'` 아니면 중단(재실행도 막는다).

```sql
ALTER TABLE app_user ADD COLUMN sort_order SMALLINT UNSIGNED NULL DEFAULT NULL AFTER title;   -- 11 판. 12 판(§11-14)이 INT UNSIGNED 로 넓힌다

-- 초기값: 직급 서열(title_code.sort_order) → 이름 순으로 10 간격. 관리자가 손대기 전에도 명부가 말이 되게.
UPDATE app_user u
  JOIN (
    SELECT u2.user_id,
           ROW_NUMBER() OVER (ORDER BY (t.sort_order IS NULL), t.sort_order, u2.name, u2.user_id) * 10 AS n
      FROM app_user u2
      LEFT JOIN title_code t ON t.name = u2.title
  ) r ON r.user_id = u.user_id
   SET u.sort_order = r.n,
       u.updated_at = u.updated_at;   -- updated_at 명시 = ON UPDATE 발화 차단
```

- **창 함수를 쓰는 이유**는 §11-1 이다 — 처음 적은 `SET @r := 0` + `ORDER BY` 형태는 다중 표 UPDATE 에서 MySQL 이 받지 않는다. 결과(직급 서열 → 이름 순, 10 간격)는 같다.
- `updated_at = u.updated_at` 을 SET 에 명시하는 이유는 09-09 마이그레이션 (5) 와 같다 — 안 적으면 서버 `ON UPDATE` 가 89행의 갱신 시각을 전부 덮는다.
- 초기값은 **참고용**이다. 관리자가 한 번이라도 순서를 저장하면 앱이 전량 재작성한다.
- 사후검증: 컬럼 위치(`title` 다음), NULL 인 활성 사용자 0명, 판번호 11.

**신규 구축 경로**(비공개 저장소 `taskmgr-company-data/01-schema-users.sql`)에도 같은 컬럼을 같은 자리에 넣는다. 시드(`03-seed-users.sql`)는 값을 넣지 않는다 — 신규 구축 뒤 첫 명부는 전원 NULL(=이름순)이고, 관리자가 첫 저장을 하면 매겨진다. 이관 경로와 신규 구축 경로는 **구조**가 같아야 하지 **값**이 같을 필요는 없다(기존 원칙).

### 3.3 왜 삭제가 없는가 — 표가 스스로 막는다

`app_user` 를 부모로 삼는 외래키 11개가 전부 `ON DELETE RESTRICT` 다(09-09 통일). 일정·근태·공수·보고가 한 건이라도 있는 사람은 DELETE 자체가 `ERROR 1451` 이다. 퇴사는 `is_active=0` 이고 행은 남는다. 이건 새 결정이 아니라 `01-schema-users.sql` 이 이미 적어 둔 것("퇴사·휴직은 0. 행은 남겨 과거 데이터 참조를 지킨다")을 화면이 따르는 것이다.

**2026-09-10 추가 — 예외는 「휴지통」 하나다.** 기록이 0건인 퇴사 계정(오등록·한 번도 안 쓴 계정)만 관리자가 `docs/TRASH-DELETE.md` 의 관문(`ProjectDb.DeleteTrashAsync`, `OpenAdminAsync` 전용, 이름 입력 확인)을 지나 실제로 지운다. `DELETE FROM app_user` 는 앱 전체에서 그 함수 안에만 있다(계약 ⑤). 기록이 있는 사람은 여전히 퇴사 상태로 남는다.

### 3.4 권한 파일

`taskmgr-company-data/05-grants.sql` 의 `app_user` 줄을 `GRANT SELECT, INSERT, UPDATE` 로. `org_unit`·`title_code` 는 그대로 SELECT. DELETE 는 주지 않는다 — 과제와 같다. `db/deploy/grants-calendar.sql` 머리말의 권한 분포 서술도 함께 고친다.

## 4. 호스트 (`widget/ProjectDb.cs`)

사용자 쓰기를 `ProjectDb` 에 둔다. 이 파일이 이미 `app_user` 읽기(`LoadMembersJsonAsync`·`LoadAppUserJsonAsync`)와 **쓰기 관문**(`OpenWriteAsync`)을 갖고 있고, `tests/admin-auth.test.mjs` 의 "쓰기 SQL 은 관문을 지난다" 계약이 이 파일을 본다. 파일을 나누면 그 계약을 넓혀야 한다.

### 4.1 관리자 관문 — `OpenAdminAsync`

`OpenWriteAsync` 와 같은 순서(세션 → 연결 → 프리앰블 → **같은 연결로** 권한 조회)이되 `edit_role='admin'` 만 통과시킨다. 거부 문구: "직원 정보는 관리자만 고칠 수 있습니다." 판정은 로그인 시점이 아니라 **요청 시점**이다([USER-LOGIN §3.3](USER-LOGIN.md)) — 관리자에서 내려간 사람은 다음 저장부터 막힌다.

### 4.2 메시지 계약 (호스트 ↔ 웹) — 과제 관리와 같은 모양

| 메시지 | 방향 | 내용 |
|---|---|---|
| `membersGet` (기존) | 웹 → 호스트 | 회신에 **관리자일 때만** 덧붙인다: `admin:true` · `members[].userId·orgId·viewScope·editRole·isActive·sortOrder` · `titles[]`(활성 직급) · `units[]`(활성 조직, 트리) · `includeInactive` 요청 시 퇴사자 포함. 관리자가 아니면 회신은 **지금과 글자까지 같다**(기존 시험이 그대로 통과해야 한다) |
| `saveUser` | 웹 → 호스트 | `{ reqId, userId?, loginId, name, title, orgId, viewScope, editRole, includeInactive }`. `userId` 없으면 INSERT, 있으면 UPDATE. **회신 `{ ok, msg, roster }`**(`reqId` 왕복 · `ReplyOnUi`). `roster` = 갱신된 명부 JSON **문자열**, **성공했을 때만** — 실패면 `""` |
| `setUserActive` | 웹 → 호스트 | `{ reqId, userId, active, includeInactive }`. 퇴사 처리와 복구. **회신 `{ ok, msg, roster }`**. `roster` 는 `ok \|\| msg == AlreadyActiveMsg` 둘일 때만(§11-32) |
| `saveUserOrder` | 웹 → 호스트 | `{ reqId, userIds: [...], includeInactive }` 화면에 보이는 순서 그대로. 호스트가 10·20·30… 으로 **전량 재작성**. **회신 `{ ok, msg, roster }`**. `roster` 는 `ok \|\| msg == StaleRosterMsg` 둘일 때만(§11-30②) |

세 쓰기는 **요청/회신 배관**(`hostRequest` ↔ `ReplyOnUi`)을 탄다 — 결과와 갱신된 명부가 **한 회신**으로 온다. 웹은 회신 하나만 받으면 결과와 화면이 같은 시점의 것이라, 뒤따르는 푸시를 기다릴 필요가 없다(2026-09-14 · §11-34).

명부 **푸시**는 **없다**(2026-09-14 · §11-35). 마지막 자리로 남겨 뒀던 「휴지통에서 인력을 복구·영구 삭제한 뒤의 갱신」도 그 조작의 회신(`roster`)을 타므로([TRASH-DELETE §4.2](TRASH-DELETE.md)), 방출부(`LoadMembersToWebAsync`)와 웹 수신부(`window.__applyMembers`)를 함께 지웠다. 명부가 화면에 닿는 길은 **회신 하나**다 — 순서 편집 중에 도착한 **남의** 회신(휴지통 복구·삭제)을 미뤄 두는 일은 그대로이고, 그 문은 `uaSeatReply` 다. 그 부재는 게이트 계약⑭-h4 가 `widget/*.cs` 전부와 웹을 함께 훑어 지킨다.

> ★ 이 문서 초판은 그 메시지를 `loadMembers` 라고 적었지만 **그런 이름은 어디에도 없다** — 브리지의 실제 `case` 는 처음부터 `membersGet` 이었다(`MainWindow.xaml.cs`). 이름을 지어 놓고 문서에만 두면 다음 사람이 코드에서 못 찾고, 못 찾으면 **문서가 낡은 것인지 자기가 못 찾는 것인지** 판단할 수 없다. 2026-09-10 에 실물 이름으로 고쳤다(§11-19).

### 4.3 검증 — 호스트가 걸러 사용자 문장으로, 최종 보증은 DB 제약

| 필드 | 규칙 | 거부 문구 |
|---|---|---|
| `loginId` | TRIM · `^[A-Za-z0-9._-]{1,50}$` · 넷커스 계정과 같아야 한다(이메일 아님) | "로그인 ID 는 영문·숫자·`._-` 만 쓸 수 있습니다." / "이미 등록된 ID 입니다."(1062) |
| `name` | TRIM · 비어 있으면 거부 | "이름을 입력하세요." |
| `title` | **신규**: 활성 `title_code` 에 있어야 · **수정**: 활성이거나 **그 사람에게 지금 저장된 값**(2026-09-10 완화 · §11-20) | "등록되지 않은 직급입니다." (최종은 `fk_user_title`) |
| `orgId` | **신규**: 활성 `org_unit` 에 있어야 · **수정**: 활성이거나 지금 저장된 값. 비워도 됨 | "등록되지 않은 소속입니다." (최종은 `fk_user_org_id`) |
| `viewScope` | `self / unit_tree / all` | "열람 범위 값이 올바르지 않습니다." (최종은 `chk_view_scope`) |
| `editRole` | `viewer / editor / admin` | "편집 권한 값이 올바르지 않습니다." (최종은 `chk_edit_role`) |
| **이미 활성인 사람의 복구**(`setUserActive` `active=true`, 2026-09-11) | 잠근 행의 `is_active` 가 이미 1 이다(낡은 화면·세워 둔 요청). 실패가 아니라 **목록이 낡은 것**이고, 그대로 진행하면 그 사람의 **살아 있는 서열(`sort_order`)이 지워진다** | "이미 복구된 항목입니다 — 목록을 새로고침합니다." (`AlreadyActiveMsg` — 휴지통 복구와 **같은 상수**, 그래서 이름에 '휴지통'이 없다 · 이 거부는 **명부를 실제로 다시 민다** · §7-1a② · §11-31 · §11-32) |
| **잠금 경합**(1205 잠금 대기 초과 · 1213 교착, 2026-09-10) | 두 관리자가 같은 행을 `FOR UPDATE` 로 잡았다 | "다른 관리자가 같은 항목을 편집 중입니다 — 잠시 후 다시 시도하세요." (§11-21) |
| **그 밖의 DB 오류**(2026-09-10) | 매핑되지 않은 번호 | "처리하지 못했습니다(DB 오류)." — **예외 원문을 문장에 잇지 않는다**(SQL·컬럼·스택은 위젯 로그에만) |

**명부 순서 저장(`saveUserOrder`, 2026-09-11)**: 받은 목록 **밖에 활성 직원이 한 명이라도 있으면** 저장을 통째로 거부한다 — "명부가 바뀌었습니다 — 새로고침한 뒤 다시 저장하세요."(`StaleRosterMsg`). 화면의 명부가 낡았다는 뜻이고, 그대로 진행하면 반만 재작성된 서열이 남는다(§7-1a · §11-25 · §11-29). 저장이 쓰는 자리는 **받은 목록뿐**이다 — 퇴사자의 옛 순번은 여기가 아니라 **복구할 때** 비워진다(`sort_order=NULL`, §11-29).

대소문자: `login_id` 는 콜레이션이 대소문자를 무시하므로 `PHMIN` 과 `phmin` 은 DB 에서 같은 ID 다. 호스트는 **입력을 그대로 저장**하되 중복 검사는 DB 에 맡긴다(1062). 정규화(소문자 강제)는 하지 않는다 — 넷커스가 어떤 표기를 쓰는지 이 앱이 정하지 않는다.

### 4.4 잠금 방지 — 관리자가 자기 문을 닫는 것을 막는다 (호스트 전담)

세 규칙. 화면은 힌트로 미리 잠그지만 **판정은 호스트**가 같은 트랜잭션 안에서 한다(`SELECT … FOR UPDATE`).

1. **자기 자신을 퇴사 처리할 수 없다.** "자기 계정은 퇴사 처리할 수 없습니다."
2. **자기 편집 권한을 바꿀 수 없다.** 올리는 것도 내리는 것도. "자기 권한은 바꿀 수 없습니다. 다른 관리자가 바꿔야 합니다."
3. **마지막 활성 관리자를 강등·퇴사 처리할 수 없다.** 대상이 admin 이고 `SELECT COUNT(*) FROM app_user WHERE edit_role='admin' AND is_active=1 FOR UPDATE` 가 1 이면 거부. "관리자가 한 명뿐이라 처리할 수 없습니다. 먼저 다른 관리자를 지정하세요."

이걸 안 막으면 관리자가 스스로를 잠그고 DB 로 가야 풀린다 — "앱에서만 관리한다"는 요구가 그 순간 깨진다.

### 4.5 동시성

낙관적 잠금은 두지 않는다. 관리자가 한두 명이고 편집이 드물다. 마지막 저장이 이긴다. 잠금 방지 셋만 `FOR UPDATE` 로 직렬화한다. `updated_at` 은 서버 `ON UPDATE` 에 맡긴다(이 표는 낙관적 잠금 토큰이 아니다 — `schema-calendar.sql` 머리말의 예외와 같은 성격).

### 4.6 세션과 반영 시점

- **권한·활성**: 즉시. 쓰기 관문이 요청마다 DB 에서 읽는다. 퇴사 처리된 사람은 다음 저장부터 막히고, 다음 부팅에서 로그인 게이트에 걸린다.
- **이름·직급·소속**: 그 사람의 세션 파일(`user.session`, 4필드)은 로그인 때 채워진다. 관리자가 고친 값은 그 사람이 **다시 로그인하거나 「사용자 정보」를 열 때** 반영된다. 즉시 반영이 필요하면 그때 세션 재조회를 넣는다 — 이번 범위 밖.
- **넷커스 계정**: 이 앱은 만들지 않는다. "신규 직원 등록"은 **이 앱에 등록**하는 것이다. 넷커스 로그인이 되는 ID 인지는 그 사람이 처음 로그인할 때 판명된다.

## 5. 화면 (`task-calendar-prototype.html`) — **두 화면은 완전히 독립이다** (사용자 결정 2026-09-10)

> 「구성원 보기」와 「구성원 편집」은 **다른 화면**이다. 보기는 전원에게 같은 모습이고, 편집은 관리자에게만 존재한다.
> 상태·렌더러·전역까지 갈라 둔다(`mb*` = 보기, `ua*` = 편집). 한 모달의 상태가 다른 모달을 물들이면 안 된다.

### 5.0 진입 — 「사용자 정보」의 버튼 둘

| 버튼 | 누가 보나 | 여는 것 |
|---|---|---|
| 「구성원 보기」 `#usMembers` | 로그인한 전원 | `#membersModal` (읽기 전용 명부) |
| 「구성원 편집」 `#usUserAdmin` | **`edit_role='admin'` 인 사람만** | `#userAdminModal` (관리 화면) |

「구성원 편집」 버튼은 **마크업에 없다.** 「사용자 정보」의 권한 조회(`userInfoGet`) 회신에 `edit_role='admin'` 이 실려 왔을 때 `usAdminBtnSync` 가 만들어 넣고, 아니면 **DOM 에서 없앤다.** 숨김이 아니라 부재다 — 숨김은 클래스 하나로 풀리고, 그러면 화면이 권한을 정하는 모양이 된다. 권한은 언제나 호스트가 요청 시점에 판정한다(§4.1).

### 5.1 구성원 보기 `#membersModal` — 순수 보기

- **지금 모습 그대로다. 관리자가 열어도 편집 컨트롤이 하나도 없다.** 회신에 `admin:true` 가 실려 와도 이 화면은 그 값을 읽지 않는다.
- 옛 관리 막대 자리(`#mbAdmin`)는 **없앴다.** 자리만 남겨 두면 다음 사람이 거기에 다시 컨트롤을 넣는다.
- 좌 조직 트리 + 우 명부, 행을 누르면 그 사람 일정 열람(`#peerModal`) — 그대로다.

### 5.1-a 구성원 편집 `#userAdminModal` — 관리자 전용

- 상단 막대(`#uaAdmin`)에 「순서 편집」·「퇴사자 보기」. **막대는 마크업에서 비어 있고**, `uaAdminBar()` 가 `admin:true` 일 때만 만들어 넣는다(§8-7).
- 「＋ 직원 등록」은 **하단 `#uaFoot` 의 주 버튼**이다(§11-16, 사용자 결정 2026-09-10). `#uaFoot` 도 마크업에서 비어 있고 같은 `uaAdminBar()` 가 채운다 — 상단 막대와 같은 '숨김 ≠ 부재' 규칙이다. **순서 편집 중에는 만들지 않는다**(등록이 명부를 다시 읽어 편집 중인 순서를 날린다). 이 자리가 주 버튼이 되면서 「닫기」는 `primary` 를 벗었다.
- 각 행 우측에 **「편집」 하나뿐이다.** 퇴사·복구는 편집 폼 하단으로 옮겼다(§5.2, §11-16). 퇴사자 행은 이름 옆에 회색 알약 「퇴사」(`.badge.badge-git`)로 표시하고 행 전체를 흐리게 한다(`.mba-line.is-off`).
- 「순서 편집」을 켜면 행마다 ▲▼ 가 나타난다. 끌어놓기는 v2 — 키보드로 닿지 않는 조작을 첫판에 넣지 않는다.
- 순서를 바꾸면 화면에 즉시 반영하고 「순서 저장」을 눌러야 `saveUserOrder` 로 나간다. 저장 전 닫으면 되돌린다.
- **명부에는 순번 숫자를 내지 않는다. 편집 폼에만 읽기전용 「서열 번호」 칸이 있다**(§5.2, §11-17).
- 조직 트리는 두지 않는다 — 트리는 '누구의 일정을 볼까'를 고르는 도구고 이 화면은 '누구를 고칠까'다. 대신 검색칸(`#uaSearch`)이 있고, 순서 편집 중에는 잠긴다(§11-8 과 같은 이유).
- 행은 눌리지 않는다(평범한 `div`). 남의 일정 열람은 보기 화면의 일이다.
- **호스트가 `admin:false` 로 답하면**(관리자에서 내려갔다) 이 화면은 「관리자만 사용할 수 있습니다.」 한 줄만 보이고 컨트롤을 하나도 만들지 않는다. 빈 화면은 고장처럼 보이므로 이유를 말한다.
- 데이터는 보기 화면과 **같은 `membersGet` 회신**을 쓴다. 다만 `admin`·`titles`·`includeInactive` 는 이 화면만 읽는다.

### 5.2 편집 폼 `#userEditModal`

로그인 ID(신규만 편집 가능 — 기존 사용자의 ID 는 넷커스 소유라 여기서 바꾸지 않는다) · 이름 · 직급(드롭다운, `titles`) · 소속(드롭다운 트리, `units`) · 열람 범위(드롭다운 3) · 편집 권한(드롭다운 3) · 서열 번호(**읽기전용** · `sortOrder` 가 NULL 이면 「미지정 — 명부 맨 뒤」).

- 자기 행을 열면 편집 권한 드롭다운이 잠기고 힌트가 뜬다(§4.4-2). 최종 판정은 호스트.
- 「서열 번호」는 **보여 주기만** 한다(§11-17). 순서를 바꾸는 길은 「구성원 편집」의 「순서 편집」 ▲▼ 하나뿐이고, 저장하면 전원이 10 간격으로 다시 매겨진다. `saveUser` 페이로드에는 이 값이 들어가지 않는다(호스트 계약 그대로).
- 저장 → `hostRequest('saveUser', …)` → 회신 `{ok, msg, roster}` → 성공이면 폼 닫고 회신에 실려 온 명부를 앉히고, 실패면 폼 안 메시지(과제 폼의 `offEdMsgSet` 과 같다). 옛 판은 `__userSaved(ok,msg)` 푸시였다(§11-34).
- **「퇴사 처리」/「복구」는 이 폼 하단의 왼쪽 버튼**(`#userEdActive`)이다(§11-16). `userEdOpen(uid)` 이 상태에 맞춰 세운다: 신규 등록(`uid=0`)이면 `hidden`(퇴사시킬 대상이 없다), 재직 중이면 「퇴사 처리」(`danger`·`data-uop="off"`), 퇴사자면 「복구」(`danger` 없음·`data-uop="on"`). 확인창 한 번("○○○ 님을 퇴사 처리합니다. 기록은 남고 명부에서만 사라집니다.") 뒤 `setUserActive` 로 나가고, 성공하면 그 회신을 받은 자리(`userEdAfterWrite`)가 폼을 닫는다. `uaSetSaving` 이 [저장]과 이 버튼을 **함께** 잠근다(같은 왕복을 쓰므로 한쪽만 잠그면 두 요청이 겹친다).
- **자기 퇴사를 화면이 미리 막지 않는다.** `isMe` 여도 버튼은 그대로 선다 — 거부는 호스트 문장(§4.4-1 「자기 계정은 퇴사 처리할 수 없습니다.」)으로 돌아와 폼 안에 뜬다. 화면이 앞질러 막으면 관문이 실제로 막는지 아무도 확인하지 못한다(`uaSend` 에 `__uaAdmin` 가드를 두지 않는 것과 같은 이유).
- 이 버튼만은 마크업에 **정적으로** 적혀 있다(`hidden` 상태로). §8-7 의 '숨김 ≠ 부재' 와 어긋나 보이지만, 이 폼 자체가 `__uaAdmin` 없이는 열리지 않으므로 비관리자에게 닿을 길이 없다.
- 이 폼은 **「구성원 편집」에서만** 열린다(`userEdOpen` 이 `__uaAdmin` 을 먼저 본다). 보기 화면에서 여기 닿을 길은 없다.
- 쓰기 회신이 나르는 갱신 명부(`roster`)는 **「구성원 편집」 화면만** 다시 칠한다. 보기 화면은 열 때마다 스스로 다시 읽으므로 낡은 채로 남지 않는다 — 한 회신으로 두 화면을 함께 칠하면 갈라 둔 이유가 사라진다.

### 5.3 정렬은 호스트가, 화면은 그대로

명부 순서는 **호스트 응답 순서 그대로** 그린다. 화면에서 다시 정렬하지 않는다 — 두 곳이면 갈린다.

```sql
ORDER BY o.name, u.sort_order IS NULL, u.sort_order, u.name
```

두 화면 모두 이 순서 그대로 그린다(`renderMembers`·`uaRender` 어디에도 `sort(` 가 없다 — §8-6).

소속 → 순번(NULL 은 맨 뒤) → 이름. 직급 서열을 여기 끼우지 않는다 — 전사 서열이 직급을 이미 담고 있고, 끼우면 관리자가 정한 순서를 직급이 뒤엎는다.

**「구성원 편집」은 다르다(§11-15, 사용자 결정 2026-09-10).** 편집 화면은 서열의 주인이고 서열은 전사 단일이므로 소속을 첫 키로 두면 그 서열이 팀에 갇힌다. 편집 화면은 `membersGet` 을 `flat:true` 로 부르고 호스트는 두 번째 리터럴로 답한다.

```sql
ORDER BY u.sort_order IS NULL, u.sort_order, u.name        -- 편집(flatOrder)
```

정렬 리터럴은 호스트에 이 둘뿐이다. 화면은 어느 쪽도 재정렬하지 않는다(계약⑥·⑥-c). 쓰기 뒤 호스트가 편집 화면으로 밀어 주는 명부도 `flatOrder` 다 — 저장 직후 화면이 소속 순으로 튀지 않게.

## 7. 정직한 한계 — 공유 계정

이 결정으로 `taskmgr_app` 계정이 `app_user` 에 쓸 수 있게 된다. 그 비밀번호는 배포본에 담겨 89대에 퍼진다. MySQL 에 직접 붙는 사람은 앱의 관리자 관문을 통째로 우회해 **누구든 admin 으로 만들 수 있다.** 과제 마스터는 이미 같은 상태이고 사용자가 이를 알고 받아들였다(2026-09-10). 다만 이 표는 "누가 관리자인가"를 담는 표라 결과가 더 무겁다.

이 관문의 목표는 [USER-LOGIN §3.4](USER-LOGIN.md) 와 같다 — **정상 경로에서 실수를 막는 것**이지 악의 방어가 아니다. 사후 추적은 서버의 바이너리 로그(ROW · 30일)가 유일한 근거다. 진짜 방어는 서버 API 경유(ROADMAP 2단계) 이후다. 그 전까지 값싼 완화 하나: 배포 시 계정 호스트를 `%` 에서 사내 대역으로 좁힌다(이미 배포 항목).

## 7-1. 알려진 구멍 — 구현하고 나서 남은 둘 (2026-09-10)

§7 이 "알고 받아들인 한계"라면 이쪽은 **아직 판단이 안 끝난 곳**이다. 둘 다 실동작으로 확인한 것이 아니라 코드를 읽고 따진 것이라, 겪은 사람이 생기면 여기를 먼저 볼 것.

**(a) 「퇴사자 보기」를 끈 채 순서를 저장하면 퇴사자의 서열이 옛 값으로 남는다. — 2026-09-10 닫힘(§11-22), 2026-09-11 두 번 고쳐 닫음(§11-25 · §11-29).**
> 닫는 방법(현재): **비우는 시점이 '저장할 때' 가 아니라 '돌아올 때' 다.** 복구하는 두 자리 —
> `SetUserActiveAsync`(편집 폼의 [복구])와 `RestoreTrashAsync`(휴지통의 인력 갈래) — 가
> `UPDATE app_user SET is_active=1, sort_order=NULL … ` 로 **서열을 비운 채** 되살린다.
> NULL 은 명부 ORDER BY 에서 맨 뒤라(§5.3) 복구한 사람은 **끼어들지 않고 맨 뒤**에 서고, 관리자가 그때 한 번
> 끌어올리면 끝난다(구분·상태 코드의 '복구 = MAX+10' 과 같은 판단이다). 퇴사(`is_active=0`)는 서열을 손대지
> 않는다 — 그 값은 어차피 돌아올 때 비워지고, 지금 지우면 '퇴사 → 곧바로 복구' 가 멀쩡하던 자리를 잃는다.
>
> 그래서 `SaveUserOrderAsync` 는 목록 **밖을 아예 건드리지 않는다**: `UPDATE app_user SET sort_order =
> CASE user_id WHEN … THEN 10·20·30… END WHERE user_id IN (…)` 한 문장이고, 쓰는 자리는 받은 목록 하나뿐이다.
> 다만 ① **낡은 명부 거부**는 그대로다 — 목록 밖에 **활성** 직원이 있으면 `FOR UPDATE` 로 세어 **아무것도 쓰지 않고**
> 거부한다(`StaleRosterMsg` — "명부가 바뀌었습니다 — 새로고침한 뒤 다시 저장하세요.", §4.3). 그건 서열 비우기가
> 아니라 '화면이 낡았다' 에 대한 가드다. 받은 목록이 통째로 비면 첫 문장을 내기도 전에 거부한다(전원 NULL 방지).
>
> 옛 판(2026-09-10 → §11-25)은 이 비우기를 **순서 저장 쪽**에 두었는데, 그 갈래(`ELSE … is_active=0 … NULL`)와
> 복구 사이가 열려 있었다: 낡은 명부 판정(COUNT)과 재작성(CASE) 사이에 남이 그 퇴사자를 복구하면 그 사람은 그 순간
> **활성**이라 비우기에 걸리지 않고 옛 숫자를 그대로 들고 새 서열 사이에 끼어들었다(§11-29).
> 아래 문단이 "그러면 '보이는 순서 = 저장되는 순서' 계약이 깨진다"고 적었지만 깨지지 않았다 — 보이는 사람의 서열은
> 받은 순서 그대로고, 안 보이던 사람은 **돌아올 때** 서열을 새로 받을 뿐이다.
>
> ② **이미 활성인 사람의 복구는 거부한다**(2026-09-11 적대 검토 R4 · §11-31). 비우기가 복구 쪽으로 옮겨 온
> 뒤로, 낡은 화면이나 세워 둔 요청이 **멀쩡히 쓰이던 사람**에게 복구를 한 번 더 걸면 그 한 줄이 그 사람의
> **살아 있는 서열을 지우고** 성공까지 돌려줬다. 잠근 행의 `is_active` 가 이미 1 이면 아무것도 쓰지 않고
> "이미 복구된 항목입니다 — 목록을 새로고침합니다."(`AlreadyActiveMsg`, §4.3)로 거부한다 — 휴지통 복구와
> **같은 판정·같은 문장**이다. 문장 자체에도 `AND is_active=0` 을 걸어 두었다(닫힌 쪽으로 실패).
> 그 문구가 약속한 새로고침은 호스트가 실제로 한다 — 브리지가 `ok || msg == ProjectDb.AlreadyActiveMsg` 일 때
> 명부를 다시 민다(§11-32).

**(a) 의 옛 판 기록(2026-09-10, 닫히기 전).** 아래 한 문단은 위 내용으로 **대체된 옛 진단**이다 — 지금의 동작이 아니다:
`saveUserOrder` 는 웹이 보낸 `userIds` — 즉 그때 화면에 보이던 사람들만 10·20·30… 으로 다시 썼고, 퇴사자는 옛 숫자를 그대로 들고 남아 복구하면 새 서열 사이에 끼어들었다. 그때는 "구조적으로 막으려면 '보이는 순서 = 저장되는 순서' 계약이 깨진다"고 보아 고르지 않았지만, **그 대신 고른 자리가 복구 쪽이었다**(§11-29 · §11-31): 복구가 `sort_order=NULL` 로 되살리므로 저장 쪽은 손댈 것이 없고, 계약도 그대로다. 조치로 적었던 "복구한 뒤 순서를 한 번 더 저장한다" 도 더는 필요 없다 — 돌아온 사람은 맨 뒤에 서고, 원하는 자리로 한 번 끌어올리면 끝난다.

**(b) 이 마이그레이션 전의 DB 에 이 판의 위젯이 붙으면 명부가 통째로 빈다 — 그래서 배포 순서는 DB 가 먼저다.**
판번호 게이트(`CalendarDb.ExpectedSchemaVersion`)는 **전량 교체만** 거부한다(설계상 의도 — 전 쓰기 봉인은 과하다). 명부 조회는 그 게이트를 지나지 않으므로, 컬럼이 없는 DB 에 새 위젯이 붙으면 게이트가 아무 말도 하지 않는 채 `SELECT … u.sort_order` 가 `ERROR 1054` 로 죽고 **구성원 명부가 빈 채로 열린다.** 반대 짝(마이그레이션을 마친 DB + 구버전 위젯)은 무해하다 — 컬럼을 모를 뿐이다. **결론: 마이그레이션을 먼저 적용하고 그 다음에 위젯을 내보낸다.** 같은 문장이 마이그레이션 머리말과 `db/deploy/README.md` 순서표에도 있다.

## 11. 정정 이력

> **2026-09-10 — 구현이 끝났다.** 본 저장소 커밋과 비공개 저장소 커밋 한 쌍으로 나갔고, 실 `taskmgr` 은 마이그레이션까지 적용해 판번호가 한 칸 올라간 상태다(값의 정본은 `db/deploy/schema-calendar.sql` 끝의 `cal_schema_meta` 시딩 줄, 실 DB 값은 `SELECT v FROM cal_schema_meta WHERE k='schema_version'`).
>
> 아래 열둘은 **설계와 다르게 처리한 곳**이다. 본문은 §3.2 만 실물에 맞춰 고쳤고, 나머지는 여기에만 적는다 — 본문을 지우면 "왜 그렇게 했나"가 함께 사라지기 때문이다. **본문과 여기가 다르면 여기가 맞다.**

**1. §3.2 의 초기값 SQL 이 MySQL 에서 안 돈다 — 창 함수로 바꿨다.**
`SET @r := 0` + `UPDATE … LEFT JOIN … ORDER BY` 형태였는데, MySQL 은 **다중 표 UPDATE 에 `ORDER BY` 를 허용하지 않는다**("For multiple-table syntax, ORDER BY and LIMIT cannot be used"). 사용자 변수 누적은 8.4 에서 평가 순서를 보장하지도 않는다. `ROW_NUMBER() OVER (…) * 10` 을 파생 표로 만들어 조인하는 형태로 대체했고 **결과 순서와 간격은 설계 그대로**다. 본문 §3.2 의 SQL 도 실제 마이그레이션(`db/deploy/migrate-2026-09-10-user-sort-order.sql`)과 같은 문장으로 고쳤다 — 문서와 SQL 을 두 벌 두면 어긋나고, 어긋난 쪽이 문서라 아무도 실행해 보지 않는다.

**2. 쓰기 세 명령의 payload 에 `includeInactive` 가 하나씩 붙었다(§4.2).**
설계는 `saveUser`·`setUserActive`·`saveUserOrder` 에 그 필드를 두지 않았다. 그런데 §4.2 마지막 줄의 약속대로 **호스트가 성공 직후 스스로 명부를 다시 읽어 밀어 주는데**, 그때 「퇴사자 보기」가 켜져 있었는지를 호스트가 알 방법이 없다. 호스트는 그 상태를 캐시하지 않는다(캐시하면 웹과 호스트에 같은 상태가 두 벌 생긴다). 그래서 웹이 매 요청에 현재 토글 값을 함께 실어 보내고 호스트는 그것을 재조회에 그대로 물려준다 — 저장했더니 켜 둔 「퇴사자 보기」가 꺼지는 일이 없다.

**3. §8-1 「정본·마이그레이션 동치」는 상시 시험에서 덤프를 뜨지 않는다.**
Node 시험은 MySQL 을 띄울 수 없다. 그래서 상시 게이트가 보는 것은 **두 소스(정본 DDL 과 마이그레이션)가 같은 것을 말하는가** — 타입·NULL 허용·`title` 바로 뒤라는 자리·UNIQUE/인덱스/COMMENT 부재다. 실제 `mysqldump --no-data` 대조는 **격리 DB 로 따로 실증**했고 두 경로의 차이는 0 이었다. 계약의 뜻은 같지만 **증명 수단이 둘로 갈렸다**는 사실을 여기 남긴다 — "시험이 초록이니 덤프가 같다"로 읽으면 틀린다.

**4. §8-3 「잠금 방지」도 절반은 정적 계약이다.**
같은 이유(단위시험이 DB 를 못 든다)로, 상시 시험은 **문구 세 개가 상수 한 곳에 있고 · 세 판정이 `FOR UPDATE` 로 읽으며 · 그 판정과 갱신이 같은 트랜잭션 안이라는 것**을 소스 모양으로 잠근다. `FOR UPDATE` 가 빠지면 두 관리자가 동시에 서로를 강등해 **아무도 남지 않을 수 있다** — 그 변이가 실제로 잡히는지까지 시험에 넣었다. 실 DB 에서의 거부는 루프 시험(`loop-ui-integrity.mjs`)의 불변식 U1(활성 관리자 ≥ 1)이 본다.

**5. 같은 날 앞선 판(`project-dev-end`)의 계약⑤ 를 완화했다.**
그 시험은 *"이 마이그레이션이 언제나 마지막 판"* 을 전제로 판번호를 검사하고 있었다. 이 판이 그 뒤에 붙자 그 전제가 깨졌다. 가정을 빼고 **① 한 번에 한 칸만 움직인다 · ② 가드가 그 출발값을 요구한다 · ③ 정본을 앞서가지 않는다** 셋으로 다시 적었다 — 이 셋은 판이 몇 개 더 붙어도 참이다. 옆 판을 손대야 했다는 사실 자체가 기록할 값이 있다: **판번호를 검사하는 시험은 "내가 마지막"을 전제하면 안 된다.**

**6. 브리지 `case` 세 개를 `membersGet` 바로 옆에 뒀다.**
설계는 자리를 말하지 않았다. 명부 조회와 명부 쓰기는 같은 도메인이고, 셋 다 성공 뒤 `membersGet` 과 같은 경로로 명부를 다시 읽는다. 흩어 두면 다음 사람이 "직원 관련 명령이 여기 전부인가"를 확신할 수 없다.

**7. `#userEditModal` 은 마크업에 **정적 껍데기**로 있다(§5.1 의 '부재' 계약 범위 조정).**
설계 §5.1 은 *"편집 컨트롤이 숨김이 아니라 부재"* 라고 적었고 §8-7 이 그것을 계약으로 잠근다. 실제로는 모달의 빈 폼(입력칸·라디오 컨테이너)이 HTML 에 정적으로 있고, **채워지는 것은 관리자 회신이 왔을 때뿐**이다. 그래서 '부재' 계약은 **명부 안의 편집 컨트롤**(「순서 편집」·「퇴사자 보기」·하단의 「＋ 직원 등록」·행의 ▲▼·[편집])에 적용된다 — 그것들은 관리자 회신 없이는 DOM 에 생기지 않는다. 폼 하단의 [퇴사 처리]/[복구](`#userEdActive`)는 §11-16 이후 이 폼의 정적 껍데기에 속한다(같은 이유로 예외다). 비관리자에게 열리는 문은 없지만, **계약 문장이 가리키는 대상이 설계보다 좁다**는 것을 알고 있어야 한다.

**8. 순서 편집 중에는 검색칸과 조직 선택을 잠근다(설계에 없던 규칙).**
▲▼ 는 "보이는 목록 안에서 한 칸"인데, 검색이나 조직 필터로 목록이 걸러져 있으면 **한 칸이 실제로 어디로 가는지 예측할 수 없다**(보이지 않는 사람을 뛰어넘는다). 그래서 순서 편집을 켜는 순간 검색어를 비우고 두 입구를 막는다 — 편집 중의 목록은 곧 전 명부다. 같은 이유로 순서 편집 중에는 「직원 등록」(§11-16 이후 하단 `#uaFoot`)·「퇴사자 보기」도 만들지 않는다(둘 다 명부를 다시 읽어 **편집 중인 순서를 날린다**).

**9. 직급이 사실상 필수가 됐다 — '직급 미정' 신규 등록이 안 된다.**
§4.3 표에 `title` 은 *"활성 `title_code` 에 있어야"* 라고만 적혀 있고 `orgId` 처럼 *"비워도 됨"* 이 없다. 구현이 그 표를 글자 그대로 따랐으므로 빈 값은 활성 코드 집합에 없어 *"등록되지 않은 직급입니다."* 로 거부된다. 설계대로이지만 **의도한 결과인지는 확인하지 않았다** — 직급이 아직 안 정해진 신입을 먼저 등록해 두는 운용이 필요하면 `title` 을 NULL 허용으로 여는 별건이다. 후속 후보로 남긴다.

**10. 비관리자 회신은 키도 순서도 같지만, 명부의 **행 순서**는 전원 바뀐다.**
§4.2 는 *"관리자가 아니면 회신이 지금과 글자까지 같다"* 고 적었다. 키 구성은 실제로 같다. 다만 명부 SQL 의 `ORDER BY` 가 §5.3 대로 `sort_order` 를 끼워 넣도록 바뀌었고 **그 정렬은 권한과 무관**하므로, 비관리자가 보는 명부도 (소속명, 이름) 순에서 (소속명, 서열, 이름) 순으로 **전원 바뀐다.** 그게 이 기능의 목적이므로 회귀가 아니라 의도된 변화지만, "비관리자에게는 아무것도 안 바뀐다"로 읽히면 틀린다.

**11. `grants-calendar.sql` 은 서술만 고쳤다 — 실제 GRANT 는 비공개 저장소에 있다.**
§3.4 는 두 파일을 함께 고치라고 적었고 그렇게 했지만, 두 파일의 **역할이 다르다**는 점이 설계에 드러나 있지 않았다. `db/deploy/grants-calendar.sql` 은 `app_user` 에 대해 `GRANT SELECT` 만 발행하고(캘린더가 그 표를 읽어야 하므로) 머리말에서 INSERT·UPDATE 의 존재를 **서술**한다. 실제로 쓰기를 여는 문장은 `taskmgr-company-data/05-grants.sql` 에 있다. **따라서 `db/deploy` 만으로 세운 서버에서는 직원 관리가 `ERROR 1142` 로 전부 죽는다** — 컬럼은 서 있으므로 명부는 보이고 저장만 실패한다. 비공개 저장소의 `05` 를 함께(또는 다시) 적용해야 한다.

**13. 「구성원 보기」 안의 관리자 편집 모드를 **독립 화면**으로 갈랐다 — 사용자 결정 2026-09-10.**

**20. 폐지된 직급·소속을 단 사람을 고칠 수 없었다 — 수정에 한해 '지금 저장된 값'을 허용한다(2026-09-10 전면 검토).**
`UpsertUserAsync` 는 직급·소속을 **활성 마스터**로만 검사했다(`activeOnly: true`). 취지는 "폐지된 값으로 새로 배정하지 않는다"였는데,
이미 그 값을 달고 있는 사람의 **이름 한 글자**를 고칠 때도 같은 검사가 걸려 "등록되지 않은 직급입니다."로 막혔다. 화면이 저장된 값을
드롭다운에 남기게 되면서(짝 변경) '보이는 값'과 '되는 값'이 갈리는 자리가 됐다. 이제 **UPDATE 는 활성이거나 잠근 행의 현재 값이면 통과**한다
— 대조 근거는 `LockedUserAsync` 의 `FOR UPDATE` 행이고(그래서 그 SELECT 가 `title`·`org_id` 를 함께 읽는다), 소속은 값이 그대로면
조회조차 하지 않는다. **INSERT 는 그대로 활성만이다.** 거부 문구는 바뀌지 않았다. 시험: 계약④ 에 세 단언(수정 완화·소속 완화·신규는 활성만)과

**21. 사용자 문장에 예외 원문이 실려 나갔다 — `MySqlUserMsg` 의 `default` 를 고정 문장으로.**
`"저장하지 못했습니다: " + Short(ex)` 는 SQL·컬럼명·스택 조각을 화면에 흘렸고, 정작 사용자는 무엇을 할지 알 수 없었다. `default` 는
"처리하지 못했습니다(DB 오류)." 로 고정하고 원문은 부르는 쪽의 `_log` 에만 남긴다. 대신 **1205(잠금 대기 초과)·1213(교착)** 은 따로 말해 준다

타임아웃 뒤 롤백 자체가 `OperationCanceled` 로 죽으면서 **원래 예외를 덮어** 위 매핑에 닿지 못하게 했다.

**22. §7-1(a) 를 닫았다 — 순서 저장이 목록 밖 사람의 서열을 `NULL` 로 민다.**

**24. §4.4-3(마지막 관리자)은 앱 경로로 닿지 않는다 — 정적 계약으로 남긴다(2026-09-10 루프 시험 C17).** 판정은 `대상이 admin && 활성 && LockedActiveAdminCountAsync <= 1` 인데, 요청을 보내려면 행위자가 이미 활성 admin 이라 **대상이 남이면 수가 최소 2** 이고, **대상이 자기 자신이면 §4.4-1·2 가 먼저** 거부한다(코드 순서: 자기 규칙이 위). 그래서 실동작으로 남는 발화 경로는 관리자 둘이 **동시에** 서로를 강등하는 경합뿐이고 — 그것이 그 COUNT 가 `FOR UPDATE` 인 이유다 — 루프 시험은 그 경합을 결정론적으로 세울 수 없다. `tests/loop-user-admin.mjs` C17 은 대신 둘을 판정한다: ① 관리자가 둘일 때 남의 강등은 **성공한다**(과잉 차단 없음) ② 활성 admin 이 하나뿐인 순간에도 자기 퇴사의 문구는 §4.4-1 이다(순서가 뒤바뀌지 않았다). 규칙 자체는 지우지 않는다 — 경합은 실재하고, 없애면 두 관리자가 서로를 내려 **아무도 남지 않는다**.

**25. §7-1a 를 닫은 그 한 줄이 활성 직원까지 쓸어 갔다 — 두 겹으로 고쳤다(2026-09-11 적대 검토 R1).** 비우기 문장(`sort_order=NULL WHERE … NOT IN (…)`)에 `is_active=0` 이 없어, 다른 관리자가 그 사이에 등록한 사람이나 화면이 걸러 낸 사람처럼 **목록에 없을 뿐 활성인 직원의 서열이 소리 없이 NULL** 이 됐다. ① 목록 밖에 활성이 있으면 트랜잭션 안에서 `FOR UPDATE` 로 세어 **아무것도 쓰지 않고** 거부하고(`StaleRosterMsg` · §4.3), ② 그래도 비우는 갈래에는 `is_active=0` 을 건다(닫힌 쪽으로 실패). 겸사겸사 N 번의 `UPDATE` + 비우기 한 번을 `CASE user_id WHEN …` **한 문장**으로 합쳐 '재작성은 됐는데 비우기가 아직'인 중간 상태를 없앴다. 계약⑥-f + 변이 넷(`is_active=0` 삭제 · 낡은 명부 세기 삭제 · `FOR UPDATE` 삭제 · 빈 목록 거부 삭제).

**26. 직원 쓰기 세 명령이 `reqId` 를 나른다(2026-09-11 R3).** `__userSaved` 는 왕복이 아니라 **푸시**라, 늦게 온 회신이 이미 다른 일을 하고 있는 폼을 건드릴 수 있었다. `saveUser`·`setUserActive`·`saveUserOrder` 가 `reqId` 를 함께 보내고 호스트가 `window.__userSaved(ok, msg, reqId)` 로 되돌려 준다 — 웹이 자기 요청의 것인지 판정할 수 있다. 요청에 없으면 `""` 라 옛 웹과도 호환된다(휴지통의 `__trashDone` 도 같은 모양 · TRASH-DELETE §11-24).

**27. 등록·수정의 직급·소속 검사를 한 벌로 합쳤다(2026-09-11 R7).** 같은 판정(문구까지 같다)이 두 분기에 두 벌 적혀 있어 한쪽만 고치면 조용히 갈릴 자리였다. '지금 저장된 값'을 `curTitle`·`curOrg`(잠근 대상 행에서만 온다, 신규면 `null`)로 받아 한 벌로 적었다 — 신규는 그 둘이 `null` 이라 완화 갈래가 저절로 닫혀 **활성만**이 된다. 동작은 그대로고, 계약④ 도 '두 벌'이 아니라 '한 벌 + 그 값의 출처'를 본다(중복을 계약으로 굳히지 않는다).

**28. 순서 저장의 한 문장에 `WHERE` 가 없었고, 거부했을 때 화면을 놓아 주지 않았다(2026-09-11 적대 검토 R2).** ① `CASE user_id … ELSE …` 의 `ELSE` 가 '제 값을 다시 쓴다' 여도 그건 값 이야기일 뿐이라, `WHERE` 가 없는 그 문장은 **`app_user` 전 행**을 대상으로 삼아 한 사람의 순서 저장이 표 전체에 X 잠금을 걸었다(로그의 '바뀐 행' 도 표 크기였다 — 게다가 MySqlConnector 가 주는 수는 '맞은 행' 이라 애초에 '바뀐 행' 이 아니다). `WHERE user_id IN (…) OR is_active=0` 을 붙이고 로그는 `대상 N명` 으로 고쳤다. 같은 자리의 "`FOR UPDATE` 가 다른 트랜잭션을 못 끼어들게 한다" 는 주석도 과장이라 정정했다 — 이 연결은 READ COMMITTED 라 갭 잠금이 없어 새 `INSERT` 는 막지 못한다(해롭지는 않다: 그 사람은 `WHERE` 에도 안 걸려 `sort_order` 가 NULL 인 채 맨 뒤에 선다). ② 호스트가 **성공했을 때만** 명부를 다시 밀어 줬다. 거부의 대표가 「낡은 명부」(`StaleRosterMsg`)인데 그때 아무것도 안 내려보내면 관리자는 같은 낡은 명부로 다시 눌러 같은 거부만 반복한다 — `SaveUserOrderAsync`(호스트)는 이제 ok 와 무관하게 `LoadMembersToWebAsync` 를 민다(웹은 순서 편집 중이면 그 갱신을 pending 으로 미루고 안내만 띄우므로 편집 중이던 순서를 덮어쓰지 않는다). 계약⑥-f 에 `WHERE`·로그 문구, 계약②-b 에 '순서 저장만 무조건 푸시' 를 더했고 변이⑥-j 를 짝으로 붙였다.

**29. §7-1a 의 비우기를 '저장할 때' 에서 '돌아올 때' 로 옮겼다 — 그 사이가 열려 있었다(2026-09-11 적대 검토 R3).** §11-22 → §11-25 의 비우기 갈래(`ELSE (CASE WHEN is_active=0 THEN NULL ELSE sort_order END)`)는 **낡은 명부 판정(COUNT)과 재작성(CASE) 사이**를 막지 못했다. 그 틈에 다른 관리자가 퇴사자를 복구하면 그 사람은 그 순간 **활성**이라 `is_active=0` 갈래에 걸리지 않고 옛 숫자를 그대로 들고 새 서열(10·20·30…) 사이에 끼어든다 — §7-1a 가 그대로 재현된다. 비우는 **시점**을 옮기면 그 틈 자체가 없다: 복구하는 두 자리(`SetUserActiveAsync` 의 `active=true` · `RestoreTrashAsync` 의 `user` 갈래)가 `is_active=1, sort_order=NULL` 로 되살린다. 그래서 순서 저장의 문장은 `… CASE user_id WHEN … END WHERE user_id IN (…)` 로 좁아졌고(목록 밖은 안 건드린다 · `OR is_active=0` 도 없다), 로그는 `일치 행 N / 대상 M명` 두 수를 함께 낸다 — 둘이 다르면 뜻이 하나다: 목록에 **이미 지워진 id** 가 섞여 있었다(낡은 명부 거부는 '목록 밖 활성' 만 보므로 그 경우를 못 잡는다). 그 수는 `CLIENT_FOUND_ROWS` 라 '바뀐 행' 이 아니라 **맞은 행**이다(존재 확인으로는 읽되 '몇 명의 서열이 달라졌나' 로는 읽지 않는다). 계약⑥-f 가 복구 두 자리 + `WHERE` + 로그를 함께 보고, 변이 여섯(복구 NULL 삭제 ×2 · 퇴사에 NULL 추가 · 옛 비우기 갈래 부활 · `WHERE` 삭제 · 로그 삭제)이 짝이다. 휴지통 쪽 짝은 [TRASH-DELETE §11-27](TRASH-DELETE.md).

**30. 명부 푸시(`__applyMembers`)에도 `reqId` 를 싣고, 순서 저장의 '무조건 푸시'(§11-28②)를 두 경우로 좁혔다(2026-09-11 적대 검토 R3).** ① 그 푸시는 회신(§11-26)과 달리 인자에 아무 표식이 없어, 버려진 요청의 늦은 푸시가 다른 조작에 잘못 귀속될 수 있었다. `LoadMembersToWebAsync(includeInactive, reqId)` 가 `window.__applyMembers(json, reqId)` 로 밀고, 쓰기 뒤의 갱신이면 그 쓰기의 `reqId` 를 · 그 밖의 갱신(휴지통 복구 등)은 `""` 를 싣는다(옛 웹과 호환). ② §11-28② 의 '실패해도 무조건 민다' 는 너무 넓었다 — 웹은 순서 편집 중의 갱신을 pending 으로 미뤄 두므로, 명부가 **바뀌지도 않은** 실패(권한·연결·DB)까지 밀면 그 푸시는 쌓이기만 한다. 지금은 `ok || msg == ProjectDb.StaleRosterMsg` 둘뿐이고, 그 문장 대조의 정본은 `ProjectDb.StaleRosterMsg` **한 줄**이다(그래서 `internal` 로 열었다 — 같은 문장을 브리지에 한 벌 더 적으면 한쪽만 고쳐지는 순간 푸시가 조용히 멈춘다). 계약⑭-h(푸시의 `reqId`)·⑭-h2(푸시 정책 + `internal`) + 변이 다섯.

**31. 비우기를 복구 쪽으로 옮기면서 새로 생긴 구멍 — 이미 활성인 사람을 다시 복구하면 살아 있는 서열이 지워졌다(2026-09-11 적대 검토 R4).** §11-29 이후 `SetUserActiveAsync` 의 복구는 `UPDATE app_user SET is_active=1, sort_order=NULL WHERE user_id=@uid` 를 **조건 없이** 돌렸다. 그래서 낡은 화면의 [복구] 나 세워 둔 요청이 **이미 재직 중인 사람**에게 한 번 더 닿으면, 그 사람의 멀쩡하던 `sort_order` 가 NULL 로 지워지고 호스트는 **성공**을 돌려준다 — 그 사람은 아무 일도 하지 않았는데 명부 맨 뒤로 간다. 잠근 행의 `is_active` 가 이미 1 이면 아무것도 쓰지 않고 롤백한 뒤 "이미 복구된 항목입니다 — 목록을 새로고침합니다." 로 거부한다(`AlreadyActiveMsg` — 휴지통 복구가 쓰던 그 상수를 **그대로 나누어 쓴다**: 같은 사건에 같은 말을 두 벌 적으면 한쪽만 고쳐진다). 문장에도 `AND is_active=0` 을 걸어 닫힌 쪽으로 실패하게 했다. 계약④(잠금 방지)가 '이미 활성 거부 · 잠근 행의 값으로 판정 · UPDATE 보다 앞' 을, 계약⑥-f 가 문장의 `AND is_active=0` 을 보고 변이 셋(⑥-f · ⑥-f5 · ⑥-f6)이 짝이다. 휴지통 쪽 짝은 [TRASH-DELETE §11-27](TRASH-DELETE.md) 의 같은 판정이다.

**32. 그 거부가 약속한 새로고침을 실제로 하지 않았다(2026-09-11 적대 검토 R5).** §11-31 이 돌려주는 문장은 "이미 복구된 항목입니다 — **목록을 새로고침합니다**." 인데, 브리지(`MainWindow.SetUserActiveAsync`)는 `if (ok)` 일 때만 `LoadMembersToWebAsync` 를 밀었다 — 그 문장은 정확히 **실패**로 나오므로 약속한 새로고침은 한 번도 일어나지 않았다. 관리자는 그 문구를 읽으면서 퇴사자가 그대로 남아 있는 낡은 명부를 보고 같은 [복구] 를 다시 눌러 같은 거부만 반복한다(휴지통이 [TRASH-DELETE §11-23](TRASH-DELETE.md) 에서 닫은 것과 **같은 구멍**이다). 이제 `ok || msg == ProjectDb.AlreadyActiveMsg` 두 경우에 민다 — 나머지 실패(권한·연결·DB·자기 퇴사·마지막 관리자)는 명부가 바뀌지 않았으므로 밀지 않는다(§11-30② 와 같은 규율). 그 상수는 휴지통 전용이 아니므로 이름에서 `Trash` 를 떼고(`AlreadyActiveMsg`), 브리지가 문장을 한 벌 더 적지 않도록 `internal` 로 열었다(`StaleRosterMsg` 와 같은 이유). 계약②-b(성공에만 밀지 않는다)·⑭-h3(푸시가 그 둘뿐 · `internal` · 이름) + 변이 넷(⑭-h3 · h3b · h3c · h3d)이 짝이고, 변이⑥-f6 도 '첫 번째 등장' 대신 `SetUserActiveAsync` 슬라이스에만 걸도록 좁혔다(두 복구 경로가 같은 상수를 쓰므로 첫 등장은 파일 순서라는 우연이다). **그 새로고침은 목록까지만이다(2026-09-11 적대 검토 R6).** 푸시는 그 쓰기의 `reqId` 를 함께 싣지만(§11-30①), 열려 있는 편집 폼의 [복구]/[퇴사] 라벨과 `dataset.uop` 은 `userEdOpen` 에서만 정해지므로 거부 뒤에도 폼은 낡은 채다 — 관리자는 갱신된 목록 위에서 **같은 폼의 [복구]** 를 다시 눌러 같은 거부를 반복한다. 호스트 쪽은 그 `reqId` 를 계약⑭-h3 이 잠그고(변이⑭-h3e), 그 푸시로 열린 폼을 다시 맞추는 것은 웹 쪽 몫이다.

**33. 그 폼을 다시 맞추는 웹 쪽 절반 + 5회차 수정이 만든 구멍 둘(2026-09-11 적대 검토 R6).** ① §11-32 의 푸시는 목록까지만이었다 — 이제 `__applyMembers` 가 `uaApplyData` 뒤에 `userEdSyncActive()` 를 부른다. 편집 폼이 열려 있고 그 사람이 새 명부에 있으면 **상태 컨트롤만** 다시 칠한다(`#userEdActive` 의 라벨·`dataset.uop`·danger · 읽기전용 `#userEdSort`). 관리자가 고치는 중일 수 있는 입력칸(ID·이름·직급·소속·범위·권한)은 **건드리지 않는다** — 갱신을 이유로 사람이 친 것을 지우면 그건 다른 종류의 사고다. 그 사람이 명부에서 사라졌으면(다른 자리에서 영구 삭제) 폼을 닫지 않고 `#userEdMsg` 로만 알린다(닫으면 편집 중이던 값이 함께 사라진다). 같은 규칙이 `userEdOpen` 과 `userEdSyncActive` 두 곳에 있으므로 계약⑦-e2 가 **그 네 줄이 글자까지 같은지**를 본다(한쪽만 고쳐지는 순간 잡힌다). ② `uaRender` 의 '같은 화면' 키가 `{순서편집, 퇴사자보기}` 뿐이라 **검색어를 쳐도 같은 화면**으로 쳐서 옛 스크롤 자리를 앉혔다(§11-31 이후 새로 생긴 회귀 — 89명에서 아래를 보다 검색하면 결과가 중간부터 시작한다). 키에 검색어와 `__uaAdmin` 을 넣어 **보이는 것이 달라지면 맨 위**로 간다. 검색어 정규화는 `uaVisible` 과 같은 식이어야 해서 계약이 그 둘을 함께 본다. ③ 푸시가 안 올 때의 자가 재조회(`__uaAwaitPush`)를 `uaSend` 가 **모든 쓰기에서 무조건 껐다.** 그런데 순서 저장 외의 쓰기는 성공해야만 명부를 미므로, 3초 안에 나간 다음 쓰기가 **실패**하면 버린 명부(남의 신규등록·퇴사)가 다시 묻힌다 — R5 가 닫으려던 그 구멍이 그대로 다시 열린다. 이제 '아직 명부를 빚지고 있다'는 사실(`__uaAwaitSeen`)은 **도착한 푸시만** 지운다: 새 쓰기는 빚을 끄지 못하고, 타이머가 울릴 때 아직 왕복 중이면 다시 건다(워치독이 12초 안에 잠금을 풀어 주므로 끝난다). 계약⑬(화면 키)·⑯(빚)·⑦-e2(폼 맞추기) + 변이 열둘.

**34. 다섯 쓰기를 요청/회신 배관으로 옮기고, 손으로 지은 상관관계를 지웠다(2026-09-14).** `saveUser`·`setUserActive`·`saveUserOrder`(+ 휴지통의 `trashRestore`·`trashDelete`)는 이 저장소의 관리자 쓰기 중 **유일하게** `hostRequest` ↔ `ReplyOnUi` 배관을 쓰지 않는 자리였다. 결과를 **푸시**(`__userSaved`)로 내보내면 그 회신에는 상관관계가 없다 — 그래서 §11-26·§11-30①·§11-33③ 이 차례로 손으로 그것을 지었다: 요청 표(`__uaReq`) · 폼 표(`__ueTok`/`__ueTokSeq`) · 푸시에 실은 `reqId` · 워치독 둘 · '명부를 빚지고 있다'(`__uaAwaitSeen`)는 await/빚 한 쌍. 하나하나가 **배관이 이미 보장하는 것의 복제**였고, 복제를 깁는 수정이 다음 구멍을 만드는 자리이기도 했다. 이제 셋은 발주처·코드 브리지와 **같은 모양**이다 — `ReplyOnUi(reqId, new { ok, msg, roster })`. 갱신된 명부도 별도 푸시가 아니라 그 회신에 함께 실린다(`roster` = 옛 `__applyMembers` 가 나르던 그 JSON 문자열, 못 읽었으면 `""`). **동작은 한 글자도 바꾸지 않았다**: 거부 문구·관문(`OpenAdminAsync`)·트랜잭션 규칙 그대로고, 명부를 다시 읽는 **조건**도 옛 푸시의 조건 그대로다(저장=성공만 · 퇴사/복구=`ok ‖ AlreadyActiveMsg` · 순서=`ok ‖ StaleRosterMsg`). 지운 것: `UserSaved`/`TrashDone` 헬퍼와 `window.__userSaved`/`window.__trashDone` 방출, `LoadMembersToWebAsync` 의 `reqId` 인자, 휴지통 푸시(`LoadTrashToWebAsync`). 이때 남겨 두었던 인자 하나짜리 `__applyMembers(json)` 푸시도 곧 지웠다 — 휴지통에서 인력을 건드린 뒤 「구성원 편집」을 갱신하던 그 한 자리마저 회신이 나르게 되어 **부르는 곳이 0 이 됐기 때문**이다(§11-35). 계약②-b·⑭-h(회신 + 인자 하나)·⑭-h2·⑭-h3 + 변이 열둘. 휴지통 쪽 짝은 [TRASH-DELETE §11-28](TRASH-DELETE.md).

**35. 부르는 곳이 없어진 명부 푸시를 지웠다(2026-09-14).** §11-34 는 "부탁하지 않은 갱신을 다시 밀어야 할 날" 을 위해 방출부(`LoadMembersToWebAsync`)와 웹 수신부(`window.__applyMembers`)를 **모양만** 남겨 뒀고, [TRASH-DELETE §11-29](TRASH-DELETE.md) 가 마지막 호출부를 지우면서 그 둘은 **부르는 곳이 하나도 없는** 길이 됐다. 그 상태가 위험한 이유는 둘이다: ① 아무도 실행하지 않으므로 낡아도 아무도 모르고, 그 모양을 지키는 계약 조각들이 **죽은 코드를 붙들고** 있었다(아무것도 없는 것 위의 계약은 없는 계약보다 나쁘다) · ② 남아 있다는 사실 자체가 다음 사람에게 "명부는 이 길로도 보낼 수 있다" 고 말한다 — 배달이 둘로 갈리는 순간이 바로 §11-29 가 잡은 그 결함이다. 그래서 **삭제만** 했다: 동작은 한 글자도 바뀌지 않는다(그 길로는 이미 아무것도 흐르지 않았다). 지운 것 — `LoadMembersToWebAsync` 와 그 `JsCall` · 웹의 `window.__applyMembers` · 그 모양을 붙들던 계약 조각(⑭-h 의 (d) · 변이⑭-h·⑭-h1b · ⑯ 의 푸시 갈래와 변이 셋 · 휴지통 계약②의 두 줄과 변이②-c) · 쓰지 않게 된 `TrashRefreshRelatedAsync` 의 `includeInactive` 인자. 남긴 것 — **역사**다: "이건 원래 푸시였고, 그래서 웹이 상관관계를 손으로 지었다" 는 설명은 시제만 고쳐 그대로 둔다. 새로 둔 것 — 계약⑭-h4 **하나**: `widget/*.cs` **전부**와 웹에 `__applyMembers` 가 없다(양쪽을 되살려 보는 변이 둘 + 살아 있는 `__applyProjects` 를 통제군으로 함께 본다 — 이 계약이 "푸시가 하나도 없다" 가 아니라 "이 푸시만 없다" 임을 그 줄이 증명한다). `__uaPendingData` 와 미뤄 두기는 **그대로**다 — 순서 편집 중에 도착한 남의 회신(휴지통 복구·삭제)을 `uaSeatReply` 가 여전히 미뤄 두는 **살아 있는 길**이다. 휴지통 쪽 짝은 [TRASH-DELETE §11-30](TRASH-DELETE.md).
