# 사내 서버 DB 운용과 배포 방안 (DB-RELEASE-OPS)

- 상태: **설계 확정(2026-10-21), 구현 전.** 첫 사내 배포판에서 구현한다.
- 대상: 사내 개발 서버 MySQL 의 `taskcalendar` 에 여러 사용자가 붙은 뒤의 스키마 변경, 앱 배포, 장애 대응.
- 이 문서가 이 앱의 운용과 개발 방식의 기준이다. 스키마나 배포 절차를 바꾸는 작업은 먼저 이 문서를 읽고, 바꾸면 이 문서를 함께 고친다.

## 0. 배경

- 2026-10-15 까지는 개발 PC 의 MySQL 이 서버 역할을 했고 사용자는 개발자 한 명이었다. 스키마는 cmd(PowerShell) 이관 도구로 바꿨다.
- 2026-10-20 개발 PC 의 `taskcalendar` 를 사내 개발 서버에 부었다(구조 번호 13). 사내 배포는 보류 중이라 서버에 붙은 사용자는 아직 없다.
- 운영자는 서버 셸(SSH)이 없다. 관리자가 만들어 준 `taskmgr_app`@`%` 계정(`taskcalendar.*` 전체 권한)과 MySQL Workbench 만 쓴다. 앱도 같은 계정으로 붙는다.
- 사용자는 수십 명 규모이고 피드백이 잦아 스키마가 자주 바뀐다. 그래서 정책은 **단순함**을 최우선으로 한다.
- 사내의 악의적 사용자(DB 삭제, 차단 값 조작)는 고려하지 않는다. 아래 차단 장치는 보안 장치가 아니라, 정직한 구버전 앱이 실수로 데이터를 꼬이게 하지 않도록 막는 난간이다.

## 1. 기본 규칙

**DB 의 구조 번호와 앱이 아는 구조 번호가 같으면 동작하고, 다르면 읽기와 쓰기를 모두 막고 안내를 띄운다.**

- 검토했다가 버린 것: 호환형과 차단형 구분, 최소 앱 버전(min_app_version), 버전별 DB 분리. 규모에 비해 복잡하고, 판단할 일이 운영자에게 넘어간다.
- 대가: DB 구조가 바뀔 때마다 모든 사용자가 업데이트 버튼을 한 번 눌러야 한다. 변경을 모아 퇴근 후에 반영해 부담을 줄인다.
- 앱만 바뀐 배포는 구조 번호가 그대로라 아무도 막히지 않는다(배너만 뜬다).

## 2. DB 에 두는 값

새 표를 만들지 않고 기존 `cal_schema_meta`(k, v, updated_at)에 키 다섯 개를 둔다. 값 칸 `v` 는 64자다.

| 키 | 값 예시 | 뜻 |
|---|---|---|
| `db_structure_version` | `14` | DB 표 구조 번호. 표가 바뀔 때만 1씩 오른다. **앱과 같아야 동작** |
| `db_updating` | `0` / `1` | 1이면 DB 갱신 중. 모든 앱이 잠시 대기 |
| `app_latest_version` | `0.24.0` | 지금 배포 중인 최신 앱 버전. 업데이트 배너에 뜬다 |
| `app_installer_file` | `TaskCalendarWidget-Setup-v0.24.0.exe` | 공유 폴더에서 받을 설치 파일 이름 |
| `app_installer_sha256` | 64자 | 받은 파일 대조용 해시 |

- `db_` 로 시작하면 DB 이야기, `app_` 으로 시작하면 앱 배포 이야기다.
- 기존 키 `schema_version` 은 `db_structure_version` 으로 바꾼다(첫 배포판에서. 서버에 사용자가 없어 옮길 사람이 없다).
- 공유 폴더의 `latest.json` 은 없앤다. 그 역할을 `app_` 세 키가 한다.
- 변경 안내 문구는 DB 에 두지 않는다. 바뀐 내용은 업데이트 뒤 앱의 패치노트 창에서 본다.
- 구조 번호를 앱 버전과 같은 번호로 쓰지 않는 이유: 정확 일치 규칙이라, 합치면 앱만 고친 배포에서도 전원이 막힌다.

## 3. 앱의 동작

### 3.1 관문

- 이 앱은 DB 작업 하나마다 연결을 새로 열고 닫는다(`Pooling = false`). 연결을 여는 곳을 **관문 하나**로 모으고, 관문이 연결을 열 때마다 `cal_schema_meta` 를 읽어 판정한다. 작업마다 한 번 확인하는 셈이다.
- 지금 연결을 여는 곳: `CalendarDb.OpenReadAsync`, `CalendarWriteDb.SaveAsync`, `ProjectDb.OpenReadAsync / OpenWriteAsync / OpenAdminAsync`, `ReportDb.OpenWriteAsync`(그리고 데이터를 다루지 않는 `OfflineHost` 핑). 시험으로 "`new MySqlConnection` 은 관문에만" 을 강제한다.
- 비용: 키로 몇 줄 읽는 쿼리 하나. 연결 프리앰블이나 권한 확인 쿼리에 붙이면 왕복도 늘지 않는다.
- 쓰기는 트랜잭션 **안에서** `cal_schema_meta` 를 `FOR SHARE` 로 한 번 더 읽는다. 확인과 저장 사이에 이관 SQL 이 끼어드는 틈을 닫는다(이관 SQL 의 `db_updating` 갱신은 진행 중인 쓰기가 끝날 때까지 기다리고, 그 뒤의 쓰기는 새 값을 보고 멈춘다).
- 회사 보고 전송은 회사 사이트로 **보내기 전에** 확인한다. 보고는 사이트로 먼저 나가고 DB 기록은 나중이라(`OfflineHost` S10), 막힌 상태에서 보내면 기록만 실패한다.
- 막힌 상태에서도 `app_` 세 키 읽기는 허용한다. 그래야 업데이트 버튼이 동작한다.

### 3.2 판정과 화면

| 상황 | 화면 | 버튼 | 재확인 |
|---|---|---|---|
| `db_updating = 1` | "서버 갱신 중입니다. 잠시 기다려 주세요" | 없음 | 30초마다 |
| DB 구조 번호 > 앱 | "새 버전이 있습니다. 업데이트해 주세요" | 업데이트 | 사용자 클릭 |
| DB 구조 번호 < 앱 | "서버 갱신 전입니다. 관리자에게 문의하세요" | 없음 | 30분마다 |
| 같음 | 정상 | | 30분마다(배너 확인) |

- 판정 순서: `db_updating` 먼저, 그다음 구조 번호. 값이 없거나 숫자가 아니면 막는다.
- 차단 화면은 업데이트 배너와 따로 떠 있어야 한다. 공유 폴더에 접근하지 못하면 설치 파일 경로를 직접 보여 줘 수동 설치를 안내한다.
- 막힌 상태에서 새 버전을 못 찾으면 "새 버전 준비 중" 을 띄우고 몇 분마다 다시 확인한다.
- 저장되지 않은 변경이 있으면 차단 화면에 그 사실과 내용을 보여 준다(업데이트로 앱이 다시 켜지면 사라진다).
- 다른 사람 일정 보기 창에도 같은 차단 화면을 띄운다.
- 일정 시작 알림은 로컬 파일로 돌아 차단과 무관하게 울린다.

### 3.3 업데이트

- 앱은 DB 의 `app_latest_version` 이 자기보다 높으면 배너(또는 차단 화면의 버튼)를 띄운다.
- 버튼을 누르면 공유 폴더에서 `app_installer_file` 을 받아 `app_installer_sha256` 과 대조하고, 조용한 설치(`/SILENT`) 뒤 앱만 다시 켠다. PC 재부팅은 필요 없다. 설치는 사용자 폴더라 관리자 권한(UAC)이 필요 없다.
- 자동 설치는 하지 않는다. 잘못된 배포가 저절로 퍼지는 것을 막고, 사용자가 때를 고르게 한다.
- 설치 시도를 기록해 두고, 다음 실행에서 버전이 그대로면 설치 실패로 보고 수동 설치 경로와 연락처를 띄운다.
- 업데이트 기능은 더 높은 버전으로만 올린다. 되돌리기는 항상 더 높은 번호로 고쳐 올린다.

## 4. 배포 절차 (운영자)

### 4.1 DB 구조가 바뀌는 배포

퇴근 후에 한다. 사용자는 다음 날 버튼을 한 번 누른다.

1. 새 Setup 파일을 공유 폴더에 올린다. 옛 Setup 파일은 지우지 않는다. 이 시점에는 아무도 새 버전을 안내받지 않는다.
2. Workbench **Data Export** 로 `taskcalendar` 를 백업한다(Dump Structure and Data, Self-Contained File, Single Transaction, Include Create Schema). 파일 끝에 `-- Dump completed` 가 있는지 본다.
3. 받은 이관 SQL 을 Workbench 에서 열고 **전체 실행(Ctrl+Shift+Enter)** 한다. 오류가 나면 멈추는 기본 설정을 그대로 둔다.
4. 마지막 확인 쿼리로 `db_structure_version`, `db_updating = 0`, `app_latest_version` 을 본다.
5. 내 PC 에서 업데이트 버튼을 눌러 새 버전이 정상 동작하는지 본다.

### 4.2 앱만 바뀌는 배포

1. 새 Setup 파일을 공유 폴더에 올린다.
2. `app_` 세 키만 바꾸는 짧은 SQL 을 실행한다(구조 번호는 그대로).

아무도 막히지 않고, 배너를 보고 편할 때 업데이트한다.

### 4.3 공지

- 구조가 바뀌는 배포 전날: "○일 퇴근 후 업데이트가 있습니다. 다음 날 아침 화면의 [지금 업데이트] 를 눌러 주세요. 버튼이 동작하지 않으면 (공유 폴더 경로)의 Setup 을 직접 실행하거나 담당자에게 연락해 주세요."

## 5. 이관 SQL 작성 규칙 (개발자)

### 5.1 형식

- `.sql` 파일 하나. Workbench 에서 `taskmgr_app` 권한으로 실행 가능한 문장만 쓴다. cmd, PowerShell, mysql.exe, 로컬 경로에 기대지 않는다.
- 쓰지 않는 것: SUPER, CREATE USER, GRANT, SET GLOBAL, 다른 DB, 저장 프로시저(객체가 남는다).
- 조건 검사는 `PREPARE` 로 실행할 문장을 고르고, 틀리면 없는 표를 SELECT 해 오류(1146)로 멈추는 방식을 쓴다(`migrate-2026-10-15-code-ids.sql` 의 관문 패턴).
- 맨 위 `SET SESSION lock_wait_timeout = 10;` 으로 잠금 대기를 끊는다.
- 새 열과 표에는 CHARSET, COLLATE 를 적는다. 열 추가는 가능하면 `ALGORITHM=INSTANT` 를 적어, 즉시 변경이 안 되면 조용히 표를 복사하지 않고 실패하게 한다.

### 5.2 순서 (닫기, 바꾸기, 열기)

1. **확인:** `db_structure_version` 이 기대값(예: 13)인지 본다. 이미 목표값(14)이고 `db_updating = 0` 이면 아무것도 하지 않고 끝낸다. 그 밖이면 멈춘다.
2. **닫기:** `db_updating = 1`. 이 순간부터 모든 앱이 "갱신 중" 으로 대기한다.
3. **바꾸기:** 표 구조 변경과 데이터 옮기기.
   - 단계마다 information_schema 를 보고 "이미 했으면 건너뛰기"(MySQL 에는 `ADD COLUMN IF NOT EXISTS` 가 없다).
   - 이름만 바뀌는 열: `ALTER TABLE ... RENAME COLUMN`.
   - 값이 바뀌는 열: 새 열 추가, 트랜잭션으로 변환해 채우기, 검증, 필수로 바꾸기, 옛 열 삭제.
   - 큰 변경: 새 표(`X_new`)를 만들어 채우고 검증한 뒤 `RENAME TABLE X TO X_old, X_new TO X` 한 문장으로 바꿔 끼운다(여러 표를 원자적으로 바꾼다). 앞서 실패한 실행의 잔여물(`X_new`)이 있으면 먼저 지운다.
   - 값 바꾸기(INSERT, UPDATE, DELETE)는 `START TRANSACTION ... COMMIT` 으로 묶는다. 그 사이에 구조 변경 문장을 섞지 않는다(자동 확정된다).
   - "지우고 다시 넣기" 로 저장하는 표(`cal_room`, `cal_todo_day_note`, `cal_entry_commit`, `cal_entry_except`)는 앱의 저장 방식을 함께 확인한다.
4. **검증:** 행 수, 남은 NULL 등. 틀리면 오류로 멈춘다(`db_updating = 1` 인 채로).
5. **열기(한 트랜잭션):** `db_structure_version = 14`, `app_latest_version`, `app_installer_file`, `app_installer_sha256`, `db_updating = 0`.

### 5.3 앱 쪽 짝

- 앱의 구조 번호 상수(`CalendarDb.ExpectedSchemaVersion`, 키 이름 변경 뒤에도 같은 역할)와 정본 스키마 `db/deploy/schema-calendar.sql` 의 시드 값을 같은 커밋에서 올린다. `tests/schema-guards.test.mjs` 가드가 어긋남을 잡는다.
- 이관 SQL 은 이 PC 의 MySQL 에서 **같은 권한의 시험 계정**(`taskcalendar.*` 전체 권한만)으로, 운영 DB 사본에 먼저 끝까지 돌려 본 뒤 넘긴다.

## 6. 실패했을 때

- MySQL 은 구조 변경 문장이 하나씩 즉시 확정되어, SQL 파일 전체의 원자성은 없다. 위 순서가 그것을 대신한다.
- 중간에 실패하면 `db_updating = 1` 에 멈춰 모든 앱이 대기한다. 반쯤 바뀐 DB 를 쓰는 앱이 없다.
- 운영자가 할 일:
  1. 멈추고 아무것도 건드리지 않는다. 오류 메시지를 개발자에게 넘긴다.
  2. **기본: 고쳐서 다시 돌리기.** 이관 SQL 은 다시 돌려도 이미 된 단계를 건너뛰고 이어서 끝낸다.
  3. **30분 안에 못 고치면 백업 복원.** 갱신 직전 백업을 Data Import 로 붓는다. 구조 번호와 `app_` 값이 옛것으로 돌아가 옛 앱이 그대로 동작한다. 막혀 있던 동안 들어온 데이터가 없어 잃는 것도 없다. 공유 폴더의 새 Setup 은 아무도 가리키지 않으니 그대로 둬도 된다. 실패한 실행이 새로 만든 표는 복원 뒤에도 남지만 해는 없고, 다음 실행이 먼저 지운다.
- 이미 새 앱으로 업데이트한 사람이 있는 상태에서(앱만 바뀐 배포 등) 문제가 생기면, 옛 버전으로 내리지 않고 더 높은 번호로 고쳐 올린다.

## 7. 개발 환경

- 개발과 검증은 개발 PC 의 MySQL 에서 한다. 큰 변경 전에는 서버 DB 를 Data Export 로 받아 개발 PC 에 부어 실제 데이터 사본으로 이관 SQL 을 먼저 돌린다.
- 개발 중인 앱(구조 번호가 더 높음)이 실수로 서버에 붙어도 관문에서 막힌다. 운영 DB 가 개발 빌드로부터 보호된다.

## 8. 첫 사내 배포판에 넣을 것

- 버전 관문: 연결 입구 통합(시험으로 강제), 쓰기 트랜잭션 안 재확인, 회사 보고 전송 전 확인.
- `cal_schema_meta` 키 다섯 개와 `schema_version` 이름 변경(정본 스키마, 앱 상수, 시험).
- 업데이트: `latest.json` 대신 DB 의 `app_` 값 읽기, 파일은 공유 폴더에서.
- 차단 화면: 배너와 분리, 수동 설치 경로, 저장 안 된 변경 표시, 열람 창 포함.
- 업데이트 기능 수정: 설치 실패 감지와 안내, `installer/publish-update.ps1` 의 복사 순서(지금은 `latest.json` 을 exe 보다 먼저 복사한다).
- 서버 주소(`DeployConfig.DbHost`)와 공유 폴더 경로.
- 배포 체크리스트 갱신: 워크스페이스 `CLAUDE.md` 의 "버전 갱신 = 전체 릴리스" 중 `latest.json` 항목을 이 문서의 4절로 바꾼다(구현과 같은 커밋에서).
