## 1. 최종 그림 (목표 상태)

한 문장: **netcus와 같은 origin의 서브 경로에 배포된 웹 캘린더 + 서버 DB 단일 소스, 위젯은 로컬 능력(git/svn 등)을 가진 또 하나의 클라이언트.**

```
   [ 브라우저 ]  (사내·재택, 무설치, 로그인)     [ 위젯 .NET/WPF/WebView2 ]
     │ ①앱 로드  │ ②데이터 fetch  │ ③보고 직행     │ ②데이터(동기화)  │ ③보고(보조 WebView2)
     ▼          ▼               ▼               ▼                ▼
  ┌──────────────────────────────────────────────────────────────────┐
  │                  www.netcus.com  (회사 리눅스 서버)                 │
  │   ① /calendar/       정적 HTML/JS (우리 앱)                        │
  │   ② /calendar/api/…  데이터 API ──▶ DB   ← 문지기: 인증·인가·검증    │
  │   ③ /pjm/…           기존 보고 시스템(JSP)                          │
  └──────────────────────────────────────────────────────────────────┘
  ③ 보고 = same-origin이라 "브라우저 JS"가 netcus 폼을 직접 채움·제출(우리 API 경유 ❌).
    위젯 보고는 지금처럼 보조 WebView2로 직접(변화 없음). 둘 다 사용자 세션·자격증명 무보관.
  위젯 로컬 전용 능력 잔존: git/svn 커밋 수집 · 트레이 · 리마인더 · 오프라인 캐시
```

### 목표 상태의 성질
| 축 | 목표 |
|---|---|
| **배포** | `www.netcus.com/calendar` — netcus와 **같은 origin**이 되도록 경로로 배포. origin = **scheme+host+port 3요소**이므로 같은 host의 **경로**여야 하고(서브도메인 ❌) **https·포트도 netcus와 동일**해야 함. 이때 SOP 소멸 |
| **회사 보고** | 브라우저가 netcus 폼을 **직접 채우고 제출**(사용자 자신의 netcus 로그인 세션 공유, euc-kr은 same-origin iframe으로 netcus 문서 안에서 처리). **우리 서버를 경유하지 않음** — 자격증명 무보관 |
| **데이터** | **서버 DB 단일 소스**(일정·할일 + 사용자·과제·조직 마스터). 어느 자리·어느 PC에서든 **로그인**으로 내 데이터 접근(식별자는 IP가 아니라 세션). ※ [결정4](DECISIONS.md)의 하이브리드(개인=로컬 원본+공유 프로젝션)는 **T2 성립 전까지의 중간 모델**이고, 최종(3단계)에서 단일 소스로 승격 — 결정4의 갱신 노트 참조 |
| **서버 역할** | 단순 저장소가 아니라 **문지기 + DB**: 인증(누구냐) → 인가(권한 있냐) → 검증(규칙에 맞냐) → 저장/응답 |
| **클라이언트** | **2종 공존**: 브라우저(범용·무설치·외부접근) + 위젯(로컬 능력·상주). 둘 다 같은 HTML/JS 코어(**코드 원트랙, 전달 투트랙**) |
| **로직 배치** | 표시·조작 = 클라이언트 JS · **신뢰 필요 로직 = 서버가 재검증**(클라 검증은 UX용) · 로컬 능력 = 위젯 .NET |
| **동기화** | 위젯↔브라우저 불일치 문제는 **DB가 단일 소스가 되면서 자동 해소** |

### 위젯의 최종 위치 — 은퇴가 아니라 역할 재편
- **.NET은 제거 대상이 아니다.** 브라우저가 영원히 못 하는 것(로컬 git/svn 실행·트레이·리마인더·완전 오프라인)의 유일한 통로.
- **위젯도 서버 DB의 클라이언트가 된다** — 저장 어댑터를 로컬 XML→데이터 API로 교체. 단 위젯의 강점(오프라인)을 지키기 위해 **로컬 캐시 + 동기화**(offline-first)로 간다(§4 3단계).
- netcus 자동 보고: 위젯은 지금 방식(보조 WebView2) 유지 가능, 브라우저는 same-origin JS로 — **어느 쪽이든 사용자 세션·무보관 원칙 동일**.

## 2. 현재 수준 (v0.5 기준, 2026-07-08)

한 문장: **로컬 우선 위젯 완성 단계 + 미래 승격을 위한 이음새(어댑터·테스트망)까지 확보. 서버 쪽은 착수 전.**

| 축 | 현재 |
|---|---|
| 배포 | WPF 단일 exe(폐쇄망 수동 배포). HTML은 exe 임베드, `https://tcapp.local` 가상 호스트 |
| 데이터 | **로컬 전용** — 위젯 `data.xml`(호스트 동기 기록) / 브라우저 localStorage(그 PC·그 브라우저에 갇힘) |
| 회사 보고 | **위젯**: 일간 자동 전송 + 주간 채움·검토(보조 WebView2, euc-kr 처리, DPAPI) ✅ / **브라우저**: netcus 창 열기 + 복사·위젯 이관 **안내만**(SOP로 자동화 불가 — [DECISIONS 결정5](DECISIONS.md)) |
| 커밋 수집 | git + svn, 과제별 저장소·VCS별 작성자 분리, `ResolveVcs` 단일 진실소스 — **위젯 전용** |
| 로그인/사용자 | 없음(개인 도구). netcus 자격증명만 위젯 DPAPI |
| 서버/DB | **없음** — 조직 결정 대기([DECISIONS 결정4](DECISIONS.md)) |
| 이음새(준비된 것) | **Platform 어댑터**(caps + report 포트, 환경 판별 한 줄) · **테스트망**(Node 내장, 의존성 0) · 문서(ARCHITECTURE/DECISIONS) — **문은 달아뒀고 아직 열지 않은 상태** |

### 능력 매트릭스 — 현재 vs 최종
| 기능 | 위젯(현재) | 브라우저(현재) | 위젯(최종) | 브라우저(최종) |
|---|---|---|---|---|
| 캘린더·할일·보고서 생성 | ✅ | ✅ | ✅ | ✅ |
| 데이터 위치 | 로컬 XML | 그 PC localStorage | **서버 DB**(+로컬 캐시) | **서버 DB** |
| 회사 보고 자동 작성 | ✅ | ❌ 안내만 | ✅ | ✅ (same-origin) |
| git/svn 커밋 수집 | ✅ | ❌ | ✅ | ❌ (**영구 위젯 전용**) |
| 외부(재택) 사용 | ❌ | ❌ | (회사망 정책에 따름) | ✅ |
| 다른 자리 PC에서 내 데이터 | ❌ | ❌ | ✅ | ✅ |
| 오프라인 동작 | ✅ | — | ✅ (캐시+동기화) | ❌ (온라인 전제) |

## 3. 격차 요약 — 최종까지 부족한 것

1. **배포 격차**: netcus 서버의 `/calendar/` 경로에 정적 파일을 올릴 **권한·절차** (기술적으론 파일 복사 수준)
2. **데이터 격차**: 서버 DB(스키마: 사용자·과제·조직 + 개인 일정/할일) + **데이터 API** + 로그인 — 신규 구축
3. **클라이언트 격차**: ① 브라우저 보고 어댑터(same-origin 채움·제출 JS) — **어댑터 교체로 충분**(포트 계약 기존과 동일) ② 위젯 저장 전환(XML→API) — **저장 포트 신설 + 오프라인 캐시·동기화 + 로그인 UI**가 수반되어 어댑터만으로 끝나지 않음(어댑터가 파급을 줄여줄 뿐 0은 아님)
4. **조직 격차**: 공식 채택 결정(§5) — 실질적으로 가장 큰 격차

## 4. 단계별 승격 경로

> 원칙: 각 단계는 **독립적으로 가치**가 있고, 이전 단계를 되돌리지 않으며, 변경은 어댑터/포트 경계에 격리해 도메인 코드 파급을 최소화한다(보고=어댑터 교체로 충분, 저장 전환=포트 신설+동기화·로그인 수반). 빅뱅 없음.

### 0단계 — 지금: 로컬 완성도 (진행 중)
- 위젯 단독으로 유용한 제품 유지·다듬기. 서버 관련 코드는 **만들지 않는다**(YAGNI, [DECISIONS 결정3](DECISIONS.md)).
- 산출물: 안정된 v0.x 위젯, 어댑터·테스트망(완), 문서(완).

### 1단계 — same-origin 정적 배포 (서버 코드 0)
- `www.netcus.com/calendar/`에 현재 HTML을 **정적 파일로** 올린다. 리눅스 서버는 파일만 서빙(신규 서버 로직 없음).
- 이때 열리는 것: **브라우저 보고 자동 작성**(SOP 소멸 — `BrowserPlatform.report` 어댑터만 same-origin 채움 구현으로 교체), 무설치 접근.
- 데이터는 아직 로컬(localStorage) — 즉 "브라우저에서도 보고 작성이 되는" 중간 상태.
- **전제(기술)**: 배포 권한 · **같은 origin 조건 충족(같은 host의 경로 + https·포트 동일)** · netcus `X-Frame-Options`가 DENY 아님. (= [결정5](DECISIONS.md) 기술 트리거 1~3 — 이 셋만으로 자동 작성 구현 가능, 트리거 4(외부 작성 공식화)는 2~3단계의 게이트)

### 2단계 — 서버 신뢰 계층: DB + API + 로그인
- DB(사용자·과제·조직 마스터 + 개인 일정/할일) + 데이터 API + 로그인/세션. **서버 = 문지기**(인증·인가·검증) 원칙 적용.
- 브라우저 저장 어댑터: localStorage → API. 이때부터 **어느 자리에서나 내 데이터**.
- 과제명 목록 선택 강제(기술적 무결성, [DECISIONS 결정4](DECISIONS.md)) 활성화.
- 로컬 MySQL 프로토타입 → 시연 → 서버 승격 순서(결정4의 "테이블은 미리, 활용은 나중" 그대로). ※ **로컬 프로토타입·시연은 T2를 얻기 위한 설득 수단이므로 T2 이전에도 허용**(결정4) — §5의 "선행 구축 금지"는 **운영 서버**를 말하며 로컬 검증기는 예외.

### 3단계 — 위젯 DB 전환 (위젯도 서버 클라이언트로)
- 위젯 저장 어댑터: `data.xml` → 데이터 API. **위젯↔브라우저 동기화 문제 종결**(단일 소스).
- **오프라인 설계 필수**: 위젯 강점을 지키기 위해 로컬 캐시(기존 data.xml을 캐시로 강등) + 재접속 시 동기화. 동시 편집 충돌 정책(최종 수정 우선 vs 병합)은 이 단계 설계 시 결정.
- 1회 마이그레이션 도구: 기존 data.xml → DB 업로드.
- git/svn 수집·트레이·리마인더는 그대로 위젯 잔존.

### 4단계(선택) — 팀 읽기 전용 열람·집계
- 팀장/사업부 조회·과제별 집계. **[DECISIONS 결정1](DECISIONS.md)의 STOP 라인**(과제 할당·상태 전이·승인 등 PM 기능 금지) 안에서만.

## 5. 착수 스위치 (트리거) — 코드가 아니라 조직 결정

| # | 확인할 것 | 왜 결정적인가 |
|---|---|---|
| **T1** | **netcus.com 서버에 우리 정적 앱을 배포할 수 있는가?** (자체 시스템 여부·배포 절차 — 리눅스+JSP라 자체 Tomcat일 공산) | 1단계의 물리적 전제. 안 되면 same-origin 전략 전체가 무산 → 대안 재논의 |
| **T2** | **조직이 이 캘린더를 공식 보고 도구로 채택하고, 서버·DB·인증 구축을 승인하는가?** (+"회사 외부 작성"이 공식 요구인가) | 2~3단계는 개인이 못 세움(자원·운영·SoR 책임). 채택 결정 = 서버 페이즈 시작 신호 |

- **T1만 성립**(+결정5 기술 트리거 2·3 확인) → 1단계까지 진행 가능(브라우저 보고 자동화, 데이터는 여전히 로컬).
- **T1+T2 성립** → 2~3단계 본격 착수.
- **어느 것도 미정** → 0단계 유지. **운영 서버** 선행 구축 금지(로컬 MySQL 검증기·시연은 T2 설득 수단으로 예외 — 결정4).
