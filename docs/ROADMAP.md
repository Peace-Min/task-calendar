## 1. 왜 원래 계획과 달라졌나 — 정직한 기록

**원래(2026-07-08)**: T1(netcus 서버에 정적 배포 가능?) → T2(조직이 채택·서버 승인?) → **API 서버 + DB + 로그인** → 그 뒤에 위젯을 DB 클라이언트로 전환하되 **로컬 캐시 + 동기화(offline-first)** 로.

**실제(2026-08~09)**: T2를 기다리지 않고 **위젯이 MySQL에 직결**로 먼저 전환. API 서버 없음. **온라인 전용, 로컬 캐시 없음**(ADR-18, [CALENDAR-TABLE-DESIGN §2](../db/CALENDAR-TABLE-DESIGN.md)).

**왜**: 조직 채택은 개인이 못 만든다. 그 전에 "다른 자리 PC에서 내 일정 보기"·"위젯↔브라우저 따로 노는 문제"·"남의 일정 열람"을 풀려면 DB가 먼저 있어야 했고, API 없이도 폐쇄망 MySQL 하나면 된다. [DECISIONS 결정4 갱신](DECISIONS.md)이 이 경로를 **"클라이언트가 DB에 직접 붙는 중간 단계"** 로 이미 인정하고 있었다.

**그 대가 — 지금 안고 있는 것**:
| 대가 | 어디에 기록 | 상태 |
|---|---|---|
| 앱 계정 비번이 exe에 상수로 내장, 80대에 배포 | USER-LOGIN §3.4 | 문서화된 한계. 완화책 3중 권한 최소화만 됨 |
| 신뢰 경계가 API가 아니라 DB GRANT | 결정4 갱신 | 중간 단계 한정으로 수용 |
| 서버 못 붙는 날 **미리알림 0건** (예전엔 XML이라 항상 울림) | 설계 §4, db/ROADMAP C5 | **결정(09-02): 수용.** 로컬 알림표는 두 번째 진실이 되므로 두지 않는다(§5-2). 릴리스 노트에 명시 |
| 부팅 실패 시 [다시 시도] 없음 | 설계 §2가 확정한 것과 다름 | 코드가 결정을 어김 |

> 옛 로드맵의 "오프라인 캐시" 서술은 **API 서버 시대(§4)에 다시 논의할 것**이지, 지금 캐시를 만들 근거가 아니다.

## 4. 그 다음 — 원래 계획의 나머지 (게이트는 유지)

옛 로드맵의 1·2·4단계는 폐기가 아니라 **뒤로 밀린 것**이다. 착수 스위치는 그대로:

| 게이트 | 질문 | 열리면 |
|---|---|---|
| **T1** | netcus.com 서버에 우리 정적 앱을 배포할 수 있는가? (리눅스+JSP라 자체 Tomcat일 공산) | **브라우저 버전** — `www.netcus.com/calendar/`에 정적 배포. same-origin이라 SOP 소멸, 사용자 netcus 세션 재사용, 무설치 |
| **T2** | 조직이 공식 보고 도구로 채택하고 서버·DB·인증을 승인하는가? | **API 서버** — 클라이언트 직결을 API 경유로. 신뢰 경계가 GRANT → API로 이동. 브라우저도 같은 API. 이때 오프라인 캐시 재논의 |
| — | 위 둘과 무관 | **타인 일정 열람**(C4) — `view_scope` 재사용, 화면만 없음 |

> T2 전에 서버 API를 세우지 않는다 — 운영·SoR 책임은 개인이 질 수 없다. 로컬 MySQL 검증기는 T2를 얻기 위한 설득 수단이므로 허용(결정4).
