# 개인 캘린더 저장: 바뀐 행만 쓰기 (SAVE-DIFF)

- 상태: 구현(2026-11-10, 브랜치 `feat/save-diff`). DB 구조 번호는 22 그대로다. 표, 칸, 색인을 바꾸지 않는다.
- 바꾼 곳: `widget/CalendarWriteDb.cs` 한 파일. 웹(`task-calendar-prototype.html`)과 회신 모양은 그대로다.
- 시험: `tests/save-diff.test.mjs`(소스 계약과 변이), `tests/loop-calendar-write.mjs` 의 [바뀐 행만] 절(실제 MySQL).
- QA(2026-11-10, 개발 PC): 7절.

## 1. 왜

웹은 편집할 때마다 상태 전체를 호스트에 넘긴다. 호스트(`CalendarWriteDb.SaveAsync`)는 주석으로는 "차이만 쓴다"고 했지만 실제로는 값이 같은지 보지 않고 그 사람의 **모든 행**을 UPDATE 했다.

- 과제, 일정, 할 일, 근태 날짜마다 UPDATE 한 번.
- 일정과 할 일마다 자식 행(반복 예외일, 날짜별 메모)을 지우고 다시 넣기.

그래서 일정 하나를 고쳐도 왕복 수가 그 사람의 전체 행 수에 비례했다. 기록이 쌓일수록 저장이 느려지고(한 저장의 상한은 20초), 서버의 로그와 잠금도 그만큼 늘었다.

## 2. 무엇을 바꿨나

**스냅샷과 같은 행은 쓰지 않는다.**

- 호스트는 부팅 조회(또는 직전 저장)의 스냅샷을 들고 있다. 스냅샷에는 그때의 state 가 있다.
- 저장할 때 스냅샷 state 와 새 state 를 **같은 행 투영**(`RowSig`)으로 견준다. 투영은 저장이 DB 에 적는 바로 그 값이다(`CategoryParams`, `EntryParams`, `TodoParams`, 근태의 상태와 초과시간).
- 일정은 반복 예외일, 할 일은 날짜별 메모까지 함께 견준다. 과제 참조는 번호가 아니라 과제 uid 로 견준다.
- 같으면 UPDATE 도 자식 교체도 하지 않는다. 그 행의 잠금 토큰(`updated_at`)은 그대로 둔다.
- 다르면 예전과 똑같이 쓴다(토큰을 건 UPDATE, 자식 교체).
- 새 행(INSERT), 없어진 행(DELETE), 전량 교체(XML 가져오기)는 그대로다.

**어긋나면 늘 "다르다" 쪽이다.** 다르다고 보면 예전처럼 쓸 뿐이고, 같다고 잘못 보면 편집을 잃는다. 그래서 스냅샷 state 를 못 읽으면 전부 쓴다.

순서 번호(`sort_order`)도 투영에 든다. 목록 가운데에 행을 끼우거나 빼면 그 뒤 행은 순서가 바뀌어 다시 쓰인다. 맨 뒤에 더하는 보통의 편집은 한두 행만 쓴다.

## 3. 낡은 스냅샷 검사 (rev)

예전에는 모든 행을 토큰으로 UPDATE 했기 때문에, 같은 사람이 다른 PC 에서 먼저 저장했으면 나중 저장이 반드시 충돌로 끝났다. 건너뛰는 행은 토큰 검사를 받지 않으므로 이 성질이 사라진다. 그대로 두면 두 가지가 생긴다.

- 다른 PC 가 과제를 지우고 새 과제를 만들면 과제 번호가 다시 쓰일 수 있다. 낡은 번호 맵을 든 PC 가 새 일정을 넣으면 **엉뚱한 과제에 조용히 붙는다**(계약 H-1).
- 낡은 화면이 저장에 성공해, 다른 PC 의 변경을 다시 시작할 때까지 못 본다.

그래서 **사용자 감시점 `cal_user_rev` 로 따로 본다.** 저장의 첫 문장이 rev 를 올리고 잠금을 쥔 바로 뒤에, 올린 값이 스냅샷의 rev + 1 인지 본다. 아니면 그 스냅샷 뒤에 다른 저장이 있었다는 뜻이라 충돌로 끝내고 통째로 롤백한다.

- 화면 동작은 예전과 같다. "다른 곳에서 먼저 수정되었습니다" 상자가 뜨고 새로고침한다.
- 전량 교체는 보지 않는다(예전에도 토큰 없이 통째로 바꿨다).
- 응답만 끊긴 저장(S9, `OFFLINE-RESILIENCE.md`)도 같은 길이다. 다음 저장이 충돌이 되고, 호스트가 서버를 다시 읽어 내용이 같으면 성공으로 돌린다.
- 과제 캘린더의 "개인 일정에 등록"은 rev 를 올린 뒤 개인 스냅샷을 다시 싣는다. 그래서 다음 저장이 걸리지 않는다.

## 4. 하지 않은 것

- **두 PC 에서 무관한 행을 고쳤을 때 둘 다 통과시키기.** 행 단위 토큰만으로 하면 가능하지만 3절의 두 문제가 생긴다. 하려면 저장 뒤 다른 PC 의 변경을 화면에 다시 싣는 길(rev 로 감지해 조용히 새로 읽기)이 먼저 있어야 한다. 따로 정한다.
- 웹이 바뀐 행만 보내기. 호스트가 견주는 것으로 충분하고 웹의 저장 한 곳(`save()`)을 건드리지 않는다.
- 여러 문장을 한 번에 보내기(묶음 실행). 바뀐 행만 쓰면 문장 수가 이미 작다.

## 5. 확인하는 법

- 로그(`widget.log`): `캘린더 저장: user_id=… rev=… · 추가 0 · 수정 1 · 삭제 0 · 그대로 412`. "그대로"가 건너뛴 행 수다.
- 실제 MySQL(개발 PC): `node tests/loop-calendar-write.mjs`. [바뀐 행만] 절이 같은 state 저장은 0행, 한 행 수정은 1행, 예외일만 바꿔도 그 일정이 다시 쓰이는지, 무관한 행만 고친 낡은 스냅샷이 거부되는지 본다.

## 6. 배포

앱만 바뀌는 배포다. 이관 조각이 없고 아무도 막히지 않는다.

## 7. QA 기록 (2026-11-10, 개발 PC, MySQL 8.4)

| 무엇 | 결과 |
|---|---|
| 전체 strict(`TC_TEST_STRICT=1 node tests/run-tests.mjs`) | 통과(끝 줄의 수는 커밋 글) |
| `loop-calendar-write`(실제 MySQL, 저장 함수 직접) | 통과 180, 실패 0, 판정 불가 0 |
| `loop-offline`(실제 위젯, 응답만 끊긴 저장의 복구 포함) | 통과 95, 실패 0 |
| `loop-conflict-ui`(실제 위젯, 충돌 상자) | 통과 12, 실패 0 |
| `loop-default-tasks`(실제 위젯, 과제 삭제와 옮기기) | 통과 30, 실패 0 |
| `loop-project-calendar`(실제 위젯, 개인 일정에 등록 뒤 저장) | 통과 23, 실패 0, 판정 불가 1(P9 참여자 단추, 창이 좁아 목록이 접힘. 저장과 무관) |
| `loop-import-ui`(실제 위젯, 전량 교체 왕복) | 통과 25, 실패 0 |

`loop-calendar-write` 의 [바뀐 행만] 절이 보는 것:

- 같은 state 저장은 0행이고 모든 행의 `updated_at` 이 그대로다. 한 행 수정은 1행이다.
- 편집 종류별(E1~E11): 순서 바꾸기(2행), 맨 앞에 끼우기(밀린 행 전부), 맨 뒤에 더하기(1행), 과제 참조 떼기, 없는 값과 0 구분, 날짜별 메모만, 근태 초과시간만, 근태 하루 지우기, 과제와 일정 함께 더하고 지우기, 스냅샷을 못 읽으면 전부 쓰기, 전량 교체는 건너뛰지 않기. 단계마다 다시 읽어 보낸 것과 같은지 본다.
- 낡은 스냅샷은 무관한 행만 고쳤어도 거부되고 rev 가 남지 않는다.

**실제 화면이 만든 state 로도 건너뛴다.** 워크트리 빌드 위젯에서 loop 가 화면으로 편집하는 동안의 로그(개발 계정, 행 58건): 부팅 뒤 첫 저장이 `추가 1 · 수정 0 · 삭제 0 · 그대로 58`. 그 뒤 저장도 편집한 만큼만 썼다(수정 0~3).

**저장 시간**(`node tests/loop-calendar-write.mjs --bench=3000`, 행 3570건, 같은 기계의 MySQL 이라 망 지연 없음. 예전 판은 `--wdb=<옛 CalendarWriteDb.cs>`):

| 저장 | 예전 | 지금 |
|---|---|---|
| 처음 넣기(전부 INSERT) | 1645 ms | 1581 ms |
| 같은 내용 저장 | 1771 ms | 138 ms |
| 한 행 수정 | 2306 ms | 149 ms |
| 맨 뒤 한 건 추가 | 1745 ms | 163 ms |

지금 남는 약 140 ms 는 스냅샷 state 를 읽어 견주는 시간과 연결, 관문, rev 문장이다. 실제 서버에서는 문장마다 망 왕복이 붙으므로 예전 판의 시간만 더 늘어난다.

돌리지 않은 것: 폐쇄망 서버에서의 측정, 실제 PC 두 대로 하는 동시 사용(같은 스냅샷 두 저장으로 대신 봤다), 나머지 실제 위젯 loop(근태, 휴지통, 관리 화면 등 저장 함수를 바꾸지 않는 화면).
