# 서버(DB) 연결 장애 대응 — 기획서

> 2026-10-01 · 대상 v0.19.x · 파이프라인 **기획 → 개발 → QA → 위키** 의 1단계 산출물.
> 이 문서가 개발·QA 의 **정본**이다. 바꾸려면 이 문서를 먼저 고친다.

## 0. 지키는 결정(바꾸지 않는다)

| 결정 | 출처 | 이 기획에서의 뜻 |
|---|---|---|
| 온라인 전용 · 오프라인 캐시 없음 | ADR-18 · docs/DECISIONS.md | 서버가 없으면 **읽지도 쓰지도 않는다.** 로컬 파일에 몰래 쌓아 두지 않는다 |
| 서버 실패일엔 그날 알림 없음(①수용) | CALENDAR-TABLE-DESIGN §4 | 바꾸지 않는다. 대신 **연결이 돌아오면 그 자리에서 알림을 다시 건다** |
| 연결 안 되면 편집 비활성 | db/ARCHITECTURE.md §4.5 | 캘린더에도 **실제로** 적용한다(지금은 과제 화면만 막힌다) |
| 상태 폴링 없음 | CALENDAR-TABLE-DESIGN §3.7 | **정상일 때는** 여전히 폴링하지 않는다. 끊겼다고 **안 뒤에만** 짧은 재연결 확인을 돈다 |

## 1. 현재 동작 요약(2026-10-01 조사)

1. 실패 원인이 화면에 안 온다 — `CalendarDb.LoadSnapshotAsync` 가 예외를 삼키고 null → 고정 문구 「서버에서 캘린더를 받지 못했습니다」. 원인(네트워크·권한·DB 이름·표 없음)은 widget.log 에만.
2. 부팅 실패 뒤 빈 캘린더에서 **편집이 된다** → 저장은 거부되고, 재시도가 성공하면 그 편집이 **말없이 사라진다**.
3. 사용 중 저장 실패 → 2.6초 토스트뿐. 편집은 화면에 남지만 표시·재시도·닫기 경고가 없다(성공 토스트가 응답 전에 뜨는 경로도 있다).
4. 재연결은 부팅 재시도 3회(15·30·60초)가 전부. 그 뒤엔 영원히 수동. 과제 목록은 부팅 재시도 성공 때도 다시 안 읽는다.
5. 로그인 성공 뒤 캘린더를 다시 읽지 않는다(서버가 꺼진 채 시작해 로그인 화면을 거친 경우).
6. 권한 거부·DB 이름 오류도 「재시도 가능」으로 3번 헛돈다.
7. 저장 COMMIT 은 됐는데 응답만 끊기면, 다음 저장이 **가짜 충돌**이 되고 [새로고침] 이 최신 편집을 버린다.
8. 보고 전송은 성공했는데 보고 기록(cal_report_*) 저장이 실패하면 로그만 남는다.

## 2. 시나리오와 목표 동작

| # | 상황 | 목표 동작 |
|---|---|---|
| S1 | 서버 꺼진 채 시작(세션 있음) | 제목줄 아래 **연결 상자**: 원인 종류별 문구(§3) + 재시도 카운트다운. 캘린더는 **읽기 전용 잠금**(§4). 빠른 재시도 15·30·60초 → 그 뒤 **5분마다 계속**(네트워크 종류만). 성공하면 상자를 걷고 캘린더·과제 목록·코드·알림을 함께 다시 건다 |
| S2 | 서버 꺼진 채 시작(세션 없음 → 로그인) | 로그인 화면이 「DB에 연결하지 못했습니다」를 **원인 종류별**로 구분. 로그인 성공 즉시 캘린더·과제 목록을 다시 읽는다(지금은 안 읽는다) |
| S3 | 사용 중 서버가 꺼짐 → 편집 | 저장 실패가 네트워크 종류면: 편집은 **화면에 남기고** 제목줄 아래 **「저장되지 않은 변경」 막대**를 띄운다(닫을 수 없음). 재연결 확인(§5)이 돌고, 연결되면 **자동으로 다시 저장**한다. 그 동안 새 편집은 **막는다**(잠금) — 쌓이면 충돌·유실 위험만 커진다 |
| S4 | S3 상태에서 위젯을 닫으려 함 | 「저장되지 않은 변경이 있습니다 — 닫으면 사라집니다」 확인. 취소하면 닫지 않는다 |
| S5 | 서버 복구 | 재연결 확인이 성공 → 상자/막대를 걷고, 미저장분 저장 → 캘린더 다시 읽기(rev 확인) → 과제 목록·코드 다시 읽기 → 알림 다시 걸기. 사용자에게 「서버에 다시 연결되었습니다」 한 번 |
| S6 | 권한 거부·DB 이름 오류(1044/1045/3118) | **재시도하지 않는다.** 「DB 접근이 거부되었습니다 — 위젯 설정(DB 이름·계정)과 서버 권한을 확인하세요(관리자)」 + DB 이름·호스트 표시. [다시 시도]는 남긴다 |
| S7 | 구조 불일치(1146 표 없음 · 1054 컬럼 없음 · schema_version) | 재시도하지 않는다. 「DB 구조가 이 버전과 맞지 않습니다」. 서버가 **낮으면** 「서버 DB 업데이트 필요(관리자)」, 높으면 「위젯 업데이트 필요」 |
| S8 | 느린 서버(타임아웃) | 네트워크 종류로 본다(S1/S3 경로). 저장 중에는 막대에 「저장 중…」 |
| S9 | 응답만 끊긴 저장(COMMIT 은 됨) | 재시도 저장이 충돌을 받으면 호스트가 서버 스냅샷을 다시 읽어 **내용이 같으면 성공으로 처리**(가짜 충돌 제거). 다르면 지금처럼 충돌 상자 |
| S10 | 보고 기록 저장 실패(전송은 성공) | 호스트가 10·30·60초로 3회 다시 저장, 그래도 실패면 화면에 「보고는 전송됐지만 기록 저장에 실패했습니다」 경고 |
| S11 | Windows 시작 때 MySQL 이 늦게 뜸 | S1 과 같다(5분 꼬리 재시도가 해결). 별도 처리 없음 |
| S12 | 과제·구성원·휴지통·직급 화면 사용 중 끊김 | 지금 동작 유지(쓰기 거절 = OfflineMsg). 단 **연결 상태가 공유**된다: 한 곳에서 네트워크 실패가 나면 전역 「연결 끊김」 상태로 들어가 S3 의 재연결 확인이 돈다 |

## 3. 오류 분류(호스트 → 웹)

호스트는 DB 예외를 하나의 함수 `DbErrorKind Classify(Exception)` 로 나눈다.

| kind | 판정 | 재시도 | 사용자 문구(요지) |
|---|---|---|---|
| `network` | MySqlException 1042·2002·2003·2005·2006·2013 · 'Unable to connect' · SocketException · TimeoutException · OperationCanceledException(우리 토큰 시한) | 예 | 서버에 연결할 수 없습니다(꺼져 있거나 네트워크 문제) |
| `auth` | 1044·1045·1142·1143·3118(계정 잠김) | 아니오 | DB 접근이 거부되었습니다 — 설정·권한 확인(관리자) |
| `schema` | 1146·1054 · schema_version 불일치 | 아니오 | DB 구조가 이 버전과 맞지 않습니다 |
| `unregistered` | 기존 CalendarUserNotFoundException | 아니오 | (지금 문구 유지) |
| `unknown` | 그 밖 | 예(네트워크와 같게) | 서버 오류 — 잠시 뒤 다시 시도 |

- 웹으로 가는 모양: `{ kind, message, detail, db, host }` — `detail` 은 원문 한 줄(사람이 신고할 때 쓰는 값, 「자세히」에서만 보인다). 비밀번호는 절대 싣지 않는다.
- 부팅 실패 응답(`__applyStateError`), 저장 실패 응답(`saveState` 회신), 로그인 실패(`userLogin` 회신), 핑 응답이 같은 모양을 쓴다.

## 4. 편집 잠금

- 잠금 조건: `bootOk === false`(부팅 스냅샷 없음) **또는** `unsaved === true`(S3) **또는** `conn === 'offline'`.
- 잠금이면: 편집 진입점(새 기록·빠른 추가·끌어 옮기기·할 일 추가·과제 관리·가져오기·초기화 등)이 토스트 한 줄 「서버에 연결되지 않아 지금은 편집할 수 없습니다」로 끝난다. 화면은 읽을 수 있다.
- 마지막 방어: `save()` 가 잠금 상태에서 불리면 보내지 않는다. 부팅 스냅샷이 없는 상태(빈 캘린더)라면 메모리를 **마지막 정상 상태(빈 상태)** 로 되돌리고 토스트 — 그 편집은 원래도 서버에 갈 길이 없었다.
- `body.db-locked` 클래스로 주 버튼(＋ 새 기록 등)을 흐리게 보인다(토큰 색만).

## 5. 연결 상태와 재연결 확인

- 웹 전역 `conn`: `'ok' | 'offline' | 'denied'`(auth/schema). 부팅·저장·핑·과제 목록 응답이 갱신한다.
- `offline` 으로 들어가면 **재연결 확인**을 돈다: 호스트 `dbPing`(연결 + `SELECT 1`, 연결 3초) 을 15·30·60초 → 이후 300초 간격. 창이 다시 보이거나 절전에서 깨면(웹 `visibilitychange`) 한 번 즉시.
- 정상(`ok`)일 때는 아무것도 돌지 않는다(폴링 없음 원칙).
- 부팅 실패의 기존 재시도(`createBootRetry`)는 이 재연결 확인으로 **합친다**: 빠른 3회 뒤 끝내지 않고 300초 꼬리. auth/schema 는 꼬리 없음.
- 성공 시 순서(S5): 미저장 저장 → (부팅 실패였다면) reloadState → loadProjects → pushReminders → 상자·막대 제거 → 토스트 1회.

## 6. 닫기 경고(S4)

- 웹이 `unsaved` 가 바뀔 때마다 호스트에 `unsavedState {on}` 를 보낸다.
- 호스트는 창 닫기·트레이 「종료」·⚙ 종료 경로에서 그 값이 참이면 확인 창(예/아니오)을 띄운다. 「아니오」면 닫지 않는다.
- Windows 종료(세션 끝)는 막지 않는다(로그만).

## 7. QA 를 위한 장애 주입(디버그 전용)

- 호스트 명령 `__dbFault { mode }` — **`TC_DEBUG_PORT` 가 설정된 실행에서만** 받는다(배포 실행에서는 거부·로그).
- mode: `off` · `network`(모든 DB 열기가 연결 실패처럼 던짐) · `auth`(1045 처럼) · `commit-lost`(다음 저장 1회는 COMMIT 뒤 응답 직전에 네트워크 오류처럼 던짐 — S9 재현).
- 각 DB 클래스의 열기 지점(CalendarDb·CalendarWriteDb·ProjectDb·ReportDb)이 `DbFault.ThrowIfActive()` 를 한 줄 부른다.

## 9. 범위 밖

- 오프라인 편집 대기열(로컬 저장 후 나중에 올리기) — ADR-18 과 충돌. 하지 않는다.
- 다른 PC 의 변경을 실시간으로 받는 동기화(rev 폴링) — §3.7 결정 유지.
- MySQL 서비스 자체의 자동 재시작 — 운영 영역.
