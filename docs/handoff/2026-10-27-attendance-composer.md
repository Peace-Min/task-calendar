## 회사 PC의 새 세션에서 시작

회사 PC는 이미 개발 환경이 준비되어 있다. 새 환경 구축 없이 브랜치를 받아 문서와 시안부터 확인한다.

```powershell
git fetch origin
git switch feat/17-attendance-handoff
git pull --ff-only
```

처음 로컬 브랜치를 만드는 경우 `git switch --track origin/feat/17-attendance-handoff`로 명시해도 된다. 기존 작업이 있는 PC에서 파일을 강제로 덮어쓰거나 reset하지 않는다.

먼저 이 문서, [정책 정본](../ATTENDANCE-REPORT-POLICY.md), [기존 구현 검증 인계](2026-10-27-attendance-report-policy.md), [시안 안내](../prototypes/attendance-composer/README.md)를 읽는다. 초기 이슈 #17의 작성본 DB 선저장 설계보다 정책 정본이 우선한다.

`docs/prototypes/attendance-composer/index.html`을 Chrome 또는 Edge로 직접 열면 시안을 볼 수 있다. 인터넷, 회사 로그인, DB, npm 설치가 필요하지 않다. 선택적으로 저장소 루트에서 다음을 실행한다.

```powershell
node docs/prototypes/attendance-composer/server.mjs
```

주소는 `http://127.0.0.1:4319/?case=B`이며 상단에서 A/B/C를 전환한다. 이전 PC에서 열려 있던 localhost 주소가 회사 PC에서 자동으로 살아 있는 것은 아니다. 파일로 열거나 로컬 서버를 새로 실행한다.

새 대화에 붙일 요청 예시:

## 사용자가 확정한 정책

1. 회사 근태관리 시스템을 먼저 처리하고 성공을 확인한다.
2. 그 후 앱 보고 DB 관련 변경 전체를 하나의 트랜잭션으로 저장한다.
3. 어느 단계든 실패하거나 결과를 확인하지 못하면 **처리를 완료하지 못했습니다. 다시 시도해 주세요.**를 표시하고 편집창과 입력을 유지한다.
4. 재시도는 회사 보고부터 전체를 다시 처리한다. 같은 날짜 회사 값 덮어쓰기를 허용한다. DB 저장도 중복 없이 덮어쓴다.
5. 두 단계가 모두 성공한 뒤에만 완료 안내, 창 닫기와 DB 기준 캘린더 갱신을 한다.
6. 회사에만 반영된 상태는 허용한다. 회사와 DB를 묶는 분산 트랜잭션이나 회사 자동 롤백은 구현하지 않는다.
7. 새 작성본 DB 선저장, 전송 시도 표, DB 전용 재시도, 로컬 복구 큐, 부팅 및 주기적 자동 재전송은 추가하지 않는다.
8. 처리 중 입력과 반복 클릭을 막는다. 실패 후 앱 종료로 메모리 입력이 사라지는 것은 허용한다.

기존 앱의 다른 보고서 임시저장 기능까지 일괄 삭제하라는 뜻은 아니다. 새 근태 실패 복구를 위한 영구 저장을 추가하지 않는 결정이다. 상세 P01부터 P11 기준은 정책 정본에 있다.

## 최신 UI 피드백과 현재 단계

사용자가 지적한 핵심은 다음과 같다.

- 캘린더에 등록한 업무와 시간을 근태에서 재사용하지 못하면 이 앱에서 근태를 작성하는 이유가 없다. 같은 내용을 다시 입력하게 해서는 안 된다.
- 근태의 해당 날짜를 누르면 상세 화면보다 편집창이 바로 나와야 한다. 보고가 있는 날짜도 이 방향으로 검토한다.
- 과제마다 큰 입력 폼을 계속 아래로 쌓는 구조는 여러 과제를 작성하기 불편하다.
- 편집창에서 그 날짜의 캘린더 항목을 보여주고 필요한 내용을 블록으로 추가하는 방식도 비교하자.
- **이 시점의 요청은 추가 구현보다 여러 프로토타입을 먼저 보여달라는 것이다.**

따라서 이 인계 커밋에서 제품 HTML의 작성 흐름을 새 시안으로 이식하지 않는다. 보고 정책 구현은 `b5567b7` 기준으로 유지하고 독립 시안과 문서를 추가한다.

## A/B/C 시안

| 시안 | 방식 | 비교 포인트 |
|---|---|---|
| A. 선별 조립 | 왼쪽 캘린더 후보를 복수 선택하거나 끌어서 오른쪽 보고서에 추가 | 골라 넣기는 직관적이나 과제가 많으면 문서 스크롤이 길어진다 |
| B. 과제 집중 | 왼쪽 고정 과제 목록, 가운데 현재 과제의 보고 편집, 오른쪽 해당 과제의 캘린더 후보 | 과제 전환 때 입력 공간을 재사용해 긴 폼 문제를 줄인다. 가로 폭이 필요하다 |
| C. 초안 검토 | 캘린더로 채운 과제별 표를 검토하고 필요한 행만 펼쳐 블록을 편집하거나 제외 | 대부분의 업무를 보고할 때 입력이 빠르다. 자동 포함된 내용의 검토가 필요하다 |

LLM의 제안은 B의 과제별 작업 공간에 C의 캘린더 초안 채우기를 결합하는 것이다. **사용자가 채택한 결정은 아니다.** 마지막 사용 화면이 C였다는 것만으로 C 확정으로 해석하지 않는다.

시안은 과제 3개, 8개, 15개, 새 보고와 기존 보고 편집, 일간과 주간, 블록 추가와 제외, 복수 선택, 순서 이동, 직접 작성, 시간 수정과 제출 원문 미리보기를 제공한다. 기존 보고는 먼저 보존하고, 다시 채우기는 별도 확인한다.

블록은 원본을 보고에 활용하는 편집 단위다. 블록 DB 스키마를 새로 만들기로 합의한 것이 아니다. 현재 시안의 제출 미리보기는 블록을 기존 과제별 본문으로 합친다.

벤치마크 원문과 설계 적용 범위는 [시안 README](../prototypes/attendance-composer/README.md)에 있다. Todoist의 기존 작업 배치, Notion 버튼의 블록 삽입, Slack Canvas의 자료를 모아 편집하는 흐름을 참고했으며 회사 근태 시스템에 맞춘 결합은 자체 제안이다.

실제 연결 전 정할 사항:

1. A/B/C 또는 결합안 선택과 새 보고의 기본 상태. 자동으로 채우는지, 명시적 가져오기 버튼을 누르는지.
2. 개인 일정, 할 일, 메모에 더해 공용 과제 일정도 후보에 넣을지. 현재 `collectReportData`는 공용 과제 캘린더 전체를 자동 취합하는 함수가 아니다.
3. 시간 없는 캘린더 항목을 가져왔을 때의 시간 입력 안내. 일정 제목에서 시간을 추정하거나 임의 1시간을 넣지 않는다.
4. 주간 합계가 24시간을 넘는 정상 사례의 프런트와 호스트 검증. 현재 구현의 과제별 24시간 규칙을 주간 합계에 그대로 사용하면 막힌다. 일간 DB 시간 행의 계약과 주간 합계를 구분할 것.
5. 기존 보고를 편집할 때 원문을 하나의 블록으로 보여줄지, 블록 출처와 편집 구조를 저장할지. 현재 구조에는 출처 블록이 없으며 시안의 가상 데이터로 복원 가능하다고 단정하지 않는다.
6. 날짜 및 보고 기간을 바꿀 때 편집 중 내용을 어떻게 확인받을지. 비교 시안의 초기화 동작을 제품 정책으로 그대로 복사하지 않는다.
7. 완료하지 않은 할 일이나 계획성 일정도 후보에 보여줄지. 캘린더에 있다는 사실을 업무 수행 확정으로 간주해 자동 제출하지 않는다.

기술 검증에는 반복 일정의 발생 날짜와 기간 할 일의 날짜별 메모를 포함한다. 같은 원본 ID라는 이유로 여러 날짜의 서로 다른 내용을 중복으로 버리지 않는다. 기존 보고 원문을 임의로 파싱해 공수나 출처를 복원하지 않는다.

전체 검사의 환경 전제:

- 테스트용 jsdom은 `tests/package.json`과 잠금 파일을 기준으로 설치한다. 폐쇄망에서는 해당 PC의 준비된 테스트 의존성을 사용한다.
- 비공개 `taskmgr-company-data` 저장소가 이 저장소의 형제 폴더에 있어야 회사 스키마 및 권한 계약 검사까지 측정할 수 있다. 이 비공개 데이터는 공개 저장소에 복사하거나 커밋하지 않는다.
- 새 작업 폴더의 첫 전체 실행에서는 이 형제 폴더가 없어 관련 검사 12건이 실패했다. 기존 비공개 저장소를 로컬 연결한 뒤 전체를 새로 실행했으나, 커밋과 push를 우선하라는 사용자 요청에 따라 완료를 기다리지 않았다. 환경 미준비 실패를 제품 결함이나 최종 검증 결과로 해석하지 않는다.
