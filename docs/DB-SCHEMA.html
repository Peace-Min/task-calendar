이 문서에 없는 것 — 개인 일정 표(cal_*)

taskmgr에는 개인 일정·할 일을 담는 cal_* 표가 12개 더 있습니다(2026-08-11 구축). 아직 앱이 그 표를 쓰지 않고 구조도 바뀔 수 있어 이 문서에서는 일부러 제외했습니다 — 여기 없는 것이 낡아서가 아닙니다.

그쪽 구조와 결정 근거는 CALENDAR-TABLE-DESIGN.md, DDL 단일 소스는 db/deploy/schema-calendar.sql입니다.

한눈에

과제 한 건이 중심이고, 나머지 셋은 과제가 참조하는 목록입니다. 발주처·구분·상태는 각각 별도 테이블로 두어 앱에서 추가·이름변경·순서변경·숨김을 할 수 있게 했습니다.

세 참조 모두 이름(자연키)을 가리킵니다. 그래서 목록에서 이름을 고치면 그 값을 쓰던 과제들의 표기도 한 번에 바뀝니다.

이름이 같은 과제가 여러 건 있을 수 있습니다 — 정상입니다

실제 데이터를 검수해 보니 같은 발주처·같은 사업명이 정당하게 반복됐습니다. 구성품별로 계약이 갈리거나(저장장치·처리장치), 같은 사업이 연도마다 갱신되기 때문입니다. 그래서 이름에는 중복 금지 제약을 두지 않습니다.

사용자 · 조직 누가 무엇을 할 수 있는가

위 네 표가 무엇을 하는가였다면, 아래 세 표는 누가 그것을 볼 수 있고 고칠 수 있는가입니다. 위젯이 켜질 때 로그인한 ID로 이 표를 조회해 권한을 판정합니다.

비밀번호 컬럼이 없습니다 — 인증은 여기서 하지 않습니다

위젯은 사내 주간보고(netcus)로 로그인합니다. 인증이 거기서 끝나므로 이 DB에는 비밀번호가 없습니다. 로그인에 성공한 ID로 이 표를 조회해 “무엇을 할 수 있나”만 판정합니다. 즉 이 표는 인증(authentication)이 아니라 인가(authorization)를 담습니다.

권한 축은 둘이고 서로 독립입니다

view_scope는 “남의 캘린더를 어디까지 보나”, edit_role은 “과제 DB를 고칠 수 있나”입니다. 한쪽이 높다고 다른 쪽이 따라오지 않습니다 — 전사를 열람하면서 편집은 못 하는 사람도, 자기 것만 보면서 과제를 관리하는 사람도 있습니다.

app_user 사용자 — 인가의 단일 소스

사내 임직원 한 명이 한 행입니다. 위젯은 로그인 성공 직후 이 표를 한 번 읽고, 그 결과로 화면과 편집 가능 여부를 정합니다.

팀장을 직급으로 추론하면 틀립니다

실제로 같은 팀 안에 ‘책임’인 팀장과 ‘부장’인 팀원이 함께 있고, ‘선임’이 팀장인 팀도 있습니다. 직급 순으로 뽑았다면 두 팀 모두 엉뚱한 사람이 팀 전체를 열람했을 것입니다.

그래서 관리자·팀장 컬럼을 따로 두지 않고 view_scope를 사람마다 직접 지정합니다. title은 표시와 정렬에만 씁니다.

같은 unit_tree라도 보이는 인원이 다릅니다 — 값이 아니라 소속이 범위를 정합니다

조회 범위는 설정값 + 소속으로 계산됩니다. unit_tree는 “자기 소속 조직 이하 전체”라서, 팀장은 자기 팀만 보고 본부장은 산하 전 팀을 봅니다. 조직 트리의 뿌리에 있는 사람은 결과적으로 전 직원을 보게 됩니다.

그래서 1팀장이 3팀을 보는 일은 구조상 없습니다 — 조직 구조를 고치면 권한도 자동으로 따라갑니다.

DB가 강제하는 것 · 앱이 지키는 것

둘을 구분해 두면 문제가 생겼을 때 어디를 봐야 하는지가 분명해집니다.

DB가 강제 — 앱을 우회해 SQL로 넣어도 막힙니다

없는 값 금지
목록에 없는 발주처·구분·상태로는 과제를 저장할 수 없습니다(외래키).
이름 변경 전파
발주처·구분·상태의 이름을 바꾸면 그 값을 쓰던 과제가 전부 자동으로 따라갑니다.
사용 중 삭제 차단
과제가 쓰고 있는 구분·상태는 지워지지 않습니다.
uid 유일
과제의 정체성이 겹치지 않습니다.
빈 값 표기 통일
계약명·통상명칭·비고는 비어 있으면 빈 문자열입니다(NULL 아님).
권한 값 제한
view_scope·edit_role에는 정해진 세 값 외에 아무것도 들어가지 않습니다(CHECK). DB에 새 값을 넣어도 앱이 모르면 아무 권한도 생기지 않으므로, 늘리려면 어차피 코드 변경이 필요합니다.
소속·직급 실재
목록에 없는 조직·직급으로는 사용자를 저장할 수 없습니다. 소속자가 남아 있는 조직도 지워지지 않습니다.

앱이 지킴 — 규칙이지 물리적 차단은 아닙니다

중복 경고
비슷한 과제를 또 등록하려 하면 경고합니다. 진짜 중복일 수 있으므로 막지는 않습니다.
선진행 규칙
구분이 선진행이면 날짜·상태를 비웁니다(계약 전이므로).
편집 권한
관리자 인증을 통과해야 과제·발주처·코드값을 고칠 수 있습니다.
삭제는 숨김으로
화면에서 지우면 is_active=0이 될 뿐 행은 남습니다. 영구 삭제는 DB에서 직접 해야 합니다.
권한 판정
view_scope·edit_role을 읽어 화면과 편집을 막는 것은 앱입니다. DB는 그 값을 저장할 뿐 강제하지 않습니다 — 아래 경고를 보세요.

권한은 앱의 관례이지 DB가 지키는 규칙이 아닙니다

모든 PC의 위젯이 DB 계정 하나를 공유하고, 그 접속 정보는 배포본에 들어 있습니다. 그래서 앱을 거치지 않고 DB에 직접 붙으면 edit_role이 viewer여도 데이터를 고칠 수 있습니다 — 앱의 권한 검사 코드가 실행조차 되지 않기 때문입니다.

이건 결함이 아니라 알고 받아들인 한계입니다. 그래서 계정 권한을 최소로 묶고(구조 변경·다른 DB 접근 불가), 가장 민감한 근태·급여는 이 DB에 올리지 않습니다. 근본 해결은 접속 정보가 클라이언트에서 사라지는 API 서버 도입입니다. 근거는 CALENDAR-TABLE-DESIGN.md §7.

헷갈리기 쉬운 두 가지

‘비고’와 ‘설명’은 다른 것입니다

비고(project.note)는 DB에 저장되어 관리자가 관리 화면에서 보는 값이고, 모두가 같은 내용을 봅니다.

설명은 각 사용자의 PC에만 저장됩니다(캘린더 데이터 파일). Git·SVN 저장소 경로도 마찬가지입니다 — 경로는 PC마다 다르므로 DB가 가질 수 없습니다.

DB가 주는 것은 ‘이름’뿐입니다

캘린더에서 공식 과제를 쓸 때, DB가 정하는 것은 과제명(통상명칭)과 발주처·구분·상태·기간 같은 과제 자체의 정보입니다.

반면 설명·Git·SVN 경로는 사용자가 자기 PC에서 정의하는 값이라, 기존 과제를 공식 과제로 재연결해도 쓰던 내용이 그대로 따라옵니다. 바뀌는 건 이름뿐입니다.

바꾸려면 어디를 여는가

과제 추가·수정
앱 → 과제 관리 → 공식 과제(DB) → 새 공식 과제 또는 행 선택 후 편집
발주처
앱 → 공식 과제 화면 → 발주처 관리
구분 · 상태
앱 → 공식 과제 편집 → 구분·상태 관리
대량 입력
SQL로 직접 넣습니다. 순서가 중요합니다 — 발주처·코드값을 먼저 넣어야 과제가 들어갑니다(db/deploy/load-template.sql).
표 구조 변경
db/deploy/migrate.cmd — 데이터를 보존하며 최신 구조로 맞춥니다. 여러 번 실행해도 안전합니다.
처음 구축
db/deploy/init-db.cmd — 표를 새로 만듭니다. 데이터가 있는 DB에는 절대 쓰지 마세요.
사람 권한 변경
앱에는 편집 화면이 없습니다. 별도 비공개 저장소의 04-permissions.sql을 고치고 apply.cmd -SkipSchema로 다시 적용합니다 — 앱 계정에 쓰기 권한을 주면 누구나 자기 권한을 admin으로 올릴 수 있기 때문입니다.
인사이동 · 조직 개편
소속만 바꾸면 권한 범위가 자동으로 따라갑니다(UPDATE app_user SET org_unit=…). 조직 신설·개명도 스키마나 코드 변경 없이 행 하나로 됩니다.
명단 갱신
원본은 사내 주간보고 시스템의 좌측 조직도입니다. 링크의 id= 값이 그대로 login_id가 됩니다.

앱이 쓰는 DB 계정의 권한은 묶음마다 다릅니다 — 과제 네 표는 읽기·추가·수정, 사용자·조직 세 표는 읽기만입니다. 어느 쪽도 삭제나 구조 변경은 할 수 없습니다. 사용자 표를 읽기 전용으로 묶은 이유는 위 경고와 같습니다 — 쓰기가 열려 있으면 권한 자체를 탈취할 수 있습니다.

이 문서는 지금 구조가 어떻게 생겼는지를 봅니다. 왜 그렇게 정했는지(식별 규칙을 정한 근거)는 table-design-report.html, 설계 결정 이력은 ARCHITECTURE.md에 있습니다.

원본 정의 — 과제 네 표: db/schema.sql · 배포용(시드 제외) db/deploy/schema-structure.sql

사용자·조직 세 표는 이 저장소에 정의가 없습니다. 실명 89명이 함께 들어 있어 별도 비공개 저장소(taskmgr-company-data)에서 구조와 데이터를 같이 관리합니다 — 이 문서의 컬럼 표는 운영 DB의 information_schema를 그대로 읽어 옮긴 것입니다.
