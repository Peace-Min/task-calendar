과제 DB 테이블 구조

지금 운영되는 taskmgr 데이터베이스가 실제로 어떻게 생겼는지, 그리고 무엇을 DB가 강제하고 무엇을 앱이 지키는지 정리한 문서입니다.

  • 데이터베이스 taskmgr
  • 엔진 MySQL 8.4 / InnoDB
  • 문자셋 utf8mb4_0900_ai_ci
  • 테이블 4
  • 기준 2026-07-27

한눈에

과제 한 건이 중심이고, 나머지 셋은 과제가 참조하는 목록입니다. 발주처·구분·상태는 각각 별도 테이블로 두어 앱에서 추가·이름변경·순서변경·숨김을 할 수 있게 했습니다.

세 참조 모두 이름(자연키)을 가리킵니다. 그래서 목록에서 이름을 고치면 그 값을 쓰던 과제들의 표기도 한 번에 바뀝니다.

project 과제 마스터 — 이 시스템의 핵심

사업부가 관리하는 과제 한 건이 한 행입니다. 캘린더 앱은 이 표를 읽어 공식 과제 목록을 보여주고, 관리자만 편집합니다.

컬럼타입제약설명
idINT UNSIGNEDPKAUTO_INC내부 일련번호. 외부에서 참조하지 않습니다.
uidCHAR(36)UNIQUENOT NULL과제의 정체성. 등록 때 한 번 부여되고 절대 바뀌지 않습니다. 캘린더의 일정은 이름이 아니라 이 값으로 과제를 가리킵니다 — 그래서 이름을 바꿔도 연결이 끊기지 않습니다.
sectionVARCHAR(50)FKNOT NULLINDEX구분. section_code에 있는 값만 들어갑니다.
customerVARCHAR(100)FKNOT NULLINDEX발주처. customer에 있는 값만 들어갑니다.
project_nameVARCHAR(200)NOT NULL사업명.
contract_nameVARCHAR(200)NOT NULL기본 ''계약명. 없으면 빈 문자열이며 NULL을 쓰지 않습니다(비교할 때 함정이 됩니다).
common_nameVARCHAR(200)NOT NULL기본 ''★ 통상명칭 — 화면과 보고서에 실제로 찍히는 이름. 비어 있으면 사업명이 대신 쓰입니다. 보고서 집계가 사업부 관리 명칭과 맞아야 하므로 이 칸을 채워두는 것이 중요합니다.
start_dateDATENULL 허용계약 시작일. 계약 전(선진행)이면 비웁니다.
end_dateDATENULL 허용계약 종료일.
statusVARCHAR(50)FKNULL 허용상태. 비어 있으면(선진행 등) 외래키 검사를 건너뜁니다.
noteVARCHAR(500)NOT NULL기본 ''비고 — 관리 화면에서만 보이는 내부 메모. 캘린더·보고서에는 나오지 않습니다.
is_activeTINYINT(1)NOT NULLINDEX1=사용, 0=숨김. 앱에서 지우면 이 값만 0이 되고 행은 남습니다(되돌릴 수 있음).
created_atDATETIME(3)NOT NULL등록 시각(자동).
updated_atDATETIME(3)NOT NULL마지막 수정 시각(자동 갱신).

이름이 같은 과제가 여러 건 있을 수 있습니다 — 정상입니다

실제 데이터를 검수해 보니 같은 발주처·같은 사업명이 정당하게 반복됐습니다. 구성품별로 계약이 갈리거나(저장장치·처리장치), 같은 사업이 연도마다 갱신되기 때문입니다. 그래서 이름에는 중복 금지 제약을 두지 않습니다.

대신 실수로 같은 걸 또 등록하려 하면 앱이 비슷한 과제가 있다고 경고합니다(막지는 않습니다). 결정 근거는 TABLE-DESIGN.md §4.

customer 발주처 마스터

과제가 참조하는 발주처 목록입니다. 앱의 발주처 관리 화면에서 추가·이름변경·숨김을 합니다.

컬럼타입제약설명
nameVARCHAR(100)PK발주처 이름 자체가 키입니다. 여기서 이름을 고치면 그 발주처를 쓰던 과제 표기도 함께 바뀝니다.
is_activeTINYINT(1)NOT NULL1=사용, 0=숨김. 숨겨도 기존 과제의 발주처 표기는 그대로이고, 새로 고를 때만 목록에서 빠집니다.
created_atDATETIME(3)NOT NULL등록 시각(자동).
updated_atDATETIME(3)NOT NULL마지막 수정 시각(자동 갱신).

section_code · status_code 구분 · 상태 코드

두 표는 구조가 완전히 같습니다. 구분(일반계약·선진행·사업부관리)과 상태(진행중·종료·1차 납품완료·미정)를 담고, 앱의 구분·상태 관리 화면에서 다룹니다.

컬럼타입제약설명
nameVARCHAR(50)PK코드값 자체가 키입니다. 이름을 고치면 그 값을 쓰던 과제 표기도 함께 바뀝니다.
sort_orderINTNOT NULL드롭다운에 보이는 순서(작을수록 먼저). 앱의 ▲▼로 바꿉니다.
is_activeTINYINT(1)NOT NULL1=사용, 0=숨김. 숨겨도 기존 과제 표기는 유지됩니다.
created_atDATETIME(3)NOT NULL등록 시각(자동).
updated_atDATETIME(3)NOT NULL마지막 수정 시각(자동 갱신).

예전에는 이 값들을 컬럼 정의(ENUM) 안에 박아 두어 바꾸려면 스키마를 고치고 앱을 다시 배포해야 했습니다. 지금은 표의 행이라 발주처와 똑같이 앱에서 다룹니다.

DB가 강제하는 것 · 앱이 지키는 것

둘을 구분해 두면 문제가 생겼을 때 어디를 봐야 하는지가 분명해집니다.

DB가 강제 — 앱을 우회해 SQL로 넣어도 막힙니다

없는 값 금지
목록에 없는 발주처·구분·상태로는 과제를 저장할 수 없습니다(외래키).
이름 변경 전파
발주처·구분·상태의 이름을 바꾸면 그 값을 쓰던 과제가 전부 자동으로 따라갑니다.
사용 중 삭제 차단
과제가 쓰고 있는 구분·상태는 지워지지 않습니다.
uid 유일
과제의 정체성이 겹치지 않습니다.
빈 값 표기 통일
계약명·통상명칭·비고는 비어 있으면 빈 문자열입니다(NULL 아님).

앱이 지킴 — 규칙이지 물리적 차단은 아닙니다

중복 경고
비슷한 과제를 또 등록하려 하면 경고합니다. 진짜 중복일 수 있으므로 막지는 않습니다.
선진행 규칙
구분이 선진행이면 날짜·상태를 비웁니다(계약 전이므로).
편집 권한
관리자 인증을 통과해야 과제·발주처·코드값을 고칠 수 있습니다.
삭제는 숨김으로
화면에서 지우면 is_active=0이 될 뿐 행은 남습니다. 영구 삭제는 DB에서 직접 해야 합니다.

헷갈리기 쉬운 두 가지

‘비고’와 ‘설명’은 다른 것입니다

비고(project.note)는 DB에 저장되어 관리자가 관리 화면에서 보는 값이고, 모두가 같은 내용을 봅니다.

설명은 각 사용자의 PC에만 저장됩니다(캘린더 데이터 파일). Git·SVN 저장소 경로도 마찬가지입니다 — 경로는 PC마다 다르므로 DB가 가질 수 없습니다.

DB가 주는 것은 ‘이름’뿐입니다

캘린더에서 공식 과제를 쓸 때, DB가 정하는 것은 과제명(통상명칭)과 발주처·구분·상태·기간 같은 과제 자체의 정보입니다.

반면 설명·Git·SVN 경로는 사용자가 자기 PC에서 정의하는 값이라, 기존 과제를 공식 과제로 재연결해도 쓰던 내용이 그대로 따라옵니다. 바뀌는 건 이름뿐입니다.

바꾸려면 어디를 여는가

과제 추가·수정
앱 → 과제 관리 → 공식 과제(DB) → 새 공식 과제 또는 행 선택 후 편집
발주처
앱 → 공식 과제 화면 → 발주처 관리
구분 · 상태
앱 → 공식 과제 편집 → 구분·상태 관리
대량 입력
SQL로 직접 넣습니다. 순서가 중요합니다 — 발주처·코드값을 먼저 넣어야 과제가 들어갑니다(db/deploy/load-template.sql).
표 구조 변경
db/deploy/migrate.cmd — 데이터를 보존하며 최신 구조로 맞춥니다. 여러 번 실행해도 안전합니다.
처음 구축
db/deploy/init-db.cmd — 표를 새로 만듭니다. 데이터가 있는 DB에는 절대 쓰지 마세요.

앱이 쓰는 DB 계정은 네 표에 대한 읽기·추가·수정 권한만 갖습니다. 삭제나 구조 변경은 할 수 없습니다.

이 문서는 지금 구조가 어떻게 생겼는지를 봅니다. 왜 그렇게 정했는지(식별 규칙을 정한 근거)는 table-design-report.html, 설계 결정 이력은 ARCHITECTURE.md에 있습니다.
