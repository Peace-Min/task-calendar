# 월간보고 DOCX 내보내기 기획

작성 2026-10-22. 상태: 기획 확정, 단계 A(DB 조각, 그림 명령, DOCX 저장 명령) 구현 2026-10-22 밤(12장), 단계 B(월간 탭 화면, 캘린더와 주간보고 출처) 구현 2026-10-23 새벽(13장), **2026-10-23 사용자 결정으로 월간 탭을 모으기와 읽기 전용 미리 보기로 바꿈**(11.3, 15장). 실동작 QA 는 PM. 브랜치 `feat/monthly-report-plan`.

## 1. 목표

회사 월간보고는 과제별로 쓴다. 지금은 사람이 캘린더와 근태 사이트(netcus)를 보며 Word 양식 표를 손으로 채운다.
이 기능은 **지정 기간의 캘린더 기록(필요하면 netcus 읽기 결과)을 과제별로 모아 회사 양식 그대로의 표에 채워 `.docx` 로 저장**한다.

- 하는 일: 기존 기록을 읽어 양식 칸(수행 실적, 개발 일정 그림)에 채운다. 저장 전에 읽기 전용 미리 보기로 확인한다. 글은 화면에서 고치지 않고 저장한 Word 문서에서 고친다(2026-10-23).
- 하지 않는 일: 회사 사이트로 보내기, 기록 원본(일정, 할 일) 수정. DB 는 개발 일정 그림 표 하나와 개발 시작일 칸(6장, 구조 번호 17)만 더한다.
- 결과물: Word 문서(`.docx`). PDF 가 아니다. 사용자가 받은 뒤 Word 에서 마저 다듬을 수 있어야 한다.

## 2. 양식 분석

입력 두 가지를 봤다. 빈 양식 PDF(1쪽)와 사용자가 실제로 쓴 월간보고 PDF(7쪽). 실제 보고서의 과제명, 동료 이름, 본문은 **저장소에 옮기지 않는다**. 아래 예시 값은 모두 지어낸 `(예시)` 값이다.

### 2.1 원본과 페이지

- 빈 양식 PDF 의 문서 제목 메타데이터가 `Microsoft Word - 월간보고_양식.docx` 이다. 즉 **원본은 Word 문서**이고 한컴 PDF 로 인쇄한 것이다. 원본 `.docx` 는 폐쇄망 반출이 어려워 받지 않기로 했다(11.1 의 1번).
- 용지: **A4 가로**(841 x 595 pt).
- 글꼴: 본문 **맑은 고딕 10pt**, 칸 이름은 맑은 고딕 굵게 10pt, 제목은 맑은 고딕 굵게 12pt 가운데 정렬에 밑줄. 일부 영문은 Calibri.
- 색: 맨 윗줄(과제명, 월간 실적, 월간 계획) 배경 **#DBE5F1**(연한 파랑), 칸 이름 줄과 과제 수행 기간, 개발 일정 칸 배경 **#F2F2F2**(연한 회색), 본문 칸은 흰색. 테두리는 얇은 검정 실선.
- 실제 보고서는 사용자가 과제마다 열 폭을 조금씩 바꿔 썼다. 양식의 기준 폭을 기본으로 쓰면 된다.

### 2.2 제목 줄

`월간보고 (이름) (구분 기호) 2026년 09월 08일` 형태. 구분 기호는 양식 원본 글자를 그대로 쓴다(이 문서는 표기 규칙상 기호를 적지 않는다).

- 날짜는 **작성일**(제출일)이다. 실적 기간의 끝과 다르다. 실제 보고서도 파일 이름 날짜와 제목 날짜가 하루 달랐다.
- 실제 파일 이름 관례: `월간보고_<이름>_<YYMMDD>.docx`(예시: `월간보고_홍길동_261020.docx`).

### 2.3 과제 한 덩어리(표 하나)

과제마다 아래 표 하나가 반복되고, 표 사이에 빈 문단 하나가 있다. 빈 양식은 한 쪽에 과제 둘이 들어간다.

열 경계(pt, 왼쪽부터): 85.6, 141.9, 197.7, 317.4, 394.8, 458.3, 592.9, 775.0. 즉 **격자 열 7개**, 전체 폭 689.4pt(약 13,790 twip).

| 줄 | 내용(열 병합) | 배경 |
|---|---|---|
| 1 | 과제명(1열) / 월간 실적: MM월 DD일 ~ MM월 DD일(2~5열) / 월간 계획: 같은 형식(6~7열) | #DBE5F1, 굵게, 가운데 |
| 2 | 과제명 값(1열, **2줄부터 마지막 줄까지 세로 병합**) / 과제 수행 기간(2~3열) / `YYYY/MM ~ YYYY/MM`(4~7열) | #F2F2F2 |
| 3 | 개발 일정(2열) / 일정 그림 칸(3~7열) | #F2F2F2 |
| 4 | 일정 변경이력(2열, 아래 데이터 줄과 세로 병합) / 변경 내용(3열) / 변경 날짜(4열) / 변경 사유(5~7열) | #F2F2F2 |
| 5.. | (병합 계속) / 변경 내용 / 변경 날짜 / 변경 사유, 이력 수만큼 반복(없으면 빈 줄 1개) | 흰색 |
| 끝-1 | 수행 계획(2~3열) / 수행 실적(4~6열) / 수행 계획(7열) | #F2F2F2, 굵게 |
| 끝 | 세 칸의 본문 | 흰색 |

세 본문 칸의 뜻(실제 보고서에서 확인):

- **왼쪽 수행 계획**: 이번 실적 기간에 하려고 했던 계획. 지난 월간보고의 오른쪽 칸이 넘어오는 자리다. 실제 보고서는 모든 과제에서 비어 있었다.
- **가운데 수행 실적**: 실적 기간에 한 일. 보고서의 본체.
- **오른쪽 수행 계획**: 월간 계획 기간에 할 일.

### 2.4 맨 끝 기타 표

실제 보고서 마지막에 과제에 속하지 않는 일을 모은 별도 표가 있다. 빈 양식에는 없다.

- 1줄: 과제명 / 월간 실적: 기간(나머지 열 전체 병합), #DBE5F1.
- 2줄: `기타` / 본문(`-` 항목과 `;` 세부 줄).
- 계획 칸이 없다.

### 2.5 기간의 성질

**월간이라도 달력의 한 달이 아니다.** 실제 보고서는 실적이 7월 20일 ~ 9월 4일(약 7주, 월요일 시작 금요일 끝), 계획이 9월 7일 ~ 10월 23일(다음 월요일부터 약 7주)이었다. 보고 회의 사이 구간으로 보인다. 그래서 기간은 자유 지정이 기본이어야 한다.

### 2.6 개발 일정 칸

**표나 차트 데이터가 아니라 붙여 넣은 그림**이다(실제 보고서 쪽마다 그림 2~3개). 과제 제안서나 계획서의 간트 차트를 잘라 붙인 것으로, 과제마다 모양이 전혀 다르다(단계 막대, 주 단위 칸 표, 품질관리 행 등). 매달 거의 같은 그림을 다시 쓴다.

### 2.7 본문 쓰는 방식

실적과 계획 칸은 네 단계 들여쓰기로 쓴다.

```
▪ 구현                        (분류 머리, 굵게)
  1. 기능 보완                 (번호 묶음, 굵게, 선택)
     - 화면 응답 속도 개선      (항목)
       ; 목록 갱신 횟수 줄임    (세부)
▪ 회의
  - 중간 점검 회의 (09.15, 고객사)   (회의는 제목 뒤 괄호에 MM.DD, 장소)
▪ 기타
  - 내부 검토 자료 작성 (w. 김예시 선임)   (같이 한 사람은 w. 이름 직급)
```

- 분류 머리로 쓰인 말: **구현, 회의, 기타, 유지보수**. 실제 순서는 구현, 회의, 기타.
- 머리 글자는 원본에서 `◾`(U+25FE)였는데 이 글자는 맑은 고딕에 없어 Segoe UI Emoji 로 대체되고, PDF 몇 곳에서 **네모 칸(깨짐)** 으로 찍혔다. 생성 문서는 맑은 고딕에 있는 `▪`(U+25AA)를 쓴다.
- `-` 와 `;` 는 일반 글자로 쓰고 들여쓰기로 단계를 나타낸다. Word 자동 번호는 쓰지 않는다(사용자가 고치기 쉽게).

## 3. 현재 앱에서 쓸 수 있는 것

조사 근거는 `task-calendar-prototype.html`(이하 HTML)과 `widget/` 이다.

- **보고 모달** `#reportModal`(HTML:3193): 탭 일간 작성, 주간 작성, 기간 취합(`data-rmode=daily|weekly|custom`, HTML:3200~3202), 전환은 `setReportMode`(HTML:14802). 기간 칸 `#rptFrom/#rptTo`.
- **단일 수집 함수** `collectReportData(from,to,sources)`(HTML:14593): 내 카테고리 순서대로 카테고리마다 한 줄. 제목(일정, 할 일, 커밋 제목 중복 제거)과 세부(메모, 할 일 노트, 날짜별 노트, 커밋 본문), 공수 합계를 준다.
- **기간 프리셋** `monthRange`, `setReportRange`(HTML:14496~14500)가 이미 있다(이번 달, 지난달). 화면 버튼은 없다.
- **공수와 근태**: `state.taskHours`(날짜 x 카테고리, `cal_task_hours`), `state.attendance`(`cal_attendance`). 기간 합은 `collectReportData` 안에서 계산.
- **netcus 읽기**(읽기 전용 경로):
  - `netcusWeekMerge`(일일 업무일지 날짜별 읽기). **한 번에 31일까지.**
  - `netcusWeeklyRangeRead`(주간보고 게시판 읽기). 400일까지, 과제명 머리(`[과제명]`)로 나눠 `parseNetcusWeekly` 가 과제별 묶음을 만든다. 호스트가 돌려주는 `plan`(차주계획)은 지금 **버려진다**.
- **회사로 쓰는 경로**(월간보고에서 절대 쓰지 않음): `netcusSubmit`(실제 등록 POST), `netcusWeekSubmit`(작성 화면을 열고 채움). 둘 다 `Platform.report` 를 거친다.
- **공식 과제** `project` 표(`db/deploy/schema-structure.sql`:92): `project_name`(사업명), `contract_name`, `common_name`(통상명칭), `start_date`/`end_date`(계약), `dev_end_date`(개발종료일), `status_id`. 웹에서는 `dbCatalog` 항목 `{startDate, endDate, devEndDate, commonName, ...}`. **담당자, 과제 코드 칸은 없다.**
- **개인 기록과 과제의 연결**: 공식 과제를 구독하면 카테고리 id 가 `db-<uid>` 가 된다(`subscribeDbCat`, HTML:9526). 일정의 `categoryId` 가 곧 과제 연결이다.
- **일정 칸**: 제목, 날짜, 끝 날짜, 시간, `location`(장소), 메모, `source`('git'), `commits`. **종류(회의, 구현) 칸과 참석자 칸은 없다.** 이슈 #14 도 종류 선택을 넣지 않기로 했다.
- **파일 쓰기 선례** `widget/XlsxWriter.cs`: 외부 패키지 없이 `System.IO.Compression.ZipArchive` 로 OOXML 을 직접 쓴다. 흐름은 JS `hostRequest('exportProjectsXlsx')` → 호스트 `SaveFileDialog` → `Task.Run` 으로 쓰기 → `ReplyOnUi`(MainWindow:950, :1452). 패키지는 WebView2 와 MySqlConnector 뿐이다(`net9.0-windows`).
- **DOCX 관련 코드나 템플릿은 저장소에 없다.**
- **보고서 저장**: `cal_report_weekly.plan` 에 주간 차주계획이 저장되지만 읽어 오는 코드는 없다. 보고 초안은 localStorage(`tc_rptDraft:`, `tc_rptDraftW:`, 계정별, 14일 보관).

## 4. 칸과 데이터 연결

**원칙(사용자 결정 2026-10-22, 2026-10-23 보강): 문서에 채우는 것은 수행 실적 본문과 개발 일정 그림뿐이다.** 실적은 기존 취합 결과를 과제별로 그대로 옮겨 붙인다. 수행 계획 두 칸과 일정 변경이력은 **문서에 빈칸으로** 들어가고 사용자가 Word 에서 채운다(화면에서 쓰지 않는다). 화면은 고치는 칸 없이 모으기와 미리 보기만 한다(11.3).

| 양식 칸 | 채우는 곳 | 비고 |
|---|---|---|
| 제목의 이름 | 로그인 계정의 표시 이름 | 화면에서 읽기만 |
| 제목의 날짜 | 작성일, 기본 오늘 | 고르는 칸(날짜) |
| 과제명 | 정한 공식 이름: 통상명칭, 없으면 사업명(카테고리 이름과 같은 규칙, 11.2 의 4번) | 고치지 않는다 |
| 과제 수행 기간 | **DB 의 과제 개발기간**: 새 칸 `project.dev_start_date ~ dev_end_date` 를 `YYYY/MM` 로 | 개발 시작일 칸은 새로 만든다(6.5). 개발 시작, 종료의 기본값은 계약 날짜에서 한 달씩 안쪽이다(새 과제는 폼이 채우고, 기존 과제는 one-off SQL 로 채운다. 6.5). 한쪽이 비면 그쪽만 빈칸으로 둔다(계약 날짜로 대신하지 않음) |
| 월간 실적 기간 | **사용자가 읽어 온 기간 그대로**(월간 탭의 실적 기간) | 모든 과제 표에 같은 값 |
| 월간 계획 기간 | **사용자가 고르는 기간** | 기본값을 미리 넣어 두되(5.2) 자유롭게 바꿈 |
| 개발 일정 | **DB 에 사람마다, 과제별로 등록한 그림**(사람마다 과제당 5장) | 내 그림만 보고 넣고 지운다(2026-10-23). 과제 고르기 줄에서 다룬다(5.3) |
| 일정 변경이력 | **빈 줄 하나**(양식과 같음) | Word 에서 사용자가 쓴다. payload `changes: []` |
| 왼쪽 수행 계획 | **빈칸** | Word 에서 사용자가 쓴다. payload `prevPlan: []` |
| 수행 실적 | 실적 기간 취합 결과 중 그 과제 부분을 **그대로 붙임** | 5.3. 화면에서는 고치지 않는다 |
| 오른쪽 수행 계획 | **빈칸** | Word 에서 사용자가 쓴다. payload `nextPlan: []` |
| 기타 표 | 공식 과제가 아닌 카테고리 전부의 취합 결과를 그대로 붙임 | 뺄 카테고리를 고를 수 있다. 열 때마다 모두 넣음으로 시작하고 기억하지 않는다(16장) |
| 공수, 근태 | 양식에 칸 없음 | 문서에 넣지 않음 |

- **실적은 개인 기록만이다.** 과제 캘린더의 공용 일정(`cal_project_event`, 구조 번호 16)은 월간 실적에 넣지 않는다. 기존 보고 취합이 개인 기록(`state.entries` 등)만 읽는 것과 같은 규칙이고, 공용 일정을 개인 일정에 등록(복사)한 것은 개인 기록이라 들어간다.

## 5. 화면

### 5.1 위치

보고 모달에 **네 번째 탭 `월간 보고`**(`data-rmode="monthly"`)를 둔다(사용자 결정 2026-10-22, 우선 이 자리에 두고 보고 모달 개선 때 다시 본다). 탭을 고르면 기존 출력 영역을 숨기고 월간 전용 영역(`#rptMonthlyPane`)을 보인다.

- 보고 모달 개선은 사용자가 나중에 따로 할 예정이므로 기존 코드에는 **탭 버튼 한 개와 `setReportMode` 의 보이기/숨기기 분기만** 더한다. 나머지는 모두 `rptM` 으로 시작하는 새 함수와 `.rptm-` 로 시작하는 새 CSS 에 둔다.
- 월간 탭에는 **보내기 버튼이 없다.** 기존 `#btnRptSend` 는 월간 탭에서 숨긴다.
- **고치는 칸이 없다**(사용자 결정 2026-10-23). 화면의 입력은 고르는 것뿐이다: 실적 기간, 계획 기간, 작성일(날짜 다섯), 내용 출처, 과제 체크, 기타 넣기 빼기. 그리고 과제 줄의 개발 일정 그림 서랍. 나머지는 읽기 전용 문서 미리 보기다.
- **6주에 한 번 쓰는 가벼운 추출기다**(2026-10-23). 동작은 읽어 오기, 그림 서랍, DOCX 저장(그리고 닫기)뿐이다. 순서 바꾸기와 기억하는 값은 없다.

### 5.2 기간 고르기

- 실적 기간: 사용자가 읽어 올 시작, 끝 날짜. 이 값이 그대로 문서의 `월간 실적:` 이 된다. 기본값은 지난달 1일 ~ 말일(`monthRange` 재사용).
- 계획 기간: **사용자가 고르는 기간.** 편의상 실적 끝 다음 월요일부터 실적 기간과 같은 주 수, 금요일 끝을 미리 넣어 둔다. 예시: 실적 08/03(월) ~ 09/18(금)이면 계획 09/21(월) ~ 11/06(금). 계획 기간은 내용을 읽어 오는 데 쓰지 않고 문서 머리에만 찍힌다.
- 작성일: 기본 오늘.
- 내용 출처: **캘린더(기본) 또는 주간보고**(netcus 주간보고 게시판 읽기, 400일 한도). 기존 보고 모달의 출처 고르기와 같은 모양. netcus 일일 출처는 월간에서 쓰지 않는다(31일 한도라 월간 기간에 안 맞고, 사용자가 요청하지 않음).

### 5.3 배치: B안 두 칸과 그림 서랍(2026-10-23 결정)

시안 [prototypes/monthly-report-layout.html](prototypes/monthly-report-layout.html) 의 **B안**을 따른다(지금, A안, B안 비교에서 사용자가 B안을 골랐다). 간격과 위계도 시안을 따른다.

- **넓은 폭(보고 모달 1040px)**: 왼쪽 칸(360px)에 위에서부터 설정, 과제 목록과 그림 서랍, 기타 표, 미식별 항목(주간보고 출처일 때). 오른쪽 칸에 **늘 보이는 문서 미리 보기**. 두 칸은 따로 스크롤한다(900px 이상).
- **좁은 폭(620px 이하, 위젯 400px 아래 시트 포함)**: 맨 위 세그 **설정 | 미리 보기** 로 한 칸씩 본다. 열 때는 설정.
- **바로 바뀐다**: 왼쪽에서 바꾸면 오른쪽 미리 보기를 곧바로 다시 그린다(과제 체크, 기타 칩, 계획 기간, 작성일, 그림 목록과 미리 보기 그림, 읽어 오기 뒤의 기간과 글). 실적 기간은 읽어 오기를 눌러야 바뀐다(누르기 전에는 짧은 안내만).

1. **설정**(회색 상자): 실적(날짜 둘), 계획(날짜 둘과 ↺ 기본값으로), 작성일과 이름(로그인 이름, 읽기만), 출처(캘린더 | 주간보고)와 **읽어 오기**. 안내는 필요할 때 한 줄만(출처를 바꾸고 아직 안 읽음, 브라우저에서는 주간보고 불가), 긴 설명은 단추의 풍선 글.
2. **과제 목록**: 머리 `과제 n/m`(체크 수/전체). 구독한 공식 과제(`db-` 카테고리)를 **내 과제(카테고리) 순서 그대로** 나열한다. 이 탭에서는 순서를 바꾸지 않는다(▲▼ 없음, 순서는 내 과제 창에서). 줄마다 체크, 공식 이름, 기록이 없을 때만 `기록 없음`, 그림 단추(위젯만). 처음 체크는 실적이나 계획 기간에 기록이 있는 과제.
3. **그림 서랍**(내 그림, 나만 봄. 그림은 사람마다 DB 에 있어 다시 열어도 `그림 n` 이 보인다):
   - 단추는 그림이 있으면 `그림 n ▾`, 없으면 `+ 그림`. 누르면 줄 아래로 서랍이 열린다.
   - 서랍 머리 `개발 일정 그림 n/5` 와 `나만 봅니다 ⓘ`(긴 설명은 이 풍선 하나: 형식과 크기, 장 수, Ctrl+V, 나만 봄).
   - 그림 카드: 번호, ◀▶ 순서(서랍 안에서만), ✕ 삭제(확인 창). 넣은 시각은 카드 풍선.
   - 넣기 칸: **파일 고르기**, **붙여넣기**, `또는 Ctrl+V`. 5장이면 넣기 칸이 없다.
   - **Ctrl+V**: 포커스가 그 과제 줄이나 서랍 안에 있거나 마우스가 그 위에 있으면 그 과제의 클립보드 그림 넣기. 날짜 칸 같은 글 칸, 다른 창이 위에 있을 때, 월간 탭이 아닐 때는 그대로 둔다. 넣으면 그 줄의 서랍을 연다.
   - 그림 목록은 체크와 상관없이 목록의 과제마다 읽는다(단추에 장 수). 끊기면 사본 목록과 안내, 넣기, 지우기, 순서는 막는다. 브라우저에서는 그림 단추가 없다(위 안내 줄만).
4. **기타 표**: 처음은 한 줄 요약(`n개 모두 넣음`, 뺀 것이 있으면 `넣은 수/전체`). **고르기**를 누르면 칩으로 펼쳐 넣고 뺀다(접기로 다시 접음). 기억하지 않는다.
5. **미식별 항목**(주간보고 출처): 왼쪽 칸 기타 아래, 과제를 고르는 자리에서 본다. 머리 `미식별 항목 n 문서에 넣지 않음`, 항목마다 `[머리 이름]` 과 첫 줄, 펼치면 글. 읽기만 하고 문서에 없다(14장).
6. **문서 미리 보기(오른쪽 칸, 읽기 전용)**: 회사 양식을 화면에 비슷하게 그린 종이(폭 1000px)를 칸 폭에 맞춰 줄여 보인다(CSS zoom). 머리 `미리 보기 읽기 전용`(풍선: 계획 칸과 변경이력은 Word 에서)과 `과제 n개, 기타 표`. 체크한 과제마다 내 과제 순서대로 공식 과제명, 과제 수행 기간, 그림(미리 보기 그림), 수행 실적, 그리고 기타 표. 수행 계획 두 칸과 일정 변경이력(빈 줄 하나)은 문서처럼 비어 있다. 저장 payload 로 그리므로 문서와 같은 값이다. 아무것도 안 고르면 안내 한 줄. 아래 상태 줄은 `과제 n개와 기타 표를 저장합니다`.
7. **실적 채우기 규칙: 그대로 붙이기.**
   - **상세 내용은 기존 보고 모달 아래쪽에 나오는 글을 그대로 복사해 온다**(사용자 결정 2026-10-22). 새로 만들거나 분류하거나 다듬지 않는다.
     - 캘린더 출처: 같은 실적 기간의 기간 취합 결과(`collectReportData` 와 기존 글 만들기 함수 `buildReportText`)에서 그 과제(카테고리) 부분.
     - 주간보고 출처: 같은 기간의 netcus 주간보고 취합 결과(`netcusWeeklyRangeRead` 와 `buildNetcusWeeklyText`)에서 그 과제 부분.
   - 과제(카테고리)별로 자르는 것만 월간 쪽 일이다. 사용자가 이미 쓰는 보고 서식 설정(글머리, 들여쓰기)도 그대로 따른다.
   - 보고서 묶음(한 카테고리를 다른 카테고리 아래로 접기)은 월간에서 쓰지 않는다. 과제 단위가 표 단위이기 때문이다.
   - 문서로 옮길 때 줄 앞 들여쓰기 깊이를 문단 들여쓰기로 바꿔 Word 에서도 단계가 보이게 한다. 글자 자체는 바꾸지 않는다.
   - 글은 저장해 두지 않고 늘 기록에서 모은다. 탭을 열 때, 읽어 오기를 누를 때 다시 모은다.
8. **읽어 오기**: 다른 기간이면 그 기간을 새로 연다(체크는 그 기간의 기록 있음, 출처와 기타에서 뺀 것은 이 탭을 연 동안 이어 받는다). 같은 기간이면 지금 출처로 다시 모은다. 덮을 고친 글이 없으므로 확인 창을 띄우지 않는다.

### 5.4 기억하지 않음(2026-10-23 다시 바꿈)

- **기억하는 값이 없다**(사용자 결정 2026-10-23). 이 탭은 localStorage 를 읽지도 쓰지도 않는다. 열 때마다(탭을 다시 고를 때마다) 처음 값으로 연다:
  - 실적 기간 = 지난달 1일 ~ 말일, 출처 = 캘린더, 기록 있는 과제만 체크, 기타 = 모두 넣음(접힘), 계획 기간 = 기본값(5.2), 작성일 = 오늘, 좁은 폭 세그 = 설정.
- 같은 날 먼저 정했던 `tc_rptMSel:<who>`(고른 것)와 `tc_rptMEtcOff:<who>`(기타 제외)는 없앴다. 예전 키(`tc_rptMSel:`, `tc_rptMEtcOff:`, 초안 `tc_rptDraftM:`, 기억한 이관 `tc_rptMNcMap:`)는 남아 있어도 읽지 않는다. 지우려고 저장소를 건드리지도 않는다(해가 없다).
- **그림만 남는다**: 그림은 사람마다 DB(`project_schedule_image`)에 있으므로 다시 열어도 과제 줄에 `그림 n` 이 보인다.

## 6. 개발 일정 그림(DB 보관)

개발 일정은 사람이 만들어 넣는 그림이다(제안서나 계획서의 간트 차트를 잘라 만든 것). 앱에는 단계와 마일스톤 데이터가 없으니 자동으로 그리지 않는다. **그림은 사람마다 따로 DB 에 둔다**(사용자 결정 2026-10-23, 처음 결정 2026-10-22 의 '과제마다 공용'을 바꿨다). 그림마다 주인이 한 사람이고, 주인만 자기 그림을 보고 넣고 지우고 순서를 바꾼다. DOCX 에도 저장하는 사람의 그림만 들어간다. 같은 과제를 쓰는 다른 사람의 그림은 보이지 않는다.

### 6.1 권한

- **내 그림은 내가**: 앱 사용자라면 누구든 자기 그림을 어느 공식 과제에든 넣고 지우고 순서를 바꿀 수 있다. 관리자 권한 검사는 하지 않는다.
- **남의 그림은 없는 것과 같다**: 호스트의 모든 그림 SQL 이 세션의 사람(`user_id`)을 건다. 목록, 미리 보기, 받기는 내 그림만 돌려주고, 남의 그림 번호로 지우거나 옮기면 없는 번호와 똑같이 `notFound` 다(있는지 알리지 않는다). 추가는 세션의 사람을 주인으로 쓴다(웹 값이 아니다).
- 과제 줄의 그림 칸에는 등록자를 보이지 않고 넣은 시각만 보인다. 안내는 "내 보고서에 넣을 그림(나만 봅니다)". 삭제는 확인 창을 거친다.
- 권한(GRANT)은 표 단위라 그대로다(SELECT, INSERT, UPDATE, DELETE). 행을 가르는 것은 앱이다.
- PC 사본: 바이트는 해시 이름 그대로(같은 그림이면 한 벌), 목록 색인은 (로그인 id, 과제)별이다. 한 PC 를 둘이 써도 끊겼을 때 남의 목록이나 그림이 보이거나 문서에 들어가지 않는다.
- 삭제는 실제 행 삭제다(휴지통 없음). 실수로 지운 것은 백업에서 되살리거나 다시 올린다. 되살리기가 필요하면 11.2 의 1번.

### 6.2 표

새 표 `project_schedule_image`(사람마다, 공식 과제마다의 그림). 정본은 `schema-calendar.sql` 의 16번 표다(구현 때 정함, 12장):
`project`(schema-structure.sql)와 `app_user`(회사 01-schema-users.sql)를 둘 다 FK 로 가리키는데, 새 서버 구축 순서가
structure, users, calendar 라 두 부모가 모두 있는 파일은 calendar 하나뿐이다. 과제 캘린더 표(구조 16)도 같은 이유로 거기 있다.

| 칸 | 형 | 뜻 |
|---|---|---|
| `id` | INT UNSIGNED PK | |
| `user_id` | SMALLINT UNSIGNED, FK `app_user(user_id)` ON DELETE RESTRICT | 주인(이 사람만 보고 고치며 이 사람 문서에만 들어간다) |
| `project_id` | INT UNSIGNED, FK `project(id)` ON DELETE CASCADE | 과제(따로 색인) |
| `seq` | TINYINT UNSIGNED | 주인의 그 과제 안 순서(1부터, 지우면 1..n 으로 다시 매김) |
| `mime` | VARCHAR(20) | `image/png` 또는 `image/jpeg`(CHECK) |
| `bytes` | MEDIUMBLOB | 그림 원본(16MB 한도, 앱은 장당 5MB로 제한) |
| `width_px`, `height_px` | SMALLINT UNSIGNED | 문서에 넣을 때 비율 계산용(1 이상, CHECK) |
| `sha256` | CHAR(64) ascii | PC 사본 캐시 확인용(소문자 16진수 64자) |
| `uploaded_at` | DATETIME(3) | 등록 시각(UTC) |

- 사람마다 과제당 최대 5장(앱에서 막음). `(user_id, project_id, seq)` 유일. 같은 그림(해시) 거절도 같은 사람, 같은 과제 안에서만이다(다른 사람은 같은 그림을 넣을 수 있다). 순서를 바꾸는 동안 잠깐 101 이상을 쓰므로 DB CHECK 는 `seq >= 1` 만 건다. UNIQUE 의 맨 앞 열이 `user_id` 라 과제 FK 열(`project_id`)에는 따로 색인을 둔다.
- **주인 FK 는 RESTRICT 다.** 사용자 영구 삭제(휴지통)는 기록 0건인 계정만 지운다(`ProjectDb.UserRecordTables`, TRASH-DELETE §3.2). 다른 `cal_*` 기록 표와 똑같이 이 표도 그 기록 표 목록에 넣었다(`project_schedule_image.user_id`, `표.열` 로 적는다). 그래서 그림이 있는 사람은 퇴사 처리(숨김)만 되고, 지우려면 그 사람의 기록(그림 포함)을 먼저 지운다. CASCADE 는 사람과 함께 기록이 조용히 사라져서 쓰지 않는다.
- **과제 FK 는 CASCADE 다.** 과제를 영구 삭제하면 모든 사람의 그 과제 그림이 함께 지워진다.
- 구조 번호 17 은 아직 배포 전이라(2026-10-23) 새 번호를 쓰지 않고 v17 조각과 정본을 그 자리에서 고쳤다. 옛 정의로 이미 17 이 된 개발 DB 는 표를 지우고 새 정의로 다시 만든다(그 시험 그림은 버린다).
- 크기: 그림은 보통 100KB~1MB. MySQL 8 의 기본 `max_allowed_packet`(64MB)에 걸리지 않는다. 서버 값이 더 작게 바뀌어 있으면 올리기가 실패하므로, 실패 메시지에 원인을 그대로 보여 준다.

### 6.3 읽고 쓰기

- 호스트 명령 `scheduleImageList(projectUid)`(내 그림의 메타만: id, seq, 크기, 해시, 시각), `scheduleImageGet(id)`(바이트), `scheduleImageAdd(projectUid, 파일 또는 붙여넣은 그림)`, `scheduleImageDelete(id)`, `scheduleImageMove(id, seq)`.
- **과제 목록(`loadProjects`)에 그림을 싣지 않는다.** 월간 탭의 과제 고르기 줄을 그릴 때 메타만 읽고, 바이트는 해시가 PC 사본과 다를 때만 받아 앱 데이터 폴더 `schedule-images\<sha256>.png|jpg` 에 둔다.
- 넣는 방법: 과제 줄의 그림 칸에서 **붙여넣기**(잘라 복사한 그림, 그 줄에서 Ctrl+V 도) 또는 `파일 고르기`(PNG, JPG). 호스트가 WPF `BitmapDecoder` 로 형식과 가로세로를 확인하고, 그림이 아니면 거절한다.
- DOCX 저장 때 호스트가 PC 사본(없으면 DB)에서 바이트를 읽어 넣는다. 웹과 호스트 사이로 큰 바이트를 오가게 하지 않는다. 웹에는 미리 보기용 작은 그림만 넘긴다.
- 문서에서는 셀 폭(약 570pt에서 안쪽 여백을 뺀 값)에 맞춰 비율 유지로 줄이고, 여러 장이면 위에서 아래로 차례로 놓는다. 그림이 없으면 칸을 비워 둔다(양식과 같음).
- DB 가 끊겨 있으면 PC 사본으로 저장은 하고, 추가와 삭제는 막는다.

### 6.4 배포와 운영

- **구조 번호 16 에서 17.** 16 은 과제 캘린더(이슈 #14)가 먼저 가져갔다. 그림 표와 개발 시작일 칸(6.5)을 한 조각 `db/deploy/migrations/v17-monthly-report.sql` 에 담는다. 정본은 `schema-calendar.sql`(그림 표, 시드 17)과 `schema-structure.sql`(개발 시작일 칸과 CHECK). 지금 규칙대로 Workbench 에서 돌리는 순수 `.sql`(release SQL 에 묶여 나간다), Setup 먼저 올리고 SQL(버전 게이트 정책).
- 권한: 앱 계정에 이 표의 SELECT, INSERT, UPDATE, DELETE. 정본 권한 파일은 schema-calendar.sql 의 짝인 `grants-calendar.sql`, 서버 계정은 `server-app-account.sql`, 개발 PC 최소 권한 계정은 `app-account.ps1`(표가 있을 때만). 사용자 삭제와의 관계는 6.2 끝.
- **백업**: `backup-taskmgr.ps1` 의 mysqldump 에 `--hex-blob` 을 넣었다(복원 전 안전 덤프 `restore-taskmgr.ps1`, 데모 전 백업 `demo-db.ps1` 도). 백업 크기는 그림 양만큼 는다(과제 수 x 몇 MB 수준).

### 6.5 개발 시작일 칸(같은 조각에 함께)

- `project` 표에 `dev_start_date DATE NULL`(개발시작일, 미정=NULL)을 `dev_end_date` 앞에 더한다(`end_date` 와 `dev_end_date` 사이). 개발종료일과 짝이다.
- 그림 표와 **같은 마이그레이션 조각, 같은 구조 번호**에 넣는다. 번호를 두 번 올리지 않기 위해서다.
- 개발종료일이 이미 지나가는 길을 그대로 따라 붙인다: 과제 읽기(`ProjectDb.cs`), 웹 `dbCatalog` 의 `devStartDate`(`mapDbRows`), 관리 화면 과제 편집 칸, 과제 xlsx 내보내기 열(`ProjectExportCols`). CHECK 로 시작일이 종료일보다 늦지 않게 막는다(둘 다 있을 때만).
- 관리 화면은 별도 창(ADMIN-WINDOW)으로 옮겨 갔다. 편집 폼은 같은 HTML(`#officialEditModal`)이라 개발종료 칸 옆 빈자리에 개발시작 칸을 넣으면 관리 창에 그대로 뜬다.
- 개발시작일도 선진행 잠금에 넣지 않는다(개발종료일과 같은 이유).
- **기본값 규칙(2026-10-23 사용자 결정).** 개발 시작일 = 계약 시작일 + 1달, 개발 종료일 = 계약 종료일 - 1달. 그 달에 같은 날이 없으면 그 달 말일이다(MySQL `DATE_ADD`/`DATE_SUB ... INTERVAL 1 MONTH`: 01-31 + 1달 = 02-28, 윤년은 02-29, 03-31 - 1달 = 02-28/29).
  - **새 과제:** 관리 창의 공식 과제 폼에서 새 과제를 등록할 때, 계약 시작일이나 계약 종료일을 고르거나 바꾸면 개발 날짜를 채운다(`offEdAutoDev`). 개발 날짜는 각자 자기 계약 날짜에서 계산하므로 한쪽만 있어도 된다. 채우면 칸 아래에 "계약 기간에서 자동으로 채웠습니다. 바꿀 수 있습니다." 를 보인다.
  - 손으로 넣거나 고르거나 지운 개발 날짜 칸은 그 폼을 연 동안 다시 채우지 않는다(개발 날짜를 먼저 넣고 계약 날짜를 골라도 그대로다). 둘 다 손대면 안내가 사라진다.
  - 채운 결과가 시작 > 종료면 아무것도 채우지 않고(손대지 않은 칸은 비운다) 짧은 안내만 보인다. CHECK 가 시작 <= 종료를 요구한다.
  - 기존 과제 편집에서는 채우지 않는다. 호스트, DB, 저장 길은 바꾸지 않았다(시험 `tests/dev-dates-default.test.mjs`).
  - **기존 과제:** `db/deploy/oneoff/dev-dates-from-contract.sql` 을 Workbench 에서 앱 계정으로 한 번 돌린다(미리 보기, 트랜잭션 UPDATE, 결과, 건너뛴 과제와 이유). 개발 날짜가 둘 다 NULL 이고 계약 날짜가 둘 다 있고 계산한 시작 <= 종료인 행만 채우므로 다시 돌려도 안전하다. 구조 번호를 올리지 않고, 구조 17 이상이 필요하다. 배포 SQL(release-v)에는 묶이지 않는다(묶이는 것은 `db/deploy/migrations/` 뿐). 건너뛴 과제는 손으로 넣는다.

## 7. DOCX 생성

### 7.1 방식

`widget/DocxWriter.cs` 를 새로 만든다. `XlsxWriter.cs` 와 같은 원칙이다. **외부 패키지 없음**(폐쇄망은 NuGet 을 못 받는다), `ZipArchive` 로 WordprocessingML 을 직접 쓴다.

템플릿 처리 방식 비교:

- **코드로 생성(추천)**: 표 구조(열 병합, 세로 병합, 이력 줄 수, 과제 수)가 매번 달라서 어차피 코드가 표를 만들어야 한다. 원본 양식 `.docx` 의 표 XML 을 복제하고 칸을 찾아 채우는 방식은 원본 내부 구조(셀 병합 표기, 숨은 서식 조각)에 기대게 되어 약하다.
- 원본 양식 `.docx` 는 폐쇄망 밖으로 가져오기 어려워 **2장의 PDF 측정값을 상수로 쓴다**(11장 1번). 숫자 보정은 사용자가 폐쇄망 Word 에서 읽어 준 값으로 한다.
- 빈 양식(PDF 또는 원본 docx)은 저장소에 둘 수 있다. 시험의 비교 기준과 문서용으로 `docs/assets/monthly-report-form.*` 에 둔다. **실제 보고서는 저장소에 두지 않는다.**

### 7.2 만들 부품

- `[Content_Types].xml`, `_rels/.rels`, `docProps/core.xml`, `docProps/app.xml`
- `word/document.xml`: 본문
- `word/styles.xml`: 기본 글꼴 맑은 고딕 10pt(`w:rFonts` ascii, hAnsi, eastAsia 모두), 줄 간격, 표 기본 서식
- `word/settings.xml`: 최소 설정
- `word/_rels/document.xml.rels`, `word/media/imageN.png|jpg`

### 7.3 본문 구조

- 구역 설정: `w:pgSz w=16838 h=11906 orient=landscape`, 여백은 양식 측정값(왼쪽 약 85pt, 오른쪽 약 66pt) 또는 원본 docx 값.
- 제목 문단(가운데, 굵게, 12pt, 밑줄), 빈 문단.
- 과제마다 표 하나(`w:tblGrid` 7열, 2.3 의 병합은 `w:gridSpan` 과 `w:vMerge`), 표 뒤 빈 문단.
- 마지막에 기타 표.
- 칸 이름 셀은 `w:shd` 로 배경색, 가운데 정렬, 굵게.
- 본문 칸: 줄마다 문단 하나. 단계별 왼쪽 들여쓰기와 내어쓰기(`w:ind`). 글자는 붙인 그대로 두고 굵게 같은 꾸밈은 하지 않는다(사용자가 Word 에서 다듬음).
- 그림: `w:drawing` 안 `wp:inline` 그림, 크기는 EMU.
- 표는 쪽을 넘겨 이어질 수 있게 둔다(실제 보고서도 과제 하나가 두 쪽에 걸친다). 칸 이름 줄만 `w:cantSplit`.
- 모든 글자는 XML 이스케이프. 제어 문자 제거.

### 7.4 호스트 명령

- `exportMonthlyDocx`: 웹이 `hostRequest('exportMonthlyDocx', payload, 300000)`. 호스트는 `SaveFileDialog`(소유 창 = 요청한 창) → `Task.Run(DocxWriter.Write)` → `ReplyOnUi`. 응답 `{ok, path, dir} | {cancelled} | {error}`. `RunProjectsXlsxExport` 와 같은 모양.
- 그림 명령 `scheduleImageList/Get/Add/Delete/Move`: 6.3.
- payload 는 그림 바이트 없이 글과 구조만: `{name, reportDate, actual:{from,to}, plan:{from,to}, projects:[{uid, title, term, changes:[{what,date,why}], prevPlan, actual, nextPlan}], etc:{lines}}`. 2026-10-23 부터 웹은 `changes`, `prevPlan`, `nextPlan` 을 늘 빈 배열로 보내고 `title` 은 공식 이름이다. 호스트 계약은 그대로 둔다(값이 와도 쓰고, 비면 양식대로 빈칸과 변경이력 빈 줄 하나). 본문은 `{level, text, bold}` 줄 배열로 보낸다. level 은 웹에서 줄 앞 들여쓰기 깊이로 정한다(글자는 그대로). 그림은 호스트가 `uid` 로 찾아 넣는다.
- 새 호스트 코드는 `widget/MonthlyReportExport.cs`, `widget/ScheduleImageDb.cs`(partial 또는 별도 클래스)에 모으고 `MainWindow.xaml.cs` 분기에는 case 한 줄씩만 더한다. 다른 브랜치와 겹침을 줄이기 위해서다.

## 8. 진행 중인 다른 작업과의 관계

- **관리 화면 별도 창**(`docs/ADMIN-WINDOW.md`, `.claude/worktrees/admin-window` 개발 중): 보고는 그 범위 밖이다. 다만 새 호스트 명령은 그 문서의 규칙(요청 창 기준 응답 전달, 파일 창 소유자 = 요청한 창)을 따른다. 월간과 그림 명령은 관리 창 허용 목록에 넣지 않는다. 두 작업이 `MainWindow.xaml.cs` 명령 분기를 함께 고치므로 **나중에 합치는 쪽이 분기 충돌을 정리**한다.
- **이슈 #14**(과제 캘린더, 2026-10-22 병합): 공용 일정은 보고에서 뺀다. 월간 실적 붙이기도 같은 규칙(공용 일정 제외, 4장 끝). 과제 캘린더가 구조 번호 16 을 가져갔고 이 기능은 17 이다.
- **버전 게이트**(`docs/VERSION-GATE.md`, 구조 번호 16 에서 17): 앱의 `AppStructureVersion` 과 정본 시드를 17 로 함께 올렸다. 배포는 Setup 먼저, 그다음 SQL(정책 그대로). 앱 버전은 마이너 상향(기능 추가).
- **보고 모달 개선(사용자가 나중에 할 일)**: 5.1 대로 기존 코드 접점을 탭 버튼과 `setReportMode` 분기로 묶어 둔다. 기존 함수(`collectReportData`, `rptSources`, 기존 글 만들기 함수, `monthRange`)는 **읽기만 하고 바꾸지 않는다.** 과제별로 자르는 일은 월간 쪽 감싸는 함수에서 한다.

## 9. 단계

1. **DocxWriter 와 호스트 저장 명령**(2026-10-22 DocxWriter, 목업 도구 `tests/tools/monthly-docx-mock`, 시험 `monthly-docx.test.mjs`, `loop-monthly-docx.mjs` 까지 됨. 호스트 저장 명령은 아직): 지어낸 예시 payload(그림 포함)로 양식과 같은 문서가 나오는 것까지. 화면과 DB 없음, 단독 검증 가능.
2. **DB 조각(그림 표 + 개발 시작일 칸)과 그림 명령**: 마이그레이션 조각 하나, 구조 문서, 권한, 백업 `--hex-blob`, 과제 읽기와 관리 화면의 개발 시작일, 그림 호스트 명령, PC 사본 캐시.
3. **월간 탭**: 기간(실적은 읽어 온 기간, 계획은 고름), 과제 고르기, 실적 붙이기, 그림 추가와 삭제, DOCX 저장. 캘린더 출처. (2026-10-23 결정으로 직접 쓰는 칸과 초안을 없애고 모으기와 미리 보기로 바꿈, 15장)
4. **주간보고 출처**: netcus 주간보고 취합 결과를 과제별로 잘라 실적 칸에 붙인다(읽기만).

1단계와 2단계는 서로 기대지 않으므로 따로 진행할 수 있다. 3단계는 둘 다 필요하다.

### 11.3 결정(2026-10-23, 사용자): 월간 탭은 모으기와 미리 보기만

11.1 의 4번, 9번, 10번과 5장, 14.2 의 이관 부분을 아래로 바꾼다.

### 13.1 시안과 다른 점

- **이름 칸을 고칠 수 있다.** 시안은 읽기 전용, 4장 표는 "고칠 수 있음". 표를 따랐다(기본은 로그인 계정 표시 이름, 초안에 남는다).
- **그림 넣기**: 끌어다 놓기 대신 **파일 고르기**와 **붙여넣기** 두 버튼(단계 A 의 file, clipboard). 그림 칸을 눌러 포커스를 둔 뒤 Ctrl+V 도 클립보드 넣기다.
- **읽어 오기 확인**: 시안은 고친 실적이 있을 때만 묻는데, 같은 기간 다시 읽어 오기는 늘 묻는다(브리프 6번).
- **실적 표시 꼬리표**는 지금 고른 출처가 아니라 실제로 붙인 출처(`fillSrc`)를 말한다. 출처만 바꾸고 아직 안 읽었으면 출처 안내 줄이 "읽어 오기를 누르면 바꿉니다" 라고 덧붙인다.
- **기타 카테고리를 바꿀 때** 기타 본문을 고쳐 두었으면 덮기 전에 묻는다(시안은 그냥 덮었다).
- **과제 수행 기간 안내**: 서버에서 과제 정보를 못 읽은 경우(오프라인, 브라우저) 문구를 하나 더 두었다.

## 14. 주간보고 과제 나누기 정책(사용자 결정 2026-10-23)

주간보고 출처(netcus 주간보고 게시판 읽기)는 글이 `[과제명]` 머리로 나뉘어 온다. 그 머리를 월간 카드와 기타 표로 나누는 규칙이다. 캘린더 출처는 카테고리 id 로 나누므로 이 장과 상관없고 미식별 항목도 생기지 않는다. netcus 는 지금처럼 읽기만 한다(`netcusWeeklyRangeRead`).

### 14.1 맞추기

- **내 카테고리에만 맞춘다**(state.categories). 내 카테고리에 없는 공식 과제(`dbCatalog` 에만 있는 과제)는 이름이 같아도 맞지 않는다.
- 이름 비교는 `parseNetcusWeekly` 와 같은 정규화(NFC, 공백 전부 제거)다.
- **공식 과제**: 카테고리 이름, 그리고 `dbCatalog`(`mapDbRows`)가 들고 있는 그 과제의 표시 이름(통상명칭, 없으면 사업명), `commonName`(통상명칭), `projectName`(사업명) 가운데 하나와 같으면 그 과제 카드의 실적으로 간다.
- **개인 카테고리**: 이름이 같으면 기타 표로 간다. 기타의 넣기, 빼기 칩이 그대로 듣는다(이 탭을 연 동안만, 16장).
- 두 카테고리가 같은 이름을 가지면 내 카테고리 순서의 앞쪽이 이긴다.

### 14.2 미식별 항목(2026-10-23 바꿈)

- 어느 것에도 맞지 않은 머리는 **미식별 항목** 칸(B안: 왼쪽 칸 기타 아래)에 머리 이름, 첫 줄, 글로 보인다. 칸 전체와 항목마다 접을 수 있고(`details`) 읽기만 한다. **문서에 넣지 않는다**(payload 에 없다). 예전의 기타 `(미등록)` 항목은 없앴다.
- **이관, 다음에도 이 과제로, 기억한 이관 목록과 해제는 없앴다.** `tc_rptMNcMap:<who>` 는 읽지도 쓰지도 않는다. 예전에 기억해 둔 값이 남아 있어도 무시하므로 그 머리도 미식별로 나온다. 미식별 글을 문서에 넣고 싶으면 Word 에서 붙이거나, 주간보고의 머리 이름이나 내 카테고리 이름을 맞춘다.
- 칸 위 출처 안내와 읽은 뒤 안내가 미식별 개수를 말한다.

- 상태 `__rptM = { v, from, to, src, fillSrc, pFrom, pTo, planEdited, date, order, checked }`. 글은 들고 있지 않다. 실적 글은 `rptMAuto(S)`(캘린더는 `__rptMCal` 캐시, 주간보고는 `__rptMWeek`)에서 매번 읽는다. 탭을 다시 열면 캘린더 글을 지금 기록으로 다시 모으고, 주간보고 글이 그 기간 것이 아니면 캘린더로 보인다(`fillSrc`).
- 기억 `rptMSelLoad`, `rptMSelSave`(`tc_rptMSel:<who>`, PEER 관문과 try). 작성일은 기억하지 않는다.
- payload: `projects[i] = { uid, title: 공식 이름, term, changes: [], prevPlan: [], actual: rptMLines(모은 글), nextPlan: [] }`, `name` = 로그인 이름. 호스트(`MonthlyReportPayload.Parse`, `DocxWriter`)는 바꾸지 않았다. 빈 배열이면 빈칸과 변경이력 빈 줄 하나를 쓴다.
- 저장 막기(`rptMCheck`): 주간보고를 읽는 중, 실적 기간을 바꾸고 안 읽음, 기간과 작성일 형식, 넣을 과제와 기타가 모두 없음.

### 15.4 없앤 것

CSS 의 카드, 변경이력 행, 세 본문 칸, 이관과 기억 목록 규칙.
- 시험: 예전 MW6(계획과 변경이력을 다시 읽어 오기가 덮지 않음), MW9 의 초안 6건, MW18(한 번만 이관), MW19(기억한 이관), 카드 실적 다시 읽어 오기 확인 창. 대신 MS7, MS8, 새 MW6, MW9, MW18 이 고치는 칸 없음, 빈 계획과 변경이력, 고른 것 기억, 예전 키 무시를 지킨다.
