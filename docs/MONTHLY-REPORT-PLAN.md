# 월간보고 DOCX 내보내기 기획

작성 2026-10-22. 상태: 기획(구현 전). 브랜치 `feat/monthly-report-plan`.

## 1. 목표

회사 월간보고는 과제별로 쓴다. 지금은 사람이 캘린더와 근태 사이트(netcus)를 보며 Word 양식 표를 손으로 채운다.
이 기능은 **지정 기간의 캘린더 기록(필요하면 netcus 읽기 결과)을 과제별로 모아 회사 양식 그대로의 표에 채워 `.docx` 로 저장**한다.

- 하는 일: 기존 기록을 읽어 양식 칸에 채운다. 저장 전에 과제별로 미리 보고 고칠 수 있다.
- 하지 않는 일: 회사 사이트로 보내기, 기록 원본(일정, 할 일) 수정, 새 DB 표 추가(1차 범위에서는).
- 결과물: Word 문서(`.docx`). PDF 가 아니다. 사용자가 받은 뒤 Word 에서 마저 다듬을 수 있어야 한다.

## 2. 양식 분석

입력 두 가지를 봤다. 빈 양식 PDF(1쪽)와 사용자가 실제로 쓴 월간보고 PDF(7쪽). 실제 보고서의 과제명, 동료 이름, 본문은 **저장소에 옮기지 않는다**. 아래 예시 값은 모두 지어낸 `(예시)` 값이다.

### 2.1 원본과 페이지

- 빈 양식 PDF 의 문서 제목 메타데이터가 `Microsoft Word - 월간보고_양식.docx` 이다. 즉 **원본은 Word 문서**이고 한컴 PDF 로 인쇄한 것이다. 원본 `.docx` 는 폐쇄망 반출이 어려워 받지 않기로 했다(11.1 의 1번).
- 용지: **A4 가로**(841 x 595 pt).
- 글꼴: 본문 **맑은 고딕 10pt**, 칸 이름은 맑은 고딕 굵게 10pt, 제목은 맑은 고딕 굵게 12pt 가운데 정렬에 밑줄. 일부 영문은 Calibri.
- 색: 맨 윗줄(과제명, 월간 실적, 월간 계획) 배경 **#DBE5F1**(연한 파랑), 칸 이름 줄과 과제 수행 기간, 개발 일정 칸 배경 **#F2F2F2**(연한 회색), 본문 칸은 흰색. 테두리는 얇은 검정 실선.
- 실제 보고서는 사용자가 과제마다 열 폭을 조금씩 바꿔 썼다. 양식의 기준 폭을 기본으로 쓰면 된다.

### 2.2 제목 줄

`월간보고 (이름) (구분 기호) 2026년 09월 08일` 형태. 구분 기호는 양식 원본 글자를 그대로 쓴다(이 문서는 표기 규칙상 기호를 적지 않는다).

- 날짜는 **작성일**(제출일)이다. 실적 기간의 끝과 다르다. 실제 보고서도 파일 이름 날짜와 제목 날짜가 하루 달랐다.
- 실제 파일 이름 관례: `월간보고_<이름>_<YYMMDD>.docx`(예시: `월간보고_홍길동_261020.docx`).

### 2.3 과제 한 덩어리(표 하나)

과제마다 아래 표 하나가 반복되고, 표 사이에 빈 문단 하나가 있다. 빈 양식은 한 쪽에 과제 둘이 들어간다.

열 경계(pt, 왼쪽부터): 85.6, 141.9, 197.7, 317.4, 394.8, 458.3, 592.9, 775.0. 즉 **격자 열 7개**, 전체 폭 689.4pt(약 13,790 twip).

| 줄 | 내용(열 병합) | 배경 |
|---|---|---|
| 1 | 과제명(1열) / 월간 실적: MM월 DD일 ~ MM월 DD일(2~5열) / 월간 계획: 같은 형식(6~7열) | #DBE5F1, 굵게, 가운데 |
| 2 | 과제명 값(1열, **2줄부터 마지막 줄까지 세로 병합**) / 과제 수행 기간(2~3열) / `YYYY/MM ~ YYYY/MM`(4~7열) | #F2F2F2 |
| 3 | 개발 일정(2열) / 일정 그림 칸(3~7열) | #F2F2F2 |
| 4 | 일정 변경이력(2열, 아래 데이터 줄과 세로 병합) / 변경 내용(3열) / 변경 날짜(4열) / 변경 사유(5~7열) | #F2F2F2 |
| 5.. | (병합 계속) / 변경 내용 / 변경 날짜 / 변경 사유, 이력 수만큼 반복(없으면 빈 줄 1개) | 흰색 |
| 끝-1 | 수행 계획(2~3열) / 수행 실적(4~6열) / 수행 계획(7열) | #F2F2F2, 굵게 |
| 끝 | 세 칸의 본문 | 흰색 |

세 본문 칸의 뜻(실제 보고서에서 확인):

- **왼쪽 수행 계획**: 이번 실적 기간에 하려고 했던 계획. 지난 월간보고의 오른쪽 칸이 넘어오는 자리다. 실제 보고서는 모든 과제에서 비어 있었다.
- **가운데 수행 실적**: 실적 기간에 한 일. 보고서의 본체.
- **오른쪽 수행 계획**: 월간 계획 기간에 할 일.

### 2.4 맨 끝 기타 표

실제 보고서 마지막에 과제에 속하지 않는 일을 모은 별도 표가 있다. 빈 양식에는 없다.

- 1줄: 과제명 / 월간 실적: 기간(나머지 열 전체 병합), #DBE5F1.
- 2줄: `기타` / 본문(`-` 항목과 `;` 세부 줄).
- 계획 칸이 없다.

### 2.5 기간의 성질

**월간이라도 달력의 한 달이 아니다.** 실제 보고서는 실적이 7월 20일 ~ 9월 4일(약 7주, 월요일 시작 금요일 끝), 계획이 9월 7일 ~ 10월 23일(다음 월요일부터 약 7주)이었다. 보고 회의 사이 구간으로 보인다. 그래서 기간은 자유 지정이 기본이어야 한다.

### 2.6 개발 일정 칸

**표나 차트 데이터가 아니라 붙여 넣은 그림**이다(실제 보고서 쪽마다 그림 2~3개). 과제 제안서나 계획서의 간트 차트를 잘라 붙인 것으로, 과제마다 모양이 전혀 다르다(단계 막대, 주 단위 칸 표, 품질관리 행 등). 매달 거의 같은 그림을 다시 쓴다.

### 2.7 본문 쓰는 방식

실적과 계획 칸은 네 단계 들여쓰기로 쓴다.

```
▪ 구현                        (분류 머리, 굵게)
  1. 기능 보완                 (번호 묶음, 굵게, 선택)
     - 화면 응답 속도 개선      (항목)
       ; 목록 갱신 횟수 줄임    (세부)
▪ 회의
  - 중간 점검 회의 (09.15, 고객사)   (회의는 제목 뒤 괄호에 MM.DD, 장소)
▪ 기타
  - 내부 검토 자료 작성 (w. 김예시 선임)   (같이 한 사람은 w. 이름 직급)
```

- 분류 머리로 쓰인 말: **구현, 회의, 기타, 유지보수**. 실제 순서는 구현, 회의, 기타.
- 머리 글자는 원본에서 `◾`(U+25FE)였는데 이 글자는 맑은 고딕에 없어 Segoe UI Emoji 로 대체되고, PDF 몇 곳에서 **네모 칸(깨짐)** 으로 찍혔다. 생성 문서는 맑은 고딕에 있는 `▪`(U+25AA)를 쓴다.
- `-` 와 `;` 는 일반 글자로 쓰고 들여쓰기로 단계를 나타낸다. Word 자동 번호는 쓰지 않는다(사용자가 고치기 쉽게).

## 3. 현재 앱에서 쓸 수 있는 것

조사 근거는 `task-calendar-prototype.html`(이하 HTML)과 `widget/` 이다.

- **보고 모달** `#reportModal`(HTML:3193): 탭 일간 작성, 주간 작성, 기간 취합(`data-rmode=daily|weekly|custom`, HTML:3200~3202), 전환은 `setReportMode`(HTML:14802). 기간 칸 `#rptFrom/#rptTo`.
- **단일 수집 함수** `collectReportData(from,to,sources)`(HTML:14593): 내 카테고리 순서대로 카테고리마다 한 줄. 제목(일정, 할 일, 커밋 제목 중복 제거)과 세부(메모, 할 일 노트, 날짜별 노트, 커밋 본문), 공수 합계를 준다.
- **기간 프리셋** `monthRange`, `setReportRange`(HTML:14496~14500)가 이미 있다(이번 달, 지난달). 화면 버튼은 없다.
- **공수와 근태**: `state.taskHours`(날짜 x 카테고리, `cal_task_hours`), `state.attendance`(`cal_attendance`). 기간 합은 `collectReportData` 안에서 계산.
- **netcus 읽기**(읽기 전용 경로):
  - `netcusWeekMerge`(일일 업무일지 날짜별 읽기). **한 번에 31일까지.**
  - `netcusWeeklyRangeRead`(주간보고 게시판 읽기). 400일까지, 과제명 머리(`[과제명]`)로 나눠 `parseNetcusWeekly` 가 과제별 묶음을 만든다. 호스트가 돌려주는 `plan`(차주계획)은 지금 **버려진다**.
- **회사로 쓰는 경로**(월간보고에서 절대 쓰지 않음): `netcusSubmit`(실제 등록 POST), `netcusWeekSubmit`(작성 화면을 열고 채움). 둘 다 `Platform.report` 를 거친다.
- **공식 과제** `project` 표(`db/deploy/schema-structure.sql`:92): `project_name`(사업명), `contract_name`, `common_name`(통상명칭), `start_date`/`end_date`(계약), `dev_end_date`(개발종료일), `status_id`. 웹에서는 `dbCatalog` 항목 `{startDate, endDate, devEndDate, commonName, ...}`. **담당자, 과제 코드 칸은 없다.**
- **개인 기록과 과제의 연결**: 공식 과제를 구독하면 카테고리 id 가 `db-<uid>` 가 된다(`subscribeDbCat`, HTML:9526). 일정의 `categoryId` 가 곧 과제 연결이다.
- **일정 칸**: 제목, 날짜, 끝 날짜, 시간, `location`(장소), 메모, `source`('git'), `commits`. **종류(회의, 구현) 칸과 참석자 칸은 없다.** 이슈 #14 도 종류 선택을 넣지 않기로 했다.
- **파일 쓰기 선례** `widget/XlsxWriter.cs`: 외부 패키지 없이 `System.IO.Compression.ZipArchive` 로 OOXML 을 직접 쓴다. 흐름은 JS `hostRequest('exportProjectsXlsx')` → 호스트 `SaveFileDialog` → `Task.Run` 으로 쓰기 → `ReplyOnUi`(MainWindow:950, :1452). 패키지는 WebView2 와 MySqlConnector 뿐이다(`net9.0-windows`).
- **DOCX 관련 코드나 템플릿은 저장소에 없다.**
- **보고서 저장**: `cal_report_weekly.plan` 에 주간 차주계획이 저장되지만 읽어 오는 코드는 없다. 보고 초안은 localStorage(`tc_rptDraft:`, `tc_rptDraftW:`, 계정별, 14일 보관).

## 4. 칸과 데이터 연결

**원칙(사용자 결정 2026-10-22): 캘린더가 채워 주는 것은 수행 실적 본문 하나뿐이다.** 실적은 기존 취합 결과를 과제별로 그대로 옮겨 붙인다. 계획 두 칸과 일정 변경이력은 사용자가 직접 쓴다. 표 머리의 세 값은 아래처럼 정해진 곳에서 가져오거나 직접 고친다.

| 양식 칸 | 채우는 곳 | 비고 |
|---|---|---|
| 제목의 이름 | 로그인 계정의 표시 이름 | 고칠 수 있음 |
| 제목의 날짜 | 작성일, 기본 오늘 | 고칠 수 있음 |
| 과제명 | 카테고리 이름(= 통상명칭, 없으면 사업명) | 고칠 수 있음 |
| 과제 수행 기간 | **DB 의 과제 개발기간**: 새 칸 `project.dev_start_date ~ dev_end_date` 를 `YYYY/MM` 로 | 개발 시작일 칸은 새로 만든다(6.5). 개발 시작, 종료는 지금 비어 있고 **사용자가 일괄로 모두 채울 예정**(앱 밖 데이터 작업, 종료 기본은 납품일 한 달 전). 한쪽이 비면 그쪽만 빈칸으로 둔다(계약 날짜로 대신하지 않음) |
| 월간 실적 기간 | **사용자가 읽어 온 기간 그대로**(`#rptFrom ~ #rptTo` 에 해당하는 월간 탭의 실적 기간) | 모든 과제 표에 같은 값. 따로 고치지 않음 |
| 월간 계획 기간 | **사용자가 직접 고침** | 기본값을 미리 넣어 두되(5.2) 자유롭게 바꿈 |
| 개발 일정 | **DB 에 과제별로 등록한 그림**(6장) | 과제를 쓰는 사람 누구나 추가, 삭제 |
| 일정 변경이력 | **사용자 직접 입력** | 앱에 원천 데이터 없음 |
| 왼쪽 수행 계획 | **사용자 직접 입력** | 자동 채움 없음 |
| 수행 실적 | 실적 기간 취합 결과 중 그 과제 부분을 **그대로 붙임** | 5.3. 붙인 뒤 고칠 수는 있음 |
| 오른쪽 수행 계획 | **사용자 직접 입력** | 자동 채움 없음 |
| 기타 표 | 공식 과제가 아닌 카테고리의 취합 결과를 그대로 붙임 | 뺄 카테고리를 고를 수 있음 |
| 공수, 근태 | 양식에 칸 없음 | 문서에 넣지 않음 |

## 5. 화면

### 5.1 위치

보고 모달에 **네 번째 탭 `월간 보고`**(`data-rmode="monthly"`)를 둔다(사용자 결정 2026-10-22, 우선 이 자리에 두고 보고 모달 개선 때 다시 본다). 탭을 고르면 기존 출력 영역을 숨기고 월간 전용 영역(`#rptMonthlyPane`)을 보인다.

- 보고 모달 개선은 사용자가 나중에 따로 할 예정이므로 기존 코드에는 **탭 버튼 한 개와 `setReportMode` 의 보이기/숨기기 분기만** 더한다. 나머지는 모두 `rptM` 으로 시작하는 새 함수와 `.rptm-` 로 시작하는 새 CSS 에 둔다.
- 월간 탭에는 **보내기 버튼이 없다.** 기존 `#btnRptSend` 는 월간 탭에서 숨긴다.

### 5.2 기간 고르기

- 실적 기간: 사용자가 읽어 올 시작, 끝 날짜. 이 값이 그대로 문서의 `월간 실적:` 이 된다. 기본값은 지난달 1일 ~ 말일(`monthRange` 재사용).
- 계획 기간: **사용자가 직접 고치는 칸.** 편의상 실적 끝 다음 월요일부터 실적 기간과 같은 주 수, 금요일 끝을 미리 넣어 둔다. 예시: 실적 08/03(월) ~ 09/18(금)이면 계획 09/21(월) ~ 11/06(금). 계획 기간은 내용을 읽어 오는 데 쓰지 않고 문서 머리에만 찍힌다.
- 작성일: 기본 오늘.
- 내용 출처: **캘린더(기본) 또는 주간보고**(netcus 주간보고 게시판 읽기, 400일 한도). 기존 보고 모달의 출처 고르기와 같은 모양. netcus 일일 출처는 월간에서 쓰지 않는다(31일 한도라 월간 기간에 안 맞고, 사용자가 요청하지 않음).

### 5.3 과제 목록과 미리 보기

1. **과제 고르기**: 구독한 공식 과제(`db-` 카테고리)를 내 카테고리 순서로 나열하고, 실적이나 계획 기간에 기록이 있는 과제는 기본 체크. 순서는 위아래로 바꿀 수 있다.
2. **과제별 카드**(접기 가능). 각 카드에:
   - 과제명(글 칸), 과제 수행 기간(DB 값 표시, 고칠 수 있음)
   - 개발 일정 그림 칸(6장): 그림 목록, 추가, 삭제, 순서
   - 일정 변경이력 행 편집(내용, 날짜, 사유, 행 추가와 삭제). **사용자 직접 입력.**
   - 세 본문 칸: 왼쪽 계획과 오른쪽 계획은 **빈 글 칸에서 직접 쓴다.** 가운데 실적만 자동으로 채워진다.
3. **기타 카드**: 공식 과제가 아닌 카테고리 목록(넣기/빼기 체크, 계정별 기억)과 붙여진 실적 본문.
4. **실적 채우기 규칙: 그대로 붙이기.**
   - **상세 내용은 기존 보고 모달 아래쪽에 나오는 글을 그대로 복사해 온다**(사용자 결정 2026-10-22). 새로 만들거나 분류하거나 다듬지 않는다.
     - 캘린더 출처: 같은 실적 기간의 기간 취합 결과(`collectReportData` 와 기존 글 만들기 함수 `buildReportText`)에서 그 과제(카테고리) 부분.
     - 주간보고 출처: 같은 기간의 netcus 주간보고 취합 결과(`netcusWeeklyRangeRead` 와 `buildNetcusWeeklyText`)에서 그 과제 부분.
   - 과제(카테고리)별로 잘라 각 카드의 실적 칸에 넣는 것만 월간 쪽 일이다. 사용자가 이미 쓰는 보고 서식 설정(글머리, 들여쓰기)도 그대로 따른다.
   - 보고서 묶음(한 카테고리를 다른 카테고리 아래로 접기)은 월간에서 쓰지 않는다. 과제 단위가 표 단위이기 때문이다.
   - 문서로 옮길 때 줄 앞 들여쓰기 깊이를 문단 들여쓰기로 바꿔 Word 에서도 단계가 보이게 한다. 글자 자체는 바꾸지 않는다.
   - 붙인 뒤에는 글 칸에서 자유롭게 고칠 수 있다.
5. **다시 읽어 오기** 버튼: 실적 칸들을 기록에서 다시 붙인다. 고친 내용을 덮으므로 확인 창을 띄운다. 계획 칸과 변경이력은 건드리지 않는다.

### 5.4 초안 저장

- 직접 쓴 칸(계획 두 칸, 변경이력, 고친 과제명, 계획 기간)을 잃지 않도록 초안을 기존 패턴대로 localStorage 에 계정별로 둔다. 키 `tc_rptDraftM:<who>:<실적시작>_<실적끝>`, 최근 6건 보관.
- 지난 보고 내용을 새 보고로 자동으로 넘기지 않는다(직접 쓰는 칸이므로). 원하면 11.2 의 2번.
- 한계: localStorage 는 그 PC 에만 있다. 초안은 쓰는 동안의 안전장치일 뿐이고, 남는 결과물은 저장한 `.docx` 다.

### 5.5 저장

- `DOCX 저장` 버튼 → 호스트 저장 창. 기본 파일 이름 `월간보고_<이름>_<작성일 YYMMDD>.docx`, 기본 폴더는 지난번 저장 폴더.
- 결과 토스트에 경로와 `폴더 열기`. 실패하면 이유를 그대로 보여 준다(파일이 Word 에 열려 있어 잠긴 경우가 가장 흔할 것).

## 6. 개발 일정 그림(DB 보관)

개발 일정은 사람이 만들어 넣는 그림이다(제안서나 계획서의 간트 차트를 잘라 만든 것). 앱에는 단계와 마일스톤 데이터가 없으니 자동으로 그리지 않는다. **과제별로 그림을 DB 에 등록해 두고, 그 과제를 쓰는 사람 모두가 같은 그림을 쓴다**(사용자 결정 2026-10-22).

### 6.1 권한

- **누구나 추가, 삭제**: 관리자가 매번 넣을 수 없으므로, 앱 사용자라면 누구든 어느 공식 과제의 그림이든 추가하고 삭제하고 순서를 바꿀 수 있다. 관리자 권한 검사는 하지 않는다.
- 대신 그림마다 **등록한 사람과 시각**을 남기고 카드에 보여 준다. 삭제는 확인 창을 거친다.
- 삭제는 실제 행 삭제다(휴지통 없음). 실수로 지운 것은 백업에서 되살리거나 다시 올린다. 되살리기가 필요하면 11.2 의 1번.

### 6.2 표

새 표 `project_schedule_image`(구조 문서 `schema-structure.sql` 쪽, 공식 과제에 딸린 공용 데이터):

| 칸 | 형 | 뜻 |
|---|---|---|
| `id` | INT UNSIGNED PK | |
| `project_id` | INT UNSIGNED, FK `project(id)` ON DELETE CASCADE | 과제 |
| `seq` | TINYINT UNSIGNED | 과제 안 순서(1부터) |
| `mime` | VARCHAR(20) | `image/png` 또는 `image/jpeg`(CHECK) |
| `bytes` | MEDIUMBLOB | 그림 원본(16MB 한도, 앱은 장당 5MB로 제한) |
| `width_px`, `height_px` | SMALLINT UNSIGNED | 문서에 넣을 때 비율 계산용 |
| `sha256` | CHAR(64) | PC 사본 캐시 확인용 |
| `uploaded_by` | FK `app_user(user_id)` | 등록한 사람 |
| `uploaded_at` | DATETIME | 등록 시각 |

- 과제당 최대 5장(앱에서 막음). 같은 과제 안에서 `(project_id, seq)` 유일.
- 크기: 그림은 보통 100KB~1MB. MySQL 8 의 기본 `max_allowed_packet`(64MB)에 걸리지 않는다. 서버 값이 더 작게 바뀌어 있으면 올리기가 실패하므로, 실패 메시지에 원인을 그대로 보여 준다.

### 6.3 읽고 쓰기

- 호스트 명령 `scheduleImageList(projectUid)`(메타만: id, seq, 크기, 해시, 등록자, 시각), `scheduleImageGet(id)`(바이트), `scheduleImageAdd(projectUid, 파일 또는 붙여넣은 그림)`, `scheduleImageDelete(id)`, `scheduleImageMove(id, seq)`.
- **과제 목록(`loadProjects`)에 그림을 싣지 않는다.** 월간 탭에서 과제 카드를 열 때 메타만 읽고, 바이트는 해시가 PC 사본과 다를 때만 받아 앱 데이터 폴더 `schedule-images\<sha256>.png|jpg` 에 둔다.
- 넣는 방법: 카드의 그림 칸에 **붙여넣기**(잘라 복사한 그림) 또는 `파일 고르기`(PNG, JPG). 호스트가 WPF `BitmapDecoder` 로 형식과 가로세로를 확인하고, 그림이 아니면 거절한다.
- DOCX 저장 때 호스트가 PC 사본(없으면 DB)에서 바이트를 읽어 넣는다. 웹과 호스트 사이로 큰 바이트를 오가게 하지 않는다. 웹에는 미리 보기용 작은 그림만 넘긴다.
- 문서에서는 셀 폭(약 570pt에서 안쪽 여백을 뺀 값)에 맞춰 비율 유지로 줄이고, 여러 장이면 위에서 아래로 차례로 놓는다. 그림이 없으면 칸을 비워 둔다(양식과 같음).
- DB 가 끊겨 있으면 PC 사본으로 저장은 하고, 추가와 삭제는 막는다.

### 6.4 배포와 운영

- **구조 번호 하나 상향(v16 예상).** 그림 표와 개발 시작일 칸(6.5)을 한 조각에 담는다. 이슈 #14 도 다음 번호를 쓰므로 구현 시점에 실제 번호를 정한다. 조각 `db/deploy/migrations/v<N>-monthly-report.sql` 과 `schema-structure.sql` 반영, 지금 규칙대로 Workbench 에서 돌리는 순수 `.sql`, Setup 먼저 올리고 SQL(버전 게이트 정책).
- 권한: 앱 계정에 이 표의 SELECT, INSERT, UPDATE, DELETE. 이 표는 `app_user` 를 참조하므로 `ProjectDb.cs` 의 `UserRecordTables` 등록 여부를 확인한다(사용자 삭제 시 처리).
- **백업**: `backup-taskmgr.ps1` 의 mysqldump 에 지금 `--hex-blob` 이 없다. 그림 바이트를 안전하게 덤프하고 되살리려면 넣어야 한다. 백업 크기는 그림 양만큼 는다(과제 수 x 몇 MB 수준).

### 6.5 개발 시작일 칸(같은 조각에 함께)

- `project` 표에 `dev_start_date DATE NULL`(개발시작일, 미정=NULL)을 `dev_end_date` 앞에 더한다. 개발종료일과 짝이다.
- 그림 표와 **같은 마이그레이션 조각, 같은 구조 번호**에 넣는다. 번호를 두 번 올리지 않기 위해서다.
- 개발종료일이 이미 지나가는 길을 그대로 따라 붙인다: 과제 읽기(`ProjectDb.cs`), 웹 `dbCatalog` 의 `devStartDate`(`mapDbRows`), 관리 화면 과제 편집 칸, 과제 xlsx 내보내기 열(`ProjectExportCols`). CHECK 로 시작일이 종료일보다 늦지 않게 막는다(둘 다 있을 때만).
- **관리 화면이 별도 창으로 옮겨 가는 중**(admin-window 브랜치)이라 과제 편집 칸 추가가 그 작업과 겹친다. 그 브랜치가 먼저 들어오면 옮겨 간 쪽에, 아니면 지금 자리에 넣고 합칠 때 정리한다.
- 값 채우기(개발 시작, 종료 일괄 입력)는 사용자가 나중에 직접 한다. 이 기능은 칸을 만들고 읽기만 한다.

## 7. DOCX 생성

### 7.1 방식

`widget/DocxWriter.cs` 를 새로 만든다. `XlsxWriter.cs` 와 같은 원칙이다. **외부 패키지 없음**(폐쇄망은 NuGet 을 못 받는다), `ZipArchive` 로 WordprocessingML 을 직접 쓴다.

템플릿 처리 방식 비교:

- **코드로 생성(추천)**: 표 구조(열 병합, 세로 병합, 이력 줄 수, 과제 수)가 매번 달라서 어차피 코드가 표를 만들어야 한다. 원본 양식 `.docx` 의 표 XML 을 복제하고 칸을 찾아 채우는 방식은 원본 내부 구조(셀 병합 표기, 숨은 서식 조각)에 기대게 되어 약하다.
- 원본 양식 `.docx` 는 폐쇄망 밖으로 가져오기 어려워 **2장의 PDF 측정값을 상수로 쓴다**(11장 1번). 숫자 보정은 사용자가 폐쇄망 Word 에서 읽어 준 값으로 한다.
- 빈 양식(PDF 또는 원본 docx)은 저장소에 둘 수 있다. 시험의 비교 기준과 문서용으로 `docs/assets/monthly-report-form.*` 에 둔다. **실제 보고서는 저장소에 두지 않는다.**

### 7.2 만들 부품

- `[Content_Types].xml`, `_rels/.rels`, `docProps/core.xml`, `docProps/app.xml`
- `word/document.xml`: 본문
- `word/styles.xml`: 기본 글꼴 맑은 고딕 10pt(`w:rFonts` ascii, hAnsi, eastAsia 모두), 줄 간격, 표 기본 서식
- `word/settings.xml`: 최소 설정
- `word/_rels/document.xml.rels`, `word/media/imageN.png|jpg`

### 7.3 본문 구조

- 구역 설정: `w:pgSz w=16838 h=11906 orient=landscape`, 여백은 양식 측정값(왼쪽 약 85pt, 오른쪽 약 66pt) 또는 원본 docx 값.
- 제목 문단(가운데, 굵게, 12pt, 밑줄), 빈 문단.
- 과제마다 표 하나(`w:tblGrid` 7열, 2.3 의 병합은 `w:gridSpan` 과 `w:vMerge`), 표 뒤 빈 문단.
- 마지막에 기타 표.
- 칸 이름 셀은 `w:shd` 로 배경색, 가운데 정렬, 굵게.
- 본문 칸: 줄마다 문단 하나. 단계별 왼쪽 들여쓰기와 내어쓰기(`w:ind`). 글자는 붙인 그대로 두고 굵게 같은 꾸밈은 하지 않는다(사용자가 Word 에서 다듬음).
- 그림: `w:drawing` 안 `wp:inline` 그림, 크기는 EMU.
- 표는 쪽을 넘겨 이어질 수 있게 둔다(실제 보고서도 과제 하나가 두 쪽에 걸친다). 칸 이름 줄만 `w:cantSplit`.
- 모든 글자는 XML 이스케이프. 제어 문자 제거.

### 7.4 호스트 명령

- `exportMonthlyDocx`: 웹이 `hostRequest('exportMonthlyDocx', payload, 300000)`. 호스트는 `SaveFileDialog`(소유 창 = 요청한 창) → `Task.Run(DocxWriter.Write)` → `ReplyOnUi`. 응답 `{ok, path, dir} | {cancelled} | {error}`. `RunProjectsXlsxExport` 와 같은 모양.
- 그림 명령 `scheduleImageList/Get/Add/Delete/Move`: 6.3.
- payload 는 그림 바이트 없이 글과 구조만: `{name, reportDate, actual:{from,to}, plan:{from,to}, projects:[{uid, title, term, changes:[{what,date,why}], prevPlan, actual, nextPlan}], etc:{lines}}`. 본문은 `{level, text, bold}` 줄 배열로 보낸다. level 은 웹에서 줄 앞 들여쓰기 깊이로 정한다(글자는 그대로). 그림은 호스트가 `uid` 로 찾아 넣는다.
- 새 호스트 코드는 `widget/MonthlyReportExport.cs`, `widget/ScheduleImageDb.cs`(partial 또는 별도 클래스)에 모으고 `MainWindow.xaml.cs` 분기에는 case 한 줄씩만 더한다. 다른 브랜치와 겹침을 줄이기 위해서다.

## 8. 진행 중인 다른 작업과의 관계

- **관리 화면 별도 창**(`docs/ADMIN-WINDOW.md`, `.claude/worktrees/admin-window` 개발 중): 보고는 그 범위 밖이다. 다만 새 호스트 명령은 그 문서의 규칙(요청 창 기준 응답 전달, 파일 창 소유자 = 요청한 창)을 따른다. 월간과 그림 명령은 관리 창 허용 목록에 넣지 않는다. 두 작업이 `MainWindow.xaml.cs` 명령 분기를 함께 고치므로 **나중에 합치는 쪽이 분기 충돌을 정리**한다.
- **이슈 #14**(과제별 공유 캘린더, 다른 세션이 기획 중): 이슈는 공유 일정을 보고에서 뺀다고 했다. 월간 실적 붙이기도 같은 규칙(공유 일정 제외). **그림 표가 구조 번호를 하나 쓰므로 #14 와 번호가 경합한다.** 먼저 구현하는 쪽이 v16 을 가져가고 다른 쪽이 다음 번호를 받는다. 구현 시점에 확인.
- **버전 게이트**(`docs/VERSION-GATE.md`, 지금 구조 번호 15): 그림 표 조각이 들어가면 앱의 `AppStructureVersion` 과 DB 의 구조 번호를 함께 올린다. 배포는 Setup 먼저, 그다음 SQL(정책 그대로). 앱 버전은 마이너 상향(기능 추가).
- **보고 모달 개선(사용자가 나중에 할 일)**: 5.1 대로 기존 코드 접점을 탭 버튼과 `setReportMode` 분기로 묶어 둔다. 기존 함수(`collectReportData`, `rptSources`, 기존 글 만들기 함수, `monthRange`)는 **읽기만 하고 바꾸지 않는다.** 과제별로 자르는 일은 월간 쪽 감싸는 함수에서 한다.

## 9. 단계

1. **DocxWriter 와 호스트 저장 명령**: 지어낸 예시 payload(그림 포함)로 양식과 같은 문서가 나오는 것까지. 화면과 DB 없음, 단독 검증 가능.
2. **DB 조각(그림 표 + 개발 시작일 칸)과 그림 명령**: 마이그레이션 조각 하나, 구조 문서, 권한, 백업 `--hex-blob`, 과제 읽기와 관리 화면의 개발 시작일, 그림 호스트 명령, PC 사본 캐시.
3. **월간 탭**: 기간(실적은 읽어 온 기간, 계획은 직접 고침), 과제 고르기, 실적 붙이기, 직접 쓰는 칸(계획 두 칸, 변경이력), 그림 추가와 삭제, 초안 저장, DOCX 저장. 캘린더 출처.
4. **주간보고 출처**: netcus 주간보고 취합 결과를 과제별로 잘라 실적 칸에 붙인다(읽기만).

1단계와 2단계는 서로 기대지 않으므로 따로 진행할 수 있다. 3단계는 둘 다 필요하다.

### 10.3 위젯 QA

- **복사본 DB** 에서만 한다(시드/데모 DB). 실제 운용 DB 는 건드리지 않는다.
- 위젯은 한 번에 하나만 뜨므로 실동작 QA 는 다른 세션과 시간을 맞춘다.
- 두 계정으로 같은 과제 그림을 올리고 지워 보아 서로 보이는지(공유), 등록자 표시가 맞는지 본다.
- netcus 는 읽기 경로만 쓴다. **QA 중 회사 사이트에 아무것도 보내지 않는다.** 월간 탭에는 보내기 버튼이 없고, 호스트 로그에 `NetcusSubmit`, `NetcusWeekFill` 호출이 없는지 확인한다. netcus 출처 시험은 가능하면 가로챈 가짜 응답으로 한다.
- 시험 데이터, 그림, 스크린샷에는 지어낸 과제명과 이름만 쓴다.

## 11. 결정과 열린 질문

### 11.1 결정(2026-10-22, 사용자)

1. 원본 양식 `.docx` 는 받지 않는다(폐쇄망 반출이 어렵다). PDF 측정값으로 만든다. 맞춤이 더 필요하면 파일 대신 숫자만 옮긴다: 폐쇄망 Word 에서 원본의 여백(위, 아래, 왼쪽, 오른쪽)과 표 열 폭(표 속성의 cm 값)을 읽어 알려 주면 상수에 반영한다. 1단계 결과 문서를 폐쇄망에서 원본과 나란히 열어 다른 점을 알려 주는 것으로 검수한다.
2. 개발 일정 그림은 DB 에 과제별로 두고, 사용자 누구나 추가, 삭제한다(관리자 전용 아님).
3. 캘린더가 채우는 것은 수행 실적뿐이고, 기존 취합 결과를 그대로 붙인다(재분류 없음).
4. 수행 계획 두 칸과 일정 변경이력은 사용자가 직접 쓴다.
5. 과제 수행 기간은 DB 의 과제 개발기간, 월간 실적은 읽어 온 기간 그대로, 월간 계획은 직접 고친다.
6. 개발 시작일 칸(`dev_start_date`)을 새로 만들고, 과제 수행 기간 = 개발 시작일 ~ 개발종료일. 두 값은 지금 비어 있고 사용자가 나중에 직접 일괄로 채운다(종료 기본은 납품일 한 달 전). 이 작업용 SQL 은 여기서 만들지 않는다. 월간보고 기능은 이 값을 읽기만 한다.
7. 실적 상세 내용은 기존 캘린더 취합 또는 주간보고 취합의 아래쪽 글을 그대로 복사해 온다.
8. 화면은 우선 보고 모달의 네 번째 탭에 둔다.

### 11.2 열린 질문(추천 기본값)

1. **삭제한 그림 되살리기**: 기본은 바로 지움(백업에서만 복구). 실수가 걱정되면 지운 표시만 하고 30일 뒤 정리하는 방식으로 바꿉니다.
2. **계획 칸 이월**: 기본은 이월 없음(직접 씀). 지난 보고의 오른쪽 계획을 새 보고의 왼쪽 계획에 미리 넣어 두길 원하면 켭니다.
3. **기타 표 범위**: 기본은 공식 과제가 아닌 카테고리 전부(제외 목록 기억). 휴가 같은 근태성 기록은 기본 제외할지요.
4. **과제명 표기**: 기본은 통상명칭(없으면 사업명).
5. **내용 출처 기본**: 캘린더. 주간보고를 기본으로 바라면 바꿉니다.
6. **한컴오피스 호환**: 회사에서 이 문서를 Word 로 여나요, 한글로 여나요. 기본은 둘 다 확인합니다.
