## 1. 한 장 요약

과제 데이터는 폐쇄망 서버에 구축돼 운영 중이다. 이 문서는 그 다음 조각 — **개인 일정·할 일**을
DB 로 옮기는 설계다. 지금은 PC 하나의 `%APPDATA%\TaskCalendar\data.xml` 에만 있어서
**다른 자리 PC 에서 내 일정을 못 보고**, 위젯과 브라우저가 따로 놀고,
**남의 일정을 열람할 방법이 없다**(「구성원」의 「준비 중」이 그것이다).

**환경**: 사원 80명 · 폐쇄망 MySQL 8.4 단일 서버 · **API 서버 없음**(각 PC 의 위젯이 DB 에 직접 접속) ·
추후 브라우저 지원 시 API 서버 도입 예정(스택 미정).

## 2. 대전제 — 온라인 전용, 로컬에 아무것도 남기지 않는다

**DB 가 유일한 원본이다.**

```
부팅 → DB 조회 (커밋 제외 전부)
        성공 → 메모리에 로드
        실패 → 데이터 없음 + "서버에 연결하지 못했습니다" + [다시 시도]

편집 → DB 에 쓴다
        성공 → 메모리 반영
        실패 → 오류 표시. 메모리는 건드리지 않는다

커밋 → 그 화면(커밋 내역 탭 · 보고서)을 열 때만 조회
```

상태는 **둘뿐**이다 — 데이터 있음 / 없음. 그 사이 전이가 없다.
과제 데이터가 이미 같은 정책이다(**ADR-18**: *"조회·편집 모두 온라인, 캐시로 대체하지 않는다"*).

### 서버 상태를 사전 확인하지 않는다

"살아있나?" 를 먼저 묻고 그다음 조회하면, 그 사이에 죽을 수 있어 확인이 거짓말이 된다.
**조회·쓰기의 성공/실패가 곧 상태다.** 과제 목록이 이미 그렇게 판정한다(`dbOnline`).

### 커밋만 지연 조회하는 이유 — 무게가 거기 있다

| | 추정 |
|---|---|
| 일정 자체 | 365B × 3,000건 = **약 1.0MB** |
| 커밋 | 500B × 12,500건(하루10 × 250일 × 5년) = **약 6.0MB** |

무게의 대부분이 커밋이고 **커밋은 캘린더를 그리는 데 쓰이지 않는다.**
실측: 5년/저장소1 부팅 전송량 **1.15MB**, 10년/저장소3/과제5(최악) 3.84MB.

## 3. ★ 동시성 규약 — 이 절을 어기면 조용히 깨진다

### 3.1 모든 쓰기 트랜잭션의 첫 문장

```sql
INSERT INTO cal_user_rev(login_id, rev) VALUES(?, 1)
  ON DUPLICATE KEY UPDATE rev = rev + 1;
```

**락 획득·행 생성·rev 증가를 한 문장으로** 한다. 이 한 문장이 세 가지를 동시에 한다:

1. 같은 사용자의 쓰기를 **직렬화**(다른 사용자와는 다른 행이라 안 막힌다)
2. 나중에 켤 **폴링 동기화의 단일 감시 지점**(테이블 9개를 각각 볼 필요 없음)
3. **삭제까지 감지**(`MAX(updated_at)` 은 삭제를 놓친다)

**왜 `SELECT ... FOR UPDATE` 가 아닌가** — 실측:

| 방식 | 빈 테이블 80세션 동시 |
|---|---|
| `SELECT ... FOR UPDATE` | **79/80 ERROR 1213 데드락** |
| `INSERT ... ON DUPLICATE KEY UPDATE` | **80/80 성공, 데드락 0** |
| `INSERT IGNORE` 후 `FOR UPDATE` | 중복키에서 S락 → **전 사용자 상시 데드락**(더 나쁨) |

더 위험한 변종: rev 를 평범한 `UPDATE ... SET rev=rev+1` 로 구현하면 **행이 없을 때
`ROW_COUNT()=0`, 오류 없음, 양쪽 커밋, rev 행 영구 미생성.** 그 사용자는 이후로도
직렬화 없이 쓰고 감시점도 없다. 조용히 영구 결함이 된다.

**배포 시 전원 시딩 필수** — `INSERT IGNORE INTO cal_user_rev SELECT login_id, 0 FROM app_user;`
(부분 시딩 금지. 결번이 같은 갭에 들어가면 그대로 데드락)
**릴리스 게이트**: `app_user LEFT JOIN cal_user_rev` 결과가 0건.

### 3.2 쓰기 트랜잭션은 READ COMMITTED

세션 단위로만 건다. **서버 `my.ini` 전역 변경 금지**(부팅 조회가 찢어진다).

이유 — 실측으로 확인된 문제:

```
세션A: DELETE FROM cal_entry WHERE login_id='mmm'   (트랜잭션 유지)
  → 'aaa' INSERT   ERROR 1205 차단   ← 무관한 사용자가 막힘
  → 'zzz' INSERT   통과
```

범위 `DELETE` 가 만드는 next-key 락이 **키 순서상 이웃한 사용자**를 막는다.
차단 시간 실측 4,950ms → RC 적용 후 **0~13ms**.

> ★ 이전에 "다른 사용자는 안 막힌다"고 기록했던 것은 **`cal_user_rev` 행에 한해서만** 참이었다.
> 정작 큰 락은 `DELETE` 가 만든다. **한 번 통과한 것을 근거로 삼지 말 것** — 재측정은
> 범위 DELETE · 경계 키 · 반복 실행으로 한다.

**순서 의존**: RC 는 3.1(시딩 + ODKU) 이 선행돼야 안전하다. rev 행이 없는 상태의 RC 는
조용한 이중 커밋이다.

#### ★ 읽기 연결에는 걸지 않는다 — 프리앰블을 공용화하지 말 것

> **2026-08-10 정정.** 이 절은 처음에 격리수준을 '접속 프리앰블'로 적었고, §3.5 는 같은 접속에서
> `START TRANSACTION WITH CONSISTENT SNAPSHOT` 을 쓰라고 적었다. 둘은 양립하지 않는다.

`START TRANSACTION WITH CONSISTENT SNAPSHOT` 은 **REPEATABLE READ 에서만** 듣는다.
그 밖의 격리수준에서는 오류도 실패도 아니고 **Warning 138 하나만 내고 조용히 무시**된다.

실측(8.4.9, 이 문서 갱신 시 재현):

| 세션 격리수준 | `START TRANSACTION WITH CONSISTENT SNAPSHOT` |
|---|---|
| `READ-COMMITTED` | **Warning 138** `WITH CONSISTENT SNAPSHOT was ignored…` — 무시됨 |
| `REPEATABLE-READ` | 경고 0건 — 적용됨 |
| `SERIALIZABLE` | **Warning 138** — 무시됨 |

프리앰블을 읽기·쓰기가 공유하면 §3.5 가 막으려던 부팅 조회 찢어짐이 **아무 신호 없이** 재현된다.
경고 하나뿐이라 로그를 안 보면 영영 모른다.

- **읽기(부팅 조회) 연결**: `SET SESSION transaction_isolation='REPEATABLE-READ'` 를 **명시**한 뒤 스냅샷 시작
- **쓰기 연결에만** READ COMMITTED
- 프리앰블을 한 함수로 합치지 말 것. 합치는 순간 둘 중 하나가 반드시 틀린다

### 3.3 낙관적 잠금 — UPDATE 와 **DELETE 둘 다**

```sql
UPDATE cal_entry SET ..., updated_at = ?      -- 앱이 UTC 로 계산해 보낸 값
 WHERE id=? AND login_id=? AND updated_at=@prev
```

- 영향 행 **1** → 성공
- 영향 행 **0** → `다른 곳에서 먼저 수정되었습니다 — 새로고침 후 다시 시도하세요`

**삭제에도 같은 조건을 건다.** 폴링이 없고 부팅 1회 로드라 **세션 수명 = 스테일 윈도우**이고,
상주형 위젯은 창이 하루 종일 열려 있다. 조건이 없으면 언제 읽은 화면이든 영향 행 1 이라
조용히 지워진다.

**영향 행 0 의 원인 분기는 반드시 잠금읽기(`FOR SHARE`)로.** 일반 `SELECT` 는 RR 스냅샷 때문에
'이미 삭제됨'을 '수정됨'으로 오보한다(실측: 일반 SELECT=1, `FOR SHARE`=0).
선례 `ProjectDb.cs:684`.

**전량 DELETE(가져오기)에는 걸지 않는다** — 일부만 지워지고 뒤 INSERT 가 1062 로 터진다.

#### '영향 행 0' 은 한 가지 뜻이 아니다 — 무엇을 세는지가 접속 플래그로 갈린다

서버는 두 숫자를 따로 센다: **matched**(조건에 맞은 행)와 **changed**(값이 실제로 바뀐 행).
`ROW_COUNT()` 가 돌려주는 것은 **changed** 다. 실측(8.4.9):

| UPDATE | 서버 info | `ROW_COUNT()` |
|---|---|---|
| 값이 바뀜 | `Rows matched: 1  Changed: 1` | 1 |
| 조건은 맞는데 값이 그대로 | `Rows matched: 1  Changed: 0` | **0** |
| 조건이 안 맞음(= 진짜 충돌) | `Rows matched: 0  Changed: 0` | 0 |

그런데 앱이 보는 숫자는 `ROW_COUNT()` 가 아니라 드라이버가 주는 값이고, 그건 접속 플래그
`CLIENT_FOUND_ROWS`(= `UseAffectedRows` 의 반대)로 갈린다.
실측(MySqlConnector 2.3.7, `TaskCalendarWidget.csproj:31`. 실제 UPDATE 를 쳐서 잰 값):

| `UseAffectedRows` | 값이 그대로인 UPDATE | 조건 불일치(진짜 충돌) |
|---|---|---|
| **미지정(현행)** = 기본 `False` | **1** | 0 |
| `false` 명시 | 1 | 0 |
| `true` | **0** ← 충돌 오탐 | 0 |

즉 위의 **'영향 행 0 = 충돌' 계약은 지금은 참이지만, 드라이버 기본값에 얹혀서 참이다.**
`ProjectDb.cs:46-57` 은 `UseAffectedRows` 를 지정하지 않는다.
→ **연결 문자열에 `UseAffectedRows=false` 를 명시할 것.** 누가 `true` 로 바꾸거나 드라이버를 갈면,
값이 그대로인 저장이 전부 "다른 곳에서 먼저 수정되었습니다" 로 뜬다. 이 조합이 나오는 경로는
좁지만 실재한다 — `updated_at` 이 밀리초라 보통은 매번 달라지지만, §5.3 이 기록했듯 이 앱은
같은 밀리초가 흔하다(`created_at` 37개 중 33개).

0 을 받았을 때의 원인 분기는 그대로 위의 `FOR SHARE` 규칙을 따른다(삭제됨 / 수정됨).

#### `@prev` 는 불투명 토큰이다

| 보낸 값 | 결과(실측) |
|---|---|
| `2026-01-02 03:04:05.678` | 영향 행 **1** ✔ |
| `2026-01-02T03:04:05.678Z` | **`ERROR 1292`** 문 전체 실패 |
| `2026-01-02 03:04:05` (ms 절삭) | 영향 행 **0** — **조용한 충돌 오탐** |
| `2026-01-02 03:04:05.6789` (소수 4자리) | **경고 0건**으로 `.679` 반올림 → 영향 행 **0** — **조용한 충돌 오탐** |

> **소수 4자리가 왜 별도 행인가**(2026-08-10 추가, 8.4.9 재실측). 위 두 실패는 최소한 시끄럽거나
> (1292) 자릿수를 눈으로 셀 수 있지만, 4자리는 **아무 신호가 없다.** 열에 넣을 때 `SHOW WARNINGS`
> 가 0건인 채로 반올림되고(`.6789` → 저장 `.679`), **초 경계도 넘는다**(`05.9999` → 저장 `06.000`).
> 그런데 `WHERE updated_at='…05.6789'` 는 저장된 `.679` 와 **일치하지 않아** 영향 행 0 이다
> (실측: 4자리 `WHERE` matched 0 / 3자리 `WHERE` matched 1, 값을 실제로 바꾸는 UPDATE 로도 0 vs 1).
> 즉 **쓸 때도 읽을 때도 조용하고, 결과만 '다른 곳에서 먼저 수정되었습니다' 로 나온다.**
> 이 자릿수는 사람이 손으로 만들지 않는다 — `new Date().toISOString()` 계열이나 `DateTime` 기본
> 포맷을 그대로 태우면 나온다(§8 시각 변환 규칙 참조).

- 포맷 **`yyyy-MM-dd HH:mm:ss.fff`** 고정. 밀리초 필수 · 소수 **정확히 3자리**
  (모자라도 넘쳐도 영향 행 0 이 된다. 넘치는 쪽은 경고조차 없다)
- **C#↔JS 경계에서 문자열 그대로 왕복.** `Date` 파싱·재포맷 금지
- **앱의 `entry.updatedAt` 을 그대로 쓰지 마라** — JS 가 편집마다 `nowIso()` 로 덮는다
  (8767·8789·8885·8906·8913·10101). 서버가 준 값을 **별도로** 들고 있어야 한다

### 3.4 부속 테이블을 건드리는 쓰기

`cal_entry_except` · `cal_entry_commit` · `cal_todo_day_note` 를 건드리는 저장은:

1. **한 트랜잭션**으로 묶는다
2. 첫 문장은 3.1 의 rev 문장
3. **같은 트랜잭션에서 부모 `cal_entry.updated_at` 을 올린다**

3번이 빠지면 반복 일정의 "이 날짜만 삭제"가 부모 버전을 안 올려 **3.3 의 보호가 그대로
뚫린다**(실측: 버전조건 통과, except 3건 동반 소실).

부속 테이블 자체에는 `updated_at` 을 두지 않는다 — **부모가 잠금 단위**다.

> 커밋 재수집은 `[from,to]` 범위 전량 삭제 후 재생성이다(10872·10888·10896).
> XML 시절엔 파일 한 번 쓰기라 원자적이었다. 트랜잭션 없이 하면 **DELETE 성공·INSERT 실패 시
> 그 기간 커밋이 영구 소실**된다 — 로컬 사본·큐·tombstone 이 전부 없어 복구 경로가 0 이다.

### 3.5 부팅 조회는 단일 트랜잭션

**8개** 테이블을 **한 연결**에서,
`SET SESSION transaction_isolation='REPEATABLE-READ'` 를 **명시한 뒤**
`START TRANSACTION WITH CONSISTENT SNAPSHOT` … `COMMIT`.

> 격리수준 명시가 왜 여기 붙는지는 §3.2 의 '읽기 연결에는 걸지 않는다' 참조.
> READ COMMITTED 위에서는 이 구문이 Warning 138 하나만 남기고 무시된다.

**대상 8개**(세어서 적는다 — 게이트가 셀 수 있어야 한다):
`cal_category` · `cal_entry` · `cal_entry_except` · `cal_todo` · `cal_todo_day_note` ·
`cal_room` · `cal_task_hours` · `cal_user_pref`

빠지는 것과 이유:

| 빠지는 테이블 | 왜 |
|---|---|
| `cal_entry_commit` | 지연 조회(§2). 무게의 대부분이 여기다 |

### 3.6 접속 프리앰블과 오류 처리

접속 프리앰블(연결을 연 직후 반드시 실행):

- `SET SESSION innodb_lock_wait_timeout=5` (`DefaultCommandTimeout=8s` 보다 짧게 —
  그래야 DB 가 진단 가능한 1205 를 먼저 낸다)
- **`SET SESSION time_zone='+00:00'`** — 2026-08-10 추가. `schema-calendar.sql` 헤더의 **'시각 컬럼 규약'** 절이 이 줄을
  전제로 서버 `DEFAULT`·`ON UPDATE` 를 전부 뺐는데 이 문서에는 없었다.
  DATETIME 컬럼 자체는 세션 tz 변환을 받지 않지만, 서버 함수가 한 줄이라도 섞이면 그 값만 9시간
  어긋난 채 같은 컬럼에 영구 혼재한다(실측: 세션 `SYSTEM` 에서 `NOW(3)`=10:51:10 vs
  `UTC_TIMESTAMP(3)`=01:51:10. `+00:00` 적용 후 둘이 같은 값). 세션을 UTC 로 고정하면 그런 실수가
  **값 손상이 아니라 무해한 중복**이 된다
- **격리수준은 연결 종류마다 다르다** — 읽기(부팅 조회) `REPEATABLE-READ` / 쓰기 `READ-COMMITTED`
  (§3.2·§3.5). **한 프리앰블 함수로 합치지 말 것**
- **`SELECT v FROM cal_schema_meta WHERE k='schema_version'` 1회** — 2026-08-10 추가.
  읽은 값을 위젯 빌드 상수와 비교해 다르면 **파괴적 연산만** 막는다(§5.5). 여기 없던 것이
  누락이었다: §3.5 는 이 읽기를 부팅 조회 트랜잭션에서 **뺀 이유**를 적었고 §5.5 는 '접속 시 1회
  비교'를 요구했는데, 정작 **어디서 읽는지를 정의한 곳이 없었다**. 정의가 없으면 구현자가
  부팅 조회 스냅샷 안으로 끌어넣게 되고(§3.5 가 막으려던 것) 또는 아예 안 읽는다

오류 처리:

### 5.2 키·제약 (★ 결정)

| 항목 | 결정 | 근거 |
|---|---|---|
| **PK** | `cal_entry`·`cal_todo`·`cal_category` 모두 **`(login_id, id)`** | ① `cal_category` 는 공식 과제 id 가 `db-<project.uid>` 라 **전 사용자 공통** → `PK(id)` 면 두 번째 구독자에서 `ERROR 1062`(실측) ② 소유자 지역성 — 콜드 IO **52배** 차이(80부팅 디스크 58,964 vs 1,135) |

| **`project_uid`** | **FK 걸지 않음** | 공식 과제가 삭제돼도 구독 행은 남아야 한다. FK 면 `RESTRICT`/`CASCADE` 둘 다 그 요구와 어긋난다 |
| **`cal_task_hours.category_id`** | **FK 걸지 않음** | 과제를 지워도 지난 공수 기록은 남아야 한다(집계 이력) |
| **소프트 삭제** | **없음.** `DELETE` | §2 — 오프라인 동기화가 없어 tombstone 의 존재 이유가 없다 |
| **`updated_at`** | **서버 `DEFAULT`·`ON UPDATE CURRENT_TIMESTAMP` 절대 금지** — 앱이 UTC 로 계산해 **명시 대입**한다. 타입·정밀도는 적지 않는다(단일 소스는 [`schema-calendar.sql`](deploy/schema-calendar.sql)) | §3.3 + [`schema-calendar.sql`](deploy/schema-calendar.sql) 헤더의 '시각 컬럼 규약'. ① `CURRENT_TIMESTAMP` 는 세션 `time_zone`(현 서버 `SYSTEM`=KST)으로 평가된다 — 서버가 한 번이라도 값을 쓰면 같은 컬럼에 KST 와 UTC 가 섞이고 `DATETIME` 은 사후 구분 수단이 없다(복구 불가) ② `updated_at` 은 동시에 낙관적 잠금 토큰이라 **쓰기 주체가 둘이면 토큰 자체가 무너진다** |

> 서두가 경고한 *"표를 두 벌 두면 사고가 난다"* 가 이 문서 안에서 그대로 재발한 사례다 —
> 컬럼 속성을 다시 적고 싶어지면 **적지 말고 SQL 파일로 링크만 걸 것.**
> 회귀는 배포마다 `information_schema.COLUMNS.EXTRA` 에 `on update` 가 **0건**임을 확인해 잡는다.

> **2026-08-10 정정 — ① 의 '12테이블' 을 11로 고쳤다.** 12 는 폐기된 `cal_app_log` 가 아직 §5.1 명부에
> 있던 시절의 **명부 개수를 그대로 옮긴 숫자**였지, `CASCADE` 로 실제 지워질 표를 센 값이 아니었다
> (§3.5 의 '12개' 와 같은 출처의 같은 실수다). 표 이름을 여기 옮겨 적지 않는다 — **세는 규칙**만 남긴다:
> `login_id` FK 를 건 표 + 그 표를 부모로 하는 `ON DELETE CASCADE` 자식. 값은 SQL 이 정본이고
> 게이트가 다시 셀 수 있다:
> ```sql
> SELECT TABLE_NAME, REFERENCED_TABLE_NAME, DELETE_RULE
>   FROM information_schema.REFERENTIAL_CONSTRAINTS
>  WHERE CONSTRAINT_SCHEMA = DATABASE();
> ```
> 격리 DB 에서 8개 FK 를 전부 `ON DELETE CASCADE` 로 바꿔 재현해 확인했다(직접 실행). **덤으로 나온
> 사실이 ② 의 근거를 하나 더한다** — 과제를 참조하는 일정이 한 건이라도 있으면 그 `CASCADE` 삭제는
> `fk_cal_entry_category` 의 `RESTRICT` 에 걸려 `ERROR 1451` 로 **막힌다.** 즉 `CASCADE` 로 바꿔도
> 결과가 데이터에 따라 '전부 삭제' 와 '아예 실패' 로 갈린다. 어느 쪽이든 원하는 동작이 아니다.

| **CHECK** | **식도 목록도 개수도 여기 적지 않는다.** **CHECK 전량의 단일 소스는 [`schema-calendar.sql`](deploy/schema-calendar.sql)** 이다(제약 이름이 `chk_cal_*`). 문서가 남기는 것은 *왜 두는가* 뿐 — 아래 문단 |

> **2026-08-10 정정.** 이 칸은 원래 식을 그대로 옮겨 적었고, 그중 반복 항목(`recur_freq IN('weekly','monthly')`)은
> **실제 제약과 달랐다.** MySQL CHECK 는 결과가 FALSE 일 때만 거부하고 **NULL(UNKNOWN)이면 통과**시키므로,
> `IS NOT NULL` 을 명시하지 않은 그 형태는 반쪽짜리 반복(주기만 · 간격만 · 주기+횟수 …)을 하나도 막지
> 못한다(실측). 식을 두 벌 두면 이렇게 어긋나고, **어긋난 쪽이 문서라서 아무도 실행해 보지 않는다.**
> 공수 범위도 여기서는 `hours BETWEEN 0 AND 1440` 이라 `cal_task_hours.hours`(시간 단위)처럼 읽혔지만
> 실제 대상은 `cal_entry` 의 분 단위 공수 컬럼이었다(**그 컬럼은 2026-08-11 에 제거됐다** — 아래 정정).

> **2026-08-10 정정(2) — 그때 남겨 둔 '무엇을 막는가' 6줄짜리 요약마저 걷어냈다.** 식은 지웠지만
> **여섯 항목짜리 목록**이 남아 있었고, 그 목록은 실제 제약의 일부만 덮고 있었다(직접 세어 확인:
> 스키마의 `chk_cal_*` 는 **20개**). 하필 빠진 것 중에 [`grants-calendar.sql`](deploy/grants-calendar.sql) 이
> `cal_task_hours` 에 `DELETE` 를 주는 근거로 **직접 인용하는** `chk_cal_task_hours_range` 가 있었다 —
> 문서만 보고 판단하면 '0 을 UPDATE 하면 되지 않느냐'는 잘못된 결론에 이른다.
> **여기에 개수를 다시 적지 않는 이유**(위의 20도 이 정정의 근거일 뿐 유지 대상이 아니다): 목록이든
> 개수든 문서에 두면 스키마가 CHECK 를 더할 때마다 같이 고쳐야 하고, 안 고치면 이번처럼 **부분 목록이
> 전체인 척**한다. 전량은 SQL 이 정본이고, 세고 싶으면 다음 한 줄이면 된다:
> ```sql
> SELECT CONSTRAINT_NAME FROM information_schema.TABLE_CONSTRAINTS
>  WHERE TABLE_SCHEMA = DATABASE() AND CONSTRAINT_TYPE = 'CHECK';
> ```

> **2026-08-10 정정 — '실제 교정' 칸에서 컬럼 수치를 걷어냈다.** 원래는 `location 100→200` ·
> `subject 500→2000` · `ID VARCHAR(48)` + `safeId {1,48}` 로 **숫자와 타입을 그대로 적어** 두었는데,
> 그 뒤 스키마가 근거를 다시 따져 `subject` 를 가변 텍스트 타입으로, ID 폭을 `safeId` 정규식과 함께
> 더 넓은 값으로 바꿨다. **문서만 옛 숫자를 들고 남았다** — 서두가 경고한 *"표를 두 벌 두면
> 어긋나고, 어긋난 쪽이 문서라서 아무도 실행해 보지 않는다"* 가 §5.2 에 이어 여기서도 재발한 것이다.
> 그래서 숫자를 지우고 판단 근거만 남겼다. **실제 값이 궁금하면 SQL 파일을 열 것.**

> **2026-08-11 결정 — `cal_entry` 의 분 단위 공수 컬럼(`hours_min`)을 제거했다.** 컬럼 이름을 여기
> 남겨 두는 것은 *"왜 없는가"* 를 묻는 다음 사람이 스키마에서 못 찾고 헤매지 않게 하기 위한 것이며,
> 컬럼 정의를 되살리라는 뜻이 아니다. 근거는 넷이고 **전부 코드에서 확인한 것**이다:
> · **채우는 UI 가 없다.** 일정 편집 폼에 그 값을 입력하는 자리가 없고 자동 계산도 없다 —
>   즉 이관해 넣은 값 말고는 영원히 `NULL` 인 컬럼이다
> · **소비처가 하나뿐이다.** 연구노트용 캘린더 md 내보내기의 「일정」 줄에 붙는 *'· 2시간'* 표기가
>   전부다. 과제별 분 합계를 계산하는 코드는 있지만 **그 결과를 읽는 코드가 없다**
> · **회사(netcus) 일간보고 전송에 들어가지 않는다** — 그쪽이 쓰는 공수는 `cal_task_hours` 다
> · 같은 뜻의 값이 두 표에 단위마저 다르게(분 vs 시간) 있으면 **어느 쪽이 진짜인지가 매번 쟁점**이 된다.
>   실제로 이 문서의 §5.3 정정과 `chk_cal_task_hours_range` 인용에서 두 번 헷갈렸다
>
> → **공수의 단일 소스는 `cal_task_hours`(날짜 × 과제, 시간 단위 소수 2자리) 하나다.**
> 되살릴 조건: 일정 단위 공수를 **입력하는 UI 가 생기고**, 그 값을 읽는 소비처가 md 내보내기 말고
> 하나 더 생길 때. 그때도 `cal_task_hours` 와의 관계(합계인가 별개인가)를 먼저 정할 것.

CHECK 를 두는 이유: **API 계층이 없어 앱이 유일한 검증기**다. SQL 직독으로 바뀌면 매 로드마다
`fromXML` 이 하던 자가치유가 사라진다.

### 5.4 인덱스

`KEY (login_id, entry_date)` — 부팅 전량 조회의 접근 경로 + 날짜순 정렬 이득.
(범위 조회는 폐기했으나 §2 재검토 조건이 발동하면 그대로 범위 인덱스가 된다)

### 5.5 스키마 진화 규칙

- **추가 컬럼은 NULL 허용 또는 DEFAULT 필수.** `NOT NULL` 무DEFAULT 는 ALTER 백필만으로
  전 사용자 설정을 뒤집는다(`remind=0` = '알림 없음')
- **순서는 항상 ALTER → 배포.** 반대는 1054 로 불가능
- 스키마 버전 행 + 빌드 상수를 접속 시 1회 비교(**어디서 읽는지는 §3.6 프리앰블**). 낡은 클라이언트는
  **파괴적 연산만 차단**(전 쓰기 봉인은 과하다 — 조회·편집은 계속되게)
- ★ **버전 행에 대한 앱 계정 GRANT 는 `SELECT` 하나뿐이다.** `INSERT`/`UPDATE`/`DELETE` 를 한 줄이라도
  주면 **낡은 클라이언트 차단이 무의미해진다** — 막으려는 대상 자신이 자기 통과증을 발급할 수 있게 된다.
  값을 올리는 것은 구조를 바꾸는 `migrate-*.sql` 의 몫이고 그건 관리 계정으로 돈다.
  (버전을 올려야 할 주체가 앱이라면 애초에 이 게이트가 필요 없다는 뜻이다.)
  이 문장이 배포 스크립트가 '버전 행에 쓰기 권한이 하나라도 있으면 중단' 하는 근거다 —
  근거가 문서에 없으면 그 중단은 언젠가 '과한 검사'로 지워진다.

## 6. 개인 과제 vs 공식 과제

`state.categories` 는 단일 목록이고 개인 과제와 공식 과제(DB 유래)가 함께 담긴다(P3.5).
원본이 다르다.

**`cal_category` 한 테이블에 담되 `source` 로 가른다.**

- `source='local'` → `name` 저장
- `source='db'` → `project_uid` 로 `project` 를 조인해 이름을 읽는다. 보고서에 찍히는 과제명이
  사업부 관리 과제명과 **정확히 같아야** 하기 때문(v0.14.0)
- **`name` 은 양쪽 다 저장한다** — 공식 과제가 소프트삭제되면 라벨 소스가 0 이 되어 삭제된
  과제 N개가 전부 `(공식 과제)` 로 뭉친다. 저장하되 **project 해석 성공 시 표시에 쓰지 않는
  스냅샷 폴백**이다
- 색상·설명은 양쪽 다 저장 — 공식 과제도 색은 사용자 것이다(v0.16.0)

**`db_gone` 컬럼은 두지 않는다.** 파생값 캐시라 ADR-18 과 충돌하고 쓰기 주체·시점이 정의되지
않는다. 조회 시 파생한다:

```sql
LEFT JOIN project p ON p.uid = c.project_uid
-- is_active 는 조인 조건이 아니라 파생식 안에 (ON 에 넣으면 이름까지 NULL 이 된다)
(c.source='db' AND (p.uid IS NULL OR p.is_active=0)) AS db_gone
```

## 7. 권한 — 앱 관례이며 **DB 가 강제하지 않는다**

### 7.1 실증된 한계

80대가 `taskmgr_app` 계정 하나를 공유하고, 그 자격이 배포본에 들어 있다. **재현 가능하다:**

```
① phmin 을 edit_role='viewer' 로  →  앱: "편집 권한이 없습니다" 거부
② taskmgr_app 으로 직접 접속       →  UPDATE 성공. 앱 검사를 거치지 않음
③ 남의 계정·일정·근태 조회         →  전부 통과
```

`OpenWriteAsync` 의 권한 판정은 **앱을 통과하는 요청만** 본다. 앱을 안 쓰면 그 코드가 실행조차
안 된다. 자격은 배포본에서 꺼낼 수 있다(개발 빌드 DLL 에서 `taskmgr1234` **UTF-16 평문 검출**,
배포 exe 에서 `taskmgr_app`·`localhost` 검출).

### 7.2 그래서 암호화하지 않는다

클라이언트에 담긴 비밀은 비밀이 아니다 — 암호화하면 **복호화 키도 같이 배포**해야 한다.
난독화·암호화는 시간을 늘릴 뿐이고, 더 나쁜 건 **"암호화했으니 안전하다"는 거짓 안심**을
만든다는 것이다. 그 오해 위에서 나중에 근태·급여를 같은 구조에 올리게 된다.

**노출을 전제로 설계한다** — `DeployConfig.cs` 주석이 이미 그 태도다
(*"접속정보는 전 사용자에게 배포되므로 root 금지 — 노출돼도 피해가 '앱이 허용하는 것'까지로
제한된다"*).

### 7.3 그 전제 위의 조치

| 조치 | 무엇을 제한 | 상태 |
|---|---|---|
| **권한 최소화** | 꺼내도 할 수 있는 일이 앱 수준까지 | ✔ (root 아님·DDL 없음·타 DB 없음) |
| **호스트 제한** | 어디서 쓸 수 있는지 | ❌ 지금 `@'%'`. **사내 대역으로 좁힐 것** |
| **DELETE GRANT 최소화** | `cal_user_rev`·`cal_user_pref`·`cal_migration_log`·`cal_schema_meta` 에는 **DELETE 금지**. 부여 명세의 단일 소스는 [`grants-calendar.sql`](deploy/grants-calendar.sql) | ✔ 작성됨 |
| ~~**감사 트리거**~~ | ~~우회를 사후 탐지~~ | **폐기(2026-08-11)** — 근거는 §7.5. 대신 **주간 덤프 + binlog**(§9) |
| **근태 보류** | 가장 민감한 걸 안 올림 | §4 |

> **2026-08-10 정정 — 'DELETE 금지' 명단에서 `cal_category` 를 빼고 두 표를 더했다.**
> `cal_category` 는 개인 과제 삭제·공식 과제 구독 해제 두 UI 가 실재해서, 옛 명단을 글자대로
> 부여하면 둘 다 `ERROR 1142` 로 실패한다. §7.4 가 **문서보다 코드를 따랐고**, 대신 그 표를
> §7.5 감사 트리거 대상에 넣어 사후 탐지로 상쇄한다(**그 상쇄는 2026-08-11 에 폐기됐다** — §7.5).
> 반대로 `cal_migration_log`(재실행 방지가
> 존재 이유)와 `cal_schema_meta`(§5.5 차단 게이트)는 원래 이 명단에 있었어야 하는데 빠져 있었다.
> **이 칸에 표 목록을 두는 것 자체가 어긋남의 원인**이므로 판단 근거만 남기고 명세는 SQL 파일로 넘긴다.

**호스트 제한의 단계**:

```
지금   위젯 80대 ──MySQL──▶ DB      taskmgr_app@'192.168.x.%'
최종   위젯·브라우저 ──HTTP──▶ [API 서버] ──▶ DB    taskmgr_app@'<API서버IP>' 또는 @'localhost'
```

브라우저는 MySQL 드라이버가 없어 **DB 에 직접 못 붙는다.** 그래서 브라우저 지원 =
API 서버 구축이고, 그 순간 자격이 클라이언트에서 사라진다(공격 표면 **80 → 1**).
호스트 제한은 MySQL 접속에만 걸리므로 **브라우저 접근과 충돌하지 않는다.**

### 7.4 GRANT

기존 `create-app-user.sql` 은 `SELECT, INSERT, UPDATE` 만 주고 근거가
*"소프트삭제는 UPDATE 라 DELETE 불필요"* 다. §2 가 소프트삭제를 버렸으므로 **그 관례를 글자대로
따르면 앱의 모든 삭제가 권한거부로 실패한다.** `cal_*` 전용 GRANT 표를 별도로 만든다.
자식 단독 삭제 경로가 실재하므로(커밋 개별 삭제 8915·8921, freq 변경 시 예외 비우기 5660)
`cal_entry_commit`·`cal_entry_except` 에도 DELETE 가 필요하다.

#### `DELETE` 를 주는 진짜 근거 — 그리고 무엇이 위험을 상쇄하는가

> **2026-08-11 정정.** 이 절과 [`grants-calendar.sql`](deploy/grants-calendar.sql) 주석은
> *"감사 트리거가 상쇄하므로 `DELETE` 를 줄 수 있다"* 를 부여의 근거처럼 적고 있었다.
> 트리거를 폐기(§7.5)한 지금 그 문장을 그대로 두면 **없는 상쇄를 있다고 쓰는 것**이 된다.
> 아래가 실제 관계다.

**부여 근거(상쇄와 무관하다)** — `cal_*` 에는 **소프트 삭제가 없다**(§5.2). 일정·할 일·과제·회의실·
예외일·커밋·공수는 **행을 지우는 것이 정상 동작**이고, 공수에 0 을 넣는 것도 0 저장이 아니라 행 삭제다
(`chk_cal_task_hours_range` 가 0 을 거부한다). 즉 `DELETE` 는 *"위험하지만 감수한다"* 가 아니라
**주지 않으면 앱의 삭제 UI 가 전부 `ERROR 1142` 로 죽는 필수 동사**다. 트리거가 있든 없든 부여는 같다.

**남는 위험** — 접속 자격이 배포본에 담겨 80대에 퍼진다(§7.1·§7.2). 앱을 우회한 사람이
그 자격으로 남의 행을 지울 수 있다. 이건 `DELETE` 부여의 부작용이 아니라 **공유 자격 구조 자체의
성질**이고, `UPDATE` 만 있어도 데이터를 망가뜨리는 데는 충분하다.

**무엇이 그 위험을 상쇄하는가** — 두 가지뿐이고 **둘 다 DB 밖에 있다**:

| 수단 | 무엇을 되돌리나 | 한계 |
|---|---|---|
| **주간 mysqldump**(§9, `backup-taskmgr`) | 마지막 덤프 시점까지의 전체 상태 | 그 사이 변경은 못 되돌린다 |
| **binlog 30일**(ROW, §9) | 덤프 시점 이후를 재생 | **기준 스냅샷이 없으면 시작조차 못 한다.** 그리고 CASCADE 로 지워진 자식의 before-image 는 안 남는다(§9 실측) |

**탐지는 상쇄가 아니다.** 폐기한 트리거가 하던 일은 *사후 탐지*였고, 복구는 어차피 위 두 가지가
했다. 탐지 자체도 같은 DB 안에 있어 서버가 죽으면 함께 사라졌다(§7.5).
→ **`grants-calendar.sql` 은 표별 동사와 그 근거의 단일 소스로 유지하되, 근거 문장에서
'감사 트리거가 상쇄한다'를 지우고 위 표를 가리킨다.**

### 7.5 감사 트리거 — **폐기(2026-08-11)**

> 이 절은 **폐기됐다.** 절을 지우지 않고 남기는 이유는 하나다 — 감사 트리거는 이 설계에서
> 두 번(§7.3 조치 표·§7.4 GRANT 근거) 기둥처럼 인용되던 물건이라, 흔적 없이 사라지면
> 다음 사람이 *"삭제 흔적이 안 남는데 왜 아무 대책이 없지?"* 하며 **같은 것을 다시 만든다.**

**무엇이었나** — `DEFINER` 트리거 15개가 `cal_*` 8개 표의 변경 전 행을 `before_img JSON` 으로
`cal_audit_trash` 에 적재했다. 실체는 `db/deploy/triggers-calendar.sql`, 표는 §5.1 명부에 있었다.
**둘 다 폐기한다** — 파일 삭제 · 표 제거 · 배포 순서에서 제외(`db/deploy/README.md`).

**왜 뺐나**

1. **서버 장애 복구에 무력하다.** 휴지통이 **감사 대상과 같은 DB 안**에 있다. 디스크·서버가
   죽으면 원본과 휴지통이 **함께** 사라진다. 즉 가장 큰 데이터 유실 시나리오에서 0의 값어치다.
2. **표준 복구 경로는 덤프 + binlog 다.** 실수·우회 삭제를 되돌리는 실제 수단은 §9 의
   주간 mysqldump + ROW binlog 30일이고, 트리거는 그 위에 얹힌 **탐지**일 뿐 복구가 아니었다.
   그런데 정작 그 복구 수단은 **정책 문장만 있고 실행체가 없었다**(§9). 순서가 거꾸로였다 —
   있어야 할 것을 안 만들고, 없어도 되는 것을 만들어 두었다.
3. **API 서버를 도입하면 어차피 그 계층으로 옮길 물건이다.** 감사는 *"누가 무엇을 했는가"* 를
   남기는 일인데, 지금 구조에서는 **모두가 같은 계정**(`taskmgr_app`)이라 트리거가 남기는
   `CURRENT_USER()` 는 80명 전원에게 동일하다. 행위자를 특정하지 못하는 감사는 감사가 아니다.
   행위자가 갈리는 시점 = API 서버가 서는 시점이고, 그때 그 계층에서 설계한다(§10 의 `cal_app_log` 와 같은 결론).
4. 유지 비용이 실재했다 — 트리거 SQL 은 **모든 컬럼을 이름으로 나열**한다. 스키마가 컬럼 하나만
   바꿔도 트리거를 같이 고쳐야 하고, 안 고치면 조용히 낡은 이미지를 남긴다.
   `schema-calendar.sql` 재실행이 `DROP TABLE` 로 트리거를 함께 지우는 사고 경로도 있었다.

**대체** — 복구는 §9(주간 덤프 + binlog). `DELETE` GRANT 의 정당화는 §7.4 로 옮겼다
(*상쇄가 아니라 필수 동사*라는 것이 실제 근거다).

**재도입 조건** — §10 표 참조. 요약하면 **행위자를 계정으로 구분할 수 있게 된 뒤**(= API 서버 또는
사용자별 DB 계정), 그리고 **감사 기록을 감사 대상과 다른 저장소에 둘 수 있을 때**.

**남겨 두는 실측** — 폐기해도 사실은 사실이다. 재도입 검토 시 다시 재기 말 것:

- FK `ON DELETE CASCADE` 로 지워지는 자식 행은 **트리거가 발화하지 않는다**(실측 0건).
  그래서 자식은 부모 `BEFORE DELETE` 안에서 흡수해야 했다. **같은 성질이 ROW binlog 에도 있어**
  CASCADE 자식의 before-image 가 binlog 에 안 남는다(§9) — 덤프가 필수인 이유가 여기서 나온다.
- 3,000행 삭제 178ms(오버헤드는 문제가 아니었다). 앱 계정은 `SELECT`/`DROP TRIGGER`/`TRUNCATE`
  전부 1142 거부, `information_schema.TRIGGERS` 에서 비가시 — **격리 자체는 의도대로 됐다.**
  폐기 사유는 성능도 격리 실패도 아니고 위의 1~3 이다.

>   권한을 그대로 둔 채 설명만 약화시키는 것이라 실질이 없어 기각했다.

1. FK `ON DELETE CASCADE` 로 지워지는 자식은 트리거가 발화하지 않는다(실측 0건) →

2. 그 성질 덕에 자식 트리거는 **부모 흡수와 중복되지 않는다.** 부모를 지우면 자식 트리거는 돌지 않고
   기록이 부모 쪽 `_except`/`_commits`/`_day_notes` 에만 남으며, **자식만 지우는 앱 경로에서만**
   자식 트리거가 돈다. 즉 둘은 배타적이고 휴지통에 같은 행이 두 번 들어가지 않는다.
   ★ 이 배타성은 가정이 아니라 **양쪽을 다 실행해 확인해야 하는 사실**이다(부모 삭제 → 자식 트리거
   0건 / 자식 단독 삭제 → 1건). 한쪽만 시험하면 어느 쪽 결론도 서지 않는다.

## 8. 이관 (`data.xml` → DB, 1회성)

- **ID 유지** — 기존 문자열 ID 를 PK 로 그대로. 재발급하지 않으므로 **건수·ID 왕복 대조**가
  그대로 게이트가 된다
- **순서** — `cal_category` → 나머지(FK 가 category 를 가리킨다)
- **도구는 INSERT 전용** — UPSERT·REPLACE·선삭제 금지
- **재실행 방지** — `cal_migration_log(login_id PK, source_host, migrated_at)` 를
  **데이터 INSERT 와 같은 트랜잭션**에 넣는다. 행이 있으면 도구는 **거부**한다
  > XML 은 **PC 단위**인데 이관은 **사람 단위**다. 두 자리를 쓰는 사람이 두 번째 PC 에서
  > 또 돌리면 **삭제한 일정이 되살아난다.** 이 프로젝트가 이미 같은 사고를 겪었다 —
  > 구 localStorage 이관의 `lsMigrated` 마커가 그 흔적이다(*"재실행하면 사용자가 지운 값이
  > 되살아나므로(좀비) 절대 주기 실행하지 않는다"*).
  > *베타 단계에서는 두 PC 에 XML 을 구축한 사례가 없다 — 다만 같은 PC 재실행 방지로도 유효하다.*
- **두 PC 의 XML 을 자동 병합하지 않는다** — 앱의 「가져오기(병합)」은 ID 기준이라 두 벌이 된다.
  사람이 한쪽에서 내보내기 → 다른 PC 에서 **교체**로 합친 뒤 그 파일 하나만 올린다
- **누락 필드 기본값** — XML 은 빈 값이면 속성을 생략한다. **파서가 이미 쓰는 기본값과 같은 값**을
  DB 기본값으로 둘 것
- **`<entry>` 의 `hours` 속성은 이관하지 않는다** (2026-08-11 추가). XML 에는 남아 있고 파서도 계속
  읽지만, **받을 컬럼이 DB 에 없다**(§5.3 — `cal_entry` 의 분 단위 공수 컬럼을 제거했다).
  → 어댑터가 **읽고 버린다.** 대조 서명에도 넣지 않는다.
  · **왕복 대조 게이트가 이것 때문에 빨간불이 되면 안 된다** — 서명 정의(아래 표)에서 애초에
    제외돼 있으므로 정상 이관은 통과한다. 반대로 서명에 넣으면 DB 쪽에 대응 값이 없어
    **모든 사용자의 이관이 불일치로 뜬다.**
  · 값이 아깝다고 `cal_task_hours` 로 합산해 옮기지 말 것. 단위(분 vs 시간)도 키(일정 vs 날짜×과제)도
    다르고, 사용자가 이미 손으로 넣은 `<taskHours>` 와 **이중 계상**된다.
  · 이관 도구는 버린 건수를 리포트에 **한 줄로 보고**한다(조용히 버리지 않는다).
- **`''` → `NULL` 변환은 어댑터 단일 함수로 강제한다.** 대상 컬럼 8개와 각각의 결과(무음 오염 3 /
  시끄러운 실패 5)는 [`schema-calendar.sql`](deploy/schema-calendar.sql) 헤더가 앱 줄번호와 함께 열거한다 —
  여기 다시 적지 않는다
- **`cal_category.updated_at` 은 `created_at` 을 그대로 복사한다** (2026-08-10 추가). 원본이 없다:
  `toXML` 의 category 직렬화가 쓰는 것은 `id`·`color`·`gitRepo`·`svnRepo`·`createdAt`·`source`·`dbGone`
  + `<name>`·`<description>` 뿐이고 **`updatedAt` 이 없다**(4540-4558 직접 확인).
  컬럼은 `NOT NULL` 무DEFAULT 라 이관 INSERT 가 그 자리에서 `ERROR 1364` 로 멈춘다.
  > **왜 '이관 시각'이 아닌가** — 그러면 전 사용자의 모든 과제가 '방금 수정됨'이 되어, 부팅 직후
  > 사용자가 들고 있는 `@prev` 와 어긋나 **첫 편집이 전부 §3.3 충돌 오탐**이 된다.

  `cal_user_pref.updated_at` **만** 이관 시각을 쓴다 — 복사할 원본이 아예 없고(루트 속성에 시각이
  없다), 사용자당 1행이라 오탐 위험이 과제만큼 크지 않다. 예외라는 사실을 스키마 주석에도 남겼다.
- **`cal_category.project_uid` 는 파생값이다** (2026-08-10 추가). XML 에 대응 속성이 없다.
  규칙: `source='db'` 이면 `project_uid = SUBSTRING(id, 4)`.
  **단 `id` 가 `db-` 로 시작하고 나머지가 정확히 36자일 때만**(공식 과제 id 는 `'db-' + project.uid`,
  prototype:3681 확인).
  조건에 안 맞는 `source='db'` 행은 **조용히 버리지도, 추측해 채우지도 않는다** — 이관 도구가
  사람에게 보고하고 **중단**한다(아래 "버리지 않는다" 와 같은 태도).
  > 왜 중단인가: `fromXML` 의 `safeId`(4706, `/^[A-Za-z0-9_-]{1,80}$/`)가 id 를 재발급하면 `db-` 접두가
  > 사라져 **복원 근거가 영구 소실**된다. 그 상태로 넣으면 `chk_cal_category_projuid` 가 `ERROR 3819` 를
  > 내고, 이관이 단일 트랜잭션이라 그 과제에 달린 일정·공수까지 함께 막힌다.
  > 도구가 고칠 수 있는 문제가 아니라 **사람이 원본 XML 을 보고 정해야 하는 문제**다.
- **중복 제거 — 반복 예외일(`cal_entry_except`)** (2026-08-10 추가, **08-10 확대**).
  PK 가 `(login_id, entry_id, except_date)` 인데 **앱은 예외일을 어디서도 dedup 하지 않는다**
  (직접 전수 확인): 파싱(4752)은 `filter(isRealDate)` 뿐, 정규화 두 곳(3591·4423)은 `YYYY-MM-DD`
  **형식 필터일 뿐 중복을 보지 않으며**, 추가 경로(10152·10493)는 `[...prev, occDate]` 로 `includes`
  가드 없이 덧붙이기만 한다. 같은 날짜가 두 번 들어오면 실측 `ERROR 1062` 로 **다중행 INSERT 문
  전체가 0행 삽입**이 되고, 단일 트랜잭션이라 그 사용자의 이관 전체가 롤백된다.
  → **dedup 은 이관 도구가 아니라 어댑터가 저장 직전에 항상 한다. 이관 도구도 같은 함수를 쓴다.**
  **왜 '이관 전용'이 아닌가**(이 항목이 처음에 이관 절에만 있었던 것이 좁았다): 중복은 XML 안에서
  끝나지 않는다. 「가져오기」로 들어온 XML 의 중복 예외일은 파서가 그대로 통과시켜 `state` 에 남고,
  그 `state` 를 저장하는 **런타임 쓰기가 똑같이 1062 를 맞는다.** 화면은 이 상태를 보여주지도 않는다 —
  전개 로직(3183)이 `includes` 로 건너뛰기만 해서 **중복이 있어도 UI 는 정상으로 보인다.**
  즉 이관 도구에만 dedup 을 두면, 그 함수를 타지 않는 저장 경로가 전부 구멍이다.
  · 이관 도구는 그 위에 **제거 건수를 왕복 대조 리포트에 별도 줄로 보고**한다
  (조용히 줄이면 아래 건수 대조가 불일치로 뜬다).
- **시각 변환 — XML 원형을 그대로 INSERT 하면 첫 줄에서 멈춘다** (2026-08-10 추가).
  `toXML` 은 `nowIso()`(= `new Date().toISOString()`, 3148) 산출물을 XML 속성에 **그대로** 쓴다.
  즉 `data.xml` 안의 모든 시각이 `2026-08-10T02:33:44.123Z` 형태다. 실측(8.4.9):
  원형 그대로 → **`ERROR 1292`**, `'T'`·`'Z'` 를 벗긴 `2026-08-10 02:33:44.123` → 통과.
  이관은 단일 트랜잭션이라 **첫 행에서 전체가 롤백**된다.
  → 어댑터가 `'T'`·`'Z'` 를 벗겨 `yyyy-MM-dd HH:mm:ss.fff` 로 보낸다. **소수는 정확히 3자리.**
  대상 컬럼(XML 에서 값이 오는 것 전부)과 줄번호 근거는
  [`schema-calendar.sql`](deploy/schema-calendar.sql) 헤더가 열거한다 — **여기 다시 적지 않는다**
  (`''`→`NULL` 목록과 같은 취급이다. 둘은 **별개의 계약**이니 한 함수에 뭉뚱그리지 말 것).
  · 시각을 **이관 도구가 직접 만드는** 두 컬럼(`cal_user_pref.updated_at`·`cal_migration_log.migrated_at`)은
  XML 을 안 거치므로 이 변환 대상이 아니지만, **도구가 그 값을 만들 때 같은 형식 규칙을 지켜야 한다.**
  · **소수 3자리가 왜 1292 보다 무거운가**: 4자리 이상은 오류도 경고도 없이 **반올림**된다(§3.3 표).
  1292 는 시끄러워서 반드시 잡히지만 반올림은 이관을 성공시킨 뒤 **그 사용자의 첫 편집을 전부
  충돌 오탐으로 만든다.** `toISOString()` 은 항상 3자리라 앱 경로는 안전하다 — **위험한 쪽은
  다른 언어로 짠 이관 도구다.**
- **`source='db'` 인데 `project` 에 없는 과제** — 버리지 않는다(그 과제에 달린 일정이 미아가 된다)
- **INSERT 는 다중행 배치 필수** — 단건 15,500문 2,237ms → 500행 배치 33문 **624ms**(락 보유 0.34s)
- **청크 커밋 분할 금지** — 원자성을 잃고 왕복 대조 게이트가 무효화된다

### 게이트 — `xmlRoundTrip()` 은 재사용할 수 없다

그 함수는 **DB 를 볼 수 없고**(전역 state 를 XML 로 자기왕복하는 자가진단), 서명이 양방향으로
어긋난다: 커밋 **body 없음**(§2 가 "무게의 대부분"이라 한 데이터), entry/todo/category
**createdAt/updatedAt 없음** → **손실이 초록불로 통과**한다. 반대로 §4 가 이관 제외한
`gitRepo`·`svnRepo` 를 비교해 **정상 이관이 실패**한다.

**이관 전용 서명**을 따로 만든다:

| 대상 | 포함 |
|---|---|
| 커밋 | `hash · short · time · subject · **body**` |
| 엔트리·할일 | 필드 + `created_at` · `updated_at` |
| 카테고리 | 필드 + `created_at` · **`updated_at`** · **`sort_order`** |
| 공수 | 소수 **2자리 원값** |
| 제외 | 범위 밖 필드 · `source='db'` 행의 name · `cal_user_pref.updated_at`(아래) |

자식 테이블 포함 **건수 대조**를 독립 항목으로 둔다.
예외일 dedup 으로 줄어든 건수는 **별도 줄로 보고**한다(위 중복 제거 항목) — 안 그러면 정상 이관이
건수 불일치로 뜬다.

**`updated_at` 을 서명에 넣는 이유**(2026-08-10 추가): 카테고리의 `updated_at` 은 XML 에 원본이 없어
위에서 *`created_at` 복사* 로 규칙을 정했다. 규칙만 적어 두면 잘못 채운 값이 **초록불로 통과**한다.
그래서 **원본 쪽 서명에는 `createdAt` 을, DB 쪽 서명에는 `updated_at` 을 넣어 대조**한다 —
이관 시각 등을 채우면 그 자리에서 불일치로 뜬다.
`cal_user_pref.updated_at` 은 반대로 규칙이 *'이관 시각'* 이라 대조할 원본이 없다 → **서명에서 제외**하고,
"이관 시각과 같은가" 를 이관 도구의 자체 점검 항목으로 둔다.

### 「가져오기」는 유지한다 — 병합 포함

현행 도움말이 *"XML 가져오기로 복원합니다"* 라고 안내하고, 실수 복구는 **[병합]** 이 담당한다.
병합을 제거하면 **앱이 공식 안내하던 유일한 비파괴 경로가 사라진다** = 현행 대비 안전성 후퇴.

- **병합** = `INSERT IGNORE` 한 문장(실측 3,000→3,001, 기존 행·커밋 무손실). DB 에서는
  오히려 교체가 더 복잡하다(전량 DELETE + FK 순서 재삽입)
- **교체**는 ⋯ 메뉴 2단계로 강등. 전량 DELETE + INSERT 를 **한 트랜잭션**
- 확인 모달에 **커밋 건수를 서버 COUNT 로 별도 조회**해 표시(커밋은 지연조회라 state 에 없어
  현재 모달 숫자는 4배 거짓말이 된다) + "되돌릴 수 없습니다" + XML 이 DB 보다 오래되면
  기본 포커스 [취소]
- 교체 직전 **현재 DB 상태를 로컬 XML 로 자동 저장**(`pre-import-<ts>.xml`)
- 삭제 대상에서 **`cal_user_rev` 명시적 제외**(rev 는 단조증가)
- **가져오기 중 동시 쓰기**: rev 락 규약(§3.1)을 그대로 쓰면 그 사용자의 쓰기가 직렬화된다
  (실측: 같은 사용자 1205 차단, 다른 사용자 통과, 전량 교체 완전)

### 중앙 앱 로그 테이블(`cal_app_log`)은 만들지 않는다 — 폐기(2026-08-10)

이 절에는 세 번째 층으로 `cal_app_log` 테이블이 있었고 §5.1 명부에도 올라 있었다. **폐기한다.**
근거는 이 절이 *스스로 적어 두었던 한계* 그대로다:

- **위조 가능** — 클라이언트가 쓴다. 앱을 우회한 사람은 로그를 안 남긴다.
  **정작 남기고 싶은 행위가 안 남는 로그**다
- **DB 다운 시 못 남김** — 로그가 가장 필요한 순간에 못 쓴다. 그래서 어차피 `widget.log` 를 유지해야 하고,
  그러면 중앙 테이블은 두 벌째가 된다
- 사용자별 앱 로그를 DB **테이블**로 관리하는 것 자체가 통상적인 구조가 아니다

→ **중앙 앱 로그는 API 서버를 도입할 때 그 계층에서 다룬다.** 그때는 쓰는 주체가 서버라 위조 불가가
되어 위 세 한계가 한꺼번에 사라진다. **그때까지 클라이언트 로그는 `widget.log` 하나다.**

  변경 이력은 binlog 가, 되돌리기는 아래 **백업** 이 담당하지만 **탐지(누가 우회했는가)는 공백**이다.
  그 공백은 **행위자를 계정으로 구분할 수 있게 될 때**(API 서버 / 사용자별 계정) 메운다 —

### 백업 — 정책만 있고 **실행체가 없었다**(2026-08-11 에 만들었다)

> **★ 그 문장이 전부였다.** `binlog_expire_logs_seconds=2592000` 은 서버 기본값이라 저절로 참이었고,
> **주간 mysqldump 를 실제로 돌리는 것은 이 저장소에도 서버에도 없었다.** 한 줄도.

> 담당한다"* 고 적었다 — **복구의 절반이 존재하지 않는 상태에서 다른 결정들이 그것을 근거로 서 있었다.**
> 감사 트리거는 만들어 두고 백업은 안 만든 것이 §7.5 폐기 사유 2 의 *"순서가 거꾸로"* 다.
>

> 여기에는 **왜 그 형태여야 하는지**만 남긴다.

#### binlog 는 백업이 아니다 — 기준 스냅샷이 없으면 재생을 시작할 수 없다

binlog 는 **변경 이력**이다. *"어느 상태에서 출발해 이 변경들을 적용하는가"* 의 그 **어느 상태**를
스스로 갖고 있지 않다. 기준이 되는 덤프가 없으면 30일치 binlog 를 손에 쥐고도 **재생을 시작할 지점이
없다**(`mysqlbinlog | mysql` 은 빈 DB 를 채워 주지 않는다 — `CREATE TABLE` 이 그 안에 있다는 보장도 없고,
로그가 회전돼 30일 전 이후만 남으면 그 앞은 영영 없다).

정리하면 역할이 겹치지 않는다:

| | 무엇 | 없으면 |
|---|---|---|
| **주간 mysqldump** | **기준 스냅샷.** 그 시점의 전체 상태 | binlog 가 있어도 **복구 불가**(출발점 없음) |
| **binlog 30일** | 스냅샷 **이후의 변경 이력** | 마지막 덤프 이후 최대 7일치 유실 |

→ **둘 다 있어야 하나가 성립한다.** 어느 하나를 "다른 하나가 있으니 됐다"로 대체하지 말 것.

#### ★ 덤프는 exit 0 으로 끝나고도 통째로 비어 있을 수 있다 — 내용 대조가 필수다

**메인 실측(8.4.9).** 백업 전용 계정에 `SELECT` 만 주고 `mysqldump` 를 돌렸다:

| 백업 계정 권한 | 결과 | 산출물 |
|---|---|---|
| `SELECT` 만 | **exit 0**, 화면에 오류 없음 | **48K** — **트리거가 통째로 빠짐** |
| 필요한 권한 전부 | exit 0 | **72K** — 트리거 포함 |

**24K 가 조용히 사라졌는데 종료코드는 0 이었다.** `mysqldump` 는 권한이 없어 못 읽은 객체 종류를
**건너뛰고 성공으로 끝낸다.** 그러니:

- **종료코드만 보는 백업 점검은 점검이 아니다.** 스케줄러가 초록불을 켠 채 몇 달간 반쪽 덤프를
  쌓아 두는 시나리오가 실재한다 — 그리고 그건 **복구하려는 날에야** 드러난다
- → **덤프 내용을 대조한다**: 표 개수 · 표별 행수 · 파일 크기가 직전 회차 대비 급감하지 않았는지.
  기대값의 출처는 DB 자신(`information_schema`)이지 덤프 파일이 아니다
  (덤프를 파싱해 기대값을 만들면 §7.5 가 지적한 *"자기 자신을 기준으로 삼는 게이트"* 가 된다)
- 이 실측은 트리거로 드러났지만 **트리거만의 문제가 아니다.** 같은 성질이 루틴·이벤트·뷰에도 있고,
  캘린더 트랙에서 트리거를 폐기한 지금도 **과제 트랙과 앞으로 생길 객체**에 그대로 남는다.
  그래서 백업 계정 권한을 깎는 최적화는 하지 말 것 — **덜 준 만큼 조용히 덜 담긴다**

**★★ 그런데 내용 대조만으로도 부족하다** — `information_schema.TRIGGERS` **자체가 `TRIGGER` 권한으로
걸러진다.** `SELECT` 만 가진 계정 눈에는 **DB 쪽 트리거 수도 0** 으로 보이므로, 덤프의 0 과 DB 의 0 이
같아서 **대조까지 초록불로 통과한다**(실측: 같은 DB 를 SELECT 만으로 세면 0, TRIGGER 까지 있으면 3).

> 이것이 이 절에서 가장 값나가는 교훈이다 — **검증 기준을 검증 대상과 같은 권한으로 읽으면
> 그 게이트는 자기 자신을 속인다.** §7.5 가 지적한 *"검증 대상 파일을 파싱해 기대값을 만드는 게이트"* 와
> 같은 결함이 여기서는 **권한 경계**를 통해 나타난다.
> → 그래서 백업 도구는 덤프 **전에** `SHOW GRANTS` 로 필요한 권한 보유를 먼저 확인한다.
> 두 겹(사전 권한 확인 + 사후 내용 대조) 중 **실제로 걸러 내는 겹은 사전 확인**이다.
> 계정 정의와 그 근거는 `db/deploy/create-backup-user.sql` 이 단일 소스다.

#### 어디에 두는가

**같은 볼륨에 두면 백업이 아니다.** 디스크가 죽는 시나리오가 백업이 존재하는 첫째 이유인데,
원본과 같은 디스크에 있으면 그 시나리오에서 함께 사라진다 — §7.5 가 감사 휴지통을 폐기한 것과
**정확히 같은 논리**다(같은 DB 안 → 같은 볼륨 안). 다른 볼륨 / 네트워크 공유에 둔다.

## 10. 검토했다가 버린 안 (재론 방지)

| 안 | 왜 버렸나 | 다시 볼 조건 |
|---|---|---|
| **읽기 전용 로컬 사본**(`cache.xml`) | 상태 전이(오프라인·사본 → 온라인 → 편집 해제)를 데려오고, 자동화하려면 연결 폴링 타이머가 필요하다. 낡은 사본은 빈 화면보다 나쁠 수 있다("오늘 회의 없네") | — |
| **자동 재시도 타이머** | 재진입 가드·생명주기·예외 안전이 따라온다. 무엇보다 **서버에 붙어보지도 않았고** 고장 빈도 데이터가 0 이다(YAGNI) | *"위젯이 비어 있다"* 문의가 반복되면. **데이터 없을 때만 도는 자기 종료형**으로 |
| **범위(월) 조회** | 무게가 커밋에 있었고 커밋만 떼면 불필요해진다. 데려오는 복잡성이 전부 실재한다 — 월 상태 관리, **반복 일정을 범위로 못 거름**(종료일 없으면 2020년 시작이 2026년에 떠야 한다), 월 경계 중복, 서버 검색 | 커밋을 뺀 뒤에도 부팅 전송량이 수 MB 를 넘으면 |
| **tombstone(소프트 삭제)** | 오프라인 동기화가 없어 "지웠는지/못 받았는지" 모호함이 생기지 않는다. 넣으면 모든 조회에 `WHERE is_deleted=0` 이 강제되고 한 군데만 빠뜨려도 지운 일정이 화면에 나온다 | — (실수 복구는 **주간 덤프 + binlog**(§9)가 담당한다. 2026-08-11 정정: 여기 "binlog + 감사 트리거"라고 적혀 있었으나 트리거는 폐기됐고, 애초에 트리거는 탐지지 복구가 아니었다) |
| **rev 락 제거** | 제거하면 §8 의 전량 DELETE 가 낙관적 잠금(UPDATE 전용 감지기)을 빠져나가 **affected=1 "저장되었습니다" 직후 행이 사라지는 조용한 유실**이 재현된다. 대기 단축은 0.016초뿐 | — |
| **JSON 컬럼으로 테이블 통합** | 기존 스키마에 JSON 이 하나도 없어 관례가 갈리고, **DB 가 형식을 못 막는다**(ADR#22 가 코드테이블을 택한 이유). 이관 검증도 문자열 비교라 약해진다 | — |
| **사용자별 MySQL 계정** | 이 시스템은 **비밀번호 개념이 없다**(인증=netcus 위임, `app_user` 에 비번 컬럼 없음). 두 번째 자격증명 체계 신설 = 확정 로그인 설계 역행. 입퇴사마다 DB 계정 관리 | — |
| **접속정보 암호화·난독화** | §7.2 — 복호화 키도 같이 배포된다. 거짓 안심만 만든다 | — |
| **파티셔닝** | 실측 `ERROR 1506` — FK 와 함께 못 쓴다. 파티션 키를 PK 에 넣어야 해 스키마도 뒤틀린다 | — |
| **`user_uid` 대리키 전환** | 다중경로는 구조적으로 동일하고, `app_user` 운영 ALTER + 신원 모델 재배선이 따른다 | API 서버 세울 때 |
| **중앙 앱 로그 테이블**(`cal_app_log`) | 클라이언트가 쓰므로 **위조 가능**하고(앱을 우회한 자는 안 남긴다), **DB 다운 시 못 남긴다**(정작 필요한 때). 사용자별 앱 로그를 DB 테이블로 관리하는 것 자체가 통상 구조가 아니다. §9 가 그 한계 셋을 스스로 인정하고 있었다. 이관 로깅은 1회성 도구의 자체 리포트 + `widget.log` 로 대체된다(우회 탐지를 감사 트리거가 대체한다고 적었었으나 **그 트리거도 폐기됐다** — 아래 행) | **API 서버를 세울 때.** 쓰는 주체가 서버로 바뀌면 위조 불가가 되어 세 한계가 한꺼번에 사라진다. 그때 그 계층에 맞게 새로 설계한다(지금 만든 테이블을 물려주지 않는다) |
| **감사 트리거 + 휴지통 표**(`trg_cal_*` · `cal_audit_trash`) — **만들었다가 뺐다(2026-08-11)** | **① 서버 장애 복구에 무력** — 휴지통이 감사 대상과 **같은 DB 안**이라 디스크·서버가 죽으면 같이 사라진다. **② 표준 복구 경로는 덤프 + binlog** 이고 트리거는 그 위의 *탐지*일 뿐 복구가 아니었다 — 정작 그 덤프는 정책 문장만 있고 **실행체가 없었다**(§9). **③ 행위자를 특정하지 못한다** — 80명이 `taskmgr_app` 한 계정을 공유해 `CURRENT_USER()` 가 전원 동일하다. **④** 컬럼을 이름으로 전부 나열해 스키마 변경마다 동반 수정이 필요했고, `schema-calendar.sql` 재실행이 `DROP TABLE` 로 트리거를 조용히 지웠다. 상세는 §7.5 | **두 조건이 동시에** 충족될 때: **㉠ 행위자가 계정으로 갈릴 것**(API 서버 도입 또는 사용자별 DB 계정 — 지금 구조에선 무엇을 남겨도 "누가"가 안 나온다) **㉡ 감사 기록을 감사 대상과 다른 저장소에 둘 수 있을 것**(다른 서버/볼륨. 같은 DB 안이면 ①이 그대로 재발한다). ㉠만 충족되면 그때는 트리거가 아니라 **API 계층 감사 로그**가 답이다(`cal_app_log` 행과 같은 결론) |
