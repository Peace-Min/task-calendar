## 1. 한눈에 보기

- **목적**: 사업부 과제(사업/프로젝트) 목록을 캘린더 앱에서 조회·편집하는 시스템.
- **데이터 원본**: **DB가 원본(source of truth)**. Admin(+확인된 유저)이 앱에서 편집, Excel은 DB에서 뽑는 리포트.
- **엔진**: **MySQL** (SQLite 아님 — 이유 §4.3).
- **배포**: 사용자는 **앱만 설치**(MySQL 설치 불필요). 중앙 DB는 **폐쇄망 PC(고정 IP)**가 임시 서버 → 나중에 전용 박스/회사 서버로 이관.
- **동작 규칙**: **조회 = 온라인 필요(로컬 캐시 없음)**, **편집 = 온라인일 때만**. 서버에 못 붙으면 공식 과제 목록은 비어 있다. 이미 태그된 일정의 **라벨(과제명·색)만** 로컬에서 해석된다(§4.7.4).
- **접속 주소**: 사용자 설정이 아니라 **배포 구성(베이크)** — 배포자가 `ProjectDb.cs` 상단 "★ 배포 구성" 상수를 설정하고 빌드·배포한다. 지금 `localhost` → 폐쇄망 IP → 나중 서버 IP로 교체(재빌드·자동업데이트로 전파). 상세 §4.6.

## 3. 확정 데이터 모델 (요약)

2 테이블 (상세는 `schema.sql`):
- **`customer`** — 발주처 마스터. `name` PK(자연키) + `is_active` + 감사.
- **`project`** — 과제 마스터. `id` PK(내부 대리키·autoinc) + **`uid`(외부 안정 참조키, UUID assign-once — 일정이 `db-<uid>`로 참조)** + `section`/`status` ENUM + `customer` FK(ON UPDATE CASCADE) + 사업명 + 계약명·통상명칭(`NOT NULL DEFAULT ''`) + 시작/종료일 + `is_active` + 감사. 유니크는 **`UNIQUE(uid)` 하나뿐** — 이름 기반 하드 유니크(`(customer, project_name)`)는 **제거**했다(ADR-21: 실데이터에 정당한 중복 다수, 실수 중복은 앱 소프트 경고로). 상세: [`TABLE-DESIGN.md`](TABLE-DESIGN.md) §4.

편집 권한 통제를 위해 **`app_user` 테이블이 추가될 예정**(§5, 앱 연동 단계에서).

## 4. 배포 아키텍처

### 4.1 MySQL은 "파일"이 아니라 "서버"다
MySQL은 항상 서버 프로세스가 떠 있어야 하는 **클라이언트-서버** DB다. 데이터 파일만 복사해선 못 읽는다.
- **한 대(중앙)에만** MySQL 서버 설치.
- 나머지는 **네트워크로 접속하는 클라이언트**.

### 4.2 사용자는 앱만 있으면 된다 (MySQL 설치 불필요)
앱 안에 접속 기능(커넥터)이 내장되므로, 일반 사용자 PC엔 **MySQL 설치 불필요**. 앱만 배포.
> ⚠️ 사용자마다 각자 로컬 MySQL을 깔면 → 각자 따로 노는 별개 DB가 되어 **공유 불가**. 하지 말 것.

### 4.3 SQLite를 검토했으나 기각
"DB 파일을 앱에 번들해 설치 없이 읽기"는 SQLite에 맞는 모델이지만 **기각**:
- **편집자가 여럿**(Admin + 확인된 유저)이라 각자 파일을 고치면 **병합 불가**(갈라짐).
- "승인된 유저만 편집"을 강제할 **중앙 권한소**가 필요.
→ 중앙 저장소 = **서버 MySQL**이 맞다. 또한 최종 목적지가 서버라면 `MySQL(로컬)→MySQL(서버)`가 같은 엔진이라 전환 비용이 거의 없다(SQLite→MySQL은 중간 공수 발생).

### 4.4 중앙 DB 위치 — 단계적
| 단계 | 위치 | 비고 |
|---|---|---|
| 개발 | 이 외부망 PC `localhost` | DHCP 무관 |
| **임시 운영** | **폐쇄망 PC(고정 IP)** | 이미 고정 IP 설정됨 |
| 최종 | 전용 상시가동 박스 / 회사 서버 | 배포 구성 상수만 교체·재빌드(§4.6) |

내 메인 PC를 서버로 쓰면 꺼졌을 때 **조회·편집이 모두** 멈춘다(캐시가 없으므로). 캘린더 본체(일정·할일)는 로컬 XML이라 계속 쓸 수 있다. 더 깔끔한 임시안은 안 쓰는 PC를 상시 켜두는 것.

### 4.5 조회·편집 모두 온라인 only (로컬 DB 캐시 없음)
- **조회**: 앱은 과제 목록을 **캐싱하지 않는다** → 서버에 못 붙으면 목록은 빈 상태이고 그 사실을 화면에 명시한다. (2026-07-24 정정 — ADR-18)
- **편집**: **중앙 DB에 연결될 때만** 허용(바로 DB 저장). 연결 안 되면 편집 버튼 비활성(읽기 전용).
- **오프라인 편집은 만들지 않는다** — 동기화 큐·충돌 해결이 필요해 무겁고, 편집이 월 2~3회뿐이라 불필요. "편집하려면 서버 온라인" 제약이 충돌 문제를 통째로 없앤다.
- 이 로직은 **서버 이관 후에도 동일**(중앙 DB 주소만 바뀜).

### 4.6 접속 정보 = 배포 구성 (베이크) — 2026-07-21 개념 정정
~~설정 파일 외부화~~ → **DB 접속 정보(호스트/포트/계정/비번)는 사용자 설정이 아니라 "배포 구성"이다.**
- **배포자(Admin)가 배포 전 호스트 코드의 디폴트 상수(`ProjectDb.cs` 상단 "★ 배포 구성" 블록)를 설정하고 빌드·배포.**
- 일반 사용자에겐 연결 설정 UI가 **아예 없음**(만질 이유도, 만져서 고장날 일도 없음). 설정창의 관리자 섹션엔 **상태 배지 · (미인증) 비밀번호+인증 버튼 · (인증됨) 해제 + 비밀번호 변경 · DB 상태줄·새로고침**이 있다. **인증은 설정에서만 한다** — netcus 자격증명과 같은 구조다(2026-07-24, ADR #19). 편집을 누른 순간에 비번을 묻던 just-in-time 프롬프트는 **제거**했다. 미인증 상태에서 편집을 누르면 안내와 함께 **설정 열기**로 유도만 한다. 인증 상태는 **이 PC에 영속**되어 앱을 다시 켜도 유지되며(`db-config.json`의 `adminUnlocked`), **해제** 버튼으로 잠근다.
- **비밀번호 변경은 인증된 상태에서만 가능**하다. UI에서 변경 블록을 숨기는 것에 더해 **호스트(`ProjectDb.SaveAdminCred`)가 `adminUnlocked==false`면 거부**한다 — 브리지 메시지는 웹에서 직접 던질 수 있어 클라이언트 검사만으론 우회되기 때문이다(ADR #19). 변경에 성공해도 관리자 모드는 **유지**된다(같은 사람이 바꾼 것이라 재인증은 불필요한 마찰).
- **비밀번호 분실 복구**: `db-config.json`을 삭제하면 배포 구성(`DeployConfig`)의 베이크 디폴트로 되돌아가고, 그 값으로 다시 인증해 새 비밀번호를 정하면 된다.
- 이유: 폐쇄망·전원이 같은 서버·고정 IP — 접속 정보는 사용자 취향이 아니라 배포 환경의 속성.
- 서버 이관 시: 디폴트 상수만 바꿔 재배포(자동업데이트로 전파). 지금 개발값=`localhost`.
- 관리자 자격도 코드 디폴트(admin/1234) + 설정 "등록"으로 변경 가능(변경분만 `db-config.json`에 평문 저장). P6.5에서 app_user·최소권한 계정으로 교체.

### 4.7 개인(로컬) 과제와 공식(DB) 과제의 공존
캘린더는 이미 배포·사용 중이라, 사용자들이 **로컬로 직접 만든 과제(개인 카테고리)**와 그것으로 태그된 일정이 존재한다. 처리 방침(구현 확정):
- **기존 개인 과제 + 태그된 일정은 그대로 둔다** — 손대지 않음. 강제 이관·매핑 없음(폐쇄망·분산이라 지저분).
- **피커·필터는 공식(DB)과 개인 과제를 둘 다 보여준다.** 피커는 단일 목록(`state.categories`)을 출처로 그룹핑한다(공식 그룹 + 개인 그룹). **개인 과제 생성도 계속 허용**한다 — "새 과제는 DB만"은 **공식 과제에 한정된** 규칙이지 개인 과제를 막는 규칙이 아니다.
- 공식/개인은 참조에 출처가 박혀 절대 안 섞인다(공식=`db-<uid>`, 개인=`c-…` 등). 옛 일정을 편집해도 카테고리를 안 건드리면 참조 그대로 유지, 다른 것으로 바꾸면 그 시점에 참조가 교체된다(**개인↔공식 재선택 자유** — 단방향 아님).
- **재연결은 로컬 쓰기다.** 개인 과제로 태그된 일정·할일을 공식 과제로 **일괄 재태그**(entries/todos의 `categoryId` 교체)하는 도구를 제공한다. DB엔 아무것도 쓰지 않으므로 **오프라인에서도 동작**한다(상세 §4.7.1·§4.7.3).
- **중복 처리 안 함** — 현재도 과제명 중복을 막지 않으므로 회귀 아님. 로컬·DB에 동명이 있어도 각자 존재.
- **귀결**: 앞으로 필요한 **공식** 과제가 DB에 없으면 **Admin이 DB에 추가**(개인 과제는 누구나 계속 생성) — 'DB 원본' 취지(집계 대상은 공식만)와 일치.
- 옛 일정의 과제 참조가 깨지지 않도록 위젯의 **로컬 해석 저장은 유지**한다 — DB 유래 과제도 단일 목록에 편입돼 XML에 영속되므로 오프라인에도 라벨이 산다(§4.7.4).

#### 4.7.1 안 꼬이게 하는 규칙 (불변식 — 강제, 구현 반영)
카테고리 참조 혼동이 최대 위험. 아래를 **불변식으로 강제**한다:

**참조 네임스페이스**
- DB 과제 카테고리 id는 네임스페이스를 붙인다: **`db-<project.uid>`**(예: `db-8d731cec-7f69-...`). 그 외(기존 형식 `c-<uuid>` 등)는 전부 **개인(로컬)**로 간주.
- ⚠️ **콜론 금지(구현 확정)**: 위젯의 XML import 검증기 `safeId`가 categoryId를 `/^[A-Za-z0-9_-]{1,80}$/`로 검사한다(prototype.html **L3777**). 콜론이 들어가면 검증 실패 → `uid()`로 재생성돼 **DB 링크 소실**. 그래서 `db:`가 아니라 **`db-`**(하이픈)를 쓴다. UUID(하이픈 포함)와 합쳐도 이 정규식 통과.
- 로컬 id는 단일문자 접두(`c-`,`t-`,`e-`) → `db-`(2문자 접두)와 안 겹침. 판정 = `id.startsWith('db-')`(헬퍼 `isOfficialId`).
- 두 id 공간이 절대 겹치지 않음. 일정이 자기 카테고리 출처를 스스로 안다.
- 기존 일정은 형식 그대로 두면 자동으로 "개인"으로 해석됨 → **일괄 마이그레이션 없음**(참조된 고아 `db-*`만 자동 편입, §4.7.4).
- 안정성: `db-<uid>`는 UUID라 rename·덤프복원·재이관에도 불변(autoinc id와 무관). 안전.

**과제 태그 일정 편집 플로우 (구현)**
1. 편집 열면 피커에 **공식(DB) 그룹 + 개인 그룹**이 모두 나온다(단일 목록을 출처로 그룹핑).
2. 카테고리 안 건드리고 저장 → 기존 참조 그대로 기록(재해석·재작성 금지).
3. 다른 과제 선택 → 그 시점에 참조가 교체된다. **개인↔공식 어느 방향이든 재선택 자유**(단방향 아님).
4. 카탈로그를 못 읽은 상태(오프라인)의 `db-*` 값도 피커에 옵션을 주입해(`ensureCatOption`) 저장 시 값이 유실되지 않는다.

**해석(표시) 규칙 — 절대 안 깨짐 (구현)**
- 모든 태그는 **단일 목록(`state.categories`) 우선 → 미편입 `db-*`는 `dbCatalog` 폴백 → null** 순으로 해석(`catById`). 전시 코드는 출처를 모른 채 `{id,name,color}`만 소비.
- DB에서 소프트삭제되어 카탈로그 활성목록에서 사라진 과제는 편입분에 **`dbGone` 마크**를 달고 **마지막으로 동기화된 이름·색을 그대로 유지**한다(피커·필터 신규선택에서만 숨김, 태그된 라벨은 계속 해석).
  **단 오프라인에서는 `dbGone`을 판단하지 않는다** — 카탈로그를 못 읽은 것과 삭제된 것은 다른 사실이라, 연결이 끊겼다고 편입분이 피커에서 사라지면 안 된다(`syncSubscribedDbMeta`가 `dbOnline`일 때만 동작).
- 어디에서도 못 찾으면 `(공식 과제)` 플레이스홀더로 편입 → 빈칸·크래시 없음.

**불변식 목록**
1. 두 id 공간 네임스페이스 분리 → 혼동 불가.
2. 모든 참조가 출처 자기기술(`db-` 접두 유무).
3. 기존 데이터 무변경(참조된 고아 `db-*` 자동 편입만) → 마이그레이션 버그 0.
4. 안 건드린 카테고리는 저장 시 그대로 보존(자동 재작성 금지).
5. 개인 과제는 계속 생성·사용 가능(동결 아님). 공식 과제만 Admin이 DB에서 관리.
6. 해석은 항상 성공 — 편입분의 마지막 이름·색 유지 + `dbGone` 마크 + `(공식 과제)` 플레이스홀더.

> **미구현(향후)**: 각 일정에 태그 시점 `{과제명,색}`을 따로 **스냅샷**으로 박아 두는 방식은 아직 넣지 않았다. 현재는 위 '편입분 이름·색 유지 + `dbGone` 마크'로 삭제·오프라인을 견딘다(편입분이 보관하는 메타는 `name`·`color`뿐 — 상세 메타는 온라인 카탈로그에만 있다). 일정 단위 스냅샷은 필요해지면 얹는 향후 옵션.

#### 4.7.2 입력/출력 정책 — 입력 관대, 출력(보고서) 엄격
제약을 입력 시점에 걸면 끝이 없다. **제약은 보고서 생성 한 곳에만** 둔다.
- **입력**: 일정에 과제를 붙일 때 **DB 공식 과제 선택** 또는 **자유입력(freetext)** — 뭐든 허용. 입력 통제 없음.
- **출력(보고서/Excel 추출)**: **참조 기준 판정**(①) — `db-<uid>` 참조가 있으면 **공식**(집계 포함), 그 외(freetext·레거시·필드없음)는 **비공식**.
- **비공식 처리**(②): 보고서에서 **`기타` 버킷**으로 묶음(총량·투명성 유지). 완전 제거는 보고서 옵션.
- **이름 매칭 금지(자동/상시)**: 자유입력이 공식 과제명과 우연히 같아도 공식으로 인정하지 않음(오타·동명 fuzzy 회피). 공식 인정은 오직 참조(`db-<uid>`)로.
- 보고서 품질은 "사용자가 공식 과제가 있을 땐 골라주느냐"에 달림 → 피커에서 공식 과제를 잘 보이게(그래야 기타로 덜 샘).

#### 4.7.3 참조 식별자(안정 uid)와 재연결
- **안정 uid(D1)**: `project`에 `uid`(UUID, assign-once) 추가. 일정은 **내부 autoinc `id`가 아니라 `db-<uid>`로 참조**. rename·덤프복원·재이관에도 불변 → 재빌드/재채번으로 참조가 엉키는 사고 방지. (내부 PK는 autoinc `id` 유지. ✅ schema.sql 반영 완료 — 로컬 13행 UUID.)
- **재연결 도우미(v1, 순수 수동) — 구현**: 미연결 개인 과제를 사용자가 **DB 목록에서 직접 선택**해 공식으로 일괄 연결 / 또는 개인 유지. 자동 이름매칭 없음(오타·변종도 수동 해결). 자동 pre-fill은 나중 옵션.
  - 배치(구현): 설정의 **상시 버튼**("🔗 기존 과제 재연결") → 개인 과제를 **카테고리 단위로** 공식 과제에 매핑, 확인 시 그 과제로 태그된 일정·할일의 `categoryId`를 일괄 교체(로컬 쓰기, 오프라인 가능). 대상 공식 과제는 먼저 단일 목록에 편입해 필터바에도 즉시 뜬다.
  - 개별(구현): 일정 편집에서 DB 재선택(상시 가능).
  - **미구현(향후)**: 업데이트 후 **1회 비강제 넛지 + 이후 뱃지**는 아직 없다(상시 버튼만 제공).
  - 위젯 표시는 기존 정리 100% 보존. 보고서 공식 인정만 재연결로. **삭제·재입력 불필요.**

#### 4.7.4 단일 카테고리 스토어 (P3.5 — 구현 확정)
캘린더의 과제 목록은 **하나뿐이다: `state.categories`**. 개인 과제와 DB 유래 공식 과제(`source:'db'`)가 **함께** 이 목록에 담기고 **XML에 영속**된다(=DB 캐시가 아니라 **라벨 해석용 최소 메타** `name`·`color`만 보관). 별도의 라이브 DB 목록(`dbCatalog`)은 **카탈로그 화면·재연결 select 전용**이며, 사용자가 고른 것(구독)만 `state.categories`로 편입된다.

- **구독형 편입**: 카탈로그에서 추가하거나 재연결로 대상을 고르면 그 공식 과제가 `subscribeDbCat`으로 단일 목록에 들어온다(멱등). 매 `__applyProjects` 후 편입분의 이름·색·메타를 카탈로그 기준으로 재동기화(`syncSubscribedDbMeta`)하고, 카탈로그 활성목록에 없으면 `dbGone` 마크만 단다(목록에서 제거하지 않음 — 라벨·필터 보존).
- **마이그레이션(자동)**: entries·todos에 `db-*` 태그가 있는데 목록에 없으면(구버전 이중 목록 데이터) 카탈로그에서 찾아 자동 편입, 없으면 `dbGone` 플레이스홀더(`migrateDbSubscriptions`).
- **왜 단일 스토어인가**: 이전엔 목록이 둘이었다(`state.categories` vs `dbCatalog`). 소비 지점 여러 곳 중 일부만 두 목록을 병합해, **필터바에 DB 과제가 안 뜨는 실버그**가 났다. 단일 목록으로 합치고 출처를 격리해 근본 해결.

**SRP 규율 (강제)** — '출처 인지'가 허용되는 구역은 **딱 5곳**뿐이다:
1. 카테고리 모듈(구독/동기화/마이그레이션),
2. 과제관리 모달(관리 UI),
3. 공식 과제 카탈로그 화면,
4. 재연결 도구,
5. XML 직렬화(`source`/`dbGone` 속성 기록).

그 외 **전시 계층(월/일 렌더·필터바·검색·카드/칩·보고서 본문·알림·git 수집)은 목록을 균일하게 소비**한다 — `c.source`나 `db-` 접두를 직접 검사하지 않는다. 출처 판별은 헬퍼로만 노출: `isOfficialCat`(관리·피커 그룹), `isPickableCat`(신규선택 대상), 그리고 **접두 검사는 `isOfficialId` '이 한 줄'에서만**(호출은 카테고리 모듈, 향후 P4 추출도구·재연결 한정).

## 5. 권한 / 편집 통제

### ★ 인증 = 회사 사이트 위임 (2026-07-21 확정)
사용자 식별은 우리 DB가 아니라 **기존 회사 사이트(netcus) 로그인에 위임**한다:
```
위젯 → netcus 로그인 시도(회사 계정, 기존 NetcusService 재사용)
     → 성공(회사 ID = A) → app_user에 A 존재 검사
        → 있음: A의 role로 로그인 / 없음: viewer(읽기 전용)
```
- **우리 DB는 비밀번호를 저장하지 않는다**(`app_user`에 비번 컬럼 없음) — 인증(누구냐)=회사 사이트, 인가(role)=우리 DB.
- 검증은 호스트(C#) 한 지점(현 스텁 `VerifyAdmin` 자리를 이 흐름으로 교체 — P6.5).
- 트레이드오프: 편집 권한이 netcus 가용성에 의존 — "편집=온라인만" 정책·월 2~3회 편집과 일관이라 수용.

- **`app_user` 테이블**(P6.5 예정): `username`(=회사 ID), `role`('admin'|'editor'|'viewer'), `is_active`, 감사. **비번 없음.** Admin이 등록한 유저만 편집(미등록=viewer).
- 앱이 편집 전 역할 확인 → editor/admin만 쓰기, 나머지 읽기.
- **낙관적 잠금**(옵션): 두 명이 동시에 같은 과제를 고치는 드문 경우, 저장 직전 `updated_at` 비교로 덮어쓰기 방지. 월 2~3회 편집이라 나중에 얹어도 됨.

### 보안 주의 (알아둘 것)
배포 앱에 DB 접속정보(비밀번호)가 들어가면, 사용자가 그걸로 DB에 직접 붙어 앱 권한(`app_user`)을 **우회**할 수 있다.
- **완화(현 규모 충분)**: 앱용 DB 계정을 **최소 권한**으로(해당 테이블 SELECT/INSERT/UPDATE만, DROP·계정변경 금지).
- **강한 통제(지금 불필요)**: DB 계정별 GRANT, 또는 앱↔DB 사이 중간 API.

## 6. 네트워크 요건

### 폐쇄망 PC를 서버로 켤 때 체크리스트
1. **고정 IP** — ✅ 폐쇄망 PC는 이미 DHCP 비활성·고정 IP·게이트웨이 설정됨.
2. MySQL **네트워크 접속 허용** — `bind-address = 0.0.0.0`(기본은 localhost만).
3. **방화벽 3306 포트** 열기.
4. **원격 접속용 DB 계정**(최소 권한) 생성.
> 2~4는 "임시 서버로 전환하는 시점"에. 개발 단계(localhost)엔 불필요.

### DHCP vs 고정 IP (참고)
- **DHCP** = 네트워크가 IP를 자동 배정 → **바뀔 수 있음**. 서버엔 부적합.
- **고정 IP** = 항상 같은 주소. 서버 PC엔 필수.
- **확인법**: 설정 → 네트워크 → 이더넷 → "IP 할당" 자동/수동, 또는 `ipconfig /all`의 "DHCP 사용: 예/아니요".
- 현 개발 PC(외부망)는 DHCP(IP 192.168.16.3)지만 개발엔 무관. **실제 서버가 될 폐쇄망 PC는 고정 IP로 이미 준비됨.**

## 7. 운영 특성

- **편집 주체**: Admin + 승인된(확인된) 유저.
- **편집 빈도**: 월 2~3회 (쓰기 드묾). → 실시간성 불필요, 서버 부하 사실상 0.
- **조회 빈도**: 잦음(모든 사용자가 과제 목록을 봄). → 서버 가용성이 중요(캐시로 대체하지 않는다 — ADR-18).

## 8. 개발 → 배포 흐름

```
[개발] 외부망 PC, localhost MySQL 로 앱↔DB 연동·권한 개발·검증
   │  (반입/이관)
   ▼
[임시 운영] 폐쇄망 PC(고정 IP)에 MySQL 설치 + schema.sql 적용 + 데이터
            ProjectDb.cs ★배포 구성 상수를 폐쇄망 IP로 교체 → 재빌드 → 자동업데이트로 배포
   │  (배포 구성 상수만 교체·재빌드)
   ▼
[최종] 전용 상시가동 박스 / 회사 서버로 DB 이관 (같은 엔진, 저비용)
```

Excel은 이 흐름과 별개로 **DB에서 단방향 추출**되는 리포트(No는 추출 시 `ROW_NUMBER`로 생성).

## 11. 용어집

| 용어 | 뜻 |
|---|---|
| **클라이언트-서버** | DB(서버)는 한 대, 나머지는 접속(클라이언트)하는 구조 |
| **원본(source of truth)** | 데이터의 진짜 기준. 여기선 DB |
| **ENUM** | 컬럼에 허용 값 목록을 고정하는 타입(드롭다운 소스, 오타 차단) |
| **소프트삭제** | 실제 삭제 대신 `is_active=0`으로 숨김(복구 가능) |
| **감사(audit)** | `created_at`/`updated_at`로 생성·수정 시각 자동 기록 |
| **캐시** | 마지막 조회 데이터를 로컬에 복사해 둠(오프라인 조회용). **이 시스템은 DB 카탈로그를 캐싱하지 않는다**(ADR-18) |
| **낙관적 잠금** | 저장 직전 "그새 바뀌었나" 확인해 덮어쓰기 방지 |
| **DHCP** | 네트워크가 IP를 자동 배정(바뀔 수 있음) |
| **고정 IP** | PC에 항상 같은 IP를 고정(서버에 필수) |
| **bind-address** | MySQL이 어느 네트워크의 접속을 받을지 설정(0.0.0.0=전체) |
| **FK / ON UPDATE CASCADE** | 외래키 / 부모 값(발주처명) 변경 시 자식(과제)에 자동 전파 |
