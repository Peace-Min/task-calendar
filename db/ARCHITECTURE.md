## 1. 한눈에 보기

- **목적**: 사업부 과제(사업/프로젝트) 목록을 캘린더 앱에서 조회·편집하는 시스템.
- **데이터 원본**: **DB가 원본(source of truth)**. Admin(+확인된 유저)이 앱에서 편집, Excel은 DB에서 뽑는 리포트.
- **엔진**: **MySQL** (SQLite 아님 — 이유 §4.3).
- **배포**: 사용자는 **앱만 설치**(MySQL 설치 불필요). 중앙 DB는 **폐쇄망 PC(고정 IP)**가 임시 서버 → 나중에 전용 박스/회사 서버로 이관.
- **동작 규칙**: **조회 = 로컬 캐시(오프라인 OK)**, **편집 = 온라인일 때만**.
- **접속 주소**: 앱 설정값 1줄(현 FTP 경로 설정과 동일 방식). 지금 `localhost` → 폐쇄망 IP → 나중 서버 IP로 교체.

## 3. 확정 데이터 모델 (요약)

2 테이블 (상세는 `schema.sql`):
- **`customer`** — 발주처 마스터. `name` PK(자연키) + `is_active` + 감사.
- **`project`** — 과제 마스터. `id` PK(앱 편집 식별자) + `section`/`status` ENUM + `customer` FK(ON UPDATE CASCADE) + 사업/계약/통상명·시작/종료일 + `is_active` + 감사. `UNIQUE(customer, project_name)`.

## 4. 배포 아키텍처

### 4.1 MySQL은 "파일"이 아니라 "서버"다
MySQL은 항상 서버 프로세스가 떠 있어야 하는 **클라이언트-서버** DB다. 데이터 파일만 복사해선 못 읽는다.
- **한 대(중앙)에만** MySQL 서버 설치.
- 나머지는 **네트워크로 접속하는 클라이언트**.

### 4.2 사용자는 앱만 있으면 된다 (MySQL 설치 불필요)
앱 안에 접속 기능(커넥터)이 내장되므로, 일반 사용자 PC엔 **MySQL 설치 불필요**. 앱만 배포.
> ⚠️ 사용자마다 각자 로컬 MySQL을 깔면 → 각자 따로 노는 별개 DB가 되어 **공유 불가**. 하지 말 것.

### 4.3 SQLite를 검토했으나 기각
"DB 파일을 앱에 번들해 설치 없이 읽기"는 SQLite에 맞는 모델이지만 **기각**:
- **편집자가 여럿**(Admin + 확인된 유저)이라 각자 파일을 고치면 **병합 불가**(갈라짐).
- "승인된 유저만 편집"을 강제할 **중앙 권한소**가 필요.
→ 중앙 저장소 = **서버 MySQL**이 맞다. 또한 최종 목적지가 서버라면 `MySQL(로컬)→MySQL(서버)`가 같은 엔진이라 전환 비용이 거의 없다(SQLite→MySQL은 중간 공수 발생).

### 4.4 중앙 DB 위치 — 단계적
| 단계 | 위치 | 비고 |
|---|---|---|
| 개발 | 이 외부망 PC `localhost` | DHCP 무관 |
| **임시 운영** | **폐쇄망 PC(고정 IP)** | 이미 고정 IP 설정됨 |
| 최종 | 전용 상시가동 박스 / 회사 서버 | 접속 주소만 교체 |

내 메인 PC를 서버로 쓰면 꺼졌을 때 **편집만** 멈춘다(조회는 캐시로 지속). 더 깔끔한 임시안은 안 쓰는 PC를 상시 켜두는 것.

### 4.5 조회 = 캐시(오프라인 OK) / 편집 = 온라인 only
- **조회**: 앱이 과제 목록을 **로컬 캐시** → 서버 꺼져도 조회 가능, 온라인이면 최신 갱신.
- **편집**: **중앙 DB에 연결될 때만** 허용(바로 DB 저장). 연결 안 되면 편집 버튼 비활성(읽기 전용).
- **오프라인 편집은 만들지 않는다** — 동기화 큐·충돌 해결이 필요해 무겁고, 편집이 월 2~3회뿐이라 불필요. "편집하려면 서버 온라인" 제약이 충돌 문제를 통째로 없앤다.
- 이 로직은 **서버 이관 후에도 동일**(중앙 DB 주소만 바뀜).

### 4.6 접속 정보 = 배포 구성 (베이크) — 2026-07-21 개념 정정
~~설정 파일 외부화~~ → **DB 접속 정보(호스트/포트/계정/비번)는 사용자 설정이 아니라 "배포 구성"이다.**
- **배포자(Admin)가 배포 전 호스트 코드의 디폴트 상수(`ProjectDb.cs` 상단 "★ 배포 구성" 블록)를 설정하고 빌드·배포.**
- 일반 사용자에겐 연결 설정 UI가 **아예 없음**(만질 이유도, 만져서 고장날 일도 없음). 설정창엔 **관리자 인증만**(로그인/해제 + DB 상태줄 + 새로고침).
- 이유: 폐쇄망·전원이 같은 서버·고정 IP — 접속 정보는 사용자 취향이 아니라 배포 환경의 속성.
- 서버 이관 시: 디폴트 상수만 바꿔 재배포(자동업데이트로 전파). 지금 개발값=`localhost`.
- 관리자 자격도 코드 디폴트(admin/1234) + 설정 "등록"으로 변경 가능(변경분만 `db-config.json`에 평문 저장). P6.5에서 app_user·최소권한 계정으로 교체.

### 4.7 기존(로컬) 과제와의 공존
캘린더는 이미 배포·사용 중이라, 사용자들이 **로컬로 직접 만든 과제(카테고리)**와 그것으로 태그된 일정이 존재한다. 처리 방침:
- **기존 로컬 과제 + 태그된 일정은 그대로 둔다** — 손대지 않음. 강제 이관·매핑 없음(폐쇄망·분산이라 지저분).
- **신규 과제 추가 및 편집 시 카테고리 선택은 DB 마스터에서만** 읽어온다. 로컬 과제는 앞으로 **선택 목록에 노출하지 않고**, 옛 일정 **표시(해석)용으로만** 남는다(legacy).
- 옛 일정을 편집해도 카테고리를 **안 건드리면 로컬 태그 유지**, **바꾸면 그때 DB 과제로 전환**.
- **중복 처리 안 함** — 현재도 과제명 중복을 막지 않으므로 회귀 아님. 로컬·DB에 동명이 있어도 각자 존재(로컬=표시용, DB=선택용).
- **귀결**: 앞으로 필요한 과제가 DB에 없으면 사용자가 로컬로 만들지 않고 **Admin이 DB에 추가** — 'DB 원본' 취지와 일치.
- ⚠️ 옛 일정의 로컬 과제 참조가 깨지지 않도록 위젯의 **로컬 해석 저장은 유지**한다. 정확한 방식은 P3 스카우트에서 위젯 저장구조 확인 후 확정.

#### 4.7.1 안 꼬이게 하는 규칙 (불변식 — 강제)
카테고리 참조 혼동이 최대 위험. 아래를 **불변식으로 강제**한다:

**참조 네임스페이스**
- DB 과제 카테고리 id는 네임스페이스를 붙인다: **`db-<project.uid>`**(예: `db-8d731cec-7f69-...`). 그 외(기존 형식 `c-<uuid>` 등)는 전부 **로컬(legacy)**로 간주.
- ⚠️ **콜론 금지(P3 스카우트 확정)**: 위젯의 XML import 검증기 `safeId`가 categoryId를 `/^[A-Za-z0-9_-]{1,80}$/`로 검사한다(prototype.html L2496). 콜론이 들어가면 검증 실패 → `uid()`로 재생성돼 **DB 링크 소실**. 그래서 `db:`가 아니라 **`db-`**(하이픈)를 쓴다. UUID(하이픈 포함)와 합쳐도 이 정규식 통과.
- 로컬 id는 단일문자 접두(`c-`,`t-`,`e-`) → `db-`(2문자 접두)와 안 겹침. 판정 = `id.startsWith('db-')`.
- 두 id 공간이 절대 겹치지 않음. 일정이 자기 카테고리 출처를 스스로 안다.
- 기존 일정은 형식 그대로 두면 자동으로 "로컬"로 해석됨 → **마이그레이션 없음**.
- 안정성: `db-<uid>`는 UUID라 rename·덤프복원·재이관에도 불변(autoinc id와 무관). 안전.

**로컬 태그 일정 편집 플로우**
1. 편집 열면 카테고리에 로컬 과제명 + "(기존)" 표식.
2. 카테고리 안 건드리고 저장 → 로컬 참조 그대로 기록(재해석·재작성 금지).
3. 드롭다운 열면 DB 마스터(활성)만 목록. 상단에 `현재: OOO (기존)` 표기, 선택지는 DB만.
4. DB 과제 선택 → 참조가 `db-<id>`로 교체(DB 태그로 전환).
5. 취소 → 로컬 유지. **방향은 로컬→DB 단방향**(로컬 재선택 불가).

**해석(표시) 규칙 — 절대 안 깨짐**
- 로컬 태그 → 로컬 저장에서 / DB 태그 → DB 캐시에서 이름·색.
- 소프트삭제된 DB 과제도 **캐시가 해석은 계속**(피커엔 안 뜸).
- 소스 없음/오프라인 → 일정에 저장한 **이름 스냅샷** 폴백 → 없으면 `(삭제된 과제)`. 빈칸·크래시 없음.

**불변식 목록**
1. 두 id 공간 네임스페이스 분리 → 혼동 불가.
2. 모든 참조가 출처 자기기술.
3. 기존 데이터 무변경 → 마이그레이션 버그 0.
4. 안 건드린 카테고리는 저장 시 그대로 보존(자동 재작성 금지).
5. 로컬 저장은 읽기전용 legacy(신규·수정·삭제 없음) → 드리프트 없음.
6. 해석은 항상 성공(캐시가 삭제분 보관 + 스냅샷 폴백).

**강한 옵션(권장)**: 각 일정에 태그 시점 `{과제명, 색}` **스냅샷** 저장 → 표시는 라이브(DB 캐시) 우선, 스냅샷 폴백. DB 과제 삭제/오프라인에도 옛 일정 안 깨짐.

#### 4.7.2 입력/출력 정책 — 입력 관대, 출력(보고서) 엄격
제약을 입력 시점에 걸면 끝이 없다. **제약은 보고서 생성 한 곳에만** 둔다.
- **입력**: 일정에 과제를 붙일 때 **DB 공식 과제 선택** 또는 **자유입력(freetext)** — 뭐든 허용. 입력 통제 없음.
- **출력(보고서/Excel 추출)**: **참조 기준 판정**(①) — `db-<uid>` 참조가 있으면 **공식**(집계 포함), 그 외(freetext·레거시·필드없음)는 **비공식**.
- **비공식 처리**(②): 보고서에서 **`기타` 버킷**으로 묶음(총량·투명성 유지). 완전 제거는 보고서 옵션.
- **이름 매칭 금지(자동/상시)**: 자유입력이 공식 과제명과 우연히 같아도 공식으로 인정하지 않음(오타·동명 fuzzy 회피). 공식 인정은 오직 참조(`db-<uid>`)로.
- 보고서 품질은 "사용자가 공식 과제가 있을 땐 골라주느냐"에 달림 → 피커에서 공식 과제를 잘 보이게(그래야 기타로 덜 샘).

#### 4.7.3 참조 식별자(안정 uid)와 재연결
- **안정 uid(D1)**: `project`에 `uid`(UUID, assign-once) 추가. 일정은 **내부 autoinc `id`가 아니라 `db-<uid>`로 참조**. rename·덤프복원·재이관에도 불변 → 재빌드/재채번으로 참조가 엉키는 사고 방지. (내부 PK는 autoinc `id` 유지. schema.sql 반영은 구현 단계.)
- **재연결 도우미(v1, 순수 수동)**: 미연결 로컬(비공식) 과제를 사용자가 **DB 목록에서 직접 선택**해 공식으로 연결 / 또는 개인 유지. 자동 이름매칭 없음(오타·변종도 수동 해결). 자동 pre-fill은 나중 옵션.
  - 배치: 설정/도구 **상시 버튼** + 업데이트 후 **1회 비강제 넛지** + 이후 뱃지(강제·주기 팝업 없음). **카테고리 단위 매핑**(아래 일정 일괄 재연결).
  - 개별: 일정 편집에서 DB 재선택(상시 가능).
  - 위젯 표시는 기존 정리 100% 보존. 보고서 공식 인정만 재연결로. **삭제·재입력 불필요.**

## 5. 권한 / 편집 통제

### ★ 인증 = 회사 사이트 위임 (2026-07-21 확정)
사용자 식별은 우리 DB가 아니라 **기존 회사 사이트(netcus) 로그인에 위임**한다:
```
위젯 → netcus 로그인 시도(회사 계정, 기존 NetcusService 재사용)
     → 성공(회사 ID = A) → app_user에 A 존재 검사
        → 있음: A의 role로 로그인 / 없음: viewer(읽기 전용)
```
- **우리 DB는 비밀번호를 저장하지 않는다**(`app_user`에 비번 컬럼 없음) — 인증(누구냐)=회사 사이트, 인가(role)=우리 DB.
- 검증은 호스트(C#) 한 지점(현 스텁 `VerifyAdmin` 자리를 이 흐름으로 교체 — P6.5).
- 트레이드오프: 편집 권한이 netcus 가용성에 의존 — "편집=온라인만" 정책·월 2~3회 편집과 일관이라 수용.

- **`app_user` 테이블**(P6.5 예정): `username`(=회사 ID), `role`('admin'|'editor'|'viewer'), `is_active`, 감사. **비번 없음.** Admin이 등록한 유저만 편집(미등록=viewer).
- 앱이 편집 전 역할 확인 → editor/admin만 쓰기, 나머지 읽기.
- **낙관적 잠금**(옵션): 두 명이 동시에 같은 과제를 고치는 드문 경우, 저장 직전 `updated_at` 비교로 덮어쓰기 방지. 월 2~3회 편집이라 나중에 얹어도 됨.

### 보안 주의 (알아둘 것)
배포 앱에 DB 접속정보(비밀번호)가 들어가면, 사용자가 그걸로 DB에 직접 붙어 앱 권한(`app_user`)을 **우회**할 수 있다.
- **완화(현 규모 충분)**: 앱용 DB 계정을 **최소 권한**으로(해당 테이블 SELECT/INSERT/UPDATE만, DROP·계정변경 금지).
- **강한 통제(지금 불필요)**: DB 계정별 GRANT, 또는 앱↔DB 사이 중간 API.

## 6. 네트워크 요건

### 폐쇄망 PC를 서버로 켤 때 체크리스트
1. **고정 IP** — ✅ 폐쇄망 PC는 이미 DHCP 비활성·고정 IP·게이트웨이 설정됨.
2. MySQL **네트워크 접속 허용** — `bind-address = 0.0.0.0`(기본은 localhost만).
3. **방화벽 3306 포트** 열기.
4. **원격 접속용 DB 계정**(최소 권한) 생성.
> 2~4는 "임시 서버로 전환하는 시점"에. 개발 단계(localhost)엔 불필요.

### DHCP vs 고정 IP (참고)
- **DHCP** = 네트워크가 IP를 자동 배정 → **바뀔 수 있음**. 서버엔 부적합.
- **고정 IP** = 항상 같은 주소. 서버 PC엔 필수.
- **확인법**: 설정 → 네트워크 → 이더넷 → "IP 할당" 자동/수동, 또는 `ipconfig /all`의 "DHCP 사용: 예/아니요".
- 현 개발 PC(외부망)는 DHCP(IP 192.168.16.3)지만 개발엔 무관. **실제 서버가 될 폐쇄망 PC는 고정 IP로 이미 준비됨.**

## 7. 운영 특성

- **편집 주체**: Admin + 승인된(확인된) 유저.
- **편집 빈도**: 월 2~3회 (쓰기 드묾). → 실시간성 불필요, 서버 부하 사실상 0.
- **조회 빈도**: 잦음(모든 사용자가 과제 목록을 봄). → 캐시가 중요.

## 8. 개발 → 배포 흐름

```
[개발] 외부망 PC, localhost MySQL 로 앱↔DB 연동·권한 개발·검증
   │  (반입/이관)
   ▼
[임시 운영] 폐쇄망 PC(고정 IP)에 MySQL 설치 + schema.sql 적용 + 데이터
            앱 설정의 DB 주소를 폐쇄망 IP로 변경, 사용자에 앱 배포
   │  (접속 주소만 교체)
   ▼
[최종] 전용 상시가동 박스 / 회사 서버로 DB 이관 (같은 엔진, 저비용)
```

Excel은 이 흐름과 별개로 **DB에서 단방향 추출**되는 리포트(No는 추출 시 `ROW_NUMBER`로 생성).

## 11. 용어집

| 용어 | 뜻 |
|---|---|
| **클라이언트-서버** | DB(서버)는 한 대, 나머지는 접속(클라이언트)하는 구조 |
| **원본(source of truth)** | 데이터의 진짜 기준. 여기선 DB |
| **ENUM** | 컬럼에 허용 값 목록을 고정하는 타입(드롭다운 소스, 오타 차단) |
| **소프트삭제** | 실제 삭제 대신 `is_active=0`으로 숨김(복구 가능) |
| **감사(audit)** | `created_at`/`updated_at`로 생성·수정 시각 자동 기록 |
| **캐시** | 마지막 조회 데이터를 로컬에 복사해 둠(오프라인 조회용) |
| **낙관적 잠금** | 저장 직전 "그새 바뀌었나" 확인해 덮어쓰기 방지 |
| **DHCP** | 네트워크가 IP를 자동 배정(바뀔 수 있음) |
| **고정 IP** | PC에 항상 같은 IP를 고정(서버에 필수) |
| **bind-address** | MySQL이 어느 네트워크의 접속을 받을지 설정(0.0.0.0=전체) |
| **FK / ON UPDATE CASCADE** | 외래키 / 부모 값(발주처명) 변경 시 자식(과제)에 자동 전파 |
