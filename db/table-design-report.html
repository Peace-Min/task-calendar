과제의 정체성은 이름이 아니라 uid다. 실데이터가 이름 기반 유니크 제약이 이 업무와 맞지 않음을 보여줬다 — 그래서 하드 제약을 제거하고, 실수 중복은 앱의 소프트 경고로 거른다.

01 확정된 식별·유니크 규칙

이름은 중복될 수 있는 도메인이다. 정체성은 uid가 지고, 이름 기반 하드 제약은 두지 않으며, 실수 방지는 소프트 경고가 맡는다.

규칙결정근거
과제 정체성 = uid (UUID) 유지 · UNIQUE 저장(UPSERT)·일정 참조가 모두 uid 기반. rename·서버 이관에도 불변.
(customer, project_name) 유니크 제거 한 발주처·한 사업명 아래 구성품별 계약이 다수 존재(정상). 하드 제약이 정당한 데이터를 막았다.
이름 조합 유니크 (계약명 포함 등) 두지 않음 연도별 갱신·공백 변형 때문에 어떤 이름 조합으로도 유일성을 깔끔히 정의할 수 없음.
실수 중복 방지 앱 소프트 경고 정규화(공백 제거·축소) 비교로 “비슷한 과제가 있습니다” 안내 — 막지 않고, 하드 제약보다 촘촘히 잡음.
발주처 name (PK) 유지 발주처 자연키. 이건 이름 중복이 있어선 안 되므로 하드 유니크 유지.
구분/상태 = section · status 코드테이블 + FK ENUM 폐기 — 런타임 추가/개명(FK CASCADE)/순서/숨김이 필요. 발주처와 대칭 룩업으로 두고 무결성은 FK가 승계(오타 거부).

02 테이블 구조

과제 본체는 project 하나. 나머지 셋(customer·section_code·status_code)은 project의 FK 타겟인 룩업 테이블이다 — 앱에서 관리하고 무결성은 FK가 지킨다.

customer발주처
  • PK name
  • is_active · 감사
1 ──────< N FK 3종 → project
customer · section_code · status_code
ON UPDATE CASCADE / DELETE RESTRICT
project과제
  • PK id · UQ uid
  • FK customer · section · status
  • note(비고) · is_active · 감사

section_code · status_code는 발주처와 같은 형태의 코드 룩업이다: name(PK) · sort_order(드롭다운 순서) · is_active · 감사. 추가 = INSERT / 개명 = name UPDATE(→FK CASCADE) / 재배치 = sort_order / 숨김 = is_active. ENUM에서 전환(ADR-22) — 이제 런타임에 값 관리가 가능하다.

03 왜 이름 유니크를 버렸나 — 실데이터 근거

144건을 검수한 결과, 이름이 겹치는 경우가 대부분 정당한 업무 패턴이었다. (아래 예시는 형태 설명용 더미)

22조합 · 68건

구성품별 계약

한 사업 아래 구성품마다 별도 계약. 사업명은 같고 계약명만 다르다 — 정상 데이터.

(발주처A, 체계1, 저장장치) (발주처A, 체계1, 처리장치) → 사업명 동일, 계약명만 다름
매년 반복

연도별 갱신

1년 단위 유지보수 계약의 연차 갱신. 이름 4컬럼이 모두 같고 날짜만 다르다.

(발주처B, ○○유지보수, ○○유지보수) 2024–2025 종료 2026–2027 진행중 → 이름에 연도 붙이면 영구 땜질
데이터 위생

보이지 않는 차이

끝 공백 등으로 사람 눈엔 같은데 문자열은 다른 경우. 하드 유니크는 이걸 못 잡는다.

(발주처C, 체계2, 개발벤치SW) (발주처C, 체계2, 개발벤치SW␣) → TRIM + 소프트 경고가 포착

결론: 하드 유니크는 정당한 데이터(연도 갱신)를 막으면서, 정작 진짜 실수(공백 변형)는 통과시킨다. 방향이 반대다. 정규화 소프트 경고가 두 문제를 모두 해결한다.

04 유지보수 원칙

이 설계를 이어받는 사람이 지켜야 할 것과 하지 말아야 할 것.

지킨다

  • 과제는 uid로 식별·조인 — 이름은 중복될 수 있다.
  • 이름 필드는 저장 시 TRIM — 보이지 않는 공백 중복 차단.
  • 발주처 개명은 앱에서 — FK CASCADE로 과제에 자동 반영.
  • 서버 이관은 mysqldump — 구조는 스크립트 재실행, 데이터는 dump, 계정은 별도.

하지 않는다

  • 이름으로 과제 식별 — 동명 과제가 실제로 존재.
  • 연도 갱신 막으려 이름에 연도 삽입 — 계약서명과 어긋난다. 소프트 경고로 처리.
  • 데이터 폴더(.ibd) 통째 복사 이관 — 버전·설정 의존. mysqldump 사용.
  • 운영 DB에 schema/init-db 재실행 — 멱등 재구축이라 테이블을 DROP한다.
