0개

주 1회 등록하고 첫 회차를 되살려 본다. 절차는 deploy/README.md 의 복구 절.

05지킨다 · 하지 않는다

이 구조를 이어받는 사람이 알아야 할 규칙. 어기면 오류 없이 조용히 깨진다.

지킨다

  • 쓰기 트랜잭션의 첫 문장은 cal_user_rev 의 rev 증가 그 행의 락이 번호 발급과 동시 편집을 막는다.
  • UPDATE·DELETE 는 updated_at 을 비교한다 영향 행이 0 이면 충돌이다. 덮어쓰지 않는다.
  • 읽기는 REPEATABLE READ, 쓰기는 READ COMMITTED 부팅 조회 한 트랜잭션이 한 시점을 본다.
  • 새 컬럼은 NULL 허용이거나 DEFAULT 가 있어야 한다 구버전 위젯이 같은 DB 를 쓰는 기간이 있다.
  • cal_attendance 는 미기록이면 행이 없다 되돌리기는 DELETE 다. 기본값을 두면 이 계약이 깨진다.

하지 않는다

  • cal_user_rev 를 지우지 않는다 단조증가가 동기화의 기준이다.
  • 데이터 표의 소유자 FK 를 CASCADE 로 바꾸지 않는다 app_user 한 행 삭제가 캘린더 침묵 삭제가 된다. CASCADE 는 보고 기록 cal_report_daily · cal_report_weekly 두 표에만 있다.
  • login_id 를 키로 다시 쓰지 않는다 사내 사이트의 값이라 바뀔 수 있고, 그래서 user_id 를 두었다.
  • 이름에 하드 유니크를 걸지 않는다 발주처·사업명 중복은 정상 업무 패턴이다(07-24 판의 실데이터 검수).
  • 보고 기록 표를 사이트 상태의 거울로 보지 않는다 캘린더가 보낸 것만 담는다.

user_id 대리키

app_user 에 user_id 를 두고 login_id 는 UNIQUE 로 내렸다. cal_* 의 소유자 키가 전부 user_id 로 바뀌었다. login_id 는 사내 보고 사이트의 값이라 우리가 못 바꾸는데 참조가 여러 경로라 개명이 실행조차 안 됐기 때문이다.

08-24

PK 를 name 에서 org_id 로 옮겼다. 자기참조 FK 에는 InnoDB 가 CASCADE 를 수행하지 않아 본부 개명이 1451 로 막히던 것을 실측하고 바꿨다. 이름 미러는 남기지 않았다.

cal_category · cal_entry · cal_todo · cal_room 에 순서 컬럼을 더해 부팅 조회의 순서를 앱의 문서 순서와 맞췄다.
