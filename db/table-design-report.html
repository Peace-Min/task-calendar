03테이블 상세

이름, PK, 개발 DB 행 수, 앱 계정 권한 순이다. 항목을 누르면 컬럼과 제약이 펼쳐진다. 테이블 설명은 DB 의 테이블 주석 그대로다.

키 정책: 외래키가 가리키는 기본키는 번호다

"외래키 대상 기본키는 varchar 가 아니라 id 로" 라는 지적(2026-08-23)을 규칙 하나로 받아들였다(2026-10-15). 다른 표가 외래키로 가리키는 기본키는 정수 번호이고, 사람이 보는 이름은 UNIQUE 라벨로 남긴다. 외래키 규칙은 ON UPDATE RESTRICT, ON DELETE RESTRICT 다. 번호는 바뀌지 않으므로 개명은 라벨 한 행이고, 화면은 조인으로 새 이름을 읽는다.

예전(2026-08-24)에는 코드표 넷을 이름 키로 두고 개명을 FK ON UPDATE CASCADE 로 전파했다. 새 DB 가 회사 서버에 아직 없어 옮기는 비용이 기계적인 작업뿐이라는 것을 확인하고(2026-10-15) 번호로 옮겼다. 동작이 묶인 코드값(구분 2 선진행, 상태 2 종료)은 이름 글자가 아니라 고정 번호로 판정한다.

05유지보수 원칙

유지보수 시 지켜야 할 규칙. 어기면 오류 없이 데이터가 어긋난다.

지킨다

  • 쓰기 트랜잭션의 첫 문장은 cal_user_rev 의 rev 증가 그 행의 락이 번호 발급과 동시 편집을 막는다.
  • UPDATE·DELETE 는 updated_at 을 비교한다 영향 행이 0 이면 충돌이다. 덮어쓰지 않는다.
  • 읽기는 REPEATABLE READ, 쓰기는 READ COMMITTED 부팅 조회 한 트랜잭션이 한 시점을 본다.
  • 새 컬럼은 NULL 허용이거나 DEFAULT 가 있어야 한다 구버전 위젯이 같은 DB 를 쓰는 기간이 있다.
  • cal_attendance 는 미기록이면 행이 없다 되돌리기는 DELETE 다. 기본값을 두면 이 계약이 깨진다.

하지 않는다

  • cal_user_rev 를 지우지 않는다 단조증가가 동기화의 기준이다.
  • 데이터 표의 소유자 FK 를 CASCADE 로 바꾸지 않는다 app_user 한 행 삭제가 캘린더 침묵 삭제가 된다. 지금 CASCADE 인 소유자 FK 는 하나도 없다.
  • login_id 를 키로 다시 쓰지 않는다 사내 사이트의 값이라 바뀔 수 있고, 그래서 user_id 를 두었다.
  • 과제 이름에 하드 유니크를 걸지 않는다 같은 발주처, 같은 사업명의 과제가 반복되는 것은 정상 업무 패턴이다(07-24 판의 실데이터 검수). 코드표 name 의 UNIQUE 는 라벨 중복을 막는 것이라 이와 다르다.
  • 보고 기록 표를 사이트 상태의 거울로 보지 않는다 캘린더가 보낸 것만 담는다.

06변경 이력

07-24 판 이후의 구조 변경. 9월 7일의 겹쳐보기는 화면 기능이라 스키마 변경이 없다.

08-24
user_id 대리키

app_user 에 user_id 를 두고 login_id 는 UNIQUE 로 내렸다. cal_* 의 소유자 키가 전부 user_id 로 바뀌었다. login_id 는 사내 보고 사이트의 값이라 우리가 못 바꾸는데 참조가 여러 경로라 개명이 실행조차 안 됐기 때문이다.

PK 를 name 에서 org_id 로 옮겼다. 자기참조 FK 에는 InnoDB 가 CASCADE 를 수행하지 않아 본부 개명이 1451 로 막히던 것을 실측하고 바꿨다. 이름 미러는 남기지 않았다.

uses_repo

cal_report_daily, cal_report_hours(v6), cal_report_weekly(v7) 를 만들고, 주간은 보낸 것만 담도록 다시 만들었다(v8). 캘린더가 만든 것만 담고 사이트의 현재 상태는 담지 않는다.

09-09
무결성 규칙 통일

같은 DB 안에서 장치끼리 반대로 말하던 다섯을 한 판으로 맞췄다: 보고 표 두 개의 소유자 FK 를 CASCADE 에서 RESTRICT 로(GRANT 는 보고 이력을 못 지우게 하는데 FK 가 지우고 있었다), cal_report_hours 에 과제 FK 신설(쌍둥이 cal_task_hours 만 잠겨 있었다), cal_report_daily 에 근태·초과시간 CHECK(쌍둥이 cal_attendance 만 잠겨 있었다), hours 를 DECIMAL(4,2) 로, 감사 시각을 KST 에서 UTC 로 1회 정규화. 마지막 하나는 데이터를 바꾸므로 재실행 안전이 아니고 ProjectDb 의 접속 프리앰블과 같은 배포에 실려야 한다.

10-15
코드표 번호 키(v13)

customer, section_code, status_code, title_code 의 기본키를 이름에서 번호(SMALLINT UNSIGNED)로 옮기고 이름은 UNIQUE 라벨로 남겼다. 자식은 project.customer_id, section_id, status_id 와 app_user.title_id 이고 외래키는 ON UPDATE RESTRICT, ON DELETE RESTRICT. 동작이 묶인 코드값은 고정 번호(구분 2 선진행, 상태 2 종료)로 판정하고 그 두 행은 숨기거나 지울 수 없다. 데이터가 있는 DB 는 migrate-2026-10-15-code-ids.sql, 새 서버는 setup-taskcalendar.

10-21
회의실 공용화(v15)

사람마다 두던 cal_room 을 지우고 회사 공용 room_code(번호 키, name UNIQUE)를 두었다. 모든 사용자의 이름을 모아(앞뒤 공백 정리, 중복 제거) 넣었다. 관리자만 고치고, 일정의 장소는 글자라 외래키가 없다. 이관 조각 db/deploy/migrations/v15-shared-rooms.sql.

10-22
과제 캘린더(v16)

공식 과제마다 공용 캘린더를 두는 새 표 둘을 더했다: cal_project_event(과제 일정, 소프트 삭제, row_version), cal_project_change(바뀐 필드만 담는 지우지 않는 이력). 과제별 감시점 표는 없다(동시 수정은 일정의 row_version, 재시도는 이력의 mutation_uid UNIQUE). 개인 일정에 등록은 한 번 찍는 사본이라 대응표가 없다. 외래키는 번호(project.id, event_id)를 가리키고 사람은 이름 글자로만 남긴다. 두 표 모두 앱 계정에 DELETE 가 없다. 이관 조각 db/deploy/migrations/v16-project-calendar.sql.
